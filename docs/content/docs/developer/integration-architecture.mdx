---
title: Integration architecture
description: The Coppice integration taxonomy, request contract, acquisition boundary, and evidence
---

Coppice is one Rust server process with explicit integration boundaries. A
protocol adapter, metadata provider, catalog source, worker backend, or request
system may have a different owner and evidence level, but none silently owns
another class's job. The server remains authoritative for identity, permissions,
storage, and publication.

## Evidence labels

Use these labels literally in plans, issue reports, and compatibility pages:

- **Shipped** — the behavior is present in the product source and available in a
  supported build.
- **Contract-tested** — a pinned protocol, fixture, or server probe exercised the
  wire contract. This does not prove that a third-party app works.
- **Device-tested** — a real app or device was exercised against the fixture
  server; the scope and date must be stated.
- **Source-only** — pinned client or upstream source was inspected, but no
  product/device run proves the behavior.
- **Planned** — an accepted future direction with no shipped implementation.
- **Blocked** — the direction cannot be verified or started until a named
  external prerequisite is available.

Harness, source, and repository evidence never becomes app or device proof.

## Integration taxonomy

| Class | Owns | Current boundary and evidence | Does not imply |
| --- | --- | --- | --- |
| **Protocol adapters** | Translate an external client's routes, authentication, DTOs, and progress model at the HTTP/WebSocket edge. | `crates/komga`, `crates/kavita`, `crates/abs`, `crates/kobo`, `crates/koreader`, `crates/opds`, `crates/liseur-sync`, plus native GraphQL/REST/Readium. Profiles are **Shipped**; their harness and client records are separated in [Client verification](/docs/developer/client-verification). | A protocol adapter is not a search provider, downloader, metadata authority, or alignment engine. |
| **Metadata providers** | Identify and look up metadata candidates, map fields, retain provenance, and participate in ingest policy. | `crates/integrations/metadata` and `crates/ingest` implement the candidate/apply boundary. Hardcover metadata is **Shipped** and **Contract-tested** offline; live credentials are **Blocked**, and account, progress, and journal sync are **Planned**. See [Provider status](/docs/developer/provider-status). | Metadata lookup does not create a wanted request, fetch copyrighted files, or synchronize a provider account. |
| **Catalog/source providers** | Discover popular/latest/search/details/chapters/pages from a remote source and expose a materialized or virtual library. | `crates/provider`, `crates/provider-mangadex`, and `crates/provider-themes` own the `Source` contract and source definitions. The host and catalog path are **Shipped** when enabled; see [Provider host](/docs/developer/provider-host) and [Source definitions](/docs/developer/source-definitions). | A source provider is not the metadata-provider registry. It does not turn a search result into a fulfillment, and Storyteller never belongs here. |
| **Worker backends** | Execute heavy or hardware-bound jobs outside the server process and return validated, digest-bound results. | `crates/worker`, `worker_jobs`, `transcode`, and `challenge_solve` are **Shipped**. The typed `align` contract is **Shipped**; a worker-local Storyteller adapter is **Planned**, with native known-text CTC/Viterbi as an independent later backend. See [Read-aloud](/docs/developer/read-aloud). | Storyteller is not a search/catalog provider, not a bundled dependency, and not the default server-side alignment runtime. |
| **Request system** | Store metadata-backed requests, enforce permissions and per-user visibility, record approval/rejection decisions, notify users, and accept social recommendation handoff. | The ledger, GraphQL create/list/detail/approve/reject contract, and Home request UI are **Shipped**. | Approval is not acquisition, release selection, downloading, polling, retry, or ingest. |

These classes compose in the same process where the current source permits it.
A worker is an optional executor that dials the server; it is not a second
catalog or database. External systems keep their own credentials and lifecycle.

The contract-tested home-library source-worker role is separate from the
compute-worker job executor. It reports privacy-minimized catalog observations
and serves explicitly authorized bytes through private direct or outbound-tunnel
connections. The server still owns verification, explicit location linking,
ingest, reader authorization, and reader URLs. Automatic matching, publication,
placement, caching, and replication remain planned. This role never turns
request approval into acquisition or publication. See
[Remote worker libraries](/docs/developer/remote-worker-libraries).

## Search, requests, acquisition, and ingest

Universal-style search discovers metadata or remote catalog entries. Coppice can
turn that metadata into its own request record, but search results and approved
requests do not represent acquired files.

The shipped request flow is:

```text
metadata search or recommendation
  -> request metadata + optional destination intent
  -> permission and per-user visibility checks
  -> operator approval or rejection
  -> notifications and audit history
```

MAM acquisition is deferred. Coppice has no active release search/selection,
grab, polling, retry, downloader, or acquisition-gateway configuration. If
acquisition is added later, it must run in a separate authenticated provider
sidecar that owns provider credentials and transport state. That boundary does
not promise a provider, protocol, implementation, or delivery date.

Staged ingest remains an independent path for files an operator is allowed to
store. Approval does not enqueue ingest, and ingest does not automatically
fulfill a request.

## Alignment orchestration is a separate path

Alignment begins only after a user confirms the ebook and audiobook edition pair.
It does not start from metadata search or request approval. The future path
is:

```text
confirmed ebook + audiobook pair
  -> exact timing import (existing SMIL, Storyteller artifact, or manifest)
  -> validate SyncMapV1 and persist the accepted map
  -> explicit alignment job
  -> worker-local Storyteller adapter (optional external API)
  -> native known-text CTC/Viterbi fallback
  -> deterministic read-aloud EPUB derivative (future)
```

Storyteller may be used by a worker that the operator configures to reach an
external instance. Storyteller credentials and remote-library lifecycle policy
remain worker-local. The worker obtains the confirmed source EPUB/audio through
Coppice's authenticated media routes and may send those bytes only to that
operator-configured instance; only validated `SyncMapV1` timing returns as the
job result. Synchronized Storyteller read-aloud EPUB playback is not shipped.
Ordinary EPUB playback and ordinary audiobook playback remain separate
supported experiences until the future derivative and reader contract are
complete.

## Application and server boundaries

The `/editor` and `/app` static applications are separate web assets served by
Coppice when their corresponding directories are configured (`INGEST_EDITOR_DIR`
and `STUMP_HOME_APP_DIR`). Removing either static application does not remove the
native API, protocol adapters, ingest, providers, or worker socket. A headless
profile may omit both applications while retaining the backend contracts that
its Cargo features include. See [Server architecture](/docs/developer/server-architecture)
for the feature/profile matrix and lifecycle rules.

## Connections: personal delivery and provider state

Connections are split between a shared system sender and user-owned targets:

- SMTP is one server emailer. Only the server owner or `ManageServer` may read
  or change its host, sender, and TLS metadata; passwords are encrypted and
  never returned. `EmailSend` remains sufficient for sending a book.
- Kindle destinations belong to one user and can be created, renamed, made
  default, or deleted without changing legacy `devices.kindle_email`. New
  sends snapshot the destination id/name/address in `kindle_deliveries`; old
  device-id sends continue unchanged. Deleting a destination never deletes
  delivery history.
- A Hardcover PAT is encrypted per user and verified through `me` before it is
  stored. Personal status is redacted, clients are scoped by user and
  credential version, and metadata use is opt-in for interactive lookups only.
  Public metadata may use a provider/query/schema/expiry cache; journal,
  quote, and progress responses never enter it.
- Manual Hardcover sync is read-only for remote data. A quote becomes a local
  annotation only when an explicit media link and exact page locator are
  available; otherwise unresolved provider-neutral provenance is retained.
  Progress projection is opt-in, page-bounded, and uses the shared
  non-regressing reading-head conflict rule.

## Source of truth

- [Current state](/docs/developer/state) records what exists and the evidence
  level for each client and subsystem.
- [Provider status](/docs/developer/provider-status) records metadata and
  protocol-provider contracts and their gates.
- [Read-aloud](/docs/developer/read-aloud) records pairing, timing maps, worker
  execution, the shipped request backend, the implemented gateway with mocked
  contract evidence pending Main validation, and remaining alignment work.
- [Client verification](/docs/developer/client-verification) records app/device
  evidence separately from server contracts.
