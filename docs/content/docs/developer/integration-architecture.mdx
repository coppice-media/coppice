---
title: Integration architecture
description: The Coppice integration taxonomy, request contract, acquisition boundary, and evidence
---

Coppice is one Rust server process with explicit integration boundaries. A
protocol adapter, metadata provider, catalog source, worker backend, or request
system may have a different owner and evidence level, but none silently owns
another class's job. In the shipped standalone mode, the server remains
authoritative for identity, permissions, storage, and publication. Optional
stack links below are planned, not a transfer of those responsibilities today.

## Evidence labels

Use these labels literally in plans, issue reports, and compatibility pages:

- **Shipped** — the behavior is present in the product source and available in a
  supported build.
- **Contract-tested** — a pinned protocol, fixture, or server probe exercised the
  wire contract. This does not prove that a third-party app works.
- **Device-tested** — a real app or device was exercised against the fixture
  server; the scope and date must be stated.
- **Source-only** — pinned client or upstream source was inspected, but no
  product/device run proves the behavior.
- **Planned** — an accepted future direction with no shipped implementation.
- **Blocked** — the direction cannot be verified or started until a named
  external prerequisite is available.

Harness, source, and repository evidence never becomes app or device proof.

## Integration taxonomy

| Class | Owns | Current boundary and evidence | Does not imply |
| --- | --- | --- | --- |
| **Protocol adapters** | Translate an external client's routes, authentication, DTOs, and progress model at the HTTP/WebSocket edge. | `crates/komga`, `crates/kavita`, `crates/abs`, `crates/kobo`, `crates/koreader`, `crates/opds`, `crates/liseur-sync`, plus native GraphQL/REST/Readium. Profiles are **Shipped**; their harness and client records are separated in [Client verification](/docs/developer/client-verification). | A protocol adapter is not a search provider, downloader, metadata authority, or alignment engine. |
| **Metadata providers** | Identify and look up metadata candidates, map fields, retain provenance, and participate in ingest policy. | Coppice still consumes `crates/integrations/metadata`; `crates/ingest` implements the candidate/apply boundary. Hardcover metadata and personal connection/manual import are **Shipped**; offline and live evidence are separated in [Provider status](/docs/developer/provider-status) and [Hardcover integration](/docs/developer/hardcover-integration). The shared-crate cutover and linked MetaMeta configuration are not shipped in Coppice. | Metadata lookup does not create a wanted request or acquire files; personal-account sync is a separate consent-gated path. |
| **Catalog/source providers** | Discover popular/latest/search/details/chapters/pages from a remote source and expose a materialized or virtual library. | `crates/provider`, `crates/provider-mangadex`, and `crates/provider-themes` own the `Source` contract and source definitions. The host and catalog path are **Shipped** when enabled; see [Provider host](/docs/developer/provider-host) and [Source definitions](/docs/developer/source-definitions). | A source provider is not the metadata-provider registry. It does not turn a search result into a fulfillment, and Storyteller never belongs here. |
| **Worker backends** | Execute heavy or hardware-bound jobs outside the server process and return validated, digest-bound results. | `crates/worker`, `worker_jobs`, `transcode`, and `challenge_solve` are **Shipped**. The typed `align` contract and optional operator-configured Storyteller and external native-CTC worker runners are **Shipped**. See [Read-aloud](/docs/developer/read-aloud) for the configuration boundary. | Alignment runners are not bundled ML and are not a default server-side runtime. |
| **Request system** | Store metadata-backed requests, enforce permissions and per-user visibility, record approval/rejection decisions, notify users, and accept social recommendation handoff. | The ledger, GraphQL create/list/detail/approve/reject contract, and Home request UI are **Shipped**. | Approval alone does not trigger release search, a grab, or publication. |
| **Acquisition handoff** | Coordinate explicit manager search/grab through MAM Bridge and copy completed files into reviewed staged ingest. | The `mam-acquisition` feature and default-off runtime switch are **Shipped**; release calls are server-to-bridge only, and completed files use a local mapped root or verified source-worker materialization. | Coppice does not own MAM credentials, select or grab automatically, retry acquisition, or bypass Editor review. |

These classes compose in the same process where the current source permits it.
A worker is an optional executor that dials the server; it is not a second
catalog or database. External systems keep their own credentials and lifecycle.

The contract-tested home-library source-worker role is separate from the
compute-worker job executor. It reports privacy-minimized catalog observations
and serves explicitly authorized bytes through private direct or outbound-tunnel
connections. The server still owns verification, explicit location linking,
ingest, reader authorization, and reader URLs. Automatic matching, publication,
placement, caching, and replication remain planned. For MAM handoffs, an
operator-configured `MAM_BRIDGE_SOURCE_ROOT` can use this existing verified
read/materialization path; request approval alone never starts acquisition.
See [Remote worker libraries](/docs/developer/remote-worker-libraries).

## Search, requests, acquisition, and ingest

Universal-style search discovers metadata or remote catalog entries. Coppice can
turn metadata into its own request record, but search results and approved
requests do not represent acquired files.

The request and acquisition flow is explicitly gated:

```text
metadata search or recommendation
  -> request metadata + optional destination intent
  -> permission and per-user visibility checks
  -> operator approval
  -> manager with AcquireReleases explicitly searches and confirms a grab
  -> MAM Bridge refresh reports completion
  -> server copies the manifest handoff into staged Editor review
  -> ingest approval fulfils the request and notifies its requester
```

MAM Bridge remains a separate authenticated sidecar that owns the MAM account
and transport state. Coppice reads its API bearer token from a server-side file;
the browser never calls the bridge or receives that token. `mam-acquisition` is
included in headless/full profiles but disabled at runtime unless
`STUMP_ENABLE_MAM_ACQUISITION=true`. Configure `MAM_BRIDGE_URL`,
`MAM_BRIDGE_TOKEN_FILE`, and either `MAM_BRIDGE_HANDOFF_ROOT` for the local
`/downloads` mapping or `MAM_BRIDGE_SOURCE_ROOT` for the verified source-worker
path.

Search is an explicit manager action for an approved request, results are
cached, and the first successful search uses the bridge's five-result probe.
Paused/rate-limited responses are surfaced to the manager; no code enables
search or retries grabs automatically. The background job only refreshes
accepted active grabs. A completed manifest path is copied, never moved,
renamed, or deleted, into staged ingest so seeding continues. Editor review,
quality checks, and approval remain required; only that ingest approval marks
the request fulfilled.

## Alignment orchestration is a separate path

Alignment begins only after a user confirms the ebook and audiobook edition
pair. Pairing, timing import, alignment enqueue, and cache-only status/download
are shipped; synchronized reader playback and readiness quality checks remain
open.

```text
confirmed ebook + audiobook pair
  -> import existing SMIL or accepted timing data
  -> validate and persist SyncMapV1
  -> explicit alignment job
  -> optional operator-configured Storyteller or external native CTC worker
  -> validate result and persist accepted map
  -> deterministic streamed M4B-to-EPUB render and cache
```

Storyteller runs only through a worker configured by the operator to reach an
external instance; its credentials and remote-library lifecycle remain
worker-local. The worker obtains the confirmed source EPUB/audio through
Coppice's authenticated media routes and sends those bytes only to that
configured instance. The server does not bundle or execute local ML. The
deterministic renderer and cache endpoints do not by themselves provide a
synchronized reader UI; ordinary EPUB and audiobook playback remain separate
until that playback contract is shipped.

## Application and server boundaries

The `/editor` and `/app` static applications are separate web assets served by
Coppice when their corresponding directories are configured (`INGEST_EDITOR_DIR`
and `STUMP_HOME_APP_DIR`). Removing either static application does not remove the
native API, protocol adapters, ingest, providers, or worker socket. A headless
profile may omit both applications while retaining the backend contracts that
its Cargo features include. See [Server architecture](/docs/developer/server-architecture)
for the feature/profile matrix and lifecycle rules.

## Optional stack links — planned in Coppice

Every program must remain usable alone. Shared code belongs in a crate;
shared state crosses an explicit versioned, scoped link API. This is the
accepted integration direction, not a claim that the following links work
in this checkout:

| Concern | Standalone behavior today | Accepted linked-mode direction |
| --- | --- | --- |
| Metadata and search | Direct metadata adapters with Coppice-owned configuration; book/comic/manga search stays in Coppice. | Prefer `MetametaProvider` against MetaMeta's catalog service, with explicitly configured direct-adapter fallback. Provider keys stay where the adapter executes. |
| Requests | Coppice owns its request and approval ledger. | Hub becomes request authority; Coppice creates requests there and mirrors their status for mapped users. Historical import is an explicit link-time operation. |
| Acquisition | Coppice orchestrates manager-confirmed MAM Bridge calls and reviewed staged-ingest handoff. | Factor the orchestration into a shared crate for Coppice and a future dler consumer; MAM Bridge remains separate. |
| Progress, devices, notes, annotations, and files | Coppice owns device sync, reading state, annotations, permissions, and file serving. | A scoped link lets hub read widgets and deep-link to Coppice; hub does not write progress. Annotation export targets W3C Web Annotation selectors. |
| Identity | Existing Coppice users and authentication. | Explicit reviewed Coppice↔hub user mapping; network-peer identity alone is not user identity or an authorization bypass. |

A sibling `metadata_integrations` crate and its `MetametaProvider` already
exist outside this repository. That is not a Coppice cutover: `apps/server`,
`core`, `crates/graphql`, `crates/ingest`, and `crates/library` still depend
on the in-repo metadata crate. Replacing it requires an immutable source
revision fetchable by Coppice CI and Docker builds, plus publication
authorization. An external local path is not a deployable dependency.
Linked operation additionally needs provider configuration, catalog-service
credentials, and the provider-selection policy. Request linking, scoped
reading-state export, user mapping, and acquisition extraction remain
**Planned** here; no folder move, credential copy, or data migration follows
from this design.


## Connections: personal delivery and provider state

Connections are split between a shared system sender and user-owned targets:

- SMTP is one server emailer. Only the server owner or `ManageServer` may read
  or change its host, sender, and TLS metadata; passwords are encrypted and
  never returned. `EmailSend` remains sufficient for sending a book.
- Kindle destinations belong to one user and can be created, renamed, made
  default, or deleted without changing legacy `devices.kindle_email`. New
  sends snapshot the destination id/name/address in `kindle_deliveries`; old
  device-id sends continue unchanged. Deleting a destination never deletes
  delivery history.
- A Hardcover PAT is encrypted per user and verified through `me` before it is
  stored. Personal status is redacted; clients are scoped by user and credential
  version. The metadata-lookup mutation checks the user's opt-in, but unified
  external search currently falls back to their PAT without checking that flag.
  Closing this consent gap remains open. Public metadata may use a
  provider/query/schema/expiry cache; private imported records never enter it.
- Manual Hardcover import is read-only remotely and currently reads optional
  quote/note/page fields from `me.user_books`, not `reading_journals`. Its live
  authenticated wire shape remains unverified. With an explicit media
  link and an in-bounds page, it creates a page-position annotation using a
  synthetic `hardcover://<entry-id>` locator; that is not a real EPUB spine
  href, exact text range, or Kobo anchor. Otherwise unresolved provenance is
  retained. Local progress projection is opt-in, page-bounded, and uses the
  shared non-regressing reading-head rule. Remote writes and exact-edition
  locator reconciliation remain planned.

## Source of truth

- [Current state](/docs/developer/state) records what exists and the evidence
  level for each client and subsystem.
- [Provider status](/docs/developer/provider-status) records metadata and
  protocol-provider contracts and their gates.
- [Read-aloud](/docs/developer/read-aloud) records pairing, timing maps, worker
  execution, the shipped request backend, the implemented gateway with mocked
  contract evidence pending Main validation, and remaining alignment work.
- [Client verification](/docs/developer/client-verification) records app/device
  evidence separately from server contracts.
