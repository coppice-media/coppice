---
title: Unified reading state
description: Design contract for lossless reading-position and annotation synchronization
---

This page is a design contract, not an implementation. It defines the common
state layer that provider adapters can target without pretending that a Readium
locator is a lossless interchange format.

## Evidence and labels

Facts in this page are marked **[observed]** and cite the source file, line
range, and inspected revision. The `headless-modular` provider crates and
server adapters are uncommitted in the inspected worktree; those citations use
`@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)` rather than
claiming that the new files exist in the base commit. Design choices and
projections are marked **[inference]**. The Kobo API mapping is intentionally
referenced to the planned companion [Kobo sync capabilities, §7](./kobo-sync-capabilities)
and to the pinned upstream implementation instead of being re-derived from
Stump's compatibility stub.

The canonical locator type is already present in
`crates/models/src/shared/readium.rs:122-190@37fdb7d7340894a777c40d685d5262becceae007`.
It contains `href`, `type`, `title`, optional `locations` (fragments,
progression, position, total progression, CSS selector, and partial CFI),
optional text context, and optional `kobo_span`. The fields below therefore
use `ReadiumLocator` as a **projection** only. Every provider event MUST keep
its raw native locator, complete native payload, provenance, and declared
precision beside that projection.

## Domain model

### Reading position

**[inference]** A reading position is an event plus a materialized head. The
head is convenient for readers; the event is the audit/reconciliation record
and is never rewritten when a later provider overwrites the head.

```text
reading_position_event {
  id: string                         // server event id
  user_id: string
  work_id: string                    // canonical work/media identity
  edition_id: string?                // exact file/publication when known

  locator: ReadiumLocator?           // normalized projection; may be absent
  progression: decimal?              // resource-local, 0..=1
  total_progression: decimal?        // publication-wide, 0..=1
  status: reading_status?            // reading, finished, abandoned, unread

  device: { id: string, name: string? }?
  source_provider: provider
  source_record_id: string?          // op id, session id, media id, etc.
  source_locator_kind: string?       // R2, page, epubcfi, xpointer, etc.
  raw_native_locator: json           // null when the source has no locator
  raw_native_payload: json           // complete source request/row/response
  provenance: {
    source_work_id: string?
    source_edition_id: string?
    source_timestamp: timestamp?
    timestamp_kind: device | server
    received_at: timestamp
    converter: string                 // converter name and version
  }
  precision: precision_tier
  updated_at: timestamp               // effective event time
  server_seq: int64                   // monotonic per user/position stream
}

reading_position_head {
  user_id
  work_id
  edition_id?
  winning_event_id
  projection: PositionProjection        // normalized, raw, and provenance fields above
}
```

**[observed]** Stump's current `reading_session::Model` stores session date,
start/end Readium locators, start/end pages, start/end percentages, raw
`koreader_progress`, elapsed seconds, readthrough number, status, notes,
device IDs, media/user IDs, and created/updated timestamps
(`crates/models/src/entity/reading_session.rs:22-74@37fdb7d7340894a777c40d685d5262becceae007`).
The unified event keeps those session facts in provenance/history while the
head is derived from the latest accepted end position.

**[inference]** `updated_at` is the effective source event time, not a license
to discard `received_at`. If a protocol supplies a device timestamp, it is
used and `timestamp_kind=device`; if it does not (for example the current
native Stump GraphQL input or KOReader PUT), the server assigns the ingestion
time and records `timestamp_kind=server`. A converter MUST NOT silently
invent an EPUB `href`, CFI, or page when the native source did not provide one.

### Precision tiers

**[inference]** Precision is declared by the converter and is never inferred
only because a JSON field is non-empty. Tiers are ordered for fallback and
conflict display as follows:

| Tier | Meaning | Examples |
| --- | --- | --- |
| `range` | A range/anchor was validated against the exact edition bytes. | Readium CFI/range, or a Kobo span resolved against the same KEPUB transformation. |
| `resource` | A resource `href` plus a valid resource-local position/progression is known, but a text range is not guaranteed. | R2 `href` + `locations.progression`; Kobo `Location.Source` + content-source percentage. |
| `page` | A discrete page coordinate is known, but no stable resource anchor is known. | Stump paged input or numeric KOReader `progress`. |
| `publication` | Only whole-publication percentage is known. | KOReader percentage without a usable page; Kobo `ProgressPercent`. |
| `unknown` | The source has no usable position. | An empty state or a malformed/unresolvable native locator. |

A Kobo span or CFI is `range` only after validation against the exact bytes;
otherwise it remains raw evidence and is at most `resource`. A page and a
resource anchor are not interchangeable merely because both can be displayed
as a progress bar.

### Annotation

**[inference]** An annotation uses the same identity, normalized locator,
progression, device, provider, raw payload, provenance, precision, effective
time, and server-sequence fields as a reading position, and adds:

```text
annotation {
  id: string                         // provider id in a namespaced identity
  user_id
  work_id
  edition_id?
  kind: highlight | note | bookmark
  locator: ReadiumLocator?           // canonical anchor projection
  progression?
  total_progression?
  quote: {
    text?: string                    // selected text/excerpt
    before?: string
    after?: string
  }
  anchors: {
    start?: json                     // canonical/native anchor details
    end?: json
  }
  body?: string                      // user's note, distinct from quote.text
  device?
  source_provider
  source_record_id?
  source_locator_kind?
  raw_native_locator: json
  raw_native_payload: json
  provenance
  precision: precision_tier
  revision: int64
  tombstone: bool
  deleted_at: timestamp?
  updated_at: timestamp
  server_seq: int64                   // monotonic per user/annotation stream
}
```

**[observed]** Native Stump `media_annotations` has a required
`ReadiumLocator`, optional `annotation_text`, media/user IDs, and
created/updated timestamps (`crates/models/src/entity/media_annotation.rs:1-70@37fdb7d7340894a777c40d685d5262becceae007`).
Native `bookmarks` has optional preview content, optional locator, optional
page, media/user IDs, and a creation timestamp
(`crates/models/src/entity/bookmark.rs:1-80@37fdb7d7340894a777c40d685d5262becceae007`).
The unified `body` is the note/annotation text; selected text in
`locator.text.highlight` or a provider excerpt is the quote, not the note.

**[observed]** The native liseur-sync annotation contract carries `kind`, an
opaque locator, optional progression/excerpt/color/body, client timestamp,
revision, sequence, device, and deletion fields. `base_rev == 0` creates a
record and later writes use compare-and-set revisions
(`crates/liseur-sync/src/lib.rs:192-245@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`).
The unified annotation MUST retain a tombstone even when a provider's local
store normally hard-deletes rows.

## Converter contract

**[inference]** Every provider that carries a position implements the same
logical contract. The names below are language-neutral pseudocode; the
provider-specific native DTO remains owned by its provider crate.

```text
to_locator(native_position, publication_context)
  -> { locator, progression, total_progression, status,
       raw_native_locator, raw_native_payload, provenance, precision,
       losses }

from_locator(projection, publication_context)
  -> { native_payload, native_locator, losses }
```

`to_locator` MUST:

1. retain the complete native request/row/response as JSON;
2. retain the native locator separately, including opaque/foreign formats;
3. populate only fields justified by the native contract and publication
   context;
4. return a field-level loss report and a precision tier; and
5. keep provider identity and timestamps separate from the normalized locator.

`from_locator` MUST reject an unrepresentable projection or return it with an
explicit loss report. It MUST NOT substitute a different provider's locator
syntax, silently drop a note/range, or turn a server-generated URL into a
publication resource `href` without recording that derivation.

`to_annotation` and `from_annotation` use the same contract when the provider
has an annotation resource. A provider with no annotation surface returns
`unsupported` rather than treating progress text as a highlight.

## Provider contracts and loss tables

## Conflict and materialization rule

**[observed]** Komga R2 and OPDS v2 reject an update whose supplied
`modified` timestamp is older than the latest session
(`crates/komga/src/routes/readium.rs:337-349@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`;
`apps/server/src/routers/opds_backend/v2_0.rs:1261-1290@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`).
**[observed]** liseur-sync records client timestamp, device, received time,
and an atomically assigned sequence, and exposes changes ordered by that
sequence (`apps/server/src/routers/liseur_sync/storage.rs:721-838,877-906@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`).
Its annotation lane additionally uses revision CAS and tombstones
(`apps/server/src/routers/liseur_sync/storage.rs:1046-1297@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`).

**[inference]** The unified reading-position head uses **last-writer-wins by
device timestamp, with server sequence as the deterministic tie-breaker**:

1. Convert a source timestamp to `updated_at`. Prefer the provider's device
   timestamp (`R2.modified`, OPDS `modified`, Kobo state/bookmark
   `LastModified`, or liseur `client_ts`). For Stump native and KOReader,
   which do not carry a client timestamp in their write DTOs, use server
   ingestion time and mark `timestamp_kind=server`.
2. Assign an atomically increasing `server_seq` in the user's position
   stream. The sequence is a cursor/audit order, not a replacement for the
   device timestamp.
3. Compare candidates lexicographically by `(updated_at, server_seq)`; the
   greatest candidate becomes the materialized head. A later-arriving update
   with an older device timestamp is retained as an event but does not move
   the head. Equal timestamps are resolved by the larger server sequence.
4. Keep losing raw payloads and loss reports. A client can inspect the losing
   event and the winning event; no native locator is thrown away merely
   because it cannot be projected to Readium.
5. Scope the comparison by `(user_id, canonical work_id, edition_id)` and keep
   source identity aliases (media ID, Kobo entitlement, KOReader hash, liseur
   work/edition) in provenance. An identifier mismatch MUST NOT merge two
   works on title similarity alone.


**[inference]** Annotation writes apply the liseur base_rev CAS precondition
first. A matching write gets the next revision and annotation sequence; a
stale revision returns a conflict and leaves the current record/tombstone
untouched. For annotation sources without revisions, accepted events use the
same (updated_at, server_seq) LWW ordering. Once accepted, a unified
annotation head uses the same ordering; CAS protects the provider edit chain
rather than replacing cross-provider ordering. A delete is a new tombstone
revision, never a physical disappearance from the unified stream. This keeps
the requested LWW rule for provider state while preserving liseur-sync
observed revision semantics for mutable annotation identities.
 
## Migration outline from today's tables

**[observed]** The current storage is split across the v2 reading-session row,

unified registry (id, owner, name, kind, transform profile, last-seen / last-sync

`crates/migrations/src/m20260910_000000_add_devices.rs`);
`media.koreader_hash` is an optional KOReader identity hash

and `kobo_sync_sessions` stores user, selected media IDs, Kobo device id and

(`crates/models/src/entity/kobo_sync_session.rs:1-40@37fdb7d7340894a777c40d685d5262becceae007`).

### Phase 1 — add the unified event/head store

**[inference]** Add position events and heads, annotation records/events, and
provider-identity/provenance columns without removing the old tables. Keep
separate per-user position and annotation sequence counters, matching
liseur-sync's observed `op_seq`/`annotation_seq` split
(`crates/migrations/src/m20260904_000000_add_liseur_sync.rs:49-91,300-503@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`).
Raw JSON should be validated for size and parseability but stored unchanged
as a value; normalization is an additional column, never an in-place rewrite.

### Phase 2 — deterministic backfill

1. **[inference] Reading sessions:** emit one Stump position event per
   session's end state. Map `end_locator`, `end_page`, `end_percentage`,
   status, device IDs, notes, elapsed seconds, media/user IDs, and timestamps;
   retain start fields and the complete row in raw payload/provenance. Order
   equal timestamps by the existing session `id` when seeding `server_seq`.
2. **[inference] Legacy CFI:** if a deployed database still has the legacy
   `epubcfi` value, retain it verbatim and conditionally populate
   `partial_cfi`; never claim successful conversion without edition
   validation. The v2 migration's legacy copy is evidence that this value is
   historical input, not a new provider contract.
3. **[inference] KOReader:** copy `media.koreader_hash` into provider identity
   aliases/edition provenance, not into a locator. For every session with
   `koreader_progress`, create a raw KOReader event containing
   document=`media.koreader_hash` when available, `progress`, percentage,
   and device. Numeric strings can seed page; an x-pointer seeds raw
   foreign position and percentage only.
4. **[inference] Devices:** import `reading_devices` into the unified device
   registry and preserve all `reading_session.device_ids`. The materialized
   head may expose one winning device, but provenance retains the complete
   contributing set.
5. **[inference] Native annotations/bookmarks:** backfill
   `media_annotations` as highlight/note records and `bookmarks` as bookmark
   records with `revision=1`, `tombstone=false`, source `stump`, and raw rows.
   A hard delete leaves no historical tombstone; do not synthesize one.
6. **[inference] Kobo cursors:** do not convert `kobo_sync_sessions` into
   reading positions. Migrate its device id, device metadata, selected media
   IDs, and previous-sync timestamp into a provider cursor/provenance table;
   completed cursors can be retired after parity, while incomplete cursors
   remain resumable or expire by an explicit policy.
7. **[inference] Existing liseur records:** where the optional
   `liseur_sync_*` tables already exist, import position ops and annotation
   records as liseur events without interpreting opaque locator JSON. Keep
   their `seq`, `rev`, `client_ts`, `device_id`, payload, and tombstones as
   source evidence.

### Phase 3 — dual read/write and parity

**[inference]** Route every provider position write through its applicable adapter (`to_locator` where defined, the canonical identity path for OPDS 2.0, or the direct page path for OPDS 1.2), append an
immutable unified event, materialize the conflict winner, and maintain the
legacy projection needed by existing GraphQL/Komga/KOReader/Kobo clients.
Provider reads use `from_locator` and retain the winning raw native payload
when it can be replayed. Use a deterministic idempotency key such as
`(user_id, source_provider, source_record_id, payload_digest)` so a retry does
not create a second event. Compare provider responses with the legacy path
before switching reads; discrepancies must be reported as field-level losses,
not hidden by a fallback conversion.

### Phase 4 — cutover and retirement

**[inference]** After parity, switch native and compatibility reads to unified
heads, keep old rows read-only for a rollback window, and stop duplicate
writes. Only then retire compatibility columns/tables: archive
`reading_sessions`, keep the KOReader hash as a durable identity alias even
if `media.koreader_hash` is removed, and remove `kobo_sync_sessions` only
after its cursor state has moved. Native `media_annotations` and `bookmarks`
may remain as local projections; the unified annotation/tombstone stream is
the source of truth for cross-provider synchronization.

## Non-negotiable invariants

- **[inference]** A normalized Readium locator is never the sole copy of a
  provider position or annotation.
- **[inference]** Every event identifies its provider, source identity,
  timestamp kind, converter version, raw native locator, raw native payload,
  precision, and loss report.
- **[inference]** Unknown provider fields survive round trips in raw JSON;
  unsupported fields are reported, not silently repurposed.
- **[inference]** A sequence is a server ordering/audit cursor. It does not
  erase device time, and device time does not erase sequence ties.
- **[inference]** Annotation revisions and tombstones survive provider
  deletion or provider disablement.
- **[observed]** Existing provider routes already distinguish stale timestamp
  conflicts (Komga/OPDS) and keep liseur position/annotation sequence data;
  the unified layer extends those boundaries rather than changing the public
  protocol behavior (`crates/komga/src/routes/readium.rs:337-399@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`,
  `apps/server/src/routers/liseur_sync/storage.rs:721-838,1046-1297@working-tree (base 37fdb7d7340894a777c40d685d5262becceae007)`).
