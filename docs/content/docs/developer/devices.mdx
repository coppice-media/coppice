---
title: Devices
description: The unified device registry, its credentials, endpoints, and last-seen tracking
---

A *device* is a registered client owned by a user: a Kobo, a KOReader install, Mihon, Komelia, Liseur, a generic OPDS reader, a script using the API, or a browser. The registry lives in `crates/devices` (`stump_devices`) and is reached through `Ctx::devices()` (`core/src/context.rs`). It mints the credential a device authenticates with, tells the client which URLs to configure, and records when each device was last seen and last synced.

## Storage

Migration `m20260910_000000_add_devices` (`crates/migrations/src/m20260910_000000_add_devices.rs`) creates two tables and folds the old `reading_devices` registry into the first one:

| Table | Columns |
| --- | --- |
| `devices` | `id` (text PK), `user_id` (FK `users`, cascade), `name`, `kind`, `transform_profile` (JSON, nullable), `created_at`, `last_seen_at`, `last_sync_at`, `last_sync_summary` (JSON, nullable), `revoked_at` |
| `device_credentials` | `id`, `device_id` (FK `devices`, cascade), `protocol`, `credential_kind`, `credential_ref`; unique on `(credential_kind, credential_ref)` |

`kind` is one of `kobo | koreader | mihon | komelia | liseur | opds | api | web`; `protocol` is `kobo | koreader | komga | opds | liseur | api`; `credential_kind` is `api_key | liseur_token | session` (`models::shared::enums::{DeviceKind, DeviceProtocol, DeviceCredentialKind}`). `credential_ref` is polymorphic and therefore has no foreign key: the `api_keys.short_token` for an API key, the `liseur_sync_tokens.id` for a liseur token, the `sessions.session_id` for a session.

The old `reading_devices` rows (KOReader and OPDS progression clients registering themselves by id + name) become `devices` rows owned by the user whose reading sessions reference them, with kind `koreader` when any of those sessions carries a `koreader_progress` and `opds` otherwise. Rows no session references are dropped with the table. `reading_sessions.device_ids` keeps pointing at these ids as a JSON array; replacing it with a junction table that carries a foreign key to `devices` is the documented follow-up. The KOReader adapter (`apps/server/src/routers/koreader_backend/sync.rs`), the OPDS 2.0 progression route (`apps/server/src/routers/opds_backend/v2_0.rs`), and the Komga Readium progression route (`crates/komga/src/routes/readium.rs`) now register their client-reported devices directly in `devices`.

## Credentials

`DeviceService::create_device(user, kind, name)` mints the credential the kind needs and stores its reference on the device. The name defaults to `"<Username>'s <Kind>"` and is numbered on collision.

| Kind | Credential | Minted permissions |
| --- | --- | --- |
| `kobo` | prefixed API key | `ACCESS_KOBO_SYNC`, `DOWNLOAD_FILE` |
| `koreader` | prefixed API key | `ACCESS_KOREADER_SYNC` |
| `opds`, `mihon`, `komelia` | prefixed API key | `DOWNLOAD_FILE` |
| `api`, `web` | prefixed API key | inherit the user's permissions |
| `liseur` | liseur-sync device token (`liseur-<uuid>`, scopes `sync`, `read-insights`, `library-read`, bound to the device id) | n/a |

A key never grants what its owner does not hold, and an API key only authenticates for users allowed to use API keys (`validate_api_key` in `apps/server/src/middleware/auth.rs`), so creating an API-key device requires `ACCESS_API_KEYS` plus the minted permissions; the server owner bypasses the check. The plaintext secret is returned exactly once (`IssuedCredential`), afterwards only a hint such as `stump_abcdefgh_…` is available.

`rotate_credential` deletes the API key row (or revokes the liseur token) and mints a replacement. `revoke` does the same without a replacement, drops the credential rows, and stamps `revoked_at`; the device row stays so its history remains visible. `rename` also renames the API key / liseur token; `set_transform_profile` stores a free-form JSON profile for the protocol adapters.

The liseur-sync storage shares the secret format, hash, and default expiry with the registry through `stump_devices::liseur_token::{new_secret, hash_secret, DEVICE_TOKEN_TTL_SECS}`, so tokens minted either way authenticate through the same bearer middleware.

## Endpoints

`Endpoint::for_kind(kind, origin, username, secret)` describes what to configure on the client, where `origin` is the scheme and host the request arrived at:

| Kind | Endpoints |
| --- | --- |
| `kobo` | `{origin}/kobo/{key}` |
| `koreader` | `{origin}/koreader/{key}` with the username |
| `opds` | `{origin}/opds/{key}/v1.2` and `{origin}/opds/v2.0` (Bearer) |
| `mihon` | `{origin}` as a Komga server with username + `X-API-Key`, plus `{origin}/api` (Bearer) |
| `komelia` | `{origin}` as a Komga server with username + `X-API-Key` |
| `liseur` | `{origin}` as the liseur-sync server (Bearer) |
| `api`, `web` | `{origin}/api` (Bearer) |

`deviceEndpoints(id)` returns these with the secret redacted; `createDevice` and `rotateDeviceCredential` return them with the full secret.

## Sightings

`DeviceService::touch(credential, protocol, summary)` resolves the credential to its device, writes `last_seen_at`, and, when a sync summary is given, `last_sync_at` + `last_sync_summary` (stored verbatim). Plain sightings are coalesced in memory to one database write per credential per 60 seconds (`TOUCH_INTERVAL`, `crates/devices/src/service.rs`); a coalesced request does not even read the credential row, so page streams and cover bursts cost the registry nothing. A summary always lands. Each recorded sighting is forwarded as `CoreEvent::DeviceSeen { deviceId, userId, protocol, firstSeen }` (`core/src/event.rs`), `firstSeen` being `true` for the first request the device ever authenticated. Revoked devices and unknown credentials are ignored. `DeviceService::device_for_credential(credential)` is the same lookup without the write, for adapters that need per-device state such as the transform profile.

The registry is best effort at every call site: a failure is logged and never fails the request. The call sites are:

| Site | Protocol | Summary |
| --- | --- | --- |
| `api_key_middleware`, `apps/server/src/middleware/auth.rs` — path keys on `/kobo/{key}`, `/koreader/{key}`, `/opds/{key}/v1.2` | from the mount prefix | none |
| `auth_middleware`, same file — `X-API-Key` on the Komga-scoped paths | `komga` | none |
| `auth_middleware`, same file — `Authorization: Bearer <api key>`, or `Authorization: Basic` whose password is a device key | `komga` on Komga paths, `opds` on `/opds`, otherwise `api` | none |
| `authenticate`, `apps/server/src/routers/liseur_sync/storage.rs` — every liseur bearer request | `liseur` | none |
| `library_sync`, `apps/server/src/routers/kobo_backend/router.rs` | `kobo` | `{"protocol":"kobo","items","new_entitlements","should_continue","kobo_device_id"}` |
| `put_progress`, `apps/server/src/routers/koreader_backend/sync.rs` | `koreader` | `{"protocol":"koreader","document","progress","percentage","koreader_device","koreader_device_id"}` |
| `update_read_progress`, `crates/komga/src/routes/progress.rs` via `KomgaBackend::record_sync` (`apps/server/src/routers/komga_backend.rs`) | `komga` | `{"protocol":"komga","book_id","page","completed"}` |
| `append_ops`, `apps/server/src/routers/liseur_sync/storage.rs` — an accepted ops push | `liseur` | `{"protocol":"liseur","ops","applied","duplicate","conflict"}` |
| `POST /api/v2/devices/me/touch`, `apps/server/src/routers/liseur_sync/touch.rs` | `liseur` | the request body, verbatim |

### Basic authentication with a device key

Clients that only speak `Authorization: Basic` (Mihon's Komga extension, OPDS 1.2 readers) can send the owner's username with the device key as the password. The key is validated exactly as a Bearer key and must belong to the named user; the request then acts as the device with the key's narrowed permissions, and the sighting is recorded. Such a request never opens a session or a Komga remember-me token, since either would act as the full user. A password that merely looks like a key still falls through to the bcrypt check. Session and password-Basic authentication carry no per-device credential and record nothing.

## Library scope

A device can be restricted to a subset of the libraries its user can see, so the same protocol routes resolve to a different visible library set depending on which device authenticated. Migration `m20260925_000000_add_device_library_scope` adds `devices.library_scope`: a JSON array of library ids, or `NULL` for "inherit whatever the user sees". `stump_devices::LibraryScope` is the typed form (`Inherit` or `Only(ids)`), and `device::Model::library_scope_ids` falls back to inherit and logs when the column holds anything that is not an array of ids, because a corrupt scope must not hide a device's whole library.

`setDeviceLibraryScope(id: String!, libraryIds: [ID!]): Device!` writes it: `libraryIds: null` clears the restriction back to inherit, `[]` restricts the device to nothing. `Device.libraryScope: [String!]` reads it back, `null` again meaning inherit. The caller must own the device or be the server owner — the same `DeviceService::get` check the other device mutations use — and every id must name a library the device's *owner* can see, or the write is rejected with `DeviceError::InvalidScope` (`crates/devices/src/service.rs::set_library_scope`). Validating against the owner rather than the caller keeps a server-owner edit from naming a library the device's user cannot open.

Enforcement is not per protocol. `models::shared::visibility::VisibilityScope` is the single funnel behind the `find_for_user` family on `library`, `series`, and `media`, and its `library_condition` `AND`s the user's `library_exclusions` subquery with `<library column> IN (scope)`. Komga, Kavita, OPDS 1.2 and 2.0, Kobo, KOReader, liseur-sync, and GraphQL all read through those helpers, so one scope narrows every one of them at once. `From<&AuthUser>` yields the request's resolved scope, which is why existing call sites are scoped without being touched; `VisibilityScope::inherit(user)` is the only, explicit opt-out and is reserved for describing what a *user* owns rather than what a device sees.

| Device scope | Library in the user's visibility | Result |
| --- | --- | --- |
| `NULL` (inherit) | yes | visible |
| `NULL` (inherit) | no — excluded by `library_exclusions` | hidden |
| lists the library | yes | visible |
| lists the library | no — excluded by `library_exclusions` | hidden; the scope is an intersection, never a widening |
| omits the library | yes | hidden |
| `[]` | any | nothing visible |

The scope is resolved once per request from the credential that authenticated it (`DeviceService::authenticate`) onto `AuthUser::device_library_scope`, and `AuthContext::scope()` hands that to the query helpers. A session or password-Basic request carries no device credential, so it has no scope and inherits. Nothing caches the resolved value, so a change is in force on the device's next request. Kobo is the one protocol that needs further bookkeeping, because its sync is incremental and a book that entered or left a scope has no timestamp change for the incremental window to notice; both directions are recorded in `device_entitlement_deltas` (see [Kobo capabilities](/docs/developer/kobo-sync-capabilities)).

## Send to Kindle

A Kindle speaks no sync protocol. Amazon's *Send to Kindle* service takes an e-mail from an approved sender with the book attached and delivers it to the device that owns the recipient address, so the address is the whole transport. Migration `m20260928_000000_add_device_kindle_email` adds `devices.kindle_email` (text, nullable) for exactly that, next to the transform profile and the library scope.

No `kind` is a Kindle: a Kindle never authenticates, so it has no credential, no endpoints, and nothing to mint. Any device row may carry an address — in practice the row that stands for the operator's reading setup — and a row with one is a `sendToKindle` target. `setDeviceKindleEmail(id: String!, email: String): Device!` writes it (`email: null` clears it) and `Device.kindleEmail: String` reads it back. The address is validated syntactically by `stump_devices::normalize_kindle_email` — trimmed, one `@`, a non-empty local part, a hostname domain — and refused with `DeviceError::InvalidEmail` (HTTP 400) otherwise. The domain is deliberately not pinned: Amazon runs several regional Send-to-Kindle domains and an operator may point the device at their own forwarder. Nothing verifies the address with Amazon; only a delivery can.

`sendToKindle(mediaId: ID!, deviceId: ID!): KindleDelivery!` (`crates/graphql/src/mutation/kindle.rs`, `EMAIL_SEND` permission) is one book to one device:

| Step | Rule |
| --- | --- |
| Format | Amazon accepts `azw3`, `doc`, `docx`, `epub`, `htm`, `html`, `mobi`, `pdf`, `rtf`, `txt`. Anything else — a CBZ, a CBR — is refused locally: a Kindle cannot open it and Amazon discards it, which would look like a successful send. |
| Conversion | An EPUB becomes AZW3 through the `boko-convert` tool in its pinned send-to-Kindle shape (`stump_tools::boko::KindleExport`) when the operator has `boko` on `PATH`. Without it the EPUB is mailed as it is — Amazon converts EPUB itself — and the delivery reports why in `note`. A missing converter is therefore normal, not an error. See [calibre tooling](/docs/developer/calibre-tooling). |
| Delivery | The primary emailer and `stump_notify::EmailChannel`, i.e. the same SMTP client, size cap, and error mapping as `sendAttachmentEmail`, and the same forbidden-recipient list. The subject is the book's name; Stump never sends Amazon's magic `Convert` subject, so it never asks the service to reflow a PDF on the operator's behalf. |
| Recording | Only what actually went out: one `emailer_send_records` row (so the emailer history shows every send, whichever lane made it) plus `DeviceService::record_delivery`, which writes `last_sync_at` and `last_sync_summary` = `{"protocol":"kindle-email","bytes","format"}`. `last_seen_at` deliberately does not move — nothing authenticated, the device was written to, not seen. |

The converted file is a temporary under the server's cache directory and is removed when the request ends; the library file is never touched. `KindleDelivery` returns `{ deviceId, deviceName, recipient, format, bytes, converted, note }`, so the caller can say "sent Dune.azw3 (412 KB) to al@kindle.com" without a second query.

## GraphQL

Every field is scoped to the caller: users see their own devices, the server owner sees all of them (`crates/graphql/src/{query,mutation,object,subscription}/device.rs`).

| Field | Notes |
| --- | --- |
| `devices: [Device!]!`, `device(id): Device!` | `Device` flattens the row and adds `credential { kind protocol secretHint }` |
| `deviceEndpoints(id): [DeviceEndpoint!]!` | secret redacted |
| `createDevice(kind, name): DeviceWithCredential!` | `{ device, credential { kind protocol credentialRef secret }, endpoints }`; permissions enforced by the registry as above |
| `renameDevice(id, name)`, `revokeDevice(id)`, `setDeviceTransformProfile(id, profile)` | owner or server owner |
| `setDeviceLibraryScope(id, libraryIds)` | owner or server owner; `libraryIds: null` restores inherit — see [Library scope](#library-scope) |
| `setDeviceKindleEmail(id, email)` | owner or server owner; `email: null` clears it — see [Send to Kindle](#send-to-kindle) |
| `sendToKindle(mediaId, deviceId): KindleDelivery!` | `EMAIL_SEND`; mails one book to the device's address — see [Send to Kindle](#send-to-kindle) |
| `rotateDeviceCredential(id): DeviceWithCredential!` | rejected with a conflict once the device is revoked |
| `readingStats(span, deviceId): ReadingStats!` | see below |
| `subscription deviceSeen(deviceId)` | filtered `DeviceSeen` events; `readEvents` also carries them |

### Reading statistics

`readingStats(span: WEEK | MONTH | QUARTER | YEAR | ALL_TIME, deviceId)` (`crates/graphql/src/object/reading_stats.rs`) aggregates the caller's `reading_sessions` by logical reading day (`session_date`, which already honours the user's day-reset offset): `sessions`, `minutes` (`elapsed_seconds / 60`), `pages` (end page minus start page per session), `booksFinished`, `streakDays` (consecutive days ending today or yesterday, not bounded by the span), per-day buckets (`days`, active days only), and a per-device breakdown (`devices`, one row per contributing id with the registered name and kind when the id still resolves). With a `deviceId` the stats cover the sessions that device contributed to, computed for the device's owner; the server owner may name any device.
