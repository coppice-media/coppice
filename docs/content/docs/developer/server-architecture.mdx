This page is a source map for the Coppice server and its headless/modular work. The evidence labels are literal: **Shipped**, **Contract-tested**, **Device-tested**, **Source-only**, **Planned**, and **Blocked**. Source inspection and server replay never become app/device proof; see [Client verification](/docs/developer/client-verification).

The compatibility baseline is the full/default server. A headless build removes the optional GraphQL `web` fields and the GraphQL playground, not the Rust process, database, authentication, GraphQL core API, REST/media API, or protocol integrations.

## At a glance

Coppice is one Rust server process. `stump_server` adapts HTTP/WebSocket requests with Axum, `stump_core` owns orchestration and filesystem/job integration, and `crates/models` owns entities, domain types, and services. Home (`/app`) and Editor (`/editor`) are separately built SvelteKit applications with static assets that may be served by the same process. The database and authentication system remain shared by every profile.

The branch includes measured runtime and allocation work:

- The scanner shares one immutable directory-mtime snapshot through `Arc` instead of repeatedly deep-copying the map. See [`LibraryScanJob`](https://github.com/stumpapp/stump/blob/nightly/core/src/filesystem/scanner/library_scan_job.rs) and [`WalkerCtx`](https://github.com/stumpapp/stump/blob/nightly/crates/scanner/src/walk.rs).
- `Watcher` creates its OS `notify` watcher only when the first path is added. Disabling background jobs also prevents construction of its logical listener. See [`watcher.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/watcher/src/watcher.rs) and the core [`watcher_adapters.rs`](https://github.com/stumpapp/stump/blob/nightly/core/src/filesystem/scanner/watcher_adapters.rs).
- The Tokio worker and blocking-thread limits, database pool bounds, and SQLite prepared-statement cache are configurable. Unset values preserve upstream defaults.
- The GraphQL route installs a concurrency-safe schema cell; schema types and DataLoaders are built once, on the first authenticated GraphQL HTTP or WebSocket request rather than at server startup.
- The dependency graph no longer enables unused image formats, `kmeans_colors` CLI defaults, `http-cache-reqwest`'s unused CACache manager, or the SeaORM migration CLI in the server graph.
- Blocking archive and EPUB inspection stays behind synchronous media processors, while OPDS, Komga, native EPUB, and GraphQL request paths cross into it through one batch async wrapper or `tokio::task::spawn_blocking`. Pure feed/link/build operations stay synchronous.

The bare `--no-default-features` build is the lean base and is leaner than the named `minimal` aggregate. `minimal = ["formats"]`, so `--features minimal` adds the PDF/RAR/transform processor set but no optional route features. `webui = ["graphql", "graphql/web"]`, so enabling WebUI also enables GraphQL. A KOReader-only server is composed with `cargo run --package stump_server --no-default-features --features koreader` and `ENABLE_KOREADER_SYNC=true`.


Three concepts cut across every row above, which is why they have their own
pages rather than living inside a protocol:

| Concept | Rule | Where |
| --- | --- | --- |
| Unified reading state | One head per (user, book) with append-only provenance; every protocol writes through it and reads its own projection, and a page ordinal is never interchangeable with a millisecond offset | [Unified reading state](/docs/developer/unified-reading-state) |
| Event bus | One `CoreEvent` broadcast on `Ctx`; producers emit at the durable state transition, sinks subscribe and translate, and adding a variant never edits an existing sink | [Event bus and sinks](#event-bus-and-sinks) |
| Devices | Every credential belongs to a device row; `library_scope` and `transform_profile` make two devices of the same user see different libraries and receive different bytes | [Devices](/docs/developer/devices), [Device pairing](/docs/developer/device-pairing) |

## Current execution

### Development and source builds

The repository's normal development commands are defined in [`package.json`](https://github.com/stumpapp/stump/blob/nightly/package.json) and documented in [Contributing](/docs/developer/contributing):

| Command | Current behavior |
| --- | --- |
| `bun run setup` | Installs the active JavaScript workspace with Bun 1.4.1 and builds Home and Editor. |
| `bun run home dev` / `bun run editor dev` | Runs the Home or Editor SvelteKit development server. |
| `cargo run --package stump_server --bin stump_server` | Runs the Rust server directly. |
| `cargo run --package stump_server --no-default-features --features headless` | Runs backend route capabilities with optional Home and Editor static mounts. |
| `cargo run --package stump_server --no-default-features` | Runs the bare no-default REST/auth/database profile. It is leaner than `minimal` because optional formats and route trees are omitted. |
| `bun run home build && bun run editor build && cargo build --package stump_server --release` | Builds both production static apps and the release server. A source build needs a usable PDFium library (`PDFIUM_PATH` or a system library); the container supplies PDFium itself. |

The server entry point performs debug setup, bootstraps the configuration directory, parses CLI commands, initializes tracing, and enters `run_http_server`. Home and Editor are independently built static apps configured with `STUMP_HOME_APP_DIR` and `INGEST_EDITOR_DIR`.

Database selection is centralized in [`core/src/database.rs`](https://github.com/stumpapp/stump/blob/nightly/core/src/database.rs). `STUMP_DATABASE_URL` has highest precedence, PostgreSQL component variables can compose a PostgreSQL URL, and SQLite is the default; `STUMP_DB_PATH` supplies the SQLite path. Connecting always runs the SeaORM migrations before the server starts accepting requests. Pool bounds apply to both backends; the SQLite statement-cache setting applies only to SQLite.

### Docker

[`docker/Dockerfile`](https://github.com/stumpapp/stump/blob/nightly/docker/Dockerfile) now has two final targets:

```sh
docker buildx build -f docker/Dockerfile --target full .
docker buildx build -f docker/Dockerfile --target headless .
```

- **`full` (the Dockerfile's default final stage):** builds Home and Editor, copies them to `/app/home` and `/app/editor`, builds the server with its default Cargo features, and uses the shared runtime image.
- **`headless`:** builds with `--no-default-features --features headless`, copies no Home or Editor assets, and sets `STUMP_ENABLE_WEBUI=false`. It retains GraphQL, OPDS, Readium EPUB, Kobo, KOReader, native liseur-sync, authenticated REST, background jobs, PostgreSQL, and the shared PDFium runtime.
- Both targets use the common PDFium stage and runtime base. The headless image also chooses conservative, overridable runtime defaults: two Tokio workers, eight blocking threads, at most two database connections, and 32 prepared statements cached per SQLite connection. [`docker/build_server.sh`](https://github.com/stumpapp/stump/blob/nightly/docker/build_server.sh) forwards feature arguments to Cargo for the container build.

The server Cargo graph exposes three aggregates plus the bare base: default `full`, headless, `minimal = ["formats"]`, and no-default. `full` is `headless + webui`; `webui` implies `graphql` through `webui = ["graphql", "graphql/web"]`. `headless` contains every backend route feature, including optional `liseur-sync`; `minimal` adds only format processors; bare no-default is leaner and omits them. Core processor/provider crates remain linked in `headless` and `minimal` until the deeper package split described below.

## Current startup lifecycle

The startup sequence is visible in [`apps/server/src/http_server.rs`](https://github.com/stumpapp/stump/blob/nightly/apps/server/src/http_server.rs):

1. `apps/server/src/main.rs` reads optional runtime sizing from the environment, builds the Tokio multi-thread runtime, bootstraps configuration, and enters asynchronous startup. Unset runtime controls preserve Tokio's automatic worker count and blocking-thread default.
2. `StumpCore::new` creates [`Ctx`](https://github.com/stumpapp/stump/blob/nightly/core/src/context.rs). Context construction connects to the selected SQLite or PostgreSQL database and creates the core event channel; the job runtime (queue plus executor), scheduler, and logical watcher are lazy resources.
3. The server initializes server configuration, encryption and JWT secrets, and SQLite journal mode where applicable. Database migrations and these consistency operations are intentionally not lazy: all retained authenticated API routes require a valid schema and secrets.
4. With `STUMP_ENABLE_BACKGROUND_JOBS=true`, startup cancels islanded jobs with a direct database update. It creates scheduler loops only for valid enabled scheduled-job rows and creates the logical library watcher only when a ready library has watching enabled. With it set to `false`, these lifecycle steps are omitted and attempts to enqueue jobs or operate the watcher return an explicit `FeatureDisabled` error.
5. The job runtime — the queue, its single executor (an Apalis worker with the `apalis` feature, the inline blocking-pool executor without it), the cancellation registry, and the typed queue counters — is created on the first enqueue (including enqueue paths reached by GraphQL, protocol adapters, or ingest), so work submitted after boot is processed without a restart. Registering a watched library, or starting the scheduler when a valid enabled scheduled-job row exists, also creates the job runtime.
6. The OS `notify` backend remains lazy even after the logical watcher is created: it is created only when the first watched path is added. A configured path that no longer exists is skipped with a warning; listener termination and other backend failures abort watcher initialization instead of being silently ignored.
7. A configured OIDC provider is initialized. Cargo features select GraphQL, OPDS, Readium, KOReader, Kobo, and liseur-sync route trees. Existing Kobo/KOReader configuration switches still decide whether their compiled routes are mounted.
8. GraphQL router mounting allocates only a shared `OnceCell`; `build_schema` runs once after the first GraphQL request has passed authentication.
9. Session, CORS, compression, tracing, and optional OIDC layers are applied before binding the listener. The server keeps optional scheduler/watcher handles and stops only resources that were created; the job executor is independent of HTTP startup and follows the first enqueue.

Database connection/migration, server secrets, journal setup, session middleware, retained route assembly, and the HTTP listener are necessary startup work. Metadata provider clients and PDFium were already demand-initialized; this branch makes GraphQL schema construction and optional job infrastructure follow the same principle where their contracts permit it.

### OIDC group permission synchronization

OIDC group synchronization is configured in `core/src/config/oidc_config.rs`
and `core/src/config/env_keys.rs`. `apps/server/src/config/oidc.rs` extracts
the configured group claim from the verified ID token first, then falls back to
userinfo, and computes a deterministic union of mapped permissions. The OIDC
callback in `apps/server/src/routers/api/v2/oidc.rs` persists that union through
`models::txn::begin_write` before creating the login session; an admin group
grants every `UserPermission` but never the locally stored server-owner flag.
The config and mapping behavior are **Contract-tested** by the focused OIDC
tests; client/device behavior remains **Source-only** until a device replay is
run.

### OPDS Page Streaming Extension

The OPDS route handles catalog/search/acquisition and optional progression. It verifies Coppice credentials before resolving the requested library and media projection.

### KOReader interoperability

The route shape is derived from the official [KOReader sync-server routes](https://github.com/koreader/koreader-sync-server/blob/master/config/routes.lua). Coppice's hash implementation also cites the [KOReader `generateDocChecksum` algorithm](https://github.com/koreader/koreader/blob/master/frontend/util.lua#L1046-L1072). Do not replace this API-key and hash contract with the normal Coppice auth middleware: the KOReader client sends a different password/hash representation, which is why the path-key middleware is retained.

## Static app and mobile invariants

Home (`/app`) and Editor (`/editor`) are independently configured static mounts using `STUMP_HOME_APP_DIR` and `INGEST_EDITOR_DIR`; their availability does not change the API contracts.

- `/api/graphql`, `/api/graphql/ws`, `/api/v2`, OPDS 1.2/2.0, KOReader, Kobo, sessions, auth middleware, CORS, compression, and media/EPUB routes remain mounted.
- `/api/v2/health` readiness checks the database, not the availability of optional static apps.
- Media access remains user-scoped, range-capable, and permission-checked. The server-side EPUB manifest, positions, search, and resource routes remain available.

Third-party native and mobile clients do not need the Home or Editor apps to
use the server. They use the same GraphQL, media, and EPUB route contracts. The
former Expo app was removed and remains only in Git history.

## Three independent modularity layers

These layers must not be conflated:

| Layer | What it controls | Current state | Remaining boundary |
| --- | --- | --- | --- |
| **Runtime switch** | Resource sizing and work selection in an already-built binary. | `STUMP_ENABLE_WEBUI` controls GraphQL web-facing surfaces; `STUMP_ENABLE_BACKGROUND_JOBS` controls job infrastructure. Runtime thread, pool, and statement-cache keys right-size retained services. Existing Kobo, KOReader, OIDC, upload, and OPDS progression switches remain. | Metadata providers and PDFium are already initialized on first use. A provider/processor runtime switch would add no idle saving unless some caller currently initializes it. |
| **Cargo feature** | Compile-time route/code selection. | `full`, `headless`, named `minimal`, and leaf no-default compositions select route and processor code additively. Shared request-origin and pagination types live in `stump_api_types`; shared authentication context and authorization errors live in `stump_auth`. GraphQL derives are opt-in, so bare no-default, leaf profiles, and `minimal` exclude `async-graphql` unless `graphql` or `webui` is selected. |
| **Container target** | Packaged assets plus runtime defaults. | Docker `full` includes Home and Editor; Docker `headless` omits both and supplies conservative thread/pool/cache defaults. Both retain PostgreSQL support, PDFium, and the same database/auth model. |

A runtime switch can avoid doing work but cannot remove a linked dependency. A Cargo feature can remove code/dependencies but cannot choose which assets a release image copies. A Docker target chooses packaged inputs but does not create a different server architecture.

## Package seams

The following ownership boundaries keep Coppice as one process rather than splitting it into services:

- **Neutral API contracts live in `stump_api_types` (`crates/api-types`).** It owns request-origin URL construction and transport-independent offset pagination without depending on Axum or GraphQL.
- **Authentication context lives in `stump_auth` (`crates/auth`).** It owns the authenticated user/session context and authorization errors. GraphQL maps those neutral errors at its adapter boundary.
- **GraphQL schema concerns stay in `graphql` (`crates/graphql`).** GraphQL input wrappers, derives, resolver errors, and schema construction remain local and are enabled explicitly by the server's `graphql` feature.

- **Models and services stay in `crates/models`.** Entities, domain types, and persistence-facing services remain the shared source of truth.
- **File and image processing lives in `stump_media` (`crates/media`).** Format processors (`EpubProcessor`, `ZipProcessor`, `PdfProcessor` behind `pdf`, `RarProcessor` behind `rar`), `ContentType`, `FileError`, hashing (incl. the KOReader hash), Readium manifest generation, EPUB search, image resize/thumbnail primitives, and `MediaConfig`. It depends on `models` for shared option types but not on `stump_core`, jobs, events, or the database. Processors take `&MediaConfig`, a snapshot `StumpConfig` computes once in `finalize_media_config` (called by `init_config` and `Ctx::new`) and exposes as `config.media`, so per-request calls neither clone `StumpConfig` nor rebuild paths.
- **Library filesystem watching lives in `stump_watcher` (`crates/watcher`).** It owns `notify` setup, the lazily created OS watcher (first `add_watcher`), five-second change debouncing, path accumulation, and the listener lifecycle (`init`, `add_watcher`, `remove_watcher`, `stop`). Its only inputs are two traits the owner implements: `WatchedLibraries::enabled_libraries() -> Vec<LibraryRoot { id, path }>` and `ScanSubmitter::submit(ScanRequest { library_id, path })`. Core implements both in `core/src/filesystem/scanner/watcher_adapters.rs` (SeaORM query over ready libraries with `library_config.watch`, and a `StumpJob::LibraryScan` enqueue on the job runtime). `notify` is linked only through the `watcher` Cargo feature (`stump_core/watcher`, forwarded by the server's `watcher` feature; on by default and in `headless`, off in `minimal`).
- **Background job execution lives in `stump_jobs` (`crates/jobs`).** It owns the `JobLifecycle` contract (`init` → `execute_task` loop → `finalize`, driven by `run_job`), the per-job `JobContext<X>` (`conn`, `config`, `report_progress`, `report_output`, `emit_event`, follow-up `enqueue`, `cancel_token`, `complete`/`fail`/`cancel` persistence), `JobRuntime<X>` (queue, single executor, typed queue counters that publish `JobQueueStatus` on every transition, cancellation registry, `cancel_job`, `is_idle`, graceful `stop` with a 30 s grace period), and the cron `JobScheduler` (`init`/`reload` take a runtime factory that is only called once a valid enabled row exists). It never names a concrete job: the host implements `JobExecutionContext` (`type Job/Config/Output/Event`, `conn`, `config`, `emit`, `persist_started`, `persist_finished`, `run`) and `ScheduledJobDispatcher`. Core implements both on `JobServices` (`core/src/job/services.rs`: job/log rows, `JobEvent` → `CoreEvent`, the `StumpJob` dispatch table, scheduled scan and metadata-retry policy); `StumpJob` (`impl JobPayload`, incl. the `SCAN`/`ANALYZE`/`METADATA`/`THUMBNAIL` queue kinds) and `CoreJobOutput` stay in core. `JobServices` holds only the connection, config, and event sender, so the runtime never owns the `Ctx` that owns it. With the `apalis` Cargo feature (`stump_jobs/apalis`, forwarded by `stump_core/apalis` and the server's `apalis`; on by default and in `headless`, off in `minimal`) the executor is one Apalis worker over `MemoryStorage`, run directly so `Worker::stop` ends an idle worker immediately; without it `JobRuntime::inline` drains an unbounded channel one job at a time on the Tokio blocking pool with the same hooks.
- **Orchestration stays in `stump_core` (`core`).** Core owns watcher adapters, concrete scan/thumbnail/analysis/metadata jobs and their `JobServices` host, metadata coordination, and shared application context; it delegates filesystem traversal to `stump_scanner` and event watching to `stump_watcher`. File-level processing is delegated to `stump_media` and queue/executor mechanics to `stump_jobs`.
- **Axum adapters stay in `stump_server` (`apps/server`).** Routes, middleware, protocol adapters, HTTP/WebSocket extraction, and response mapping belong here. The server remains the composition root for one process.
- **Home and Editor are separate app surfaces.** Their static files are built by the SvelteKit workspaces and served from configured directories; this boundary does not fork the API server.
- **Metadata starts with provider features in `metadata_integrations`.** Add provider-level Cargo features and preserve the default dependency graph before considering a gratuitous crate split. Provider DTOs and retry/cache behavior should remain behind the existing integration boundary.
- **Komga contracts live in `stump_komga` (`crates/komga`).** It owns Komga DTOs, pagination, and error mapping; the `komga` Cargo feature in `apps/server` compiles the adapter route tree under `apps/server/src/routers/komga/`. The server still owns route mounting while existing models/services own persistence. See [Komga compatibility](/docs/developer/komga-compat) for the current spec.

Shipped and Planned seams must preserve one Rust process, one configured database, current authentication, and the existing GraphQL/REST/protocol surfaces.

## Event bus and sinks

There is one bus. `CoreEvent` (`core/src/event.rs`) is a broadcast channel on
`Ctx`; every producer calls `Ctx::emit_event` (or `JobContext::emit_event`,
which forwards through `JobServices`), and every sink *subscribes and
translates*. A sink never owns state and never becomes a second bus.

Two crates produce events without being allowed to name `CoreEvent`
(`stump_ingest` and `stump_provider` are dependencies of `stump_core`, not the
other way round). They emit their own vocabulary through a sink trait the host
installs, and `stump_core` is the only place that knows both:

| Producer crate | Crate vocabulary | Sink trait | Mapped in |
| --- | --- | --- | --- |
| `stump_ingest` | `IngestEvent` (`crates/ingest/src/event.rs`) | `IngestEventSink`, installed by `IngestServices::with_event_sink` on both the store and the coordinator | `core/src/ingest_host.rs` (`CoreEventSink`) |
| `stump_provider` | `ProviderEvent` (`crates/provider/src/event.rs`) | `ProviderEventSink`, installed by `ProviderHost::set_event_sink` | `core/src/providers.rs` (`CoreProviderEventSink`) |

### Events to sinks

`readEvents` is the unfiltered lane and carries every row below, so it is
omitted from the table. The other sinks are: `deviceSeen`, `ingestEvents`, and
`providerEvents` (`crates/graphql/src/subscription/`), Komga SSE
(`apps/server/src/routers/komga_backend.rs` translates into the Komga wire
vocabulary served by `crates/komga/src/routes/sse.rs`), and notification
routing (`core/src/notification.rs`, `route_event`, which fans out to the
configured channels).

| `JobStarted`, `JobUpdate`, `JobOutput` | `stump_jobs` worker lifecycle | notifications (`JobOutput` with a `LibraryScan` output only) |

| `DiscoveredMissingLibrary` | library scan | — |
| `CreatedMedia`, `MediaDeleted`, `SeriesDeleted` | scanner, media mutations | Komga SSE |

Two live surfaces are deliberately *not* on this bus. `ingestProgress`
(`crates/graphql/src/subscription/ingest.rs`) replays a durable, cursored
`ingest_progress_events` table so a reconnecting editor can resume, which a
broadcast channel cannot do; and Komga read-progress events come from
`Ctx::reading_state_events`, a separate channel, because a reading head moves
far more often than anything here.

### Rules for a new event or sink

- Emit at the state transition, once, after the write is durable. A
  transaction announces from the re-read row after commit.
- Announce transitions, not observations. `ProviderSourceHealthChanged` fires
  only when a `source_health` row already existed and its status differs, so
  one cold run over a full catalog cannot broadcast a thousand events.
- A payload carries what a sink needs to act without re-querying — the
  identity triple, and a display name where a client would otherwise have to
  resolve an opaque id.
- New sinks subscribe and translate. Adding a variant must not require
  touching an existing sink: every `CoreEvent` match in the tree ends in a
  catch-all.

### The liseur-sync lane

Coppice's mounted liseur-sync adapter answers `GET /v1/events` with an
explicit bearer-protected `404` (`stump_liseur_sync::routes`,
`deferred_events`) rather than a stream. The current liseur-sync server pin
[`906889ff`](https://github.com/chmouel/liseur-sync/commit/906889ffe11fc7260b071c1f142aeee1fa8a1419)
defines authenticated SSE at `GET /v1/events`, and Liseur v0.19.0
[`62ecb5a5`](https://github.com/chmouel/liseur/commit/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6)
opens it once per foreground session (`LiseurSyncLive.kt`) and stops for that
session on 404 but retries with capped backoff on any other answer, including
the SPA fallback redirect. A Coppice SSE route would implement an existing
protocol contract, not invent one; until then the 404 keeps the client on
request/response sync. The refreshed pins are source-only; the older client
device run remains separately recorded. See [Liseur provider analysis](/docs/developer/liseur-providers)
and [liseur-sync integration](/docs/developer/liseur-sync-integration).

## Profiles

### Full/default

`default = ["full"]`, and `full = ["headless", "webui"]`. The Docker `full` target packages Home and Editor assets. Unset runtime and database tuning variables preserve upstream Tokio and SQLx defaults. This is the compatibility baseline.

### Headless

`cargo build --package stump_server --no-default-features --features headless` compiles GraphQL, OPDS, Readium, Kobo, KOReader, the library filesystem watcher, authenticated REST, jobs, SQLite, and PostgreSQL without the web-specific GraphQL fields or playground. The Docker `headless` target uses this exact aggregate. `/api/v2/health` reports the database health; it does not depend on static app assets. Because `headless` omits `webui`, it also omits `graphql/web`: the schema it serves has no book-club, smart-list, custom-emoji, viewer-preference/navigation-arrangement, or `upload*` resolvers.

### Minimal

`cargo build --package stump_server --no-default-features --features minimal` retains REST authentication, database-backed library/media endpoints, sessions, health, and raw file serving while omitting the optional GraphQL, OPDS, Readium, Kobo, and KOReader route modules and the `watcher` and `apalis` features. The profile links neither `async-graphql`, `notify`, nor `apalis` (`cargo tree -p stump_server --no-default-features --features minimal -e normal | grep -c apalis` is `0`, against `2` — `apalis` and `apalis-core` — for `headless`); library `watch` settings are stored but never acted on, `/api/v2/health` reports `watcher` as `unavailable`, and queued jobs run on the inline executor. It is still a route-composition profile rather than a processor-free binary because shared core metadata, jobs, image, PDF, and archive processing remain linked.

### Runtime controls

Any compiled profile can tune resources without changing the default:

- `STUMP_RUNTIME_WORKER_THREADS` and `STUMP_RUNTIME_MAX_BLOCKING_THREADS` size Tokio before asynchronous startup.
- `STUMP_DB_MAX_CONNECTIONS`, `STUMP_DB_MIN_CONNECTIONS`, and `STUMP_SQLITE_STATEMENT_CACHE_CAPACITY` bound database runtime state.
- `STUMP_ENABLE_BACKGROUND_JOBS=false` skips islanded-job cleanup, scheduler initialization, the watcher listener, and the job executor. Job submission and watcher operations fail explicitly with `FeatureDisabled("background jobs")`.
- `/api/v2/health` reports `jobs` as `disabled`, `enabled` (configured but not yet initialized), `idle`, or `running`, and reports `watcher` as `unavailable` (compiled without the `watcher` feature), `disabled`, `inactive`, or `active`. Health reads lifecycle state without constructing the queue, executor, scheduler, or watcher.

The headless container defaults to two Tokio workers, eight blocking threads, a two-connection pool cap, and a 32-entry SQLite statement cache. Operators can override every value. Background jobs remain enabled so scanning and metadata work are available.

### Inbound rate limiting

`apps/server/src/middleware/rate_limit.rs` is one outer Axum layer, mounted in `run_http_server` outside the session layer so a rejected request never loads a session. It classifies every request by method and path (no database lookup) and keys the check on the caller's identity: the SHA-256 fingerprint of the presented credential (`Authorization`, `X-API-Key`, the `{api_key}` segment of `/opds/{api_key}/v1.2`, `/kobo/{api_key}`, `/koreader/{api_key}`, the `stump_session` cookie, or the Komga remember-me cookie), else the client IP from `extract_client_ip`, which honours `X-Real-IP`/`X-Forwarded-For` only when `trust_proxy_headers` is set.

| Class | Requests | Key | Default |
| --- | --- | --- | --- |
| `auth` | every non-`GET` `/api/v2/auth/*`, `GET /api/v2/auth/oidc/callback`, `POST /api/v2/devices/pair/start`, liseur `POST /v1/login` and `/v1/tokens`, Kobo `POST /kobo/{key}/v1/auth/device`, and the *first hit* of any Basic, `X-API-Key`, or path-key credential | client IP | 10/min, bucket 20 (`governor` GCRA) |
| `write` | every `POST`/`PUT`/`PATCH`/`DELETE` except query-over-POST endpoints (`POST /api/v2/version`, Komga `*/list`, liseur `*/resolve`), plus `GET /kobo/{key}/v1/library/sync` and GraphQL mutations (the JSON body is parsed with `async_graphql::parser` when it is `application/json` and at most 1 MiB; multipart or larger bodies count as mutations) | credential, else IP | 120/min, bucket 60 |
| `stream` | everything else, including pages, files, thumbnails, SSE, and WebSocket upgrades | credential, else IP | unlimited rate, 32 in flight; a request waits up to 10 s for a slot before `429` |

A credential counts as an authentication attempt until the server answers it with anything other than `401`; it counts again after a `401` or after sixty seconds without traffic, which mirrors the Basic-auth cache TTL in `middleware/auth.rs` after which bcrypt runs again. Every distinct wrong credential therefore costs one `auth` token per attempt regardless of path, while a Komelia, OPDS, Kobo, or KOReader burst with one valid credential spends one. The `stream` permit is held by the response body (`PermitBody` preserves the inner `size_hint`, so `Content-Length` is unchanged) and released when the body is fully sent or dropped.

Rejections are `429 Too Many Requests` with `Retry-After` (whole seconds, at least 1) and the standard `APIError` body `{"status":429,"message":"Too many requests"}`, emitted inside the CORS and compression layers so browsers see the usual headers.

Environment overrides, read by `apps/server/src/config/rate_limit.rs` at startup and never stored in `Stump.toml`: `STUMP_RATELIMIT_ENABLED` (default `true`), `STUMP_RATELIMIT_AUTH_PER_MIN` (default `10`; the bucket is `max(20, value)`), `STUMP_RATELIMIT_WRITE_PER_MIN` (default `120`; the bucket is `max(60, value / 2)`), and `STUMP_RATELIMIT_STREAM_CONCURRENCY` (default `32`). Invalid values fail startup with `ServerStartError`.

`/api/v2/health` exposes the limiter under `rate_limit`, either `{"status":"disabled"}` or `{"status":"enabled","auth":{"allowed","limited","per_minute","burst"},"write":{"allowed","limited","per_minute","burst"},"stream":{"allowed","limited","concurrency"}}`, where `allowed`/`limited` are process-lifetime counters per class. The observed replays (`make replay` 36 requests, `make replay-liseur-sync` 25 requests) run within the defaults: the Komga replay spends 3 `auth`, 1 `write`, and 32 `stream` allowances and is never limited.

### Configuration structure

`StumpConfig` (`core/src/config/stump_config.rs`) is composed of `#[serde(flatten)]` groups in `core/src/config/`: `server` (listener, logging, CORS, proxy trust), `database` (path, pool, statement cache), `jobs` (`enable_background_jobs`, `parallelism_multiplier`, `cpu_concurrency_limit()`), `protocols` (KOReader/Kobo/Komga/Kavita/OPDS switches, KEPUB settings, uploads, GraphQL web UI/playground controls), `ingest`, `providers` (provider host switch and cache bound), `auth` (hash cost, session/token TTLs), and `pdf` (PDFium path and render settings). Home and Editor asset directories are configured independently of this struct. Only `config_dir`, the `[oidc]` table, and the derived `media` snapshot stay at the top level. The groups are structural: `Stump.toml` keys and environment variables are unchanged and files written by earlier builds load as-is (covered by `test_pre_split_toml_loads_into_grouped_config`). Code reads settings through the group path (`config.server.port`, `config.protocols.enable_komga`); `StumpConfig::finalize()` computes `media` once after the file and environment overlays. The `stump_config_gen` derive supports this with `#[nested]`: the group's generated `Partial<Group>` is flattened into the parent partial, so env/TOML overlay and validators work per group without hand-written parsing. The full key-to-group table is in [Server Config](/docs/guides/configuration/server-config#key-groups).

## Uploader-prepared ingest boundary

The preferred long-term processing boundary is **uploader-prepared ingest**, not a mandatory remote-worker tier. The device that already owns the source file may hash and inspect it before upload and may attach metadata, page/archive indexes, covers, or converted derivatives. An optional node performs the same producer role for clients that lack a capability or should not spend battery, memory, or time on a heavy transform. Nodes improve throughput; they are not required for storage, reading, or database access.

The server remains authoritative. It authenticates the operation, enforces the target library and quota, streams the untouched original into server-owned staging, recomputes the full-file digest, checks the format and bounded structural invariants, validates every supplied artifact against its declared digest/type/source digest/processor version, and atomically commits the canonical file and database state. Client or node metadata is a candidate, never trusted state. Invalid optional artifacts are rejected or discarded without losing the verified original.

A future neutral ingest contract should model:

- an idempotency key, source filename, byte length, full SHA-256 digest, and detected media type;
- producer identity/version and declared capabilities;
- optional typed artifacts with their own byte lengths, digests, media types, and the source digest they derive from;
- an explicit lifecycle such as `staging -> source_verified -> committed`, with artifact acceptance reported independently;
- resumable, bounded byte transfer without exposing filesystem paths or database credentials.

All ingress adapters must converge on one service rather than implement separate import semantics:

```text
Home and Editor uploads ──> verify/stage IngestBook ─> atomic file + DB commit
```

The existing implementation does not yet provide this contract. Editor uploads are one-shot GraphQL multipart requests that copy files and enqueue a scan. The Rust processors are filesystem/native-library oriented and are not a suitable browser WASM boundary. The first implementation should therefore extract `MediaBuilder`'s projection from an already processed file and the scanner's persistence transaction into a neutral ingest service, harden staging and limits, then add the digest-bound HTTP contract. Current GraphQL upload/scan behavior remains the all-in-one fallback until that path is proven.

### Metadata and book-lab pipeline (**Planned**)

The following metadata and repair pipeline is **Planned**. It extends uploader-prepared ingest without making metadata lookup or archive repair a requirement of the always-on server. The uploader performs work when it has the capability; an optional worker can perform it later. The server receives normalized, digest-bound results and remains the authority for acceptance.

The design has two engines:

- a **books engine** for ebooks and other book-shaped inputs; and
- a **comics engine** for comics, manga, and issue-shaped inputs.

Both engines share one provider trait and candidate core. Providers return typed candidates with confidence and provenance (provider, lookup inputs, response/version information, and timestamp), rather than mutating a library record. The shared core ranks and reconciles candidates, keeps competing evidence inspectable, and leaves low-confidence or conflicting fields for review. Engine-specific parsing and normalization may differ, but candidate, confidence, and provenance types stay shared.

The provider policy is keyless-first: embedded metadata and ISBN parsing are the first pass, followed by public or anonymous providers such as [Open Library](https://openlibrary.org/developers/api), [GCD](https://www.comics.org/api/), [MangaDex](https://api.mangadex.org/docs/), and [AniList](https://anilist.gitbook.io/anilist-apiv2-docs/). Google Books, Metron, and ComicVine remain opt-in keyed providers.

Filename parsing is a local, deterministic first pass. It extracts hints such as title, series, volume, issue/chapter, year, language, and edition from common naming patterns, while treating those hints as low-confidence candidates rather than stable identity. Network lookup refines or rejects filename evidence and never turns an ambiguous filename into an authoritative match alone.

The EPUB repair lab is a separate deterministic pipeline:

1. Preserve immutable uploaded bytes and their digest as the original; never repair in place.
2. Analyze the original without mutation and emit a bounded structural report covering the ZIP container, `mimetype`, package metadata, navigation, spine, resources, and parseable content.
3. Emit an explicit repair plan and apply only bounded, reproducible changes to a new canonical EPUB.
4. Validate the canonical package, including ZIP rules, `mimetype`, OPF/container, navigation, spine/resource closure, and deterministic rebuild.

The canonical EPUB is the source for a regenerable KEPUB derivative. KEPUB generation should use [kepubify](https://github.com/pgaskin/kepubify) from that canonical input rather than treating a device-produced KEPUB as a second source of truth. Original, canonical EPUB, and KEPUB outputs are independently content-addressed; when repair makes no change, original and canonical roles may share a digest without storing duplicate bytes.

The uploader/worker handoff sends normalized metadata candidates, the accepted lab report and plan, and derivative descriptors or bytes bound to the verified original digest. The server recomputes every received digest and accepts results only when digest, media type, processor version, and dependency chain match. Unbound, malformed, or failed artifacts remain rejected candidates and never replace the original or become trusted metadata.

## Metadata and PDF caveats

### Metadata

`metadata_integrations` still compiles its provider clients and retry/rate-limit dependencies as one package, but clients are created only when a provider is used. The HTTP cache now selects only the Moka manager and required standard URL parser; the unintended default CACache manager is no longer in the graph. Provider Cargo features remain a future compile-size optimization. They are not an idle-RAM fix by themselves because no provider client/cache exists before first use.

### PDF

[`crates/media/src/media/format/pdf.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/media/src/media/format/pdf.rs) uses a process-wide `OnceLock<Result<Mutex<Pdfium>, FileError>>`. PDFium is initialized lazily on the first operation that needs it, and a failed initialization is cached until process restart. PDFium is used for more than the browser reader: scan-time processing/page counts and optional PDF metadata, page analysis, server-side page rendering/thumbnails, and OPDS/media page routes all depend on it.

Consequently, omitting the optional static apps does not make PDFium optional for a server that still promises PDF scanning, page rendering, thumbnails, or OPDS/media page streaming. The Docker runtime currently packages PDFium for both `full` and `headless`; source builds need `PDFIUM_PATH` or a system library. The upstream implementation is [PDFium](https://pdfium.googlesource.com/pdfium/) and the container binary distribution is documented by [pdfium-binaries](https://github.com/bblanchon/pdfium-binaries).

A future split between a lightweight **Planned** `pdf-core` path (identify/index/download) and a **Planned** `pdf-render` path (PDFium, page rendering, thumbnails, and page streaming) must prove that scans, media readers, OPDS pages, and mobile downloads still work before changing the default profile. The current dependency diet retains Coppice's existing GIF, JPEG, PNG, and WebP decoding paths while omitting unrelated default `image` codecs. AVIF, JPEG XL, and HEIF remain **Planned** only if a measured use case justifies their cost.

## Komga and Komelia status

Coppice's Komga compatibility is implemented behind the `komga` Cargo feature in `apps/server` (included in the `headless` aggregate) and the `STUMP_ENABLE_KOMGA` runtime gate. The `stump_komga` contract crate (`crates/komga`) defines the compatibility DTOs and mapping contracts, while the route tree lives under `apps/server/src/routers/komga/`. The current endpoint and behavior specification is [Komga compatibility](/docs/developer/komga-compat).

The external Grimmory project is a useful compatibility warning, not an implementation dependency:

- [Grimmory issue #164](https://github.com/grimmory-tools/grimmory/issues/164), **“Support Komelia app in the Komga API”**, documents that Komelia uses a larger Komga API superset. Its open checklist includes remember-me cookies, matching series/read-progress/book/media/library/pageable DTOs, several list/readlist endpoints, and `/v1/books/{book_id}/manifest`.
- [Grimmory PR #2333](https://github.com/grimmory-tools/grimmory/pull/2333) is open and addresses Komga remember-me authentication cookies, `JSESSIONID`, and the `komga-remember-me` cookie while keeping Basic auth behavior.
- [Grimmory PR #2377](https://github.com/grimmory-tools/grimmory/pull/2377) is open and addresses missing `scanDirectoryExclusions` and nullable `oneshotsDirectory` fields in `KomgaLibraryDto`; it does not add persistence for those fields.

A pinned Android capture against Komelia 0.19.0 and Komga 1.26.3 now supplies route-level evidence beyond Grimmory's checklist. It observed modern POST book/series lists; libraries and referential filters; book, series, page, thumbnail, and file reads; successful next-book navigation; `PATCH`/`DELETE` read-progress updates; nonempty read-list and collection traversal; collection updates; library scans; filesystem browsing; the SSE event stream; and Readium manifest, positions, resource, and progression routes. Separate contract probes observed unauthenticated and invalid-credential `401` responses. Komga's filesystem endpoint returned `200` to the server owner and `403` to a restricted user, so the visible directory picker is an administrative capability rather than evidence of anonymous access. Only normalized route, status, content-type, cache-marker, and JSON-shape evidence is retained; each raw phone flow is deleted after normalization.

Reverse-proxy fidelity is part of the Readium contract. Mitmproxy reverse mode must preserve the client `Host` header (for example, `--set keep_host_header=true`). Without it, Komga emits absolute manifest resource links for the loopback upstream, while Komelia rejects links outside its configured server origin before requesting the first chapter. An EPUB failure captured under the rewritten-host topology is invalid capture evidence, not a Komga or Komelia incompatibility.

With Host preservation corrected, two EPUBs rendered and hundreds of resource requests returned `200` or `304`. Progression writes returned `204`; for the book with `200` readbacks, the returned href, position, and progression matched the latest prior write in all three comparisons. Nevertheless, Komelia did not resume either book. The pinned 0.19.0 source computes the saved chapter index in `TtsuReaderState.getBookmark` but returns the first `readingOrder` href as `chapterReference`. Its table of contents also displays start-character offsets rather than page numbers and can render `0 / 0 (NaN%)` for a zero-character section. These are Komelia client-profile caveats, not missing Komga responses.

The Komga contract crate and `/komga` adapter are implemented as described in the [Komga compatibility specification](/docs/developer/komga-compat). Grimmory and the pinned Komelia capture remain interoperability evidence: they inform the route/DTO matrix and compatibility boundaries without turning unlisted methods or unsupported behavior into promises.

## Measurement gates

### Measured idle baseline and result

The measurements below are **Source-only** historical medians from five fresh launches per profile on the same 16-logical-CPU Linux host. Each launch used an empty SQLite database and state directory on tmpfs, waited for `/api/v2/health`, and then sampled `/proc/<pid>/smaps_rollup`, task count, and file descriptors 20 times. Runs were randomized and interleaved. They characterize this machine and idle workload; they are not a production memory guarantee.

The pristine binary came from a separate worktree at `origin/nightly` commit `37fdb7d7340894a777c40d685d5262becceae007` (2026-08-31). Its `/api/v2/version` response embedded revision `37fdb7d7`; the measured ELF SHA-256 was `ce91170e6e1658ed5d6e1ed6f64827db625f42a9bf69fdedb86d967bf379569d`.

| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Pristine `origin/nightly` full/default | Upstream defaults | 40,776 | 36,929 | 11,028 | 21 | 19 |

The supported headless container defaults correspond to the second row: all compiled backend protocols and background jobs remain available. Against pristine nightly, median idle RSS fell by 10,852 KiB (26.6%), PSS by 10,844 KiB (29.4%), and thread count from 21 to 5. Disabling background jobs and limiting SQLite to one connection is an opt-in lower bound, not the default capability profile.

A later spot check of the same headless release binary with the Komga compatibility adapter compiled in measured the runtime toggle's idle cost: three interleaved launches each with `STUMP_ENABLE_KOMGA=false` and `=true` on tmpfs (health-wait plus a four-second settle, single sample) gave medians of 30,416 KiB RSS / 25,173 KiB PSS with the adapter disabled and 30,664 KiB RSS / 25,434 KiB PSS enabled, five threads in both cases. The roughly 0.2 MiB difference is within run-to-run noise; the adapter adds routes, not resident state, and its only per-connection allocation is the SSE subscription.

A separate controlled debug-server probe measured a cold-ready process at 115,588 KiB RSS, with 27,384 KiB anonymous and 83,555 KiB file-backed pages across 23 threads. The first Components GraphQL request measured 120,116 KiB RSS (28,172 KiB anonymous, 91,944 KiB file-backed), and a full protocol replay reached 141,084 KiB RSS (40,312 KiB anonymous, 100,772 KiB file-backed, 30 threads). A four-worker Tokio cap with a 16-thread blocking limit changed the cold sample to 116,696 KiB RSS / 26,156 KiB anonymous / 10 threads and replay to 140,820 KiB RSS / 36,960 KiB anonymous / 17 threads: only a 264 KiB replay RSS reduction, so the default executor settings remain unchanged. The dominant retained share was file-backed code/mappings rather than an identified detachable component cache; process-wide PSS/private-dirty fields are exposed as evidence, not component attribution.

A same-checkout release spot check (`headless,liseur-sync`, fixture defaults, single launch) measured 41,752 KiB RSS / 39,104 KiB PSS at cold readiness: 12,056 KiB anonymous PSS, 27,016 KiB file-backed PSS, and 20 threads. Loading the authenticated Components query and GraphQL schema on the populated fixture measured 62,336 KiB RSS / 45,956 KiB PSS: 20,700 KiB anonymous PSS, 25,256 KiB file-backed PSS, and 20 threads. The release ELF was 86,833,752 bytes versus the debug ELF's 609,457,384 bytes. This single-run diagnostic confirms that the 100–150 MiB debug RSS is not a production baseline; it does not replace the interleaved release medians above.

Do not turn an RSS observation into a promised memory number. Before and after any modularity change, compare the current full/default build and the candidate headless build using the same commit, database, library, configuration, and workload. Record:

- clean startup time and stable idle behavior;
- process RSS **and**, where available, live-heap/allocation data, SQLite page-cache usage, mapped files/native libraries, and thread count;
- scan peak and post-scan retained state, separating allocator-retained RSS from live objects;
- image size, layer contents, frontend/PDFium presence, and build inputs;
- route/auth smoke results for GraphQL HTTP+WS, REST/media/EPUB/range, OPDS 1.2/PSE, OPDS 2.0 auth/progression, KOReader, Kobo, and native/mobile SDK flows.

The optimization-specific gates are equally strict:

- Scanner mtime skip/results are identical, and the immutable mtime map is shared rather than repeatedly deep-copied.
- `LibraryWatcher` command/public method behavior is unchanged; no `notify` backend exists before the first path is added, and the backend appears when that first path is added. Once created, the backend is retained until watcher shutdown, including after the last path is removed.
- Full/default output and startup semantics remain unchanged.
- The full image contains Home and Editor assets and PDFium; the headless image contains no app assets (its target does not copy the frontend stage), and health/readiness depends only on database status.

## Incremental upstream candidate PRs

These are independent, issue-first candidate PRs, not one fork merge. The
integration branch is an evidence/workbench branch only. Before publishing any
candidate, claim an issue, create a fresh branch from `origin/nightly`, target
`nightly`, keep the change narrow, run focused tests/docs plus Prettier and
rustfmt, disclose LLM use in the PR body, never use an LLM-signed commit, and
never open a PR from the fork integration branch. The labels below describe
local source status; the 2026-09-20 full gate and server-contract replay passed.

1. **`upstream/fix-case-insensitive-extensions` (issue #1422, local
   implementation):** make supported-extension matching case-insensitive
   without changing the advertised format set.
2. **`upstream/scanner-mtime-arc` (issue-first, local implementation):** share
   scanner directory-mtime snapshots through `Arc`; no scan semantics change.
3. **`upstream/watcher-lazy-lifecycle` (issue-first, local implementation):**
   lazily construct the `notify` backend; optionally omit the logical
   watcher/job lifecycle with an explicit disabled error.
4. **`upstream/server-profile-boundaries` (issue-first, local
   implementation):** add `full`, `headless`, `minimal`, and leaf route
   features while keeping `webui` independent; keep health/readiness and
   optional static app behavior aligned with the active server profile.
5. **`upstream/graphql-lazy-schema` (issue-first, local implementation):**
   build the GraphQL schema/DataLoaders once on first authenticated use and
   expose Tokio/database resource bounds without changing unset defaults.
6. **`upstream/narrow-default-dependencies` (issue-first, local
   implementation):** remove unused dependency defaults and narrow supported
   image-codec compilation without changing advertised formats.
7. **`upstream/neutral-request-auth` (issue-first, local implementation):**
   move shared request-origin/pagination and authentication context into
   dependency-light neutral crates, make GraphQL derives opt-in, and remove
   `async-graphql` from the minimal server graph without changing the generated
   schema.

   capability-aware processor dispatch/error variants; a manifest-only flag
   would be misleading.
9. **Proposal, not a candidate PR yet:** separate PDF core/index operations
   from PDFium rendering only after scan, media, OPDS, and mobile evidence
