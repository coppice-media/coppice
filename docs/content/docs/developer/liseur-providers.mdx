This page is an endpoint-level index of the backends the Liseur Android app talks to. It records what the client requests, what it parses, and what it sends back. It is intentionally a protocol inventory rather than a compatibility promise for every implementation of any one protocol.

## Evidence and reading guide

The Liseur source is pinned to commit [`31f8182d`](https://github.com/chmouel/liseur/commit/31f8182d524e3536cf9020594185e709a033094f). The companion server is pinned to [`f8ce32b7`](https://github.com/chmouel/liseur-sync/commit/f8ce32b79aca0cddde84e9004fedde121fb77365). Stump route links below point at the `headless-modular` baseline commit [`37fdb7d7`](https://github.com/stumpapp/stump/commit/37fdb7d7340894a777c40d685d5262becceae007) and are provisional: the Komga adapter, its SSE mutation events, virtual `url` paths, remember-me, and the provider crates described in the coverage matrix exist in the uncommitted `headless-modular` worktree on top of that commit, so those GitHub line ranges substantiate only the pre-existing routes. Treat local source paths as authoritative until the work is committed and the pin is updated. The Liseur and liseur-sync pins are immutable.

* **[observed]** means the behavior is present in the linked source at one of those commits. The links in the tables point to the exact file and line range.
* **[inference]** is used only for a conclusion drawn from observed boundaries, such as a compatibility gap or an implementation direction.
* “Status” describes Stump's current route surface, not whether a hypothetical adapter could be added. `implemented`, `partial`, `absent`, and `N/A` are deliberately conservative.

The existing [liseur-sync annotation integration](./liseur-sync-integration) explains the annotation protocol design, the implemented user-scoped bridge, and the deferred local projection. This page links to it instead of copying its full schema and conflict discussion. The existing [sync platforms](./sync-platforms) page has the fuller Stump-side KOReader and Kobo descriptions; this page adds the Liseur-side requests and keeps the provider comparison in one place.

## Shared Liseur boundary

[observed] Liseur has five stored server kinds: Calibre-Web (`calibre`), Komga (`komga`), liseur-sync (`liseur-sync`), Grimmory (`grimmory`), and user-configured Custom (`custom`). The app routes catalogs and files for all five; position sync is routed only for Calibre-Web, Komga, and liseur-sync. KOReader/KOSync is a separate peer, used alongside Grimmory or Custom rather than as their catalog protocol ([`ServerKind.kt`](https://github.com/chmouel/liseur/blob/31f8182d524e3536cf9020594185e709a033094f/app/src/main/kotlin/com/chmouel/liseur/data/remote/ServerKind.kt#L40-L215), [`AppContainer.kt`](https://github.com/chmouel/liseur/blob/31f8182d524e3536cf9020594185e709a033094f/app/src/main/kotlin/com/chmouel/liseur/AppContainer.kt#L289-L368)).

| Credential | Wire behavior | Used by |
| --- | --- | --- |
| `Anonymous` | No `Authorization` header. | An open Custom OPDS catalog. |
| `Basic(username, password)` | `Authorization: Basic <base64(username:password)>`. | Calibre-Web OPDS and browser session; Grimmory's Komga shim; password-protected Custom OPDS. |
| `ApiKey(key)` | `X-API-Key: <key>`. | Komga. |
| `Bearer(token)` | `Authorization: Bearer <token>`. | Native liseur-sync after login/token minting. |
| KOReader pairing | `x-auth-user` and lowercase hexadecimal MD5-derived `x-auth-key`; not `RemoteCredentials`. | A KOReader/KOSync peer. |

The first four credential forms are implemented by [`RemoteCredentials`](https://github.com/chmouel/liseur/blob/31f8182d524e3536cf9020594185e709a033094f/app/src/main/kotlin/com/chmouel/liseur/data/remote/RemoteCredentials.kt#L1-L66). The KOReader form is implemented separately by [`KosyncCredentials`](https://github.com/chmouel/liseur/blob/31f8182d524e3536cf9020594185e709a033094f/app/src/main/kotlin/com/chmouel/liseur/data/kosync/KosyncClient.kt#L16-L60).

## Grimmory Komga shim

[observed] Grimmory is a distinct Liseur provider, not Komga with a different label. Liseur uses Grimmory's Komga-shaped shim under `/komga`, authenticates with an OPDS user's Basic credentials, lists through `GET /api/v1/books`, and has no native progression lane. Liseur pairs KOReader/KOSync separately when position sync is wanted.

## Compatibility interpretation (inference)

* [inference] Komga is the only listed profile that is directly implemented by Stump with the Liseur-used identity, catalog, file, and exact Readium progression routes. “Implemented” here still means the observed profile, not every Komga endpoint.
* [inference] Calibre-Web and Kobo overlap Stump's existing OPDS/Kobo route families, but path/auth and the Kobo per-book state write are not exact; they remain partial until those contracts are deliberately aligned.
* [inference] The current native liseur-sync pass is a sync-only slice:
  user-scoped identity, position ops/changes/snapshots, immutable sessions, and
  revisioned annotation routes are implemented, while catalog, insights,
  administration, and local core annotation projection remain deferred.
* [inference] Native liseur-sync parity requires a user-scoped Work/Edition/Alias identity layer plus op, session, annotation, and scope-aware REST routes. Stretching OPDS or KOReader percentage sync cannot provide the native locator/annotation semantics.
* [inference] Grimmory requires either its `/komga` shim prefix and `GET /api/v1/books` profile or an explicit compatibility alias; Stump's ordinary Komga profile is not enough.
