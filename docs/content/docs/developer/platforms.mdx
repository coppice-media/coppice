One row per platform. Status cells use exactly four levels, matching
[client verification](/docs/developer/client-verification): **device-verified**
(a person ran the real app/device against the fixture server, date given),
**harness** (Hurl replay, live container, or server-side probe — proves the
server contract, not the app), **source-derived** (implemented or described from
pinned source, never run), **not verified**. Facts about hardware and third-party
tools cite the public page they come from; nothing here is inferred from memory.

Every row below is a device in the registry, and what a device sees is not
fixed by its protocol: `devices.library_scope` restricts one device to a subset
of its user's libraries, enforced in the shared query funnel rather than in any
adapter, so the same restriction applies to Kobo sync, Komga, Kavita, OPDS,
KOReader, liseur-sync, and GraphQL alike, and two devices of the same user can
see different libraries ([devices — library scope](/docs/developer/devices#library-scope)).

## Kobo eReaders

Two facts hold for every model below. Stock Nickel renders JPEG, GIF, PNG, BMP,
and TIFF only — no WebP in CBZ or KEPUB
([Kobo file formats](https://help.kobo.com/hc/en-us/articles/360017763713-File-formats-your-Kobo-eReader-and-Kobo-Books-app-support));
a WebP page therefore has to be re-encoded before delivery. Stump serves EPUB
through Kobo sync today, KEPUB when `KOBO_KEPUB_CONVERSION=true` (converter
entry-parity with kepubify on 36 books — [Kobo capabilities](/docs/developer/kobo-sync-capabilities)),
and the CBZ → fixed-layout KEPUB transform is planned ([roadmap phase 4](/docs/developer/roadmap)).
No model has been connected to Stump yet.

## Amazon Kindle

A Kindle is the one device family that never talks to Stump. It has no sync
protocol, no credential, and no endpoint, and it is reached in exactly two
ways — both of them one-way, and both implemented by one crate
(`crates/kindle`) so they cannot disagree about what the device can read:

1. **E-mail.** Amazon's *Send to Kindle* service delivers whatever an approved
   sender mails to the device's own address, so the address on the device row
   (`devices.kindle_email`) is the entire transport.
2. **USB.** The Kindle mounts as a disk and anything dropped into its
   `documents/` folder is a book. There is no gateway on that path, so it is
   the stricter of the two: a Kindle plugged into a computer opens AZW3/MOBI,
   PDF and text, and **not** EPUB.

Nothing comes back either way — not progress, not annotations.

| Device family | Reached over | Works today | Gaps | Status | Evidence |
| --- | --- | --- | --- | --- | --- |
| Kindle (Paperwhite, Oasis, Scribe, Colorsoft, basic) — e-mail | `sendToKindle(mediaId, deviceId)`: primary emailer → `<name>@kindle.com`, EPUB converted to AZW3 by the operator's `boko` when present, otherwise mailed as EPUB (Amazon converts it), recorded as a `kindle_deliveries` row plus `{"protocol":"kindle-email","bytes","format"}` on the device | One book per call to one device address; refuses formats Amazon discards (CBZ/CBR); Amazon's 50 MB per-document ceiling and the emailer's own cap enforced before the SMTP connection; failures recorded with their reason and readable back through `kindleDeliveries` | One-way: no progress, no annotations, no browse. The sender address must be on the operator's Amazon *Approved Personal Document E-mail List* — Stump cannot check that, so a rejected send only shows up as a bounce in the operator's mailbox. No KFX (`boko` can write it; AZW3 is the safer sideload) | not verified — no Kindle and no live Amazon delivery; the lane's conversion, EPUB fallback, size refusals, failure recording, and history are covered by `cargo test -p stump_kindle` (13 tests, `lettre` stub transport + a fake `boko`) and `cargo test -p graphql --lib kindle` | [devices — send to Kindle](/docs/developer/devices#send-to-kindle), [calibre tooling](/docs/developer/calibre-tooling), [Send to Kindle by e-mail](https://www.amazon.com/sendtokindle/email) |
| Kindle — USB sideload | `POST /api/v2/media/{id}/kindle-file`: the converted file as a download, `Content-Disposition: attachment; filename="<book>.azw3"`, `X-Stump-Kindle-Converted` header; save it into the mounted device's `documents/` folder | Any accepted format passes through untouched; an EPUB is converted with `boko`; no size limit (no relay involved); needs `DOWNLOAD_FILE` | An EPUB with no `boko` installed is refused with 400 rather than handed over, because the device cannot open it; nothing is recorded (there is no device on this path, so there is no delivery to log) | route-verified — `cargo test -p stump_server --no-default-features --features minimal --test api_tests kindle` (4 tests: pass-through, never-an-EPUB, CBZ refusal, unknown book) | [devices — USB](/docs/developer/devices#usb-post-apiv2mediaidkindle-file) |

## Status legend and open verification list

- **device-verified** — real app or device, dated. **harness** — Hurl replay,
  live container, or server probe. **source-derived** — pinned source read, code
  written, nothing executed against the target. **not verified** — no evidence
  either way.

Never tried on real hardware or a real app (as of 2026-09-05):

1. Any physical Kobo against `/kobo/{api_key}` — initialization, `library/sync`,
   opening a Stump-converted KEPUB on Nickel, or a device-originated `state` PUT.

   pull, backup-server failover, `/api/v2/devices/me/touch`, and the whole
   annotation lane (`Bookmark` scan, `/v1/annotations` batches, CAS

   read is not.

   [`stump.koplugin`](/docs/developer/koreader-plugin) has never been loaded by
   KOReader either: its four lanes are curl-verified and its pure logic is

   `kosync` plugin (settings file written from outside, restart required) is
