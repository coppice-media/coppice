One row per platform. Status cells use exactly four levels, matching
[client verification](/docs/developer/client-verification): **device-verified**
(a person ran the real app/device against the fixture server, date given),
**harness** (Hurl replay, live container, or server-side probe — proves the
server contract, not the app), **source-derived** (implemented or described from
pinned source, never run), **not verified**. Facts about hardware and third-party
tools cite the public page they come from; nothing here is inferred from memory.

## Kobo eReaders

Two facts hold for every model below. Stock Nickel renders JPEG, GIF, PNG, BMP,
and TIFF only — no WebP in CBZ or KEPUB
([Kobo file formats](https://help.kobo.com/hc/en-us/articles/360017763713-File-formats-your-Kobo-eReader-and-Kobo-Books-app-support));
a WebP page therefore has to be re-encoded before delivery. Stump serves EPUB
through Kobo sync today, KEPUB when `KOBO_KEPUB_CONVERSION=true` (converter
entry-parity with kepubify on 36 books — [Kobo capabilities](/docs/developer/kobo-sync-capabilities)),
and the CBZ → fixed-layout KEPUB transform is planned ([roadmap phase 4](/docs/developer/roadmap)).
No model has been connected to Stump yet.

| `Bookmark` | `BookmarkID`, `VolumeID`, `ContentID`, `StartContainerPath`/`ChildIndex`/`Offset`, `EndContainerPath`/`ChildIndex`/`Offset`, `Text`, `Annotation`, `ExtraAnnotationData`, `DateCreated`, `DateModified`, `ChapterProgress`, `Hidden`, `Version`, `Type`, `UUID`, `UserID`, `SyncTime`, `Published`, `ContextString`, `Creator`, optional `Color`. NickelStump reads all of it except `ExtraAnnotationData`, `UserID`, `SyncTime`, `Published` and `Creator`, per volume, and pushes it to `/v1/annotations`; no server-side reader (the copied-database importer is still a design) | [Kobo device DB](/docs/developer/kobo-device-database), `nickelstump/docs/PROTOCOL.md` |
| `AnalyticsEvents`, `Event`, `Activity` | Sessions (`OpenContent`/`LeaveContent`, cleared on store sync), opaque QVariant blobs, unverified table | source-derived; `Activity` quarantined | [Kobo device DB](/docs/developer/kobo-device-database) |
| `.kobo/markups/*.svg` + `*.jpg` | Handwritten on-page markups on stylus models: SVG strokes plus a JPG page snapshot. The file stem **is** the `Bookmark.BookmarkID` (a UUID on KEPUB volumes) and the row is `Type = 'markup'`; there is no `Notebook` table in the pinned `.tables` capture, so `Bookmark` is the only join. Kobo: EPUB/KEPUB handwritten notes stay on the device and cannot be exported; PDF markups are written into the PDF | source-derived — NickelStump reads the pair (size + SHA-256, SVG inline when ≤ 15 KiB) and pushes it as an annotation; the join is taken from the composite tool's own SQL at `2c095d5b` (`main.js:88-104,203-206,236-255,287-313`), still never observed on a device | [composite markup tool](https://github.com/leldr/Unofficial-Chrome-Based-Kobo-Composite-Markup-Generator/blob/2c095d5b5913d390309c50e6e562796a38b4a045/main.js), [Kobo help](https://help.kobo.com/hc/en-us/articles/1500001927562), `nickelstump/docs/PROTOCOL.md` |
| Notebooks | Exported from the device UI to `KOBOeReader/Exported Annotations` (Advanced: DOCX/TXT/HTML/ZIP; Basic: PNG/JPEG/PDF/ZIP); raw `.nebo` files at the volume root; backed up to kobo.com when "Sync My Notebooks" is on | not verified — deliberately out of scope: a notebook belongs to no work, the exports are multi-MB binaries, liseur-sync has no attachment lane, and `.nebo` is undocumented | [Kobo notebook help](https://help.kobo.com/hc/en-us/articles/360062226733-Use-your-Kobo-eReader-as-a-notebook), `nickelstump/docs/PROTOCOL.md` |

Read-only-snapshot rule for all of the above: never open a mounted device
database for writes (NickelHardcover uses `SQLITE_OPEN_READ_ONLY`, kobuddy
`immutable=1`); copy through a backup API or capture main + `-wal`/`-shm`
together; absence in a later snapshot is not a tombstone
([Kobo device DB](/docs/developer/kobo-device-database)).

## Status legend and open verification list

- **device-verified** — real app or device, dated. **harness** — Hurl replay,
  live container, or server probe. **source-derived** — pinned source read, code
  written, nothing executed against the target. **not verified** — no evidence
  either way.

Never tried on real hardware or a real app (as of 2026-09-05):

1. Any physical Kobo against `/kobo/{api_key}` — initialization, `library/sync`,
   opening a Stump-converted KEPUB on Nickel, or a device-originated `state` PUT.
2. NickelStump on a device: pairing screen and QR, `/v1/ops` push, positions
   pull, backup-server failover, `/api/v2/devices/me/touch`, and the whole
   annotation lane (`Bookmark` scan, `/v1/annotations` batches, CAS
   tombstones, markup SVG inlining) — the mapping is host-tested, the device
   read is not.
3. The KOReader app (any platform) against `/koreader/{api_key}`; only the
   server probe and Liseur's pairing lane exist.
4. Any of the seven pinned Kavita clients against the Kavita profile.
5. The Stump Mihon extension: no APK built, no device run.
6. `.kobo/markups` and notebook files — never inspected on a device. The
   markup-file-to-`Bookmark` join is now source-derived (the composite tool's
   own SQL at `2c095d5b` binds the file stem to `Bookmark.BookmarkID`), but no
   real `.svg`/`.jpg` pair has been read.
7. WebP blank-page behaviour on Nickel — inferred from Kobo's format list, not
   observed.
8. Komf automatic mode on a real `BookAdded` burst — `TaskQueueStatus` was seen
   during manual identify only.
9. Hardcover journal sink — not implemented; the hardcoverapp.koplugin overlap
   is therefore theoretical.
