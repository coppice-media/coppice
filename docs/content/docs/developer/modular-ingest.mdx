This page specifies the proposed modular ingest contract for a first-party SvelteKit editor. It narrows the future metadata/book-lab direction in [server architecture](/docs/developer/server-architecture) into a staged drop-folder workflow without changing Stump's existing upload, scan, metadata, or job APIs. **Current** means the behavior is in this worktree; **proposed** means a new persistence or API surface and is not implemented.

The server remains authoritative: a source file is immutable while it is being analyzed, all derived evidence is content-addressed to that source, and metadata providers produce reviewable candidates rather than silently changing a library. A pending item may be discarded or reworked without deleting an already committed `Media` row.

This page extends the uploader-prepared boundary and metadata/book-lab proposal already recorded in `docs/content/docs/developer/server-architecture.mdx:180-226`; it also follows the optional-provider and candidate provenance rules in `docs/content/docs/developer/hardcover-integration.mdx:1-20,167-220`. Those pages remain the broader architecture and integration notes; this page adds the queue, deterministic quality report, and editor-facing GraphQL contract.

## What exists today and what this design adds

The current path is deliberately preserved:

- GraphQL `uploadBooks` and `uploadSeries` receive multipart `Upload` values, copy them into a library path, and enqueue a library scan. They return only `Boolean`; there is no durable drop-item or analysis-report identity ([observed — `crates/graphql/src/mutation/upload.rs:43-102,108-167`]).
- The library watcher receives create/modify notifications, accumulates paths, waits until the tree has been quiet for its debounce interval, and submits a `library_scan` job ([observed — `core/src/filesystem/scanner/library_watcher.rs:15-104`]).
- `StumpJob`, queued through the `stump_jobs` runtime, currently contains library/series scans, thumbnail work, metadata fetches, and media analysis. `AnalyzeMediaJob` accepts book, list-of-books, library, and series scopes and creates one `ProcessBook` task per selected media ([observed — `core/src/job/stump_job.rs:19-44`; `core/src/filesystem/media/analysis/job.rs:12-136`]).
- Page analysis currently stores dimensions and content types in `MediaAnalysisData`; it reuses complete existing page entries unless forced and reports task/subtask progress through the job event channel ([observed — `core/src/filesystem/media/analysis/analyze.rs:99-194`; `crates/jobs/src/progress.rs:6-45`]).
- The existing `metadata_integrations::MetadataProvider` has provider identity, supported media types, series/media search, scoring, detail fetch, and credential verification methods. `MatchCandidate` already carries provider, external ID, metadata, confidence, and confidence factors ([observed — `crates/integrations/metadata/src/provider.rs:19-75`; `crates/integrations/metadata/src/types/match_candidate.rs:5-44`]).
- Core metadata fetches enabled providers, stores candidates in `metadata_fetch_records`, and can auto-apply through the existing merge path. Current records are one media or series target at a time; the existing GraphQL surface exposes `pendingMetadataMatches`, candidate acceptance/rejection, field locks, bulk accept/reject, and provider configuration ([observed — `core/src/filesystem/metadata/fetch.rs:114-224,247-378`; `core/src/filesystem/metadata/apply.rs:17-124`; `crates/graphql/schema.graphql:1648-1780,1884-1908,1959-1964,2086-2094`]).
- The existing GraphQL `readEvents` subscription forwards the core broadcast stream of `JobStarted`, `JobUpdate`, `JobOutput`, and scan events. `JobProgress` is a patch, so omitted fields must be retained by a client ([observed — `crates/graphql/src/subscription/event.rs:6-32`; `core/src/event.rs:1-58`; `core/src/job/progress.rs:8-27`]).

The proposed path is additive and may coexist with the current path:

```text
upload/watch -> immutable staging -> drop_item
                              -> analysis_job -> existing processors + quality_report
                                                   -> provider identification/lookup
                                                   -> metadata candidates + review
                                                   -> field-level apply/merge
                                                   -> explicit commit to Media/Series
```

A current library scan may still create `Media` and `Series` before the new workflow is introduced. The staged workflow instead keeps a `drop_item` pending until `approveIngestItem` commits it. A compatibility adapter can call the existing scanner/`MediaBuilder` transaction at that boundary; no existing client is required to adopt the new contract.

## Domain model

The names below are logical records. Their exact SeaORM entities and migrations are **implemented**. IDs are opaque, timestamps are UTC, and every record that derives from a file stores the source digest and the algorithm/processor version used.


| Record | Required fields and invariants | Lifecycle / purpose |
| --- | --- | --- |
| `drop_item` | `id`, `library_id`, `created_by`, source filename and normalized relative path, byte size, full source SHA-256, detected media type, staging reference (never an absolute path in GraphQL), `status`, `analysis_job_id`, `quality_report_id`, optional committed `media_id`/`series_id`, pending metadata field map, error, created/updated timestamps, and an integer revision. `(library_id, source_sha256, source_filename)` plus an idempotency key prevents duplicate admission; the staged bytes are immutable. | `RECEIVED -> STAGED -> ANALYZING -> AWAITING_REVIEW/READY -> COMMITTED`; `REJECTED` and `FAILED` are terminal for that attempt. A retry creates a new analysis attempt but does not mutate source bytes. |
| `analysis_job` | `id`, `drop_item_id`, underlying optional existing Apalis `job_id`, `status`, phase, priority score, algorithm/provider plan, attempts, timestamps, and error. The job references a drop item rather than embedding a filesystem path. | A durable editor-facing projection of work. It can be queued, running, paused, cancelled, retried, or completed while the underlying `Job` remains compatible with existing job history. |
| `quality_report` | `id`, `drop_item_id`, `source_sha256`, `algorithm_version`, `score` in `0..=100`, ordered `checks[]`, generated timestamp, and optional parser/processor evidence. A report is valid only for the exact source digest and algorithm version. | Immutable evidence for one analysis attempt. A newer report supersedes it; prior reports remain audit history. |
| `quality_check_result` (an element of `checks[]`) | `check_id`, display label, `status` (`PASS`, `WARN`, `FAIL`, `NOT_APPLICABLE`), fixed weight, normalized score `0..=1`, contribution, and bounded structured evidence (counts, hashes, dimensions, or parser candidates). | One deterministic finding. A check never inspects network results, wall-clock time, provider response order, or an AI opinion. |
| `metadata_candidate` | `id`, `drop_item_id` or committed target, stable provider ID, overall `confidence` in `0..=1`, canonical `fields` map, optional per-field confidences, source digest, identity/lookup input, provider version/model, provenance, status, and timestamps. | `PENDING -> ACCEPTED/REJECTED`. Candidates are evidence; they never become trusted metadata until a user or an explicitly enabled auto-apply policy selects fields. |
| `metadata_application` | `id`, item/target ID, expected revision/source digest, strategy, ordered field picks, actor (`user`, `auto_apply`, or `system`), applied/failed fields, and timestamp. | Audit trail for a single or bulk merge. A stale revision fails rather than overwriting a newer edit. |
| `plugin_registration` and `plugin_setting` | Provider/check ID, kind, display name, version, supported media types, capabilities, setting definitions, enabled/opted-in flags, and secret/configured markers. Secret values are encrypted and never returned. | Registry discovery and per-user/per-library settings. Built-ins can be statically registered; dynamic native loading is not required for the first implementation. |

### State and ownership rules

1. Staging is server-owned. A client supplies a file stream and an optional relative display path, never a server filesystem path. The server validates the library, normalizes path separators, rejects `..`, computes the full digest while writing, and atomically records the item.
2. A source digest is the identity of bytes; a filename is only an input to parsing. A repeated idempotency key returns the original item, while the same filename with different bytes creates a new item.
3. A `quality_report` and every candidate must name the source digest. Results from a worker/uploader whose digest does not match are rejected without losing the source.
4. A pending item has no reader-visible `Media` row until commit. If an implementation chooses to reuse the scanner's early row, it must mark that row unavailable to normal readers until the same explicit commit transition succeeds.
5. `approveIngestItem` is the only proposed transition to committed library state. It applies selected metadata in the same database transaction as the media/series association. `rejectIngestItem` removes or quarantines staging only; it does not delete unrelated existing media.
6. All list ordering is deterministic: score/priority first, then creation timestamp, then opaque ID. Provider response order is never a tie-breaker.

## Preprocess hook

`ingest_preprocess_command` (`STUMP_INGEST_PREPROCESS`) is an optional executable run once per dropped item, before analysis. It is any executable; typical uses are format normalisation and running your own conversion pipeline. It is **implemented** in `core/src/ingest/preprocess.rs`, invoked from the staging phase of staged analysis in `core/src/ingest/coordinator.rs`, and unset by default, in which case nothing about the pipeline changes.

The contract is a plain child process:

```text
<ingest_preprocess_command> <absolute staged file path>

STUMP_INGEST_ITEM_ID     the drop item id
STUMP_INGEST_LIBRARY_ID  the library the item was dropped into
```

| Aspect | Behaviour |
| --- | --- |
| Command | An executable path, or a bare name resolved on `PATH`. It is not a shell line and arguments are never parsed out of it, so wrap multi-step work in your own script. |
| Startup | A command that does not resolve to an executable file, or a zero timeout, fails server startup (`StumpCore::init_config`). A typo must never degrade into silently skipping every item. |
| Timeout | `ingest_preprocess_timeout_secs` (`STUMP_INGEST_PREPROCESS_TIMEOUT_SECS`), default `600`. A hook that outlives its budget is killed and its item fails. |
| Exit `0` | Analysis continues with whatever bytes are now at that path: the hook may rewrite the file in place or replace it at the same path. The file is re-hashed and the item's `source_sha256` and `byte_size` are updated, so the `quality_report` and every candidate name the digest of the bytes analysis actually read. The staged path itself is never renamed, so it keeps the pre-hook digest in its filename. |
| Non-zero exit | The item becomes `FAILED` with the exit code and the tail of the hook's stderr (1000 characters) as its `error`, which is what the editor lists as the failure reason. A hook that cannot be spawned at all is reported the same way. |
| Once per item | A successful run stamps `ingest_drop_items.preprocessed_at`, and a stamped item is never preprocessed again — re-analysis and retries must not run a conversion pipeline over its own output. A failed hook leaves the stamp unset, so fixing the command and retrying runs it again. |

The hook owns the staged bytes before anything parses them, which is the only ordering that makes the digest, the page index, the quality report, and the candidates describe one file.

## Analysis job and queue

`analysis_job` is the durable orchestration record for the editor; the existing Apalis job remains the execution mechanism where possible. A coordinator creates one analysis job per drop item, schedules bounded tasks, and records phase transitions. It may delegate page extraction to `AnalyzeMediaJob` and archive/EPUB parsing to the existing `FileProcessor` implementations rather than duplicate native readers.

The queue priority is the current quality score, with the lowest score first because the most defective item needs attention first:

```text
priority(item) = quality_report.score if a report exists, otherwise 0
order by priority asc, created_at asc, id asc
```

A missing report is score `0`, not an implicit pass. A re-run replaces the priority key and moves the item deterministically. The client cannot choose an arbitrary priority; an operator can only enqueue, pause, resume, cancel, or retry. `force` means re-run checks even when a source/processor version is unchanged. Existing `JobStatus` values (`QUEUED`, `RUNNING`, `PAUSED`, `COMPLETED`, `CANCELLED`, `FAILED`) are reused in the proposed GraphQL projection ([observed — `crates/graphql/schema.graphql:982-1031`]).

`AnalyzeMediaJob` currently gathers IDs from its `Book`, `Books`, `Library`, or `Series` scope, invokes `safely_analyze_book`, and reports page subtasks. The proposed coordinator supplies a staged item adapter and records the resulting `MediaAnalysisData`; it does not change those existing scopes ([observed — `core/src/filesystem/media/analysis/job.rs:75-136`; `core/src/filesystem/media/analysis/analyze.rs:104-194`]).

## Quality checks and deterministic score

Every built-in check has a fixed weight. The weights below sum to 100. `q_i` is the normalized score in the table, and `w_i` is the weight. `NOT_APPLICABLE` checks are excluded from both sums so an EPUB is not penalized for an archive-only rule; a report with no applicable checks has score `0`.

```text
\operatorname{score} = \operatorname{round}\left(100 \times
\frac{\sum_{i \in A} w_i q_i}{\sum_{i \in A} w_i}\right),
\qquad A = \{i \mid status_i \ne NOT\_APPLICABLE\}
```

For each applicable check, `contribution_i = 100 * w_i * q_i / sum_A(w_j)`; the displayed contributions sum to the unrounded score and the persisted `score` is their nearest integer. The persisted `score` is an integer in GraphQL, while each `normalizedScore` and `contribution` remains available for explanation. `WARN` is not synonymous with failure: it contributes its explicitly listed fractional value. A report records `algorithmVersion = "ingest-quality-2"` (or a future version) so changing a threshold never silently changes old scores; `ingest-quality-1` reports predate `duplicate_pages_across_books` and the 15-point `cover_present`/`page_count_matches_archive_entries` weights.

| Check ID | Weight | Deterministic definition and normalized score |
| --- | ---: | --- |
| `drm_protected` | 0 | Blocking gate, every format. Sniff the container by magic (never by extension) and look for content encryption: an OCF ZIP is protected when `META-INF/license.lcpl` plus an `EncryptedContentKey` (Readium LCP), `META-INF/sinf.xml` containing `fairplay` (Apple), a `<kdrm>` block in `META-INF/rights.xml` (Kobo), an `{http://ns.adobe.com/adept}encryptedKey` (base64 length `>= 172` is ADEPT, `== 64` is Adobe PassHash/B&N, `keyType > 2` adds hardened), a `.kfx` member starting with the DRMION magic, or any `EncryptedData` algorithm that is not one of the two font-obfuscation URIs (`http://www.idpf.org/2008/embedding`, `http://ns.adobe.com/pdf/enc#RC`); a Palm database is protected when the PalmDOC encryption type at record-0 offset 12 is non-zero or the MOBI header declares a DRM key block at `0xA8`/`0xAC`; a PDF is protected when a trailer or cross-reference stream declares `/Encrypt`; bare `TPZ` and DRMION magics are Topaz and KFX. Protected is `FAIL`, `q=0`, with the scheme, matched markers, and a plain-language reason as evidence; anything else is `PASS`, `q=1`. See [Calibre and external e-book tooling](/docs/developer/calibre-tooling). |
| `cover_present` | 15 | The format adapter must identify one cover artifact using only embedded/package structure and decode it as an image. EPUB uses its package cover declaration/nav resource; paged files use the first decodable page; an archive uses the first decodable image in stable natural-path order. `PASS`, `q=1`, means a selected image exists and decodes; `FAIL`, `q=0`, means no selected image or decode failure. Non-paged/text-only formats are `NOT_APPLICABLE`. |
| `cover_not_page_two` | 10 | If at least two pages/resources exist in the format adapter canonical reading order (ZIP natural path, EPUB spine order, or PDF page order), and a decodable cover and second page exist, canonicalize both images to the same RGBA pixel representation and compare their SHA-256 digests. Different digests are `PASS`, `q=1`; equal digests are `FAIL`, `q=0`; an undecodable comparison is `WARN`, `q=0.5`. Fewer than two pages/resources is `NOT_APPLICABLE`. This deliberately uses exact decoded pixels, not a tunable perceptual threshold. |
| `page_count_matches_archive_entries` | 15 | For ZIP/CBZ-like archives only, count non-directory image entries after excluding hidden files and known metadata files (`ComicInfo.xml`, `Thumbs.db`, and dotfiles), using the processor's stable natural-path order. Compare that count `E` with the processor/metadata page count `P`: `E=P` is `PASS`, `q=1`; `|E-P|=1` is `WARN`, `q=0.5`; a larger difference or invalid `P` is `FAIL`, `q=0`. Non-archive formats are `NOT_APPLICABLE`. |
| `image_dimensions_consistent` | 15 | Analyze every image page with the existing minimum-byte dimension reader, count `N`, and find the modal `(width,height)` pair with lexicographic tie-break. A page whose dimensions cannot be decoded contributes zero matches. `q = matching_pages / N`; `PASS` when `q=1`, `WARN` when `0.9 <= q < 1`, and `FAIL` when `q < 0.9`. A non-image or fewer-than-two-image item is `NOT_APPLICABLE`. Existing page dimensions are available in `MediaAnalysisData` ([observed — `core/src/filesystem/media/analysis/analyze.rs:104-194`; `crates/models/src/shared/analysis.rs:1-104`]). |
| `epub_toc_chapters` | 15 | EPUB only. Parse the container/rootfile and package with the existing EPUB parser; require a non-empty spine and at least one nav/NCX entry resolving to a spine resource. Valid package+spine but no resolvable TOC is `WARN`, `q=0.5`; valid package with no spine or a parse/decode failure is `FAIL`, `q=0`; both spine and TOC are `PASS`, `q=1`. Non-EPUB formats are `NOT_APPLICABLE`. |
| `duplicate_existing` | 10 | First compare the new full source digest against future full-digest records and, for compatibility, the current `Media.hash` when it was produced with the same algorithm. An exact match is `FAIL`, `q=0`. If no exact hash matches, compare the normalized filename/metadata title with existing visible media using the existing `MatchScorer` signals (exact/alternate title, Dice/Jaro-Winkler, and token overlap). A highest score `>=0.70` is a possible duplicate: `WARN`, `q=0.5`; below `0.70` is `PASS`, `q=1`. Evidence lists all matching media IDs sorted by score desc then ID. The current Stump hash is a secondary sample identifier rather than a promised full-file digest ([observed — `core/src/filesystem/media/process.rs:49-78`; `crates/graphql/schema.graphql:1297-1305`; `crates/integrations/metadata/src/scoring.rs:17-40,95-175`]). |
| `filename_series_parse` | 10 | Normalize Unicode to NFKC, trim the extension, normalize `_` and `.` to spaces, preserve one surrounded ` - ` series boundary, collapse whitespace, and parse a fixed grammar: optional parent-directory series or filename prefix before ` - `, required non-empty residual title, optional one marker (`#n`, `vN`, `vol N`, `issue N`, or `chapter N`), and optional year `1900..2099`. A standalone title with no series/number is valid. The check exposes `q` as filename/series parse confidence: exactly one tuple `(series?, title, number?, year?)` is `PASS`, `q=1`; conflicting parent/prefix or multiple numeric markers producing more than one tuple is `WARN`, `q=0.5`; an empty title or malformed marker is `FAIL`, `q=0`. The chosen tuple and rejected alternatives are evidence; no network lookup affects this score. |
| `duplicate_pages_across_books` | 5 | Paged formats only. Compute the 8×8 difference hash (dHash) of every decodable staged page and compare it, at Hamming distance `<= 4`, against the `page_hashes` rows of the target library's other books (the media under library rework is excluded from its own comparison). A page that recurs in at least `minBooks` distinct books (setting, default `3`) is a duplicate group: any group is `WARN`, `q=0.5`; none is `PASS`, `q=1`; a reflowable book or a book with no hashable page is `NOT_APPLICABLE`. Evidence lists up to 20 groups (`dhash` hex, own page, matching `media_id`/`name`/`page`), the matched book ids, `tolerance`, `min_books`, and `truncated`. The check never hides anything; see [Duplicate pages](#duplicate-pages). The weight is 5 because this advisory, `WARN`-only signal now shares the 10 points it used to hold alone with `missing_chapters_in_series`. |
| `missing_chapters_in_series` | 5 | Series completeness. Analyze the staged file name together with the visible media file names of the series it joins (the media row's own series for library rework, otherwise the library series named by the drop folder) using the one workspace sequence parser (`stump_scanner::sequence`, shared with the `missing-sequence` tool): the `Chapter/Chap/Ch/C/Episode/Ep/Volume/Vol/v` identifier vocabulary, omnibus ranges (`Chapter 01-03` covers 1, 2 and 3), decimal chapters that belong to their integer chapter and never open a gap, `()`/`[]` release-metadata stripping, and the changing-numeric-token fallback when no name carries an identifier. Any integer absent between the lowest and highest covered number is a gap: at least one gap is `WARN`, `q=0.5`; a gap-free sequence is `PASS`, `q=1`. Fewer than two numbered files, no resolvable series, or a numbering span too wide to enumerate (`> 10000`) is `NOT_APPLICABLE`. Evidence carries `series_id`, `series_name`, `file_count`, `identified_count`, `kind`, `source`, `found_ranges`, `missing` (capped at 100), `unidentified` (capped at 25), `decimals`, `truncated`, and `span_exceeded`. Behaviour source: [Kavita cbz-missing-sequence-checker](https://wiki.kavitareader.com/guides/external-tools/cbz-missing-sequence-checker/). |

The check registry must expose the same IDs, weights, algorithm version, and setting definitions to the UI. A setting can alter whether a check is enabled or a bounded parser option, but a report always stores the effective setting snapshot. If an operator changes settings, the coordinator invalidates affected reports and requeues the items instead of rewriting history.

`drm_protected` is the one check with weight `0`, and that is deliberate: a
DRM-protected file is not a low-quality book, it is a file this server cannot
decode at all, so deducting points would be the wrong signal. A weight-`0`
check contributes nothing to the score (`score_report` excludes it from both
sums), keeps the scored weights summing to 100, and surfaces instead through
the report's failed-check list, which the coordinator already collects from
every `FAIL` outcome. Clients must treat a `FAIL` on a zero-weight check as
blocking rather than cosmetic. Stump never ships or invokes DRM removal; the
check only explains precisely why the file cannot be ingested.

### Duplicate pages

Page hashes are a library-wide resource, not just a quality signal. The media analysis job writes one `page_hashes` row (`media_id`, 1-based `page`, `dhash` as the `u64` bit-cast to `i64`) per decodable image page; the quality check above, the candidate aggregation, and the serve-time filter all read that table with the same tolerance (`DUPLICATE_PAGE_TOLERANCE = 4` in `core/src/filesystem/media/visible_pages.rs`). Hashes are exchanged with clients as 16 lowercase hexadecimal digits.

A librarian records a decision per `(library_id, dhash)` in `known_duplicate_pages` with `DuplicatePageAction`:

| Action | Effect |
| --- | --- |
| `SKIP` | Every page of every book in the library whose hash is within the tolerance of the marked hash is hidden from page-serving routes. Files are never modified. |
| `KEEP` | The page was reviewed and is legitimate; it stops appearing as a candidate and stays visible. |

GraphQL surface (`ManageLibrary`, scoped to libraries visible to the caller): `knownDuplicatePages(libraryId)`, `duplicatePageCandidates(libraryId, minBooks, limit)` — aggregates `page_hashes` by hash for the library, clusters near-identical hashes around the most widespread member, drops clusters covered by a known mark, and returns the groups with their book count and occurrences (`mediaId`, `mediaName`, physical `page`, `visiblePage` for previews, exact `dhash`) — `markDuplicatePage(libraryId, dhash, action)` (upsert) and `unmarkDuplicatePage(libraryId, dhash)`. `mediaVisiblePages(id)` returns the ordered physical pages a reader currently sees for one book. The editor exposes these under **Library › Duplicate pages**.

Serve-time renumbering: `visible_pages(conn, cache, media_id, pages)` returns the ordered physical 1-based pages that remain visible (pages without a stored hash are always visible) and is cached per media on `Ctx::visible_pages_cache()`. A mark change clears the whole cache; the analysis job invalidates one media after writing new hashes. Every paged route maps a client-facing page `n` to `visible[n - 1]` and reports `visible.len()` as the page count: the native `GET /api/v2/media/{id}/page/{n}`, OPDS 1.2 PSE (`pse:count` and `/pages/{n}`), and Komga `GET /api/v1/books/{id}/pages` + `/pages/{n}` (see the renumbering test in `crates/komga/src/routes/media.rs`). A visible page past the end of the list is `404`, never a fallback to the physical page.

## Metadata providers, taggers, and AI enrichment

### Two plugin traits

The ingest layer has exactly two logical plugin seams. The provider seam is now implemented as `IngestMetadataProvider` in `core/src/ingest/contract.rs:334-365` (with `capabilities`, `settings`, a `settings` argument on `identify`/`lookup`, and a default `search`); the sketch below is the original proposal and is kept for the quality-check seam. The per-provider inventory — ids, domains, key type and `help_url`, client rate limits, capabilities, defaults, fields filled, Komf reference, and test counts — plus the facade fan-out, scoring, apply path, missing policy layer, and planned providers are maintained in [Provider status › Metadata providers](/docs/developer/provider-status#metadata-providers); this page does not duplicate that table.

```rust
#[async_trait]
pub trait MetadataProvider: Send + Sync {
    fn id(&self) -> &'static str;
    fn name(&self) -> &'static str;
    fn version(&self) -> &'static str;
    fn supported_media_types(&self) -> &[MediaType];
    fn settings(&self) -> &[SettingDefinition];

    async fn identify(
        &self,
        book: &BookSnapshot,
    ) -> Result<Vec<ProviderIdentity>, ProviderError>;

    async fn lookup(
        &self,
        book: &BookSnapshot,
        identity: &ProviderIdentity,
    ) -> Result<Vec<MetadataCandidate>, ProviderError>;
}

#[async_trait]
pub trait QualityCheck: Send + Sync {
    fn id(&self) -> &'static str;
    fn name(&self) -> &'static str;
    fn version(&self) -> &'static str;
    fn weight(&self) -> u16;
    fn settings(&self) -> &[SettingDefinition];

    async fn run(
        &self,
        book: &BookSnapshot,
    ) -> Result<QualityCheckResult, QualityCheckError>;
}

pub struct QualityCheckResult {
    pub findings: Vec<QualityFinding>,
    pub weight: u16,
}
```

`BookSnapshot` contains only a read-only source handle, digest, filename/path metadata, embedded metadata, page/archive index, and any already-computed `MediaAnalysisData`; it does not permit a provider to mutate the library. `QualityCheckResult.weight` must equal the registered fixed weight; a mismatch is a registration error. A check can emit multiple findings, but its one normalized result and fixed weight determine its score contribution.

The existing integration is reused through an adapter rather than renamed:

| Proposed seam | Reuse / new work |
| --- | --- |
| `identify` | **Reuse:** compose the existing `SearchQuery` from filename/embedded metadata, invoke current `search_media`/`search_series`, and preserve `MatchScorer` confidence factors. **New:** return a provider-neutral identity list and source provenance. |
| `lookup` | **Reuse:** call existing `fetch_media_metadata`/`fetch_series_metadata`, `ProviderClientCache`, retry/rate-limit handling, and `ExternalMediaMetadata`/`ExternalSeriesMetadata`. **New:** normalize fields into `metadata_candidate.fields` and bind them to the staged source digest. |
| Candidate persistence | **Reuse:** existing `metadata_fetch_records` is the compatibility view for a committed media/series target. **New:** a drop item needs many candidates before a `Media` exists, plus provenance/source digest and field-level confidence. |
| Apply/merge | **Reuse:** `FieldMerger`, locked fields, `MergeStrategy`, `apply_media_match`, `apply_series_match`, and current metadata permissions. **New:** field-level candidate/manual picks and a transactional pending-item projection. |
| Queue execution | **Reuse:** `StumpJob`, `JobLifecycle`, the `stump_jobs` runtime, cancellation, logs, and `JobProgress`. **New:** durable drop-item/analysis-job priority and typed progress/replay. |

The existing `metadata_integrations::MetadataProvider` is the lower-level client contract and remains source-compatible ([observed — `crates/integrations/metadata/src/provider.rs:19-75`]). It has separate `search_*` and `fetch_*` methods rather than `identify`/`lookup`; `IntegrationProvider` (`core/src/ingest/providers/facade.rs:40-224`) supplies those higher-level semantics without renaming an existing type. Implemented providers, their settings stores, and the registry are documented in [Provider status](/docs/developer/provider-status#metadata-providers).

### Registration and discovery

At startup, a `PluginRegistry` registers built-in providers and quality checks, then overlays persisted per-user/per-library settings. Each descriptor includes:

- stable ID, human name, implementation version, kind, supported media types, and capabilities (`IDENTIFY`, `LOOKUP`, `TAGS`, `AI_ENRICHMENT`);
- a deterministic setting schema (key, type, default, required, secret, description) and effective setting values with secrets redacted;
- whether the plugin is available in this build, enabled, and opted in for the current library/user; and
- the quality-check weight and algorithm version where the plugin is a check.

`ingestProviderCatalog` and `ingestQualityCheckCatalog` are discovery, not hard-coded UI lists. For an unknown persisted ID, the registry emits an unavailable descriptor (`available=false`) with no executable capabilities; the settings query still returns redacted stored values. Unknown IDs remain visible as unavailable settings and never execute. A provider that is disabled or missing required credentials is excluded from scheduling, not treated as a failed book.

### Auto-tagger and AI provider policy

An auto-tagger and an AI enricher are ordinary `MetadataProvider` implementations, not privileged writers:

- `builtin:auto-tagger` returns a `tags` field plus per-tag confidence (and, optionally, tag explanations). It is disabled by default, opt-in per user/library, and never removes existing tags unless the user selects `CLEAR` explicitly and has metadata permission.
- `ai:<provider>` returns canonical fields and/or tags with overall and per-field confidence, prompt/model/version provenance, and the exact source digest. It is disabled by default, requires an explicit opt-in and provider setting, and is never eligible for auto-apply solely because it returned a candidate.
- By default only bounded text/metadata excerpts and the digest leave Stump; source bytes, page images, annotations, and private notes are not sent. A future image-capable setting must be a separate, explicit consent and size-limited option.
- Auto-apply requires both the provider opt-in and a confidence threshold. Existing provider auto-apply defaults remain conservative (`enabled=false`, threshold `0.95`, `FILL_GAPS`), so adopting the new editor does not change current behavior ([observed — `crates/integrations/metadata/src/merge/config.rs:11-56`]). Field locks and permissions always win over provider settings.
- A candidate from AI or a tagger is still reviewable and can be selected field by field. The server records provider/model version and setting snapshot so a later model change cannot silently rewrite prior decisions.

## Field-level apply, merge, and bulk editing

The editor submits an ordered list of field picks. Each pick names a `MetadataField` and one mode:

- `KEEP_EXISTING`: do nothing;
- `CANDIDATE`: take the value for that field from a specific candidate ID;
- `MANUAL`: use the supplied JSON value after field/type validation; or
- `CLEAR`: explicitly clear a nullable field, subject to permission and lock rules.

Input validation rejects duplicate fields, requires `candidateId` only for `CANDIDATE`, requires `value` only for `MANUAL`, and rejects values for `KEEP_EXISTING` or `CLEAR`. The server validates that the candidate belongs to the same drop item/source digest, applies locked fields and the requested existing `MergeStrategy`, and records an application audit row. A candidate can supply different fields from multiple providers. If a drop item has no committed media yet, the selected values remain in its pending projection until approval; if it targets an existing media, the operation uses the existing transaction and returns the updated item.

`bulkApplyIngestMetadata` applies the same field-pick recipe to many selected drop items. It is deterministic and idempotent per item revision: each item succeeds or returns a bounded failure with no partial field write for that item. The response includes both updated items and failures. A bulk operation does not implicitly approve/reject source files. For already committed records, the existing `updateMediaMetadata`, `setMediaTags`, `setSeriesTags`, and provider match mutations remain available ([observed — `crates/graphql/schema.graphql:1883-1898,2000-2016`]).

## Policy

`bulkApplyIngestMetadata` still needs a human to choose the fields. The
per-field **metadata policy** is the standing answer to "who wins this field",
so auto-apply and the editor's *Apply best* need no recipe at all. It is
**implemented** in `crates/ingest/src/policy.rs`.

Komf keys the same information per provider: a `priority` number plus a
`seriesMetadata`/`bookMetadata` map of per-field booleans, overridable per
library through `libraryProviders`
([`application.yml` reference](https://github.com/Snd-R/komf/blob/master/README.md#example-applicationyml-config),
[aggregation rules](https://github.com/Snd-R/komf/blob/master/README.md#metadata-aggregation)).
A per-field ordered provider list is the transpose of that table: same facts,
but "who wrote this field" is one lookup instead of a scan across every
provider's toggle map.

### The rule

One rule per field: `providers` (ids in priority order; empty means the field
is never filled), `strategy`, and `lock_respected`.

| Strategy | Behaviour |
| --- | --- |
| `FIRST` | The first provider in the list that offers a value wins. This is Komf's documented default: "all metadata will be fetched from the first positive match in configured providers by order of priority". |
| `MERGE_UNION` | Case-insensitive union of the stored value and every allowed provider's values, in first-seen order, so the stored spelling survives and nothing the user has is dropped. List fields only (`AUTHORS`, `TAGS`, `GENRES`); anything else falls back to `FIRST`. |
| `LONGEST` | The longest offer wins — characters for text, items for a list. A tie keeps the higher-priority provider. |
| `PREFER_EXISTING` | Only fill the field when the row does not already hold a value. |
| `HIGHEST_RESOLUTION` | The largest *advertised* cover wins. `COVER` only; falls back to `FIRST` elsewhere. |

Within one provider, several candidates are ordered by descending candidate
confidence, with the candidate id breaking remaining ties, so a plan is
reproducible. A blank string, empty list, or empty object is absence, not
evidence, and never wins a field.

A provider hands out a cover *URL*, not an image, so `HIGHEST_RESOLUTION`
ranks what the value advertises: an explicit `{"url":…,"width":W}`, a
`<width>x<height>` token, a size component before the extension (MangaDex's
`….jpg.512.jpg`), or a `width=`/`w=` query parameter. A value that advertises
nothing ranks last, so a field where nobody advertises a size resolves in
priority order. Guessing from a provider's own size keyword (`super_url`,
`extraLarge`, `-L`) is deliberately not attempted: each is already that
provider's largest variant, so they carry no comparable pixel count, and the
alternative — downloading every candidate cover to measure it — is a network
fan-out inside a resolver.

### Defaults

`MetadataPolicy::server_default()` mirrors Komf's priority numbers for the
providers this build has (`mangaUpdates: 10`, `mal: 20`, `aniList: 40`,
`mangaDex: 90`, `comicVine: 110`), then the providers Komf has no equivalent
for (`metron`, `openlibrary`, `googlebooks`, `audible`, `hardcover`). One total order over
every provider is enough: a provider that does not support a book's media kind
never produces a candidate, so the manga providers are simply silent on an
EPUB novel.

Four documented divergences from Komf:

| Field | Default | Why |
| --- | --- | --- |
| `SERIES` | `PREFER_EXISTING` | Komf's `postProcessing.seriesTitle` is `false`: it leaves the series title alone unless asked. |
| `TAGS`, `GENRES` | `MERGE_UNION` | Komf gates the same behaviour behind `mergeTags`/`mergeGenres`, off by default *because Komf's aggregation itself is off by default*. A per-field policy aggregates by construction, and the union dedupes case-insensitively. |
| `COVER` | `HIGHEST_RESOLUTION` | Stump keeps one cover per book, so a larger source image is strictly better input for thumbnail generation. |
| `PAGE_COUNT` (only), `NUMBER`, `ISBN` (first) | `builtin:embedded` | These are measured from the file. Komf's own docs warn that a catalog provider "can mismatch issue numbers". |

`llm` is last, and only on `SUMMARY`, `TAGS`, and `GENRES`: AI enrichment is a
fallback for prose and free-form lists, never a source for identity fields.

### Storage and override

The server default lives in code. A library overrides it per field in
`library_configs.metadata_policy` (nullable JSON-in-TEXT,
`m20260929_000000_add_library_metadata_policy`): every field the override
names replaces the default rule wholesale, everything else is inherited —
exactly how Komf's `libraryProviders` relates to `defaultProviders`. `NULL`
means "inherit everything", which is what every existing library gets, so the
migration cannot change behaviour for an existing install.

A document is validated before it is stored: an unknown provider id, a
repeated provider, or a strategy that cannot apply to its field are all
refused, because each would silently disable or degrade a field later. The
allow-list is the provider registry catalog of the running build.

```graphql
metadataPolicy(libraryId: ID!): MetadataPolicy!
setMetadataPolicy(libraryId: ID!, input: MetadataPolicyInput!): MetadataPolicy!
applyBestIngestMetadata(dropItemId: ID, mediaId: ID): IngestApplyBestPayload!
```

`metadataPolicy` answers with one row per field — the effective rule plus
`overridden` (library override versus inherited default) and `storable`. An
empty `fields` list in `setMetadataPolicy` clears the override. The editor's
**Policy** tab (`editor/src/routes/(app)/settings/providers`) renders one row
per field: the ordered provider list with reorder/remove/add, the strategy,
the lock switch, and a per-row *Inherit* action that drops the field from the
override.

### One resolver for auto-apply and "apply best"

`MetadataPolicy::plan` turns candidates + the stored row + the user's locks
into the same `FieldPick` recipe the editor submits by hand: `CANDIDATE` when
one candidate wins (so the audit row keeps the provenance) and `MANUAL` when
values were merged. Both entry points go through it and then through the
existing `applyIngestMetadata` path, so there is one validation, one merge, and
one audit shape:

- `applyBestIngestMetadata` is the editor's *Apply best* action, on a staged
  item or a library media row.
- `approveIngestItem` stages the plan as the item's pending fields before
  committing, which is the auto-apply payload. Fields the user already picked
  by hand live in the same projection and outrank the policy.

A field the user locked (`media_metadata.locked_fields`) is never written while
its rule has `lock_respected`, whatever the strategy says, and the plan reports
the locks it enforced so the apply path enforces the same set. Turning
`lock_respected` off for a field is the one way a policy outranks a lock.

Every field is resolved, including the three the staged apply path has no
column for (`COVER`, `LINKS`, `STATUS`): their decision comes back with
`applied: false`, so the editor can show who would win without anything being
written. `STATUS` exists as a candidate field because provider series records
carry a publication status; `series_fields` in the façade emits it with the
same spelling the legacy series apply path writes into
`series_metadata.status`, alongside the publisher, genres, and tags it was
already discarding.

## Progress transport

### Existing compatibility stream

Today, clients can subscribe to `readEvents` over the existing GraphQL WebSocket route. It receives the core broadcast `CoreEvent`; a `JobUpdate` contains a patch with status/message/task/subtask fields and `JobOutput` contains the final output ([observed — `crates/graphql/schema.graphql:410-413,1014-1031,3332-3336`; `crates/graphql/src/subscription/event.rs:6-32`]). This remains the compatibility fallback for scans and delegated `AnalyzeMediaJob`s. It has no durable replay cursor, and the broadcast receiver can end after a lag/close, so a reconnecting editor must refetch state.

### Proposed typed subscription

`ingestProgress` is a typed, filtered subscription. Every event has a monotonically ordered opaque cursor, source/item/job IDs, phase/status, counts, score when known, and a human message. It is a state update, not a secret-bearing log. A reconnect supplies `afterEventId`; the server replays retained events when available and then continues live. If the cursor has expired, the server sends a `CURSOR_EXPIRED` error and the client refetches `ingestDropItems`, `ingestAnalysisQueue`, or `ingestItem`.

### Proposed SSE endpoint

For clients that do not keep a GraphQL WebSocket open, the same event envelope is served by an authenticated SSE endpoint:

```text
GET /api/v2/ingest/events?libraryId=<id>&dropItemId=<id>&after=<cursor>
Accept: text/event-stream
Last-Event-ID: <cursor>

id: <eventId>
event: ingest.progress
data: {"eventId":"000000000001","emittedAt":"2026-01-01T00:00:00Z","libraryId":"library","dropItemId":"item","analysisJobId":"job","status":"ANALYZING","phase":"QUALITY","completed":3,"total":7,"score":42,"message":"Running quality checks"}
```

The exact endpoint and retention store are **implemented**. SSE must enforce the same per-user/library authorization as GraphQL, emit heartbeats, bound event size, preserve event ordering, and never include API tokens, provider secrets, absolute staging paths, or raw source bytes. The GraphQL subscription and SSE payloads use the same field names so the SvelteKit editor can share a reducer.

### SDL invariants

- The block uses only new `Ingest*` names plus existing scalar/types/enums. It therefore composes with, rather than replaces, the native schema. Existing `readEvents`, `jobs`, metadata records, and upload fields remain untouched.
- `PaginationInfo` is the existing union, so generated clients must use fragments for cursor/offset-specific fields just as they do for current media/jobs queries ([observed — `crates/graphql/schema.graphql:2305-2430`]).
- `JSON` is used for provider-specific fields and setting values because the existing schema already uses that scalar for metadata overrides/configuration ([observed — `crates/graphql/schema.graphql:1758-1764,2392-2404`]). The server validates field types before applying a manual value.
- `IngestProgressEvent` is deliberately not a new `CoreEvent` union member. The existing `readEvents` union remains stable; the proposed typed subscription and SSE adapter can be introduced without changing or renaming any existing union member.

## Implementation boundary and rollout

1. Add migrations/entities for `drop_item`, analysis attempts/jobs, quality reports/checks, candidate provenance, plugin registrations/settings, and application audit. Keep original bytes and full digest separate from the current sample-oriented `Media.hash`.
2. Add a staging service used by GraphQL upload, watcher discovery, and future uploader-prepared clients. Keep `uploadBooks`/`uploadSeries` unchanged until the new path has equivalent authorization, size limits, and scan behavior.
3. Register built-in quality checks and adapt the existing `FileProcessor`/`AnalyzeMediaJob` output. Persist `ingest-quality-1` reports and priority ordering before enabling automatic commit.
4. Wrap the current provider cache/search/fetch/merge stack in the proposed `MetadataProvider` façade. Add candidate provenance and field-level application without changing existing metadata GraphQL names.
5. Add the additive GraphQL fields above and the typed subscription. Implement SSE only if a deployment needs a non-WebSocket transport; both transports share the same retained event cursor.
6. Enable AI/tagger providers only after explicit settings, redaction, permission, and confidence tests pass. The default behavior remains current scan/metadata behavior, with no new network calls or auto-apply side effects.

The first-party editor can ship against this contract while legacy clients continue using the current native schema. No provider, AI service, worker, or new drop-folder database is required for an existing Stump installation until an operator opts into the proposed workflow.
