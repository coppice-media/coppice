# Calibre and external e-book tooling

Stump converts and inspects a narrow set of formats natively:
`stump_media` reads ZIP/RAR/EPUB/PDF containers and — since the Kindle reader
landed — MOBI/PRC/AZW/AZW3 as well (see
[native Kindle formats](#native-kindle-formats-no-converter-at-all)),
`stump_kepub` converts EPUB to KEPUB in-process, `stump_tools`' `mobi2epub`
converts Kindle books to EPUB 3 with no external binary, and `stump_tools`
owns the Kavita-style maintenance tools (`cbzit`, `epub2cbz`, `cbz-covers`,
`epub-check`, `missing-sequence`).
*Writing* the Kindle formats is **boko's** territory, not calibre's:
`boko-convert` converts EPUB, AZW3/KF8 and KFX in both directions with no
plugin, no Kindle Previewer and no Wine (see
[boko](#boko-the-preferred-kindle-converter) below). What is left for calibre
is everything neither Stump nor boko can do: MOBI *output*, PDF, DOCX, FB2,
LIT, PDB, and writing metadata back into a book.

This page records what calibre offers, where boko replaces it, why both
integrations are a subprocess and never a library, and what the ingest pipeline
does when a file turns out to be DRM-protected.

<Callout type="info">
	Version and flag claims on this page are taken from the calibre manual for
	**calibre 9.14.0** (documentation last updated 28 August 2026), the version
	the [CLI index](https://manual.calibre-ebook.com/generated/en/cli-index.html)
	is generated for. `stump_tools` requires **7.0 or newer**
	(`crates/tools/src/calibre.rs`, `MIN_VERSION`).
</Callout>

## Licence: shell out, never link

calibre is **GPL-3**
([`LICENSE`](https://github.com/kovidgoyal/calibre/blob/master/LICENSE)). Stump
is not, and linking or vendoring GPL-3 code into this workspace would relicense
the server. The consequences are absolute:

| Rule | Reason |
| --- | --- |
| No calibre source is copied, translated, or adapted into this repository | Any derivative of GPL-3 source is itself GPL-3 |
| No calibre Python module is imported, embedded, or bundled | Same, at distribution time |
| calibre is invoked as a separate process over `argv` and files only | Running an independent program and exchanging data through a documented CLI is use, not derivation |
| calibre is never a dependency of a build or a container image | An operator installs it themselves; Stump degrades to "tool unavailable" without it |
| Behaviour learned from calibre's docs is reimplemented from scratch, with the source URL cited at the rule | Facts and interfaces are not the licensed expression |

The same rule governs every other GPL/AGPL project in this space
(MangaManager, cbzit, Sigil, DeDRM_tools): read the documented behaviour,
implement it independently in Rust, cite the source.

## The calibre command line

The [CLI index](https://manual.calibre-ebook.com/generated/en/cli-index.html)
documents `calibre`, `calibre-customize`, `calibre-debug`, `calibre-server`,
`calibre-smtp`, `calibredb`, `ebook-convert`, `ebook-edit`, `ebook-meta`,
`ebook-polish`, `ebook-viewer`, `fetch-ebook-metadata`, `lrf2lrs`, `lrfviewer`,
`lrs2lrf`, and `web2disk`. On macOS these live inside the bundle, e.g.
`/Applications/calibre.app/Contents/MacOS/ebook-convert` (same page).

The six that matter here:

| Tool | What it does | What Stump cannot do without it |
| --- | --- | --- |
| [`ebook-convert`](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) | `ebook-convert input output [options]`; the output plugin is guessed from the output file's extension | Every conversion outside EPUB→KEPUB |
| [`ebook-meta`](https://manual.calibre-ebook.com/generated/en/ebook-meta.html) | Read and write embedded metadata; `--to-opf` dumps it as OPF | Reading metadata from MOBI/AZW3/LIT/FB2/DOCX; writing metadata into any format |
| [`ebook-polish`](https://manual.calibre-ebook.com/generated/en/ebook-polish.html) | Minimal-diff repairs on AZW3/EPUB/KEPUB only | Font subsetting, jackets, soft hyphens, unused-CSS removal, EPUB 2→3 upgrade |
| [`fetch-ebook-metadata`](https://manual.calibre-ebook.com/generated/en/fetch-ebook-metadata.html) | Metadata lookup by title/author/ISBN/identifier; `--opf` for machine output | Nothing — Stump has its own providers (Comic Vine, Hardcover, AniList, MAL, MangaDex, MangaUpdates, Google Books, Open Library, Metron) |
| [`calibredb`](https://manual.calibre-ebook.com/generated/en/calibredb.html) | "The command line interface to the calibre database": `list`, `add`, `remove`, `add_format`, `show_metadata --as-opf`, `set_metadata`, `export`, against a library path or a Content server URL | Nothing — Stump owns its own library model |
| [`ebook-edit`](https://manual.calibre-ebook.com/generated/en/ebook-edit.html) | Launches calibre's interactive "Edit book" GUI | Nothing — a GUI has no place in a server pipeline |

`ebook-edit`, `calibredb`, and `fetch-ebook-metadata` are documented here for
completeness and are deliberately **not** wired up: the first is interactive,
and the other two duplicate capabilities Stump already owns.

### Conversion matrix

calibre converts every input format in this list to every output format
([FAQ: what formats does calibre support conversion to/from?](https://manual.calibre-ebook.com/faq.html#what-formats-does-calibre-support-conversion-to-from)):

- **Input:** AZW, AZW3, AZW4, CBZ, CBR, CB7, CBC, CHM, DJVU, DOCX, EPUB, FB2,
  FBZ, HTML, HTMLZ, KEPUB, LIT, LRF, MOBI, ODT, PDF, PRC, PDB, PML, RB, RTF,
  SNB, TCR, TXT, TXTZ
- **Output:** AZW3, EPUB, DOCX, FB2, HTMLZ, KEPUB, OEB, LIT, LRF, MOBI, PDB,
  PMLZ, RB, PDF, RTF, SNB, TCR, TXT, TXTZ, ZIP

So the two directions Stump actually wants are both covered: MOBI, AZW3, KFX
(via calibre's KFX Input plugin), DOCX, FB2, LIT, PDB → EPUB, and EPUB → MOBI,
AZW3, KEPUB, PDF. The same FAQ ranks source formats by conversion quality, best
first: LIT, MOBI, AZW, EPUB, KEPUB, AZW3, FB2, FBZ, DOCX, HTML, PRC, ODT, RTF,
PDB, TXT, PDF — and states plainly that PDF is a terrible format to convert
from.

Caveats from the same section, worth surfacing to operators: PRC is supported
only with TextRead and MOBIBook headers; PDB only for eReader, Plucker (input
only), PML, and zTxt; DJVU only when it carries embedded text; DOCX only from
Word 2007 and newer.

<Callout type="warn">
	KFX is not in calibre's built-in input list. Reading KFX needs the
	third-party **KFX Input** plugin installed in the operator's calibre; its
	KFX *Output* plugin does not write KFX itself either — it drives Amazon's
	Kindle Previewer. Both are outside Stump's control and outside this
	integration's promises, which is exactly why
	[boko](#boko-the-preferred-kindle-converter) is the preferred converter for
	KFX and AZW3.
</Callout>

### Metadata support per format

`ebook-meta` documents two different lists, and the asymmetry matters
([`ebook-meta`](https://manual.calibre-ebook.com/generated/en/ebook-meta.html)):

| Direction | Formats |
| --- | --- |
| Read | azw, azw1, azw3, azw4, cb7, cbc, cbr, cbz, chm, docx, epub, fb2, fbz, html, htmlz, imp, kepub, lit, lrf, lrx, mobi, odt, oebzip, opf, pdb, pdf, pml, pmlz, pobi, prc, rar, rb, rtf, snb, tpz, txt, txtz, updb, zip |
| Write | azw, azw1, azw3, azw4, docx, epub, fb2, fbz, htmlz, kepub, lrf, mobi, odt, pdb, pdf, prc, rtf, tpz, txtz |

Reading is broader than writing, and the manual warns that setting metadata a
format does not support is *silently ignored*. Useful flags: `--to-opf` (dump
to an OPF file), `--get-cover` (extract the cover), `--from-opf` (apply an OPF,
overridden by any values given on the command line), and `--identifier` (repeatable,
`--identifier isbn:12345`; an empty value removes one, except a package
identifier in an EPUB).

### Polish

`ebook-polish [options] input_file [output_file]` performs the *minimum* set of
changes for each effect — no CSS flattening, no renaming, no font rescaling —
and works only on AZW3, EPUB, and KEPUB
([`ebook-polish`](https://manual.calibre-ebook.com/generated/en/ebook-polish.html)):

| Flag | Effect |
| --- | --- |
| `--subset-fonts`, `-f` | Reduce each embedded font to the glyphs the book uses (often halves font file size) |
| `--embed-fonts`, `-e` | Embed referenced fonts found on the machine |
| `--jacket`, `-j` / `--remove-jacket` | Insert or remove a metadata "book jacket" page |
| `--smarten-punctuation`, `-p` | Convert plain quotes/dashes/ellipses to typographic ones |
| `--remove-unused-css`, `-u` | Drop CSS rules that match no content |
| `--compress-images`, `-i` | Lossless image recompression |
| `--add-soft-hyphens`, `-H` / `--remove-soft-hyphens` | Add or strip soft hyphens for justification |
| `--upgrade-book`, `-U` | Upgrade internal structures, e.g. EPUB 2 → EPUB 3 |
| `--cover`, `-c` | Replace or insert the cover |
| `--opf`, `-o` | Update metadata from an OPF file |
| `--download-external-resources`, `-d` | Inline remote images/stylesheets |

Table-of-contents control lives on `ebook-convert`, not `ebook-polish`:
`--level1-toc` / `--level2-toc` / `--level3-toc` (XPath), `--toc-threshold`
(default 6), `--max-toc-links` (default 50, 0 disables), `--toc-filter`,
`--use-auto-toc`, `--duplicate-links-in-toc`, and `--no-chapters-in-toc`
([`ebook-convert`](https://manual.calibre-ebook.com/generated/en/ebook-convert.html)).
`--smarten-punctuation` and `--subset-embedded-fonts` also exist on
`ebook-convert`, in its *Look and Feel* group.

## What Stump wires up

Three tools — `calibre-convert` and `calibre-meta` in
`crates/tools/src/calibre.rs`, `calibre-polish` in
`crates/tools/src/calibre_polish.rs` (it reuses the same `Calibre::locate` and
timed subprocess runner) — all following the crate's plan/apply contract:
`plan` only reads, `apply` performs exactly the planned actions, and originals
are never modified without an explicit option.

`calibre::Calibre::locate` resolves the binaries once. `stump_tools` stays
`stump_core`-free, so there is deliberately **no** `STUMP_CALIBRE_BIN_DIR`
config key: the location comes from the tool's own `bin_dir` option, else
`PATH`, else the macOS bundle path. The version comes from
`ebook-convert --version`, which calibre renders as `%prog (calibre <version>)`
([`OptionParser`](https://github.com/kovidgoyal/calibre/blob/master/src/calibre/utils/config.py)),
and anything below 7.0 — or a missing, non-executable, or unparseable binary —
raises `ToolError::ExternalToolMissing` carrying an install hint.

### `calibre-convert`

Runs `ebook-convert <source> <target> [extra_args...]` once per file, with a
finite timeout, and captures stderr into the report. The target extension is
what selects calibre's output plugin, so the `to` option maps 1:1 onto it:
`epub`, `kepub`, `azw3`, `mobi`, `pdf`.

<Callout type="info">
	`to: "kepub"` writes `Book.kepub`, because that is the extension
	`ebook-convert` dispatches the KEPUB output plugin from. Kobo sideloading
	wants the file renamed to `Book.kepub.epub`. For EPUB sources prefer the
	in-process `stump_kepub` converter (see
	[Comics transform](/docs/developer/comics-transform)); `calibre-convert` exists for
	sources `stump_kepub` cannot read at all.
</Callout>

Failure handling is deliberate: a non-zero exit, a timeout, or a "success" that
produced no file is a `skipped` entry whose reason carries the exit status and
the captured stderr tail; any partial output file is deleted, because a
truncated book in a library folder is worse than no book. A pre-existing target
is refused at plan time unless `overwrite` is set, and refused again at apply
time (a plan can be minutes stale).

### `calibre-meta`

Runs `ebook-meta <source> --to-opf <tmp>` per file and parses the OPF into a
JSON object shaped like `ExternalMediaMetadata`
(`crates/integrations/metadata/src/types/metadata.rs`), so a consumer can merge
it with provider candidates without a translation layer. Mapping: `dc:title` →
`title`, `dc:creator` → `writers`, `dc:description` → `summary`, `dc:subject` →
`tags`, `dc:date` → `year`/`month`/`day`, `dc:identifier[scheme=ISBN]` → `isbn`
or `isbn_13` by digit count, plus `publisher` and `language` as documented
extensions. Series comes from calibre's own OPF 2.0 extension,
`<meta name="calibre:series">` and `calibre:series_index`
([`opf2.py`](https://github.com/kovidgoyal/calibre/blob/master/src/calibre/ebooks/metadata/opf2.py)).

This pass is **read-only**. Writing metadata back through calibre
(`ebook-meta --from-opf`, `--title`, `--authors`, …) is not implemented: the
in-process `meta-edit` tool already edits `ComicInfo.xml` and EPUB package
metadata under the crate's plan/apply contract, without a subprocess and
without touching anything else in the container.

### `calibre-polish`

Runs `ebook-polish <source> <target> [--flags...]` per book, with a finite
timeout, and maps seven options 1:1 onto the documented flags:
`subset_fonts`, `smarten_punctuation`, `jacket`, `remove_jacket`,
`upgrade_book`, `compress_images`, `add_soft_hyphens` — always emitted in that
order, whatever order they were given in. The output file is optional in the
manual; this adapter always passes it, so calibre never rewrites the file it is
reading. A run with no flag selected is refused (it would rewrite books for no
effect), and a source that is not AZW3, EPUB or KEPUB is reported rather than
attempted, because those are the only formats `ebook-polish` reads.

`in_place` is the one mutating path: the polish is written into a
`.stump-tools-polish-*` directory beside the source (same filesystem), the
original is copied to `<file name>.bak` first, and only finished bytes are
renamed over it. A failure therefore leaves the original byte-identical, and a
backup this run created is removed so the retry is not refused.
`Calibre::locate` only proves `ebook-convert` exists, so the plan additionally
verifies `ebook-polish` is executable and fails once with an install hint
instead of skipping every book at apply time.

Per-option tables for all three tools live in `crates/tools/README.md`.

## boko: the preferred Kindle converter

[boko](https://github.com/zacharydenton/boko) is a native Rust e-book
converter, and for the Kindle formats it is what Stump reaches for first:
`boko-convert` (`crates/tools/src/boko.rs`) converts EPUB, AZW3/KF8 and KFX in
both directions with no plugin, no Kindle Previewer and no Wine, so a headless
server can produce a Kindle file at all. `calibre-convert` stays as the
**fallback** for what boko cannot do.

<Callout type="info">
	Claims here are taken from `boko --help` / `boko convert --help` of a real
	**0.5.0** install and from the format matrix in the
	[project README](https://github.com/zacharydenton/boko#formats).
	`stump_tools` requires **0.5.0 or newer** (`crates/tools/src/boko.rs`,
	`MIN_VERSION`), and compares the whole triple, because a pre-1.0 crate can
	move its CLI in a minor release.
</Callout>

boko is **GPL-3.0-or-later**, so it is governed by exactly the rules in
[Licence: shell out, never link](#licence-shell-out-never-link): it is invoked
as a separate process over `argv` and files, never linked, vendored, bundled,
or added to a `Cargo.toml`, and the operator installs it themselves with
`cargo install boko`. Nothing here removes DRM.

| Format | boko reads | boko writes | Who does it otherwise |
| --- | --- | --- | --- |
| EPUB | yes | yes | `stump_media` reads it natively; `stump_kepub` writes KEPUB |
| AZW3 (KF8) | yes | yes | calibre, slower and with worse KFX support |
| KFX | yes | yes | calibre only via KFX Input/Output plugins + Kindle Previewer |
| MOBI | yes | **no** | calibre (`ebook-convert in.epub out.mobi`) |
| Markdown, plain text | no | yes | not wired up: neither is a library format |

### `boko-convert`

Runs `boko convert --quiet <source> <target> [extra_args...]` once per file,
with a finite timeout, and follows the same failure rules as
[`calibre-convert`](#calibre-convert): a non-zero exit, a timeout, or a
"success" that produced no file is a `skipped` entry carrying the exit status
and the captured stderr tail, and any partial output is deleted. A pre-existing
target is refused at plan time unless `overwrite` is set, and refused again at
apply time.

`--quiet` is not optional. boko prints its progress (`Converting <in> -> <out>`
and `Done.`) on **stderr**, so without it every successful conversion would
come back carrying captured "error output"; `--quiet` suppresses only those
lines, and a real `error: ...` diagnostic still arrives, which is what the
`boko-stderr` warning reports.

The binary is located once, by `boko::locate`: the tool's own `bin_dir` option,
else `PATH`, else `$CARGO_HOME/bin`, else `~/.cargo/bin` — `cargo install` is
boko's only distribution channel and a server started by a service manager
rarely carries that directory in `PATH`. The version comes from
`boko --version`, whose banner is `boko 0.5.0`; a missing, non-executable,
unparseable or too-old binary raises `ToolError::ExternalToolMissing` with a
`cargo install boko` hint.

<Callout type="warn">
	`to: "mobi"` is refused. boko reads MOBI but never writes it — `boko convert
	in.epub out.mobi` exits 1 with `error: MOBI output is not supported; use
	.azw3 instead` — so the request is rejected once at plan time, before boko
	is even located, with a pointer to `calibre-convert`. That beats one failed
	child process per book.
</Callout>

### The send-to-Kindle path

`to: "azw3"` from an EPUB source is the one conversion an operator asks for by
*device* rather than by format, so it has a name: `boko::KindleExport`. It is
not a separate tool — it is `boko-convert` with the pair pinned
(`KindleExport::options`/`::input` build the options blob) — and the planner
attaches an informational `kindle-export` warning to every action that matches,
so the CLI can say out loud that the output is ready to sideload over USB or to
mail to a Kindle address. AZW3 is the safe choice there: every Kindle since the
Paperwhite 1 accepts it. `to: "kfx"` renders better on a current device
(hyphenation, kerning, ligatures) and is the better *reading* format, but it is
the newer container.

Per-option tables live in `crates/tools/README.md`.

## Native Kindle formats: no converter at all

Reading a Kindle book needs neither calibre nor boko. `stump_media` has its own
reader — `crates/media/src/media/format/mobi.rs`, `MobiProcessor` /
`MobiBook` — so `.mobi`, `.prc`, `.azw` and `.azw3` are first-class Stump
media: the scanner accepts them, `ContentType` names them
(`application/x-mobipocket-ebook` and `application/vnd.amazon.mobi8-ebook`),
and the processor dispatch routes them like any other format.

What the reader does:

| Structure | What it gives Stump |
| --- | --- |
| PDB header + record info list | The record table, and the database name as a last-resort title |
| PalmDOC header | Compression type, text record count, and the encryption type the DRM verdict rests on |
| MOBI header | Text encoding (CP1252 or UTF-8), file version (6 vs 8), the first resource record, the HUFF/CDIC record numbers, the trailing-entry flags, and the KF8 index pointers |
| EXTH | `100` author, `101` publisher, `103` description, `104` ISBN, `105` subject, `106` date, `113`/`504` ASIN, `121` KF8 boundary, `201`/`202` cover and thumbnail offsets, `503` title, `524` language |
| PalmDOC LZ77 and HUFF/CDIC | The text of every record, with the multibyte and TBS trailing entries stripped first |
| MOBI 6 markup | Sections split on `<mbp:pagebreak>`; `recindex` images and `filepos` links rewritten onto real names and anchors |
| KF8 `FDST` + `SKEL`/`FRAG` indices | The flow table, then each source file reassembled from its skeleton and its fragments; `kindle:pos:fid:`, `kindle:flow:` and `kindle:embed:` links resolved |
| NCX index (`INDX`/`TAGX`/CNCX) | The navigation tree, each entry resolved onto the section its text position lands in |

A dual-format `.mobi` (a MOBI 6 part and a KF8 part in one Palm database) is
read through its KF8 half, which is what every current reader does; EXTH `121`
names the boundary and every record number in that part's header is relative to
it.

The reader is **clean-room**. Every structure is implemented from the MobileRead
wiki ([MOBI](https://wiki.mobileread.com/wiki/MOBI),
[PDB](https://wiki.mobileread.com/wiki/PDB),
[PalmDOC](https://wiki.mobileread.com/wiki/PalmDOC),
[KF8](https://wiki.mobileread.com/wiki/KF8)) plus, for HUFF/CDIC and the
skeleton/fragment semantics the wiki does not spell out, the MOBI format notes
in [Kindling](https://github.com/ciscoriordan/kindling)'s `README.md` — MIT
licensed, and linked from the MobileRead MOBI page itself as further format
documentation — cross-checked against the record bytes of a real huffdic file.
No code is derived from calibre, KindleUnpack, DeDRM_tools, libmobi or boko, and
each structure cites the page it comes from in its doc comment.

### `mobi2epub`

With the reader in place, converting a Kindle book to EPUB 3 is a container
rewrite rather than a subprocess: `mobi2epub`
(`crates/tools/src/mobi2epub.rs`) takes the reassembled sections, the resource
records, the style-sheet flows, the EXTH metadata and the NCX navigation, and
writes an OCF container to the same rules `epub-check` validates — `mimetype`
first and stored, one `container.xml` rootfile, a package document with a
resolving `unique-identifier`, `dc:title`, `dc:language`, a `nav` document and
a `cover-image` property, plus an EPUB 2 NCX under `spine@toc`. Its own test
asserts zero `epub-check` findings and re-opens the result with
`EpubProcessor`.

That leaves the external converters for what Stump genuinely cannot do:
`boko-convert` for KFX and for *writing* AZW3, `calibre-convert` for MOBI
output, PDF, DOCX, FB2, LIT and PDB, and `calibre-meta`/`calibre-polish` for
writing metadata back into a book.

Nothing here removes DRM: `MobiBook::open` refuses a protected file with the
DRM detector's own verdict, so a `mobi2epub` run over a library reports it as
an `unreadable` warning and converts the rest.

## DRM

A cited technical study of every scheme (ADEPT EPUB/PDF, Kobo obok, Kindle MOBI/KF8/KFX, FairPlay, B&N), how DeDRM_tools handles each, and the legal position lives at [`docs/drm-study.md`](https://github.com/stumpapp/stump/blob/headless-modular/docs/drm-study.md) in the repository (plain Markdown, outside the site build). Its verdict table is why the rules below exist.

**Stump does not ship, bundle, invoke, or implement DRM removal.** There is no
code path in this repository that decrypts a protected book, and none will be
added. `ebook-convert` refuses DRM-protected input, and that refusal is
correct behaviour, not a bug to work around.

What Stump does instead is *detect* protection early and explain it, so an
operator never ends up with an unreadable book in a library.

### DeDRM_tools is a user-side prerequisite

Operators who want to convert or ingest their own purchased files generally use
the [DeDRM_tools](https://github.com/noDRM/DeDRM_tools) calibre plugin. It is a
**third-party, GPL-3, user-installed** plugin that runs **inside the operator's
own calibre**, on their own machine, under their own legal responsibility,
*before* a file is ever placed in a Stump ingest folder.

| Fact | Value |
| --- | --- |
| Current stable release | **v10.0.3**, published 13 July 2022 ([release](https://github.com/noDRM/DeDRM_tools/releases/tag/v10.0.3)) |
| Current beta | **v10.0.9**, a release candidate for v10.1.0, published 2 August 2023 ([README](https://github.com/noDRM/DeDRM_tools/blob/master/README.md)) |
| Declared calibre support | `minimum_calibre_version = (2, 0, 0)` in `DeDRM_plugin/__init__.py`; the Obok (Kobo) plugin declares `(1, 0, 0)` |
| Tested calibre range | The README states the plugin works on calibre 5.x/6.x (Python 3) and 4.x and older (Python 2); the v10.0.3 notes add "Support for Qt 6 / Calibre 6 and newer" |
| Practical caveat | The newest stable predates calibre 7-9. Operators on current calibre are effectively on the beta or alpha builds, and Amazon changes KFX DRM frequently |
| Schemes handled | Amazon, Adobe ADEPT (including the hardened variant), Barnes & Noble, Readium LCP, PDF passwords; Kobo via the separate Obok plugin |

Nothing on this list is a Stump dependency, and none of it is redistributed
here. It is documented so the failure mode — "calibre refused my file" — has an
answer that does not involve this project.

### Ingest detection: the `drm_protected` quality check

The detector is `stump_media::drm` (`crates/media/src/drm.rs`); the ingest
check that consumes it is `core/src/ingest/quality/drm_protected.rs`, with its
weight row in [Modular ingest](/docs/developer/modular-ingest). The check has
**weight 0** and is a blocking gate: a protected file is not a low-quality
book, it is a file the server cannot decode, so it fails with a named scheme,
the exact markers that matched, and a plain-language reason instead of moving a
score.

Containers are identified by magic bytes, never by extension, so a MOBI named
`.epub` is still classified correctly.

**EPUB / OCF ZIP.** `META-INF/encryption.xml` is *not* by itself evidence of
DRM: EPUB font obfuscation uses the same file. Only two algorithms mean
obfuscation — `http://www.idpf.org/2008/embedding`
([EPUB 3.3 §4.4.5](https://www.w3.org/TR/epub-33/#sec-font-obfuscation)) and
Adobe's older `http://ns.adobe.com/pdf/enc#RC`; epubcheck classifies both as
font mangling and everything else as encryption it cannot decrypt
([`OCFEncryptionFileHandler.java`](https://github.com/w3c/epubcheck/blob/main/src/main/java/com/adobe/epubcheck/ocf/OCFEncryptionFileHandler.java)).
The detector therefore allowlists those two and flags any other `EncryptedData`
algorithm. Vendor markers, checked first, follow the rules documented in the
public-domain [`epubtest.py`](https://github.com/noDRM/DeDRM_tools/blob/v10.0.3/DeDRM_plugin/epubtest.py)
(released under the Unlicense) and reimplemented in Rust:

| Scheme | Marker |
| --- | --- |
| Readium LCP | `META-INF/license.lcpl` plus `EncryptedContentKey` in `encryption.xml` |
| Apple FairPlay | `META-INF/sinf.xml` containing `fairplay` |
| Kobo | `<kdrm>` in `META-INF/rights.xml` |
| Adobe ADEPT | `{http://ns.adobe.com/adept}encryptedKey` with base64 length ≥ 172; a `keyType` above 2 marks Adobe's hardened DRM (RMSDK ≥ 10) |
| Adobe PassHash (legacy Barnes & Noble) | the same element with base64 length exactly 64 |
| Adobe ADEPT, no `rights.xml` | an `EncryptedData` algorithm of `http://ns.adobe.com/adept/xmlenc#aes128-cbc-uncompressed` |
| Amazon KFX package | a `.kfx` member starting with `EA 44 52 4D 49 4F 4E EE` (`\xeaDRMION\xee`) |

**MOBI / AZW / PRC.** The authoritative signal is the PalmDOC header's
encryption type, a big-endian `u16` at record-0 offset 12: `0` none, `1` old
single-PID Mobipocket encryption, `2` current Mobipocket/Kindle encryption
([MobileRead MOBI](https://wiki.mobileread.com/wiki/MOBI)). Record 0 is located
through the PDB record-info list at file offset 78, after confirming
`type`+`creator` at offset 60 is `BOOKMOBI` or `TEXtREAd`
([MobileRead PDB](https://wiki.mobileread.com/wiki/PDB#Palm_Database_Format)).
A declared DRM key block — `DRM Offset` at `0xA8` and `DRM Count` at `0xAC`,
both `0xFFFFFFFF` when absent — is a second positive signal, read only when a
`MOBI` header is present at offset `0x10` and its length reaches offset `0xB8`.

EXTH records `209` (tamper-proof keys) and `1`/`2`/`3` (`drm_server_id`,
`drm_commerce_id`, `drm_ebookbase_book_id`) are recorded as evidence but
deliberately **do not** flip the verdict on their own: those records survive in
DRM-free Amazon files, while encryption type `0` proves the text records are
plaintext. This is a considered deviation from a naive "EXTH 209 means DRM"
rule, which would fail perfectly readable books.

**PDF.** `/Encrypt` is required in the trailer dictionary of every encrypted
PDF ([ISO 32000-1 §7.5.5, table 15](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)),
so its presence in a trailer or cross-reference stream is the rule. The token
is only accepted when followed by an indirect reference or an inline
dictionary, so the literal text `/Encrypt` in a content stream cannot fail a
good file. The handler is named from the encryption dictionary's `/Filter`:
`/Standard` is the built-in security handler (§7.6.3), while `/EBX_HANDLER`
(with its `/ADEPT_LICENSE` blob) and `/Adobe.APS` are Adobe DRM handlers
([`ineptpdf.py`](https://github.com/noDRM/DeDRM_tools/blob/v10.0.3/DeDRM_plugin/ineptpdf.py)).
Permissions-only encryption with an empty user password also fails the check:
the pipeline has no password to supply and cannot prove the pages decode.

**Amazon Topaz and bare KFX.** A file whose first bytes are `TPZ` is a Topaz
container, a store-only format; one starting with `\xeaDRMION\xee` is an
encrypted KFX blob whose voucher lives in a sibling file, so it can never be
read alone
([`k4mobidedrm.py`](https://github.com/noDRM/DeDRM_tools/blob/v10.0.3/DeDRM_plugin/k4mobidedrm.py),
[`kfxdedrm.py`](https://github.com/noDRM/DeDRM_tools/blob/v10.0.3/DeDRM_plugin/kfxdedrm.py)).

### Known limits of detection

- **Kobo store kepubs carry no in-file marker.** Their per-file content keys
  live outside the book, in `KoboReader.sqlite`'s `content_keys` table, and the
  file itself is a bare UUID under `.kobo/kepub/`. Absence of markers is
  therefore not proof a Kobo-sourced kepub is unprotected. A filename heuristic
  is deliberately not implemented: in a drop folder it would fail legitimate
  files.
- **A licensed identity is not recorded.** `rights.xml` also carries
  `{adept}user` as `urn:uuid:<uuid>`, which identifies the purchaser's account.
  Quality reports are persisted evidence, so the detector stores the scheme and
  the matched marker path and never that value.
- **An unparseable `encryption.xml` fails.** If the file exists but cannot be
  parsed, the container cannot be shown to be readable, so it is reported as
  unidentified encryption rather than silently passed.
- **Password-protected ZIP/CBZ is out of scope.** It is an archive-level
  concern, not a DRM scheme, and is not detected.

## How to verify

```sh
# DRM detector, synthetic fixtures only (encryption.xml, MOBI/PDB header
# bytes, PDF /Encrypt, DRMION and TPZ magics)
cargo test -p stump_media --no-default-features --lib drm

# The blocking ingest gate and the registry identities it joins
cargo test -p stump_core --lib quality

# calibre adapters against a fake `ebook-convert`/`ebook-meta`/`ebook-polish`
# in a temp dir; no real calibre is installed or required
cargo test -p stump_tools calibre

# boko adapter against a fake `boko` in a temp dir; no real boko required
cargo test -p stump_tools boko
```

None of these tests invoke a real calibre or a real boko, and none of them
require a DRM-protected file to exist. The boko adapter was additionally
verified against a real `boko` 0.5.0: the fixture EPUB
(`The_Lottery_-_Shirley_Jackson.epub`, 32,381 bytes) converted to AZW3 (45,649
bytes), back to EPUB (32,233 bytes) and to KFX (50,883 bytes), each output
reopening with its title, author, language, cover and three spine documents
intact.
