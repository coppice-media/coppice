This page is the single record of client-facing verification. Three evidence
levels are used, and a row never claims more than its evidence:

- **Device** — exercised by a person on a real app against the fixture server
  (`scripts/dev-fixture-server.sh`, headless debug build, LAN address). Date and
  app version are given.
- **Harness** — replayed by the external `komga-compat` Hurl specs
  (`make replay`, `replay-negative-auth`, `replay-readium`,
  `replay-liseur-sync`, `replay-mihon`) or a server-side probe; proves the server
  contract, not the app.
- **Source** — implemented against a pinned client source; no run yet.

Device verification is the only level that counts as "works in the app".

## How a device report is triaged

1. Every failed response logs `method` + `uri` (`TraceLayer` span at DEBUG in
   `apps/server/src/http_server.rs`); read the fixture log via the `stump-komga`
   process logs and match the app's error text to the request.
2. Reproduce with `curl` against the LAN address using the same credentials
   and client headers, then against the pinned client source to confirm the
   expected shape (DTO types, status code).
3. Fix at the adapter boundary (never in Stump's native routes), add a unit
   test, and pin the shape in the relevant Hurl spec so the class cannot
   regress.
4. Redeploy the fixture (`hub restart stump-komga`), re-run `make replay`, and
   ask for a retest. Update this page.

## Known client-side limits (not Stump bugs)

- Liseur has no OPDS 2 parser (see matrix); use the OPDS 1.2 URL.
- Komelia's Readium DTOs are stricter than the Readium spec (`rel` must be a
  string, `published` a calendar date, contributors lists); the Komga alias
  normalizes to those types and the native routes keep the spec shapes.
- The `replay-readium` spec needs a book with no existing reading session for
  its `PUT /progression`; on a book the phone has opened it returns `409` by
  design (older timestamp than the live session).
