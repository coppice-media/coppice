This page maps the protocols the Coppice server speaks. Every supported or
unsupported claim traces to a linked evidence page in
`docs/content/docs/developer/`; route and setting names are taken from the
source files those pages cite. The integration classes and their boundaries are
summarized in [Integration architecture](/docs/developer/integration-architecture).

Evidence labels are exact: **Shipped**, **Contract-tested**, **Device-tested**,
**Source-only**, **Planned**, and **Blocked**. A contract or source record never
becomes app/device proof; [Client verification](/docs/developer/client-verification)
keeps those levels separate.

## OPDS 1.2 (+ Page Streaming Extension)

| | |
| --- | --- |
| What it is | XML catalog/acquisition format with OpenSearch and OPDS-PSE page access ([OPDS 1.2 spec](https://specs.opds.io/opds-1.2), [PSE](https://drafts.opds.io/page-streaming-extension)) |
| Routes + auth | `/opds/v1.2/*` and a key-in-path alias `/opds/{api_key}/v1.2/*`; Basic or session auth, API key allowed in the path |
| Feature + switch | Cargo feature `opds` (compile-time only, included in `headless`/`full`); no runtime route gate. Optional `ENABLE_OPDS_PROGRESSION=true` makes v1.2 page GETs upsert reading progress |
| We implement | Catalog, navigation and search feeds, keep-reading, libraries, series, books, latest feeds, thumbnails, pages, acquisition via `DownloadFile` |
| We deliberately do not | Auto-count page loads as progress unless opted in; strict-compliance mode (open TODO); v1 facets beyond the current set |
| Evidence | **Shipped**, **Contract-tested** — [Provider status](/docs/developer/provider-status), [Server architecture](/docs/developer/server-architecture) |

## OPDS 2.0

| | |
| --- | --- |
| What it is | JSON catalog format with an authentication document and explicit [OPDS Progression 1.0](https://drafts.opds.io/opds-progression-1.0.html) GET/PUT |
| Routes + auth | `/opds/v2.0/*`; Basic or session auth; public auth document advertises Basic. No v2 key-in-path alias |
| Feature + switch | Cargo feature `opds` (compile-time only). Progression PUT is explicit — not affected by `ENABLE_OPDS_PROGRESSION` |
| We implement | Auth document, catalog, search (mixed plus `/libraries/search`, `/series/search`, `/books/search`), browse/groups, book pages, acquisition, and user-scoped progression. Paginated feeds retain `page_size`/`zero_based`, omit `next` at the end, and recover past-end requests to the last populated page; library previews expose `/libraries/{id}/series` |
| We deliberately do not | Facets; OPDS EPUB chapter/resource streaming; a v2 path-key auth alias; a legacy Cantook progression alias or a second locator-shaped OPDS protocol |
| Evidence | **Shipped**, **Contract-tested** — [Provider status](/docs/developer/provider-status) |

### Progression wire contract and smoke recipe

The existing `/opds/v2.0/books/{id}/progression` route now advertises
`rel: "http://opds-spec.org/progression"` and
`type: "application/opds-progression+json"`. Its document is flat:

```json
{
  "modified": "2026-01-28T11:00:00Z",
  "device": { "id": "urn:uuid:reading-client", "name": "Reading client" },
  "progression": 0.23,
  "references": ["#page=20"]
}
```

`modified`, `device`, and the finite whole-publication `progression` in `0..=1`
are required; `title` and `references` are optional. Paged input uses
`#page=N` with 1-based bounds, while EPUB references such as
`chapter.xhtml#anchor` project to the existing native locator. Fraction-only
input preserves richer canonical locator context. No publication-local
position, CSS selector, CFI, quote context, or audio seek point is invented from
a whole-publication fraction.

GET returns 200 with the canonical document, or an empty 200 body before any
head exists. PUT returns 201 for a new head or 200 for an update, with the
resulting document in both cases. The shared conflict rule rejects an update
only when it is more than 60 seconds older **and** moves progression backward.
Invalid bodies/fractions/pages return 400, another user's device returns 403,
and a rejected stale update returns 409, with `application/problem+json`
(`type`, `title`). Auth remains in the existing middleware; its 401 behavior is
not replaced by progression-specific error handling. Reading-state provenance
retains rejected stale input without replacing the winning head.

For a fresh visible paged fixture book with at least 20 pages, use its discovered
progression URL and the normal OPDS Basic credentials:

1. GET before the first write: 200, empty body, stable progression media type.
2. PUT the document above with `Content-Type: application/opds-progression+json`:
   201 with a receipt. GET must match it, including fraction `0.23` (not page/count).
3. PUT a later `modified` and a larger fraction: 200 with the new receipt.
4. PUT a fraction outside `0..=1`, page zero/past the final page, or an invalid
   timestamp: 400 Problem Details and no changed head.
5. PUT a lower fraction at least two minutes before the winning timestamp:
   409 Problem Details; GET and native continue-reading retain the winner.
6. Follow a library's series group's `next` with more than ten series, then
   confirm the last page has no `next`. Exercise `zero_based=true`, exact page
   multiples, empty filtered feeds, and a past-end page whose `previous` reaches
   the last populated page.

This is a selective integration of Stump's immutable
[`7ddbed52`](https://github.com/stumpapp/stump/commit/7ddbed522d95ceb17368fde95e4494b40b07ecc0)
and [`daa509fb`](https://github.com/stumpapp/stump/commit/daa509fbb29e5ec5ee1bb368ec1979319759b34a),
not a replacement of native Readium/GraphQL. The sibling KOReader plugin's
[`35a1d5bc` baseline parser](https://github.com/coppice-media/koreader-coppice/blob/35a1d5bc58615aab79404a21ad01931855e7201e/coppice.koplugin/coppice_opds.lua)
only extracts a progression URL; its dashboard and KOSync keep their native
APIs. The working-tree parser now recognizes the stable relation **and** MIME
type without a Cantook fallback. Home's rich locator mutation/query is unchanged.


## Komga compatibility profile

| | |
| --- | --- |
| What it is | The Komga REST/SSE API subset observed from Komelia 0.19.0, pinned against Komga 1.26.3 OpenAPI, `komga-client` 0.11.0, and Komelia `65f92fde` ([Komga API](https://raw.githubusercontent.com/gotson/komga/1.26.3/komga/docs/openapi.json)) |
| Routes + auth | `/api/v1/*`, `/api/v2/*`, `/sse/v1/events`; Basic (narrowly scoped path list), Bearer, session, `X-API-Key` on Komga paths, `komga-remember-me` cookie; `HEAD /login` is public |
| Feature + switch | Cargo feature `komga` **and** runtime `STUMP_ENABLE_KOMGA=true` (default `false` in release). Both gates must be open |
| We implement | Catalog/search, libraries, books/series, read lists, collections, media/pages/files, Readium manifest + positions + progression, metadata writes, Tachiyomi tracker routes, settings/announcements/users/admin subset, visibility-filtered SSE (mutation events only) |
| We deliberately do not | Full Komga API parity: endpoints outside the Komelia profile, sharing labels, persisted settings PATCH, richer SSE event parity, unsupported search operators; the `/api/v1/{*path}` wildcard only logs and 404s |
| Evidence | **Shipped**, **Contract-tested** — [Komga compatibility](/docs/developer/komga-compat) is authoritative for this profile |

## Kobo sync

| | |
| --- | --- |
| What it is | Kobo device sync protocol (entitlements, reading state, metadata, downloads), reverse-engineered from device traffic ([capabilities](/docs/developer/kobo-sync-capabilities)) |
| Routes + auth | `/kobo/{api_key}/*`; full API key embedded in the device `api_endpoint`, requiring `ACCESS_KOBO_SYNC` (+ `DOWNLOAD_FILE` for files) |
| Feature + switch | Cargo features `kobo` (+ `stump_kepub`), runtime `ENABLE_KOBO_SYNC=true` (default `false` in release). Optional `KOBO_KEPUB_CONVERSION=true` for lazy KEPUB conversion at the existing EPUB URL |
| We implement | Initialization with resource rewriting, full and incremental sync (sync tokens, deltas, EPUB-only filter), ReadingState GET/PUT, metadata, thumbnails, EPUB download, optional KEPUB conversion with cached output |
| We deliberately do not | Real device-auth token persistence (`/v1/auth/device` returns dummy UUIDs); tags/shelves, archive/delete, store proxy, device refresh (catch-all returns `{}`); annotations/highlights; non-EPUB stock sync |
| Evidence | **Shipped**, **Contract-tested** — [Kobo sync capabilities](/docs/developer/kobo-sync-capabilities), [Kobo device database](/docs/developer/kobo-device-database) |

## KOReader sync

| | |
| --- | --- |
| What it is | KOReader's kosync progress-sync plugin protocol (auth probe + document progress by hash) ([kosync source](https://github.com/koreader/koreader/blob/009367df7ac7142bc0d1eb5782d061260b11baa6/plugins/kosync.koplugin/main.lua)) |
| Routes + auth | `/koreader/{api_key}/users/auth`, `/koreader/{api_key}/syncs/progress` (PUT), `/koreader/{api_key}/syncs/progress/{document}` (GET); full API key with `ACCESS_KOREADER_SYNC`; username/password accepted but not validated |
| Feature + switch | Cargo feature `koreader`, runtime `ENABLE_KOREADER_SYNC=true` (default `false` in release). Plus per-library `generateKoreaderHashes` (not an env key) |
| We implement | Auth probe, progress GET/PUT with percentage, device, and raw x-pointer preservation; binary partial-MD5 matching for EPUB and PDF when the library hash flag is on |
| We deliberately do not | Filename-MD5 matching (Coppice never computes that hash); CBZ/ZIP and RAR hashes (generation commented out); x-pointer → Readium locator translation; device management; visibility-scoped PUT media lookup (explicit caveat) |
| Evidence | **Shipped**, **Contract-tested**, **Device-tested** — [Provider status](/docs/developer/provider-status) (KOReader section), [sync platforms](/docs/developer/sync-platforms) |

## liseur-sync

| | |
| --- | --- |
| What it is | Coppice's native sync protocol designed for the Liseur Android reader: token lifecycle, work/edition resolution, position operations, changes feed, sessions, annotations ([integration doc](/docs/developer/liseur-sync-integration)) |
| Routes + auth | `/v1/*` under the liseur-sync tree: public `POST /v1/login`; Bearer device tokens for token, work, operation, change, head, position, session, and annotation routes |
| Feature + switch | Cargo feature `liseur-sync` (compile-time only, included in `headless`/`full`); no runtime gate. Migrations must be applied |
| We implement | Login → one-hour session → device-token mint/revoke (hashed secrets), direct `sha256`/`partial-md5` media matching, idempotent position operations with changes paging and heads, closed sessions, annotation push with CAS and tombstones (adapter-owned tables) |
| We deliberately do not | Enforcement beyond the `sync` scope (other scopes are metadata only); approximate identifier lookup (`source`/`dc`/`ta` stored, never resolved); annotation projection into Coppice `media_annotations`/`bookmarks`; catalog, insights, upload, registration, series-claim routes |
| Evidence | **Shipped**, **Contract-tested**, **Device-tested** — [liseur-sync integration](/docs/developer/liseur-sync-integration), [Liseur providers](/docs/developer/liseur-providers), [Provider status](/docs/developer/provider-status) |

## Native API (GraphQL, REST, Readium)

| | |
| --- | --- |
| What it is | Coppice's own surfaces: GraphQL (`/api/graphql`, playground in debug/web builds), REST under `/api/*`, and native Readium routes (`/readium/*`) for the Readium Web Publication spec ([Readium WP](https://readium.org/webpub)) |
| Routes + auth | Session, Basic, Bearer, or user-scoped API keys (`ACCESS_API_KEYS`); see [API docs](/docs/developer/api) |
| Feature + switch | GraphQL is compiled by the `graphql` feature; the WebUI feature is `webui=["graphql", "graphql/web"]` and therefore implies GraphQL. REST/auth remain in the lean base. See [Server architecture](/docs/developer/server-architecture) |
| We implement | The native client contract: libraries, media, progress, collections, read lists, auth/user management, Readium manifests/positions/progression for EPUB |
| We deliberately do not | Nothing withheld from the native contract — this is the primary API, not a compatibility shim |
| Evidence | **Shipped**, **Contract-tested** — [API](/docs/developer/api), [Server architecture](/docs/developer/server-architecture), [Unified reading state](/docs/developer/unified-reading-state) |

EPUB manifests prefer the OPF spine's `page-progression-direction` for
`metadata.readingProgression`. Recognized `rtl`/`ltr` values are canonical;
absent, `default`, or invalid spine values fall through to the existing
`direction` metadata (also normalized), then to `ltr`. An explicit spine wins
over conflicting metadata. Constructed EPUB regressions cover nested package
paths, namespaced/empty spines, XML escaping, precedence, and retained legacy
fallbacks. For a runtime check, fetch `/api/v2/epub/{id}/manifest.json` for RTL,
LTR, default-without-metadata, and legacy-metadata packages. This ports Stump
[`ddb87886`](https://github.com/stumpapp/stump/commit/ddb8788679d5e108b1f4a34ec364a36d5c619cea).

## Which one should a client use?

- **A Coppice client (web, desktop, mobile):** the native GraphQL/REST/Readium
  API. It is the only surface with the complete product contract; everything
  else is a compatibility subset.
- **A generic catalog client (Panels, Paperback, Kybook, …):** OPDS 1.2 for
  broadest support, or OPDS 2.0 if the client parses JSON catalogs and speaks
  progression PUT. Note the missing v2 features above.
- **A Komga client (Komelia, Mihon):** the Komga profile at `/api/v1`/`/api/v2`,
  or `/komga` if the client is Grimmory-shaped (Liseur). Scope is the Komelia
  profile, not Komga parity.
- **KOReader:** `/koreader/<api_key>` with binary document matching and the
  library hash flag enabled — only EPUB and PDF currently hash.
- **Kobo devices:** `/kobo/<api_key>` with `ENABLE_KOBO_SYNC=true`; expect
  EPUB-only stock sync.
- **Liseur:** the native `/v1` liseur-sync protocol with a Bearer device token.
