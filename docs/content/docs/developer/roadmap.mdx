# Roadmap

This roadmap tracks the current Coppice worktree. **Shipped** describes
implemented behavior; **Contract-tested** and **Device-tested** distinguish
server and real-client evidence; **Source-only** records source inspection.
Neither source review nor a replay is device proof. See the
[client verification matrix](/docs/developer/client-verification) for versions,
dates, and exact test scope, and [integration architecture](/docs/developer/integration-architecture)
for ownership boundaries.

## Open

### Hardware- and account-dependent evidence

The remaining device gaps are a physical Kobo run against `/kobo/{api_key}`,
loading `coppice.koplugin` into KOReader, and delivery to a real Kindle address.
A scoped Audiobookshelf app run does not imply complete protocol parity. Exact
client versions and evidence are recorded in the
[client verification matrix](/docs/developer/client-verification).

### Live metadata credentials

Hardcover, Metron, Open Library, and Google Books metadata clients are
contract-tested against recorded payloads. No live request with a real
credential is recorded. Hardcover account, progress, and journal synchronization
remain separate work, dependent on a stable authenticated account API.

### Incremental upstream candidates

Product-facing documentation uses **Coppice**. Compatibility-sensitive names
remain unchanged: `stump_*`, `stump_server`, `stump_worker`, `@stump/*`,
`STUMP_*`, routes, database fields, app identifiers, and deployment slugs. Any
future upstreamable changes should be split by lifecycle/feature gates, protocol
profiles, provider host, and ingest/tools; see the
[incremental upstream candidate PR sequence](/docs/developer/server-architecture#incremental-upstream-candidate-prs).

### Read-aloud product path

Read-aloud still needs readiness/quality policy, virtual composite behavior,
full synchronized playback and UI, and deployment/device evidence. Optional
worker backends do not imply a bundled server-local machine-learning runtime.
The metadata-backed request ledger, permissions, approvals, visibility,
notifications, and social recommendation handoff are implemented. Managers
with `ACQUIRE_RELEASES` can search and explicitly confirm MAM Bridge grabs for
approved requests; completed downloads are copied into staged ingest and
fulfilled only after Editor approval. The separately authenticated bridge owns
MAM credentials and torrent transport. Coppice has no in-process downloader,
automatic retries, or auto-grab. See the
[acquisition boundary](/docs/guides/integrations/acquisition).

## Future

Unordered candidates; none are promised or scheduled.

### Capabilities not currently offered

- Achievements and a user-configurable dashboard.
- Bulk metadata editing outside staged ingest.
- One reconciled annotation model across native and Liseur CAS rows.
- A Calibre-Web facade for Liseur, including its web-form, login, token, and
  delete contracts.

### Engineering carried forward

- Metadata post-processing: title-language selection, book ordering, score and
  publisher tags, and writing the selected cover.
- Home/Editor follow-up: reuse `metadata_integrations::CrossProviderScorer` for
  best-first provider matches, confidence, provider-qualified external links,
  and same-work grouping. This server change does not build or wire client UI.

- Processor-sized Cargo features so protocol-only builds can omit unrelated
  metadata/PDF/archive dependencies.
- Peer-token federation and the unstarted Komga/Kavita federation provider;
  no ActivityPub track.
- A wasmtime source sandbox, deferred until schema/catalog behavior settles.
- Operations work: observability, backup/restore, readiness, and CI feature
  profiles.
- KOReader hash generation for CBZ/ZIP and RAR.
- Home-library candidate matching/approval, placement policy, additional source
  adapters, and replication/repair.

## Non-goals

- ActivityPub federation; peer-token access is the complete federation model.
- Full Komga API parity; the Komelia/Mihon profile is the target contract, not
  persisted settings, artwork CRUD, or event parity beyond current integrations.
- DRM removal; detection remains non-blocking and does not decrypt content.
- Executing or bundling third-party scraper extensions; source definitions are
  fetched as data and no extension code, Kotlin, or APK is run.
