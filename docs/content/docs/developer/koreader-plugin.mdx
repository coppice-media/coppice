description: Coppice's KOReader client, its protocol surfaces, and the evidence for its upstream and local contracts
---

`coppice.koplugin` is the standalone KOReader companion for Coppice. It browses and downloads the library, configures KOReader's built-in KOSync client, supports explicit progress push/pull, and exports annotations through liseur-sync. It is maintained in sibling repository `koreader-coppice` and is not bundled with the server.

## Credential lanes

Pairing is the only onboarding flow. `POST /api/v2/devices/pair/start` creates a short-lived approval request. The plugin retains the six-digit display code and a scoped poll nonce; `GET /api/v2/devices/pair/{id}/status?nonce=…` returns credentials only after approval. Invalid/expired sessions are cleared; transient failures are retried without discarding the nonce.

| Surface | Credential | Coppice contract |
| --- | --- | --- |
| Library browser | `Authorization: Bearer <API key>` | Authenticated `POST /api/graphql` for catalog, details, counts, and `searchBooks(query, limit)`; `GET /api/v2/reading/continue` for Home; media file and media/series thumbnail routes for downloads/covers. |
| OPDS 2.0 browse/search | HTTP Basic username + API key | The API key is used as the Basic password on `/opds/v2.0/...`. Feed links are rebased to the configured origin before requests. |
| Automatic and explicit KOSync | API key in `/koreader/{key}` | `GET /users/auth`, `PUT /syncs/progress`, and `GET /syncs/progress/{document}`. The key-in-path is required by KOReader's custom-server contract. Checksum mode is `BINARY` (`0`). |
| Annotation lane | Paired liseur token in Bearer header | `GET /v1/token`, `POST /v1/books/{id}/resolve`, `POST /v1/annotations`, `GET /v1/works/{id}/annotations`, and revision-guarded `DELETE /v1/annotations/{id}?rev=…`. |

The client keeps the API key and liseur token in separate settings fields. It does not log the KOSync URL or display request URLs/raw response bodies in error messages. The API key appears in the KOSync URL because that protocol requires it; the polling nonce is scoped to its status request.

## Continue reading and book identity

The dashboard consumes `GET /api/v2/reading/continue`. Current camelCase fields used by the plugin include `mediaId`, `name`, `extension`, `seriesName`, `koreaderHash`, `progression`, `page`, `pages`, and `positionMs`. `progression` is whole-publication `0..=1`; `page` is present only for page-addressed positions; `positionMs` is audio time, not a page number. The route is authenticated and clamps its requested page size to `1..=50`. A downloaded Continue-reading cover opens its valid local file directly; a missing local copy opens book details, and long-press opens details.

The plugin resolves the open document in this order:

1. `coppice_media_id` in the document sidecar, written when a plugin download completes;
2. exact equality between KOReader's `partial_md5_checksum` and a `koreaderHash` in the continue-reading response;
3. an explicit OPDS search and user selection.

It never guesses a book from its title. The per-book annotation state, including ID mappings, acknowledged signatures, revisions, snapshots, and pending queue entries, is stored under `coppice_annotation_sync` in the same sidecar; `coppice_annotation_revs` remains the compatibility revision ledger.

## Cover-first library browser

The plugin's Home and catalog screens use authenticated GraphQL at `POST
/api/graphql` with the paired device API key as a Bearer token. Home combines
`librariesStats`, paginated `recentlyAddedMedia`, and `GET
/api/v2/reading/continue`; the In progress view uses GraphQL `keepReading`.
Search uses `searchBooks(query, limit)` and renders the returned media IDs in
the standard cover grid. Catalog pages include media, libraries, series,
authors, reading-list metadata, and smart lists, then fetch media details and
related series/author rows.

Media and series covers use authenticated routes:
`GET /api/v2/media/{id}/thumbnail` and
`GET /api/v2/series/{id}/thumbnail`. Only visible image covers are fetched and
cached under KOReader's cache directory with a bounded 24 MiB budget. Items
without image artwork use bordered title placeholders rather than requesting a
media thumbnail. Catalog screens show four columns by three rows, count/sort
subtitles, page controls, and a List/Covers toggle.

Home also uses KOReader's ReadHistory for recent local files and reads the
local `statistics.sqlite3` database when present for today, seven-day, and
streak totals; missing statistics storage is silent. The status line reports
time, battery, Wi-Fi, server reachability, and the KOSync progress queue plus
pending annotation count. Recent highlights and notes are the server's four
newest highlights and notes across every book and source (Liseur, Home, Kobo,
KOReader), from GraphQL `annotations(order: RECENT, filter: { kind:
[HIGHLIGHT, NOTE] })`. The last answer is cached in the plugin settings so the
section still shows offline; before the server has ever answered, the device's
own recently synced annotations are shown. Tapping a placed annotation opens its local book and uses KOReader's
bookmark position navigation. The local book is the file whose media id matches
the note, or else any downloaded file with the note book's `koreaderHash`
(byte-identical copies are separate media rows); an unplaceable cached
annotation opens the book and Remote notes, while a book without a local copy opens its details. File
Manager has a direct Main-menu entry; Coppice is first in the Tools menus for
File Manager and Reader. Page changes request full e-ink refreshes and the
library UI uses no transition animations.

Home layout rules: every section is built at the screen width (minus the
scroll container's 3 × bar-width gutter when it scrolls), so there is no
horizontal scrolling; Home fits one screen or at most two, stepping cover
scale, highlight count, and compact text rows down on short screens; swipes
move a full screen, snap to card rows, and stop at the content end.

Physical keys: the browser merges its `Back` binding into the `key_events`
table `InputContainer:_init` creates instead of replacing it, so the Home
binding KOReader master adds there survives, and adds its own on v2026.07.1.
`Browser:onClose` closes the browser (also answering KOReader's exit and
USB-storage `Close` broadcast); `Browser:onHome` defers to master's
`InputContainer:onHome` daisy chain when present and otherwise closes and
re-sends `Home` so the file manager or reader underneath acts on it too. Cover
tiles and cards are plain `InputContainer`s with no bindings of their own.
Highlight chips read `G_reader_settings` `highlight_custom_colors[name].code`
before `Blitbuffer.HIGHLIGHT_COLORS`; an unknown name such as Liseur's `pink`
keeps the plugin's own fallback.

The server exposes library/book and in-progress counts through
`librariesStats`, not daily, seven-day, or streak reading statistics; those
three reading totals are local KOReader data. The native GraphQL API lists
reading-list metadata but has no reading-list membership query, so opening a
reading-list row explains that limitation rather than inventing its books.
**On device** is derived from plugin download sidecars, not server state.

## Progress synchronization

The automatic lane configures KOReader's existing `plugins/kosync.koplugin` by writing `custom_server`, `username`, `userkey`, and `checksum_method` into `kosync.lua`; other KOSync preferences are preserved. The built-in client sends a digest of its user key, which Coppice does not use for authentication; the API key in the custom-server path is the credential. A restart is needed so KOReader's own settings handle reloads the values.

Before first configuration, the plugin records the prior KOSync auth fields. Forgetting the Coppice pairing, changing the configured server, or uninstalling restores those fields only while Coppice still owns the active custom-server value. If a prior plugin version left no backup, its KOSync fields are removed rather than leaving a stale Coppice API key or digest. A user-changed KOSync target is not overwritten.

Explicit push/pull actions use the same KOSync routes. Progress remains a string: a page number for paged documents or a crengine x-pointer for reflowable documents. The client does not coerce one representation into the other.

## Annotation synchronization

The annotation lane uses the paired liseur token. On `ReaderReady` (book open),
**Sync annotations now** pulls `GET /v1/works/{work_id}/annotations?include_deleted=true`;
`onAnnotationsModified` debounces local changes, and document close and suspend
also push. KOReader's existing KOSync client remains the sole progress lane.
These event names and `NetworkMgr:runWhenConnected` behavior were checked
against KOReader commit `9192014d8bd82a91dc1012473be0f238dedfdb54`.

`POST /v1/annotations` carries the stable annotation ID, opaque locator, body,
color, drawer style, `client_ts`, and compare-and-set `base_rev`. The plugin
sends `X-Liseur-Annotation-Capabilities: annotation-color-drawer-v1` on pushes,
work-annotation pulls, and `DELETE /v1/annotations/{id}?rev={revision}` so
extended fields are returned with conflicts and tombstones. The supported
colors are yellow, green, blue, pink, purple, orange, red, olive, cyan, and
gray; styles are lighten, underline, strikeout, and invert. KOReader
`underscore` maps to wire `underline`. Unknown palette/style values are
surfaced as errors rather than silently dropped.

Highlights preserve their color and drawer style; notes preserve body text and
may have a locator; bookmarks have no body, color, or style. KOReader-native
locators restore their original x-pointer/page positions. Readium/Liseur
locators are imported only when excerpt text and optional before/after context
produce one unique text-search match within the specified href or chapter.
Ambiguous, unmatched, or unsupported remote records appear in the read-only
**Remote notes** list instead of being assigned a guessed position. Repeated
pulls use stable IDs and do not duplicate imported annotations. Server
tombstones remove imported items. A KOReader highlight merge (master
`ReaderHighlight:mergeHighlights`) deletes the originals and saves one item
with `item1.datetime`, the joined notes and a widened range and no `coppice_id`,
so the next plan queues a server delete per original and one create for the
merged highlight; when one highlight lay inside the other the merged item has
the outer one's datetime and range, maps back to its id, and is edited in place
(or left alone when nothing changed) while only the inner one is deleted.

Per-book sidecar state persists stable ID mappings, acknowledged signatures,
server revisions, local snapshots, and pending upserts/deletes; the plugin
settings queue retains work for closed books. Network-bound writes use
`NetworkMgr:runWhenConnected` so offline actions survive until connectivity.
Revision conflicts use `client_ts` last-writer-wins: a newer local edit retries
at the server's returned revision; if the server is newer, its record is pulled
and replaces stale local content. A local edit newer than a tombstone is
recreated under a new stable ID; a tombstoned ID is never revived.

On device, check opening and manually syncing a linked book, repeat-pull
deduplication, exact KOReader restoration, unique Readium anchoring, and the
Remote notes fallback. Then add/edit/recolor/restyle/delete annotations while
online and offline; verify automatic push on debounce, close, and suspend,
reconnect retry without duplication, and server deletion removing imported
items. Confirm reading progress still follows KOSync.

## Request and download safety

Server bases reject userinfo, queries, fragments, malformed authorities, control/space characters, and path traversal. Query/path components are percent-encoded. Authenticated requests require the configured origin and JSON responses are capped at 8 MiB. Downloads stream to a unique exclusive temporary file beside the target, bound redirects to the configured origin, remove partial files on failure, and rename only after a complete successful response.

These measures protect the plugin's URL/auth and local-file boundaries; they do not replace TLS peer verification, which remains a KOReader/LuaSec runtime limitation noted above.

## Verification

In sibling repository `koreader-coppice`, run:

```sh
luajit tests/pure_checks.lua
luajit tests/browser_checks.lua
tests/static_checks.sh
for module in coppice.koplugin/*.lua; do luajit -b "$module" /dev/null; done
```

The host suite covers pure URL, settings/error classification, OPDS, KOSync
backup/restore, pairing, bidirectional annotation color/drawer mapping,
per-book queue persistence/idempotence, edit/delete conflicts, merged
highlights, native and Readium anchoring (including ambiguous/saturated-search
refusal), tombstone removal/recreation, catalog mapping/layout/paging/cache
eviction, and migration behavior; the browser harness covers search, the cover
grid, Continue-reading taps, Back/Home/Close key handling against both the
v2026.07.1 and master `InputContainer` shapes, and custom highlight chip
colours. It does not prove the KOReader UI, device filesystem, installed
LuaSec behavior, or physical Kobo/Kindle compatibility; the desktop emulator
smoke (browser open, Home key closing it and landing the file manager on its
home folder, chips tinted with a custom colour) is run by hand.
