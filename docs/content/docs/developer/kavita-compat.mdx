This page is the authoritative specification for Stump's Kavita compatibility profile. It describes the **implemented profile**, not the full Kavita API: the routes and DTOs that the inventoried Kavita clients call, reproduced against Kavita **0.9.1.4** (`develop` `d77d956b9551227d8be2ee488b08f14aa3a341e5`, `openapi.json` captured from the `kavita-ref` container). An endpoint or field not listed here is not implied to be supported.

## Independent Komf Kavita API-mode lane

Kavita is a separate media-server adapter, not a Komga alias. It is an
API-mode lane for the external Komf 2.0.1 workflow, pinned to source commit
[`5ad67370c5da6d94372e7c51bff62dd75053ac64`](https://github.com/Snd-R/komf/commit/5ad67370c5da6d94372e7c51bff62dd75053ac64),
release JAR SHA-256
`f5e01a06938cf1e13a4e9d8211db0569e89e09256072d1bbdf5b04291e809cb9`, and
container
`sndxr/komf:2.0.1@sha256:e48652eb32b06cafce4680c229bdbdb682eb1066e3bdeb2872e9dc99255a5cf6`;
the upstream `komga-client` dependency is 0.10.3. Reads and scans use the
existing Kavita surface, while metadata and upload writes target Kavita's
native series, media, and cover schemas. The sidecar wiring surface is
`/api/kavita/media-server/connected` and `/api/kavita/media-server/libraries`.
Coppice does not embed, compile, or execute Komf's Kotlin; Komf metadata
providers are not automatically exposed as Coppice HTTP endpoints.

The write contract adds case-insensitive registrations for `POST
/api/Series/update`, `/api/Series/metadata`, `/api/Chapter/update`,
`/api/Upload/series`, `/api/Upload/volume`, and `/api/Upload/chapter`.
Metadata writes update native records rather than a shadow store. An empty
chapter upload resets/unlocks the chapter; non-empty series and volume uploads
write the selected native cover and honor lock intent where the native schema
supports it. Automatic Kavita SignalR event mode is unsupported without
current-repository compatibility evidence, so the event listener is disabled.

This lane is independent of the default complete Komga lane. Its evidence must
be labeled separately as source-derived, contract-tested, or runtime-smoked;
Komga `/api/v1` Hurl history does not prove Kavita adapter behavior.

On 2026-09-23 the source-derived manifest at
`scripts/contracts/komf-media-server.json` matched its pinned Kotlin sources.
The direct Kavita Komf Hurl lane passed 37 read, metadata, cover, reset, and
scan requests; the pinned Kavita sidecar separately passed two
connection/library smoke requests. The native route regression
`komf_metadata_and_cover_writes_round_trip_through_native_read_routes`
passed. Stump has no media-level localized-name, imprint, translator, or
location fields; those Kavita write fields are not persisted. Physical Kavita
client and automatic SignalR verification remain separate.

## Enabling

The profile is compiled with the `kavita` Cargo feature (on in `headless` and `full`, off in `minimal`) and mounted when `STUMP_ENABLE_KAVITA=true` (`config.protocols.enable_kavita`, default `false`, `true` in debug builds). Every route lives directly under `/api/<Controller>/...`; Stump's own `/api/v1`, `/api/v2` and `/api/graphql` namespaces are untouched, and `stump_kavita::is_kavita_path` names the boundary.

Kavita's ASP.NET routing is case-insensitive; every route is registered under its canonical casing and fully lower-cased (`/api/Series/all-v2` and `/api/series/all-v2`), which covers every casing the inventoried clients use.

## Authentication

| Credential | Where | Behaviour |
| --- | --- | --- |
| `apiKey` query parameter | any Kavita route | A Stump API key (`stump_...`). Checked first, as Kavita does; an invalid value is `401` even if a valid header is present. |
| `x-api-key` header | any Kavita route | A Stump API key. |
| `Authorization: Bearer <token>` | any Kavita route | A Kavita token minted by `POST /api/Plugin/authenticate` or `POST /api/Account/login` (HS512, claims `name`, `nameid`, `role`, `nbf`, `exp`, `iat`, three-day lifetime, signed with Stump's access-token secret), or a Stump access token / API key. |

`POST /api/Plugin/authenticate?apiKey&pluginName` and `GET /api/Plugin/version?apiKey` validate the Stump API key; `POST /api/Account/login` accepts `{apiKey}` or `{username, password}`. The `UserDto.apiKey` echoes the key used to log in and is `null` after a password login (Stump never reveals stored keys). `refreshToken` is `null`; there is no refresh endpoint in this wave. `preferences` is the Kavita 0.9.1.4 default object; `roles` are `Admin` (server owner), `Login`, and `Download` (`DownloadFile` permission).

Unauthenticated requests answer `401` with `WWW-Authenticate: Bearer` and an empty body, like Kavita. Missing, deleted and hidden entities are indistinguishable.

## Identity mapping

Kavita ids are integers. The `kavita_ids` table (migration `m20260912_000000_add_kavita_compat`) allocates one stable id per `(kind, stump_id)`; ids never change or get reused, and every kind draws from one sequence so an id names exactly one entity (`KavitaIds::lookup_any`). Kinds: `library`, `series`, `book_series`, `media`, `user`, plus the `install` id reported by `server-info-slim`.

What a Kavita series is depends on the library type, exactly as in Kavita itself:

| Stump library type | Kavita `type` | Kavita series | Series id |
| --- | --- | --- | --- |
| Manga, Manhwa, Webtoon, Mixed (`0`), Comic (`1`) | grouped | one Stump series; its media are the volumes | `series` kind keyed by the Stump series id |
| Book, WebNovel (`2`), LightNovel (`4`) | book | **every media item is its own series** (Kavita's Book/LightNovel scanner makes one series per file); the Stump series is only the folder it is filed under | `book_series` kind keyed by the media id — distinct from the media's `media` id, which stays its volume/chapter id |

Every route that takes a `seriesId` (`/api/Series/{id}`, `volumes`, `series-detail`, `metadata`, `continue-point`, `has-progress`, `mark-read`/`mark-unread`, `mark-volume-*`, `remove-from-on-deck`, `Image/series-cover`, `Tachiyomi/*`) resolves both kinds through one lookup; a `book_series` id whose media has since left a Book library answers as unknown. Listings (`all-v2`, `v2`, `recently-added-v2`) select Stump series outside Book libraries `UNION ALL` media inside them, so filters, sorts, the `Pagination` total and paging apply to both kinds in one SQL pass (`routes/query.rs` `select_series_keys`); `on-deck` and `recently-updated-series` expand Book-library series the same way (a recently added book is its own group with `count: 1`).

| Kavita | Stump |
| --- | --- |
| Library | Library. `type` from the library's `library_type`: Comic→`1`, Book/WebNovel→`2`, LightNovel→`4`, everything else (Manga, Manhwa, Webtoon, Mixed)→`0`. `folders` is the library path; `libraryFileTypes` is always Archive/Epub/Pdf/Images. |
| Series (grouped) | Series. `name` is the metadata title or series name, `sortName` the metadata sort title, `pages`/`pagesRead` are sums over the media, `format` follows the first media's extension (Archive `1`, Epub `3`, Pdf `4`, Image `0`, Unknown `2`). |
| Series (book) | One media item. `name` = `originalName` = the media metadata title, else the file name without extension; `sortName` the media sort title; `folderPath`/`lowestFolderPath` the folder holding the file; `created`/`lastFolderScanned` the file's timestamps; `pages`, `pagesRead`, `format`, `coverImage` from that file. Copied field-for-field from `kavita-ref` (`komga-compat/kavita/capture/book-library.json`, `book_series_list`). |
| Volume | One per media item, in Kavita's single-file-volume shape: `minNumber == maxNumber == number`, one chapter. Grouped: the number is the media metadata volume, else an integral metadata number, else the media's 1-based position in name order. Book: the loose-leaf volume `-100000` (`Parser.LooseLeafVolumeNumber`; `name: "-100000"`), as Kavita builds for a file that carries no volume. |
| Chapter | The media item again with the same id as its volume (`volumeId == chapterId`), `number: "-100000"` / `minNumber: -100000` (`Parser.DefaultChapterNumber`), one `MangaFileDto` (`extension` with the leading dot, `koreaderHash`). Grouped: `isSpecial: false`, `range` the file name, `sortOrder` the volume number, `totalCount: 0`. Book: `isSpecial: true`, `range` and `title` the title (file name when the file has none, `titleName` then empty), `sortOrder: -100000`, `count: 0`, `totalCount: 1`, `volumeTitle: ""`, `publicationStatus: 0` (`book_volumes_4`). |
| Series detail | Grouped: `volumes` in volume order, `specials`/`chapters`/`storylineChapters` empty. Book: the chapter under `specials`, `volumes` empty, `totalCount: 1`, `unreadCount` `1` while unread, `libraryType` `2`/`4` (`book_series_detail_4`, `lightnovel_series_detail_6`). |
| Series metadata | Grouped: the union of the series metadata row and the metadata of **every** media item under it, the way `SeriesMetadataService` recomputes a series from its chapters. Book: from that one media's metadata, `maxCount: 1`, `totalCount: 1`, `publicationStatus: 2` (Completed — Kavita's scanner marks a series whose count matches its max complete) (`book_metadata_4`). See [Metadata mapping](#metadata-mapping). |
| People, genres | Kavita entities with ids; Stump stores comma-separated text. Ids are a stable FNV-1a hash of the lower-cased name (`mapper::name_id`) and round-trip through `Metadata/genres`, `Metadata/people` and the series filters. Tags use Stump's real tag ids (`tags.id`), so a tag chip a client taps filters correctly whether the tag sits on the series row or on a file. |
| Age rating | Stump's minimum age mapped onto the closest `AgeRating` (`AgeRating::from_min_age`). |
| Publication status | Grouped: Stump's free-text status folded onto `PublicationStatus` (`ongoing`/`continuing` `0`, `hiatus` `1`, `completed` `2`, `cancelled` `3`, `ended` `4`). Book: always `2`. |

Timestamps render as .NET `DateTime` strings without an offset and with seven fractional digits (`2026-09-05T00:30:44.5870451`); unset values are `0001-01-01T00:00:00`. Local and UTC pairs (`created`/`createdUtc`) both carry the UTC instant. Whole floats render without a fractional part (`100000`, not `100000.0`).

## Metadata mapping

Kavita's `SeriesMetadataService` recomputes a series' metadata from **every chapter under it**, so `GET /api/Series/metadata` here is the union of the Stump `series_metadata` row and the `media_metadata` of every media item backing the series: values are ordered by first appearance (series row first, then the files in volume order) and de-duplicated case-insensitively. Scalars prefer the series row and fall back to the files. A book series is one file presented as its own series, so it takes that file's metadata alone.

This is what the clients render. Kamigura's series detail shows `summary`, the eight credit roles it merges into one "Credits" chip row (`writers`, `coverArtists`, `pencillers`, `inkers`, `colorists`, `letterers`, `editors`, `translators` — `series/internal/SeriesDetailSummary.kt:265-284`), `publishers` and `imprints` under "Publisher" (`:104-105,182-193`), `genres` (`:106-110,248-253`) and `tags` (`:111-115,254-259`), plus `releaseYear` and `publicationStatus` in its meta lines (`series/internal/SeriesMetadataText.kt:24-28,133-142`). Its issue sheet shows the chapter's `volumeTitle`/`titleName`/`title` (`series/IssueDetailSideSheet.kt:381-397`), `releaseDate` (`series/internal/ChapterText.kt:31-37`), `pages` and `summary` (`series/IssueDetailSideSheet.kt:173-174,199`).

## Reading progress

Kavita's `pageNum` is the zero-based page being read and `pageNum == pages` means finished; Stump's reading session stores the one-based page and completion. `pagesRead` is `pages` for a finished session, `end_page - 1` for an open one, and `percentage × pages` for locator-only (EPUB) sessions. `POST /api/Reader/progress` writes `pageNum + 1` and marks the session finished when `pageNum >= pages`, ignores `pageNum: 0` with no existing progress and unchanged pages (like `ReaderService.SaveReadingProgress`), and stores `bookScrollId` per user and media in `kavita_progress`. Every write also updates the unified reading head (`SourceProtocol::Kavita`). `mark-unread`/`mark-volume-unread` delete the user's sessions for the affected media.

`GET /api/Reader/continue-point` follows `ReaderService.GetContinuePoint` over the volumes in order (a book has one). `GET /api/Tachiyomi/latest-chapter` returns `204` without progress and otherwise a chapter whose `number` is the volume number divided by 10 000 (`R` formatting), which `POST /api/Tachiyomi/mark-chapter-until-as-read?chapterNumber` decodes back (`0` is ignored, values `< 1` are encoded volumes). A book is a loose-leaf volume, so Kavita returns its chapter unencoded (`number: "-100000"`, files included) and `mark-chapter-until-as-read` never marks it in either form — both reproduced (`kavita-ref` `book_latest_chapter_4`, `tachiyomi_mark_until_probe`). Progress written through a book's chapter lands on the media's `reading_sessions` row like every other protocol.

## Series filters

`POST /api/Series/all-v2` and `/v2` accept `SeriesFilterV2Dto` with `PageNumber`/`PageSize` (default: page 1, everything; `0` means everything) and answer with the `Pagination` header (`{currentPage, itemsPerPage, totalItems, totalPages}`, exposed through `Access-Control-Expose-Headers`). Supported statements: `SeriesName`, `Summary`, `Path`, `FilePath`, `PublicationStatus`, `Languages`, `AgeRating`, `Tags`, `Genres`, all people fields (ids or, as the extension sends them, names), `Libraries`, `Formats`, `ReleaseYear`, `ReadProgress`. Comparisons are validated per field as in `SeriesFilter.cs` (an inapplicable comparison is `400`, where Kavita answers `500`). Sorts: `SortName`, `CreatedDate`, `LastModifiedDate`, `LastChapterAdded`, `TimeToRead` (page count), `ReleaseYear`, `Random`, `ReadProgress`, `UnreadChapterCount`; `AverageRating`/`UserRating` fall back to sort name. `limitTo` truncates after sorting. Fields with no Stump equivalent (`UserRating`, `AverageRating`, `ReadTime`, `ReadingDate`, `ReadLast`, `FileSize`, `WantToRead`, `CollectionTags`, `CollapseSeriesRelationships`) and unknown field numbers are ignored. Every statement and sort is built twice (`routes/series_filter.rs` `Target`): against `series`/`series_metadata` for grouped series and against `media`/`media_metadata` for books, so a `SeriesName` match finds the book itself rather than the folder it is filed under; `Path` compares the book's file path, `PublicationStatus` treats books as `Completed`, and `Tags` matches no book (`IsEmpty` matches every book).

`GET /api/Filter` is always empty and `POST /api/Filter/decode` implements `SmartFilterHelper.Decode` (statement separator U+FFFD, inner separator U+00A6, double URL escaping), verified against `kavita-ref`.


## Dashboard streams (Kamigura/Kover wave)

`POST /api/Series/on-deck?PageNumber&PageSize&libraryId` (libraryId `0` = all) answers with the user's in-progress series — `pagesRead > 0 && pagesRead < pages` summed over the media's reading sessions, newest progress first, then most recently added chapter — as `SeriesDto[]` with the `Pagination` header, echoing the requested `PageNumber` verbatim (Kamigura sends `PageNumber=0` and the reference answers `currentPage: 0`). `POST /api/Series/remove-from-on-deck?seriesId` (`200`, `400` for an unknown series) records a per-user removal in `kavita_on_deck_removals` (migration `m20260922_kavita_on_deck_removals`, the `AppUserOnDeckRemoval` equivalent) keyed by the Kavita series' Stump target — `(target_kind, target_id)` = `series` + series id, or `media` + media id for a book — that hides exactly that series from on-deck until the next `Reader/progress` or mark-read event on it, mirroring `ClearOnDeckRemovalAsync`. Targets carry no foreign key: read events delete the row, and a row for a deleted target hides nothing because the target no longer lists.

Deviations from Kavita's `GetOnDeckAsync`: Stump applies no recent-activity window (Kavita restricts to 30 days of progress / 7 days of chapter adds, `OnDeckProgressDays`/`OnDeckUpdateDays`), so an in-progress series stays on deck however stale. `POST /api/Series/recently-added-v2` runs the `SeriesFilterV2Dto` pipeline with `Created` descending as the primary sort; `POST /api/Series/recently-updated-series` returns `GroupedSeriesDto[]` for media created within the last 12 days, grouped per series with an added-chapter `count` and a 0-based `id`, `chapterId`/`volumeId` `0` as captured from `kavita-ref`. `GET /api/Account` returns the full login `UserDto` with `token: null` (as Kavita documents); `apiKey` is only echoed when the request authenticated with it, because Stump stores API keys hashed. `GET /api/Account/roles` answers the full `PolicyConstants` role list and `GET /api/Users/has-library-access?libraryId` maps the Kavita library id and checks Stump's `library_exclusions`.

## EPUB readers and the image lane

Kavita splits reading in two: `GET /api/Reader/image?chapterId&page` serves rendered page images, and `GET /api/Book/{chapterId}/book-page?page` serves an HTML fragment. An EPUB has no image lane at all — `kavita-ref` 0.9.1.4 answers `404` for `Reader/image` on its EPUB chapter at every page and under every flag, including after the `chapter-info?extractPdf=true` extraction that does turn a PDF chapter into `200 image/png` — and Stump reproduces that (an EPUB `chapter-info` still reports a positive `pages`, as the reference's does). A PDF keeps serving images: Stump renders PDF pages on demand instead of pre-extracting them, so it answers before the extraction step rather than 404 until it.

That divides the inventoried clients:

| Client | Reader | EPUB |
| --- | --- | --- |
| Inkita, Kover | `Book/{id}/book-page` in a `WebView` | reads EPUBs |
| Turnleaf | `Book/{id}/book-page` | reads EPUBs |
| Kamigura | `Reader/image` only | **cannot open an EPUB** |
| extension, Mihon, Kamare | `Reader/image` | comics only by design |

Kamigura ships no book reader and no `Book/*` client: `KavitaApi.kt` declares no `api/Book` route, its `SeriesDto` carries no `format`, the tree contains no `WebView`, and the only page source is Coil over `Reader/image` (`reader/ReaderScreen.kt:575` for the page count, `:687-692` with `KavitaClient.kt:196-199` for the URL). EPUB is refused outright even for offline download (`download/OfflineIssueRepository.kt:580-581`). It therefore opens an EPUB chapter into an image reader that can never paint it, against Kavita and Stump alike. Use Inkita, Kover or Turnleaf for EPUB libraries.

`book-page` answers with the spine document's **body as a fragment**, never a whole document, matching `kavita-ref`: `<div class="<body classes>">`, the document's CSS inlined as a single `<style>` scoped under `.book-content` (a leading `body`/`html` selector becomes the scope itself and `@page` is dropped, so a book's page box cannot fight the reader's layout), then the body markup with its own `<style>`/`<link>` elements removed. Resource references are absolute — `//{host}/api/book/{chapterId}/book-resources?apiKey=<key>&file=<name>`, host from the request — and carry the API key only when the request presented one, because Stump stores keys hashed; Inkita appends its own idempotently (`ui/reader/screen/ReaderScreen.kt:1109-1112`) and loads the fragment with the server as the `WebView` base URL (`:1304-1305`).

## Downloads

`DownloadController` sits behind Kavita's `RequireDownloadRole` policy, which Stump satisfies with the `DownloadFile` permission — the one `Account/roles` already reports as the `Download` role. Every route in the controller, `chapter-size` included, is a bare `403` without it, as on `kavita-ref` for a `Pleb`/`Login` user; a server owner bypasses the check like every other Stump permission.

A Stump media item is both the Kavita volume and its single chapter, so `Download/chapter?chapterId=` and `Download/volume?volumeId=` are the same download.

| Route | Body | Content type |
| --- | --- | --- |
| `GET /api/Download/chapter?chapterId` | the media file itself | by extension: `application/epub+zip`, `application/x-cbz`, `application/x-cbr`, `application/pdf`, else `application/octet-stream` |
| `GET /api/Download/volume?volumeId` | the same file (`volumeId == chapterId`) | as above |
| `GET /api/Download/series?seriesId` | the lone file when the series holds one — which is every Book/LightNovel series, resolved through the shared book-series id path — otherwise a stored zip of every file | the file's type, or `application/octet-stream` for the zip |
| `GET /api/Download/chapter-size?chapterId` | `media.size` in bytes | `application/json` |

A stored file streams through the same file service every other Stump download uses, so `Content-Length`, `Accept-Ranges: bytes`, `Range` → `206 Partial Content` and conditional requests all keep working; only the Kavita labels are added on top. `Content-Disposition` is the pair `kavita-ref` emits — `attachment; filename="multi v01.cbz"; filename*=UTF-8''multi%20v01.cbz` — with the plain name always quoted, and the name is the file's own name on disk. Series-zip entry names are made unique within the archive, because a series can legitimately hold two identically named files in different folders and a duplicate entry makes the zip undecodable for half the clients that read it. Entries are **stored, not deflated**, as `kavita-ref` does: every payload here (CBZ, EPUB, PDF) is already compressed.

A provider-backed (`provider://`) media item has no file to stream, so its download is a CBZ built on the fly from its pages through the virtual resolver — the same thing Komga's book download does for one — named after the chapter and served whole (no `Range`, since there is no file to range over). `chapter-size` answers `200` with `0` for a chapter it cannot resolve, matching `kavita-ref` (`chapterId=9999` → `0`); the download routes answer `404`.

## Known deviations

- `/api/Library/{id}` and `/api/Volume/{id}` are served although Kavita 0.9.1.4 itself answers `404` for the path form (the extension requests them and degrades on failure).
- EPUB `pages` is Stump's synthetic Readium page count, not Kavita's spine length; `pageNum` for EPUBs therefore addresses Stump pages. `GET /api/Book/{chapterId}/book-page?page=` keeps that same space: a spine item is worth `ceil(compressed_size / 1KiB)` pages (at least one), so page `N` resolves to the spine item whose budget covers it and every `0..pages-1` is addressable. `book-info.pages` is the chapter's `pages`, and a `chapters[]` navigation entry sits on the first page of the spine item it points at. The fragment shape itself is the reference's, described under [EPUB readers and the image lane](#epub-readers-and-the-image-lane).
- `wordCount`, hours-to-read, ratings, colours, external ids and locks are zero/false/null; `coverImage` names (`v{id}_c{id}.png`) are synthetic and only need to be non-blank.
- `Plugin/authenticate` returns the real mapped user id where Kavita returns `0`.
- `firstInstallDate` is `null` (Stump keeps no install timestamp); `isDocker` reports `/.dockerenv`.
- In Book/LightNovel libraries every file is its own series, always. Kavita additionally groups EPUBs whose OPF carries `calibre:series` + `calibre:series_index` (or `belongs-to-collection` + `group-position`) into one series with numbered volumes; Stump does not, so such books list individually with the loose-leaf volume. In Manga/Comic libraries an EPUB keeps Stump's grouped volume shape (`number` from metadata or position, `isSpecial: false`), where Kavita would build the same loose-leaf special it builds for books.
- A book's `folderPath` filter (`Path`) compares against the file path, so `Equal` on the folder does not match; `Matches`/`BeginsWith` do.
- `ChapterInfoDto.libraryType` is always `0` (`Manga`). This is not a Stump gap: `ReaderController.GetChapterInfo` never assigns the field, so `kavita-ref` reports `0` for a Comic-library and a Book-library chapter alike.
- `chapter-info` page dimensions come from Stump's recorded page analysis (`media_analysis`); a stored file that has not been analysed reports `[]`/`{}` with `includeDimensions=true`, and `fileName` is the name `GET /api/Reader/image` serves the page under (`{media}-{page}.img`) because Stump stores no per-page archive entry name. `isWide` is `width > height` and `doublePairs` is `ReaderService.GetPairs` over those dimensions. `extractPdf` is accepted and ignored: Stump renders PDF pages on demand rather than pre-extracting them.
- A **provider-backed** chapter (`provider://`, e.g. a MangaDex source) has no page analysis to report, and not because the job skips it: the analysis job runs, tries to read every page off the `provider://` path as a file, fails on all of them, and writes the `media_analysis` row anyway with an **empty** dimension list (`core/src/filesystem/media/analysis/analyze.rs:219-257,308`). So the fallback keys on an empty list, not on a missing row — keying on the row is what left `pageDimensions: []` on every MangaDex chapter. Those dimensions are **probed** instead: one page is fetched through the same virtual resolver `GET /api/Reader/image` uses, its image header read with `imagesize` (header only, no decode), and that size reported for every page of the chapter.

  The page probed is the **middle** one, not page 1. Kavita's page 0 of a scanlation chapter is usually the group's banner or a colour splash rather than a page of the story — 1268×634 for two of the three MangaDex chapters in the fixture, against a 1671×2400 interior — so measuring it would mark every page `isWide` and cost the reader its spreads for the whole chapter. A genuine double-page spread mid-chapter is still reported at the interior size and so still pairs; that is the residual cost of a single fetch, and it is what an empty array does today for *every* page. Exact per-page dimensions would take one remote fetch per page (~1.4 s each, measured), which no client would wait for.

  Cost: one fetch, and the provider host caches the page — measured against the fixture's MangaDex source, the first `chapter-info` of a chapter takes 1.01 s and every later one 8 ms. A provider that refuses the page (the fixture's One Piece chapter is no longer served: `Reader/image` → `404 "Chapter is not available from mangadex-en"`) or answers something without a readable image header degrades to `[]`/`{}` with a `200`, because the reader needs `pages` to open the chapter at all and opens fine without the layout hints.

  This is what the array is for: Kamigura turns it into the map every page decision reads (`reader/ReaderScreen.kt:575-578` → `reader/internal/ReaderLayout.kt:33-53` pairs a spread only when neither side is wide, `reader/internal/ReaderPrefetchPlan.kt:73-88` sizes the decode from the source pixels), and `GetPairs` cannot emit a single pairing from an empty array.
- The reading profile is always Kavita's `Default Profile` (`kind: 0`), copied field-for-field from `kavita-ref`: Stump keeps no per-user, per-series or per-device reader settings, so `skipImplicit` and `deviceId` change nothing.
- Want-to-read membership is stored in Stump's own `favorite_series`/`favorite_media` (a Book-library series is a media item), so the shelf is the same one the native API shows rather than a Kavita-only side table.
- A Kavita reading list is a Stump reading list; `update-by-series`/`-volume`/`-chapter` append through the canonical container service and answer `200` with `Updated` or `Nothing to do`. Stump has no promoted lists, CBL provenance, list age rating or computed date range, so `promoted`, `provider`, `sourcePath`, `shaHash`, `ageRating`, `startingYear`/`endingYear` and `totalItemsAtImport` keep the values `kavita-ref` shows for a freshly created list, and `includePromoted` adds nothing. `DELETE /api/ReadingList?readingListId=` deletes from the caller's own lists and answers `200 "Reading List was deleted"` whether or not anything was deleted — `kavita-ref` says it for an id that never existed too — so a readable list the caller does not own is left alone rather than refused. `ReadingList/lists` and `lists-for-series` order by title with the Kavita id breaking ties, so lists that share a title keep a stable place across refreshes.
- `POST /api/Series/series-by-ids` answers the visible series among `seriesIds` sorted by `sortName` (`GetSeriesDtoForIdsAsync`), skipping unknown ids and rejecting a body without `seriesIds` with `400 "Invalid payload"`, both as `kavita-ref` does. It has to be registered as a literal segment: `POST` on the unregistered path falls through to `GET /api/Series/{seriesId}` and answers `405`, which is what left Kamigura's reading-list grid empty (it maps `ReadingList/items` onto series ids and asks for them in one call, `library/SearchScreens.kt:637-639`).
- `Download/chapter-size` answers `200` with `0` for a chapter it cannot resolve, matching `kavita-ref` (`chapterId=9999` → `0`).
- `GET /api/Search/search` matches a case-insensitive substring per group (libraries by name, files by path, chapters by name, bookmarks by their series name, annotations by their note) where Kavita matches a *normalized* substring — Stump stores no normalized name columns, so punctuation is not folded. Each group is capped at 30 rows: Kavita's `SearchService` caps too, but its constant is not observable from the reference fixture. Annotation highlights live inside the Readium locator JSON and are not searched; only the note is. A blank `queryString` is `400` like `kavita-ref`, in Stump's `ApiException` envelope rather than ASP.NET's `ProblemDetails`.
- Bookmarks are Stump's own `bookmarks` rows (`media_id` + `page`), so a bookmark set in Stump's UI shows up in a Kavita client and back. `volumeId == chapterId`, `imageOffset` is always `0` (Kavita's split-image offset has no Stump equivalent) and `xPath` carries the Readium fragment of a locator-addressed bookmark. `POST /api/Reader/bookmark` is idempotent per `(chapter, page)`. `GET /api/Reader/all-bookmarks` answers `404`, matching `kavita-ref`, where the route is `POST`-only. `bookmark-image` re-renders the page from the file instead of serving a stored image copy, and requires the `apiKey` query parameter exactly as Kavita does.
- `POST /api/Reader/bookmark`/`unbookmark` and `GET /api/Reader/chapter-bookmarks` are served although no inventoried client calls them (Kamigura posts `all-bookmarks`, Inkita gets `series-bookmarks`): without a write path a Kavita client can never fill the bookmark grid it renders, and all four share one projection.
- A Kavita collection is a Stump collection. Stump has no promotion, colours, cover lock, age rating or external (MAL/scrobble) source, so `promoted`, `ageRating`, `coverImage`, `primaryColor`, `secondaryColor`, `source`, `sourceUrl`, `totalSourceCount`, `missingSeriesFromSource` and `lastSyncUtc` keep the values `kavita-ref` shows for a locally created collection, and `ownedOnly=false` lists every collection (Kavita's "mine plus promoted" degenerates when nothing can be promoted). Adding a Book-library Kavita series to a collection adds the Stump series holding the file, because collection membership is per series — the same compromise the Kobo shelf write-back makes.
- `POST /api/Series/scan` and `/refresh-metadata` enqueue Stump's series-scan job (metadata refresh always forces a rebuild, because Stump reads metadata during a scan), `/analyze` enqueues the media-analysis job scoped to the series, and `POST /api/Library/scan` enqueues the library-scan job Komga's `/api/v1/libraries/{id}/scan` uses. All four answer `200` with an empty body, including for an unknown series or library, exactly as `kavita-ref` does. `forceColorscape` is accepted and ignored (Stump extracts no cover colours). `POST /api/Library/scan-folder` is not served: no inventoried client calls it, and it is a `POST` with a `ScanFolderDto` body on the reference rather than the `GET` some older clients used.
- `GET /api/Stats/user/{userId}/read` and `GET /api/Stats/user/reading-history` are the **pre-0.9 spellings Inkita is pinned to**; `kavita-ref` 0.9.1.4 answers `404` for both and exposes `/api/Stats/user-read?userId` and `/api/Stats/reading-history` instead. The response is the reference's `UserReadStatistics` field set plus the two fields Inkita reads (`chaptersRead`, `lastActive`). Numbers come from Stump's reading sessions with the same `pagesRead` translation the rest of the profile uses; `totalWordsRead` is `0` (Stump records no word counts) and `avgHoursPerWeekSpentReading` is elapsed hours over the weeks since the first session. A non-owner asking about another user is `403`. `reading-history` emits one event per session, newest first, with `chapterNumber: -100000` because every Stump file is a single-file volume holding one chapter. The other 30 `Stats/*` routes (`reading-count-by-day`, `pages-per-year`, `words-per-year`, the server and breakdown families) are not served.
- `/api/Annotation/*` is read-only, because Inkita only reads annotations. `GET /api/Annotation/all-for-series?seriesId` and `GET /api/Annotation/all?chapterId` project Stump's `media_annotations`: the locator's `text.highlight` becomes `selectedText` with its surrounding context in `context`, the note becomes `comment`/`commentHtml`/`commentPlainText` (identical, since Stump stores plain text), the locator fragment becomes `xPath` and its `position` becomes `pageNumber`. Stump records no sharing, so `likes` is empty, `containsSpoiler` is `false`, `endingXPath` is `null`, `selectedSlotIndex` is `0` and `highlightCount` is `1` for a highlight. `create`, `update`, `like`, `unlike`, `bulk-delete`, `all-filtered`, the export routes and `DELETE /api/Annotation` stay unmounted and answer `404`. The reference's OpenAPI types `all-for-series` as a single `AnnotationDto`, but the route returns an array — the array is reproduced.
- `kavita_ids` gained the `collection`, `annotation` and `bookmark` kinds; no migration was needed because the table is generic on `kind`.
- `Reader/bookmark-image` re-renders the bookmarked page through the same projection as `Reader/image`, so a bookmark inside an EPUB is `404` for the same reason the page image is; Kavita only ever creates bookmarks from its image reader.
- A non-numeric segment under `/api/Library/{id}` (`scan-folder`, `scan-all`, `refresh-metadata`, …) answers `404`, not the `400` a malformed path parameter would give: `matchit` cannot host a path parameter and a catch-all at the same position, so `LibraryController` sub-paths are reported as missing routes the way every other unimplemented controller is.
