This page records the current, feature-gated Stump implementation of the
liseur-sync native protocol. The `liseur-sync` server feature exposes login,
token minting and device-token introspection, catalog folders/books, covers,
downloads, catalog work resolution, sync operations, position changes,
sessions, and annotation revision endpoints. Upload/delete, insights, token
listing/scope updates, and series-claim mutation routes remain deferred. The
wire contract is grounded in the pinned liseur-sync
`f8ce32b79aca0cddde84e9004fedde121fb77365` OpenAPI and implementation; Stump
specific status is called out below.

The server remains authoritative and the adapter remains optional, consistent
with the [server architecture](/docs/developer/server-architecture). The implementation
stores a user-scoped sync identity and revision bridge; it does not make a
remote liseur-sync service a prerequisite for local Stump annotations.

## Current implementation status

| Area | Status | Stump implementation |
| --- | --- | --- |
| Authentication | **implemented (session + device tokens)** | `POST /v1/login` verifies Stump credentials and returns a one-hour token-management session bearer with no scopes. `POST /v1/tokens` accepts that session and returns a one-time device secret; `GET /v1/token` describes a device token. |
| Token management | **implemented (mint, introspect, revoke)** | Device rows store a generated device ID, name, canonical scopes, hashed secret, expiry, and revocation state separately from the login session. `DELETE /v1/tokens/{id}` revokes a device token with the login session. |
| Scope boundary | **implemented (catalog + sync lanes)** | Login sessions can mint or revoke but cannot sync or catalog. Minted device tokens must carry `sync` for work/position/session/annotation routes and `library-read` for folders/books/covers/downloads/series/resolve. |
| Work identity | **implemented (partial identifier coverage)** | User-scoped Work/Edition/Alias/media-link tables are created by the liseur migration; media-backed SHA-256 resolution computes a full-file digest when readable and retains Stump's sampled/Koreader hashes as evidence. |
| Position sync | **implemented** | `POST /v1/ops`, `GET /v1/changes`, `GET /v1/heads`, and `GET /v1/works/{id}/positions` use per-user sequence counters and idempotent `op_id` writes. |
| Sessions | **implemented** | `POST /v1/sessions` stores immutable, idempotent closed sessions. After a successful source write, a linked work is projected into `reading_sessions` in the same transaction with its Liseur session id and device; the nullable source-id/index migration is `crates/migrations/src/m20260949_000000_add_liseur_session_id.rs`. |
| Annotations | **implemented (bridge only)** | Push, CAS delete, change feed, and live-work reads preserve revisions, sequences, opaque locators, and tombstones in adapter-owned tables; local `media_annotations`/`bookmarks` projection is deferred. |
| Attachments | **implemented (Stump extension)** | `PUT /v1/annotations/{id}/attachments/{kind}` and `GET .../attachments` store markup/notebook bytes as side objects keyed by annotation id, idempotent on SHA-256; downloads go through an authenticated `/api/v2` route. Not part of the pinned OpenAPI. |
| Catalog | **implemented (read-only)** | `GET /v1/folders`, folder books/search, book detail/cover/download/series, and `POST /v1/books/{id}/resolve` are mounted. Folder and book pages use bounded opaque cursors; uploads, deletes, and series-claim mutations remain deferred. |

The package is compiled only when the server's `liseur-sync` feature is
enabled; `headless` enables it alongside the other compatibility providers.

## At a glance

liseur-sync is the annotation lane because its native contract models annotations as mutable, user-owned records rather than as a side effect of progress or catalog transport. Each record has a client identity, a server revision, compare-and-set writes, a separate change sequence, and deletion tombstones. Komga, Kobo, and OPDS can carry books, files, progression, or position data, but their observed contracts do not carry a portable highlight/note/bookmark object with this lifecycle.

The current Stump adapter therefore:

- keeps the core `media_annotations` and `bookmarks` entities independent of the
  optional provider;
- stores a user-scoped bridge for remote work, edition, alias, annotation ID,
  revision, sequence, payload, device, and tombstone state;
- resolves remote work identities to a user's Stump media without treating a
  `media_id` as a globally valid work; and
- exposes catalog folders/books, covers, downloads, and catalog work
  resolution alongside annotation, session, and position routes under the
  feature-gated provider. Upload/delete and series-claim mutations remain
  deferred.

The verified research baseline is the `liseur-sync` repository at commit
`f8ce32b79aca0cddde84e9004fedde121fb77365`, whose OpenAPI document reports API
version 1.0. The implementation and line references below point to that pinned
source ([`docs/openapi.yaml`](https://github.com/chmouel/liseur-sync/blob/f8ce32b79aca0cddde84e9004fedde121fb77365/docs/openapi.yaml)).
Liseur client evidence is pinned to release [`v0.16.0`](https://github.com/chmouel/liseur/releases/tag/v0.16.0), commit [`bf5a4fd6fb0aca92a1f47c7feaf102202fd99d53`](https://github.com/chmouel/liseur/commit/bf5a4fd6fb0aca92a1f47c7feaf102202fd99d53). The release includes the note/highlight control and blank-note/timestamp fixes described below. This is source-only evidence; preserve the existing 2026-09-04 device-tested run separately.
The protocol's annotation ADR explicitly keeps annotations beside, rather than inside, the append-only
position-operation log and says that KOReader/KOSync adapters do not carry
annotations ([`docs/adr/0028-annotation-sync.md`](https://github.com/chmouel/liseur-sync/blob/f8ce32b79aca0cddde84e9004fedde121fb77365/docs/adr/0028-annotation-sync.md)).

The other observed lanes are insufficient as annotation contracts:

- **Komga:** the Liseur Komga client uses an API key and synchronizes catalog/file and `R2Progression` position data. Its position fallback can fetch saved positions, but the client has no annotation endpoint or annotation object ([ResearchLiseurSync, `docs/SERVER_CAPABILITIES.md:10-74`; Liseur `KomgaCatalogClient.kt:1-180`, `KomgaProgressionClient.kt:1-220`).
- **Kobo:** Stump's current Kobo surface is a library/metadata/download compatibility adapter. Its advertised reading-state and tag routes are handled by compatibility stubs, and its inbound contract does not provide annotation text, notes, bookmarks, or Readium ranges ([`sync-platforms.mdx`](/docs/developer/sync-platforms) and ResearchLiseurSync, `docs/SERVER_CAPABILITIES.md:10-74`).
- **OPDS:** OPDS 1.2/2.0 surfaces catalog and progression/download capabilities; they do not define a user-scoped, revisioned annotation resource or delta feed. OPDS progression therefore cannot be stretched into annotation replication without inventing a second protocol ([`server-architecture.mdx`](/docs/developer/server-architecture) and ResearchLiseurSync, `docs/adr/0028-annotation-sync.md:266-280`).

This is a protocol distinction, not a claim that those clients cannot display local annotations. Stump's native GraphQL/EPUB path already stores user-owned annotations and bookmarks; the missing piece is a durable cross-device wire contract ([`sync-platforms.mdx`](/docs/developer/sync-platforms)).

## Verified liseur-sync contract

The following matrix records observed external behavior, not current Stump routes.

| Surface | Verified contract | Source |
| --- | --- | --- |
| Push | `POST /v1/annotations` accepts `{ annotations: [...] }`, at most 100 items. Each item uses `base_rev: 0` for create or the revision read for an edit. The response is per-item and the batch is not atomic: `applied`, `duplicate`, `conflict`, or `invalid`. | ResearchLiseurSync, liseur-sync `docs/openapi.yaml:625-670`; `docs/integrating.md:263-312` |
| Pull changes | `GET /v1/annotations/changes?since=<seq>&limit=<n>` defaults to `since=0`, `limit=500`; absent, zero, negative, non-numeric, and oversized limits all use `500`. Position changes use the same rule with default `50`. The annotation response contains `{ annotations, high_water, has_more }`; its high-water counter is separate from the position-operation counter. | ResearchLiseurSync, `docs/openapi.yaml:672-702`; pinned Liseur client query construction; `docs/integrating.md:321-338` |
| Delete | `DELETE /v1/annotations/{id}?rev=N` requires the revision the client read. A matching delete returns `200` with `applied` and a new `rev`/`seq`; an already deleted record is `duplicate`; a stale revision returns `409` with the current server copy. | ResearchLiseurSync, `docs/openapi.yaml:703-738`; `internal/store/sqlite/annotations.go:65-199,253-356` |
| Live set | `GET /v1/works/{id}/annotations` returns live annotations only, with no tombstones, ordered by `progression` and then `client_ts` (records without progression sort last). | ResearchLiseurSync, `docs/openapi.yaml:739-765` |
| Push notification | **None.** The pinned OpenAPI has no SSE, WebSocket, or long-poll route; both change feeds are cursored polls. | ResearchLiseurSync, `docs/openapi.yaml` (no `text/event-stream` producer, no `ws` scheme) |

A successful write starts at revision 1 and increments the revision. The changes feed is state, not history: an edit moves the current record to the feed head. Deletes are tombstones containing identity/revision/sequence and deletion timestamps, retained for 180 days by default and then swept. A client that was offline longer than retention must reconcile its local set against the live-work endpoint ([ResearchLiseurSync, `docs/integrating.md:298-338`; `docs/adr/0028-annotation-sync.md:107-226`; `internal/store/sqlite/annotations.go:358+`).

### There is no push lane, by evidence

Stump's core event bus ([server architecture](/docs/developer/server-architecture))
would happily feed a liseur-sync push transport, and it is deliberately not
wired to one: neither end of the pinned contract can consume it.

- **Server.** liseur-sync `f8ce32b7` advertises exactly two change feeds,
  `GET /v1/changes?since=<seq>` for position operations and
  `GET /v1/annotations/changes?since=<seq>&limit=<n>` for annotations, both
  returning `high_water`/`has_more` cursors. Adding an event stream to
  Stump's `/v1/*` tree would be inventing a route the protocol does not
  define, which every other client would then have to ignore.
- **Client.** Liseur v0.16.0 (`bf5a4fd6fb0aca92a1f47c7feaf102202fd99d53`) depends on plain `okhttp`: its
  `gradle/libs.versions.toml` lists `okhttp`, `okhttp-tls`, `mockwebserver3-junit4`,
  and `coil-network-okhttp`, and does **not** list `okhttp-sse` or any
  WebSocket/ktor artifact. No file under
  `app/src/main/kotlin/com/chmouel/liseur/data/liseursync/` references
  `EventSource`, SSE, or a WebSocket; `LiseurSyncHttp.kt` and
  `LiseurSyncApi.kt` are request/response only.

A push lane would therefore have exactly zero consumers while adding a second,
unpinned wire contract to maintain. Stump's live surfaces stay where clients
actually read them: the GraphQL subscriptions and Komga SSE.

### Annotation wire shape

`AnnotationInput` requires `id`, `base_rev`, `work_id`, `kind`, and `client_ts`. `kind` is one of `highlight`, `note`, or `bookmark`; highlights and bookmarks require a locator, notes forbid one and require a body, and bookmarks forbid a body. Optional fields are `edition_sha`, `locator`, `progression` in `[0,1]`, `excerpt` (1 KiB default cap), `color` (the six lowercase palette tokens `yellow`, `green`, `blue`, `pink`, `purple`, and `orange`), and `body` (16 KiB default cap). The locator is arbitrary reader-native JSON, opaque to the server and replayed verbatim; the default locator cap is 16 KiB ([ResearchLiseurSync, liseur-sync `docs/openapi.yaml:2720-2794`; `internal/api/annotations.go:84-183`; `internal/config/config.go:105-151`).
Liseur v0.16.0 maps the six persisted/sync colors to exact Android values: yellow `#FFD54F`, green `#9CCC65`, blue `#64B5F6`, pink `#F06292`, purple `#B39DDB`, and orange `#FFB74D`. The server continues to carry lowercase palette tokens on the wire; this hex mapping is client evidence, not a new liseur-sync server contract.

A live wire record includes `id`, `rev`, `seq`, `work_id`, `edition_sha`, `kind`, `locator`, `progression`, `excerpt`, `color`, `body`, `device_id`, `client_ts`, `updated_at`, and deletion flags. A tombstone carries only `id`, `rev`, `seq`, `updated_at`, `deleted`, and `deleted_at` ([ResearchLiseurSync, `docs/openapi.yaml:2766-2788`; `internal/api/annotations.go:1-80`).

The server never merges stale edits. A stale `base_rev` returns the current copy; the client must show or choose a copy and retry from the new revision. The batch can fail items independently, while malformed, empty, over-100-item, or impossible-sized requests are rejected as a whole ([ResearchLiseurSync, `docs/integrating.md:298-312`; `docs/openapi.yaml:625-670`).

## Attachments

A Stump extension, not part of the pinned liseur-sync OpenAPI: `AnnotationInput`
carries only bounded text (`locator` and `body` 16 KiB, `excerpt` 1 KiB), so a
Kobo handwritten markup — an SVG stroke layer plus a JPEG page snapshot of a
few hundred KiB — has nowhere to go. Attachments are **side objects keyed by
annotation id**: storing one never touches the record's revision or feed
sequence, so the compare-and-set contract above is unchanged and a client that
ignores these routes sees exactly the protocol it pinned.

| Route | Scope | Behavior |
| --- | --- | --- |
| `PUT /v1/annotations/{id}/attachments/{kind}` | `sync` | Raw body. `Content-Type` is the media type, `X-Attachment-Sha256` the lowercase-hex digest of the bytes, `Content-Length` the size. `200` returns `{id, sha256, byte_size}`. |
| `GET /v1/annotations/{id}/attachments` | `sync` | `{ attachments: [{id, annotation_id, kind, media_type, byte_size, sha256, created_at}] }`, oldest first. |
| `GET /api/v2/annotations/{id}/attachments/{attachment_id}` | owner | The bytes, with the stored media type and `Cache-Control: private, max-age=31536000, immutable` (the path is content-addressed). Accepts the owner's Stump session/API key **or** the liseur device secret already used on `/v1/*`. |
| `annotationAttachments(annotationId: ID!)` | any user, own records | GraphQL metadata list, including the filename `extension` the bytes are stored under. |

`kind` is closed: `markup-svg` (handwritten strokes), `markup-page` (the page
snapshot they were drawn on), or `notebook` (a device notebook export). The
accepted media types are per kind — `markup-svg` requires `image/svg+xml`,
`markup-page` accepts `image/jpeg` or `image/png`, and `notebook` accepts PDF,
ZIP, EPUB, DOCX, HTML, plain text, or one of those images. Anything else is a
`400`.

**Limits.** One attachment is at most `STUMP_ATTACHMENT_MAX_BYTES`
(`protocols.attachment_max_bytes`, 8 MiB by default). A `Content-Length` over
the limit is refused with `413` before the body is streamed; a chunked body is
cut off by the same bound while reading. An empty body is a `400`. The
annotation id names the directory the bytes live in, so an id carrying
attachments must match `[A-Za-z0-9._-]` and must not start with a dot; a
`400` says so rather than letting a client-chosen id escape the attachment
root. The annotation lane itself keeps accepting any bounded id.

**Idempotency.** The digest is the key. The server hashes the received bytes
and compares them to `X-Attachment-Sha256`; a mismatch is `409` and nothing is
stored. A repeat of the same digest returns the **same attachment id** and
writes nothing, so a device replaying a batch on its backup URL costs one
request and never a second copy. A *different* digest for the same
`(annotation, kind)` replaces the slot: the row keeps its id, the new bytes
land, and the superseded file is unlinked. An unknown or tombstoned annotation
is `404`; a missing or invalid bearer is `401`, and a login session (or a
device token without `sync`) is `403`.

**Storage.** Bytes live at
`<config_dir>/attachments/<annotation_id>/<sha256>.<ext>` and the row stores
that path relative to the attachment root, so moving the configuration
directory does not invalidate rows. Writes go through a sibling `.partial`
file and a rename, so a reader never sees a half-written content-addressed
file. `annotation_attachments` (migration `m20260926`) carries
`id`, `user_id`, `annotation_id`, `kind`, `media_type`, `byte_size`, `sha256`,
`storage_path` and `created_at`, with a unique index on
`(user_id, annotation_id, kind)` and a foreign key to the annotation's
`(user_id, annotation_id)` unique index that cascades on delete — a liseur
annotation id is client-chosen and therefore unique per user, never globally.
A CAS delete cascades explicitly: the tombstone keeps identity and revision,
not content, so the rows are dropped and the files unlinked in the same
transaction that writes the tombstone.

The first producer is NickelStump, which uploads both halves of a
`.kobo/markups/<BookmarkID>.{svg,jpg}` pair and keeps a per-book digest ledger
so a steady-state sync uploads nothing
(`nickelstump/docs/PROTOCOL.md`, "Handwritten markups"). Kobo notebook exports
still do not travel: the `notebook` kind exists, but an attachment needs an
annotation to hang off and a notebook has no `Bookmark` row.

## Catalog

The read-only catalog is implemented for the routes the pinned Android client
actually walks. URL construction is defined in
`app/src/main/kotlin/com/chmouel/liseur/data/liseursync/LiseurSyncApi.kt` at
lines 135–169 and 202–203; response parsing is in
`LiseurSyncCatalogClient.kt` at lines 26–69 and 79–183. The server keeps the
wire keys consumed by that client and does not require a second catalog API.

| Route | Scope and behavior | Client evidence |
| --- | --- | --- |
| `GET /v1/folders?limit=<n>&after=<cursor>` | Requires `library-read`. Returns `folders`, each with `folder_id`, `name`, and `accepts_uploads: false`; `next_after` is present when another page exists. `limit` is 1–200. | `LiseurSyncApi.kt:135–141`; `LiseurSyncCatalogClient.kt:79–102`; upload target paging and `accepts_uploads` filtering: `LiseurSyncUploadClient.kt:56–87`. |
| `GET /v1/folders/{folder_id}/books?limit=<n>&cursor=<cursor>` | Requires `library-read`. Returns `books` with `next_cursor` when another page exists. Books are visible media in the Stump library, ordered by `title` then `book_id`. | `LiseurSyncApi.kt:143–148`; `LiseurSyncCatalogClient.kt:26–56`. |
| `GET /v1/folders/{folder_id}/search?q=<text>` | Requires `library-read`. Returns `{ books }`, searching title, author, and series. | `LiseurSyncApi.kt:150–155`; `LiseurSyncCatalogClient.kt:58–69`. |
| `GET /v1/books/{book_id}` | Requires `library-read`. Returns the same book object as a catalog page, including `folder_id`, `contributors`, `series`, `status`, `size_bytes`, `cover_url`, and `updated_at`; it does not hash the source file merely to populate optional `sha256`. | `LiseurSyncApi.kt:164–166`; `LiseurSyncCatalogClient.kt:134–159`. |
| `GET /v1/books/{book_id}/cover` | Requires `library-read`. Uses Stump's saved-thumbnail/first-page helper and returns an image content type. | `LiseurSyncApi.kt:202–203`; cover URL consumed by `LiseurSyncCatalogClient.kt:143–149`. |
| `GET /v1/books/{book_id}/download` | Requires `library-read`. Streams the original file through `ServeFile`, preserving range requests and returning the original filename as an attachment. | `GET /v1/books/{book_id}/series` | Requires `library-read`. | `POST /v1/books/{book_id}/resolve` | Requires `library-read` and `sync`; the client posts `{}` or `{ "confirmed": true }`. | `GET /v1/works/{work_id}/annotations` | Requires `sync`; returns the live annotation list used after catalog resolution. | URL builder: `LiseurSyncApi.kt:74–84`; response parsing after resolution: `WorkResolver.kt:226–238`; Stump response contract: `crates/liseur-sync/src/lib.rs`. |

Catalog list/detail responses deliberately omit `sha256`: Stump's stored
`media.hash` is a sampled fingerprint, not a full-file digest. Explicit
`POST /v1/books/{book_id}/resolve` opens and hashes the visible file and always
includes the stable `source` identifier, so digest evidence is bound to the
file the server actually serves.

Folder `after` and book `cursor` values are opaque URL-safe base64 tokens
encoding the last `(name, folder_id)` or `(title, book_id)` sort key. The
client URL-encodes them before sending (`LiseurSyncApi.kt:136–148`), and the
client requests pages of 200 (`LiseurSyncCatalogClient.kt:104–115`). A malformed
cursor or a `limit` outside 1–200 is a `400`; a hidden or unknown folder/book
is a `404`. `cover_url` is an absolute URL formed from the request origin so
the client can fetch it without path rewriting.

Upload (`POST /v1/folders/{folder_id}/books`), delete
(`DELETE /v1/books/{book_id}`), and series-claim mutation routes
(`PUT`/`DELETE /v1/books/{book_id}/series` and
`/v1/entities/series/{id}/{order,name}`) are not needed by the catalog walk.
The folder response advertises `accepts_uploads: false`; the deferred entity
routes return a JSON `404` with an `error` field instead of an empty Axum
not-found body. Upload status handling remains documented by the oracle at
`LiseurSyncUploadClient.kt:90–146`.


## Stump projection (bridge implemented; local projection deferred)

### Preserve the core entities

Stump's current `media_annotations` row has a required `ReadiumLocator`, optional `annotation_text`, `media_id`, `user_id`, and timestamps. `bookmarks` has optional preview text, an optional `ReadiumLocator`, an optional page, `media_id`, `user_id`, and creation time. Both are user-owned; the EPUB query paths filter by the current user and media ([`media_annotation::Model`](https://github.com/stumpapp/stump/blob/nightly/crates/models/src/entity/media_annotation.rs#L5-L23), [`bookmark::Model`](https://github.com/stumpapp/stump/blob/nightly/crates/models/src/entity/bookmark.rs#L7-L24), and ResearchLiseurSync, Stump `crates/models/src/entity/*`).

**Implemented bridge:** Stump keeps liseur-specific revision, sequence,
remote-ID, raw-payload, and tombstone state in adapter-owned tables rather than
adding those fields to core `media_annotations` or `bookmarks` rows. The bridge
is user-scoped and remains usable only while the optional provider is enabled;
local core rows stay independent.

| Bridge field | Purpose |
| --- | --- |
| `user_id` | Tenant boundary for every lookup and feed cursor. |
| `annotation_id` (`id`) | Stable client-chosen liseur-sync record ID, distinct from a Stump annotation/bookmark ID. |
| `rev` / `seq` | Compare-and-set revision and annotation-feed sequence. |
| `work_id` / `edition_sha` | Remote identity and optional exact-file provenance used for authorization and locator context. |
| `kind`, `locator`, `progression` | Opaque reader anchor and its wire kind (`highlight`, `note`, or `bookmark`) plus optional position. |
| `excerpt`, `color`, `body` | Bounded wire fields preserved without inventing a local projection. |
| `device_id` / `client_ts` | Origin device and client idempotency timestamp. |
| `updated_at`, `deleted`, `deleted_at` | Current record/tombstone lifecycle state. |
| `payload` | Canonical request payload used for retry/conflict comparison and audit. |

A user-scoped cursor is represented by the caller's `since` value and the
adapter's annotation sequence counter; this pass does not add a separate
cursor table. Tombstones remain in the bridge so an old device cannot recreate
a deleted annotation with `base_rev: 0`. This supplemental
revision/sequence/tombstone layer is the essential protocol adaptation;
distorting `media_annotations` or `bookmarks` would couple local CRUD to a
remote feed that can be disabled or compacted.

### Conservative field mapping

**Deferred local projection:** map only information Stump actually has. The
current pass does not import remote records into `media_annotations` or
`bookmarks`, so no locator, excerpt, color, progression, edition digest, or
remote kind is fabricated.

| Stump source | liseur-sync projection | Guard |
| --- | --- | --- |
| `media_annotations.locator` + `annotation_text` | `highlight` with the locator and `body` set to `annotation_text` when the local row represents a highlighted passage and the locator is valid. | The wire field is `body`, not `note`; do not serialize a note field that the protocol does not define. Preserve the local distinction between `ReadiumLocator.text.highlight` and the user's note. |
| `bookmarks.locator` | `bookmark` with the locator. | `page` and `preview_content` have no wire fields; omit them, and never put a page number in opaque locator JSON. Rows without a locator cannot be sent as anchored bookmarks. |
| A local annotation with a locator and no note | `highlight` with no `body`, if the selected passage is represented by the locator. | If it is only an anchor and not a text selection, choose `bookmark` only with an explicit, deterministic rule; otherwise hold it for review. |
| A genuinely unanchored note from a future/imported source | `note` with a non-empty `body` and no locator. | Current `media_annotations` requires a locator, so do not turn an existing anchored row into an unanchored note merely to fit the wire shape. |
| `ReadiumLocator` JSON | `locator` JSON, bounded and preserved. | liseur-sync treats it as opaque; validate size and JSON shape, but do not assume the server understands Readium ranges. |

The inverse local-projection path is deferred. If a future remote edit races
with a local edit, it must keep both payloads and mark a conflict for user
resolution rather than use timestamp-only last-writer-wins. A remote tombstone
must not silently erase a user-owned local row.

## Work, Edition, and Alias identity (implemented with limits)

liseur-sync separates an abstract Work, a concrete Edition, and identifiers (Aliases), because positions and annotations are private to a user while catalog files may be shared. The verified model uses user-scoped records, resolves aliases in priority order `sha256 > partial-md5 > source > dc > ta`, and rejects conflicting strong aliases without mutation. Title/author (`ta`) is low-confidence and is not promoted until confirmation ([ResearchLiseurSync, liseur-sync `docs/adr/0003-catalog-work-identity.md:14-83`; `docs/DESIGN.md:138-194`; `internal/store/store.go:888-955`; `internal/workident/identifiers.go:20-117`).

**Implemented:** the adapter owns a user-scoped identity layer rather than
treating a Stump `media_id` as a globally valid `work_id`:

- **Work:** `(user_id, work_id, title, author, pending)` for the user's abstract reading identity.
- **Edition:** `(user_id, edition_sha, work_id, page_count, char_count, metadata)` for the exact publication bytes and their optional derived metadata.
- **Alias:** `(user_id, kind, value, work_id)` for `sha256`, `partial-md5`, stable `source`, EPUB `dc`, or low-confidence `ta` evidence.
- **Media link:** `(user_id, media_id, work_id, edition_sha, resolution_status)` connecting the Stump file to the user's identity without making catalog identity global.

A full-file SHA-256 is computed for explicit media-backed resolution whenever
the file is readable; ordinary catalog listing does not hash the object.
Stump's sampled `media.hash` and optional `media.koreader_hash` are retained as
evidence, never substituted for a verified full digest. A bare caller-provided
`sha256` can create unverified edition evidence but cannot select a media row;
a stable `source` identifier is required to open and verify the corresponding
file. If that source-backed verification later produces the same digest, the
existing edition is upgraded to verified provenance. `partial-md5` and
`source` remain the only direct media lookups; `dc` and `ta` aliases are stored
as opaque identity evidence and do not receive approximate matching.

The TA normalizer remains a known compatibility hazard. The liseur contract
and Android `WorkIdentifiers.kt:73-108` specify Unicode NFKD, removal of
combining marks, lower-casing, punctuation/non-alphanumeric runs converted to
spaces, and normalization. The server implementation at
`metadata/entities.go:9-27` currently only lower-cases and collapses
whitespace, preserving accents and punctuation (ResearchLiseurSync,
`docs/integrating.md:154-163`). Stump therefore keeps TA-only evidence
unresolved and never silently merges because two incompatible normalizers
happen to match.
## Scope and authentication model (implemented session/device split)

The external API uses `Authorization: Bearer <token>`. Stump's
feature-gated `POST /v1/login` verifies a Stump username and password, stores a
per-user token-management session, and returns its one-hour `auth_token` with
an empty scope set. The session is accepted only by `POST /v1/tokens` and
`DELETE /v1/tokens/{id}`; using it on a sync route returns `403`, and using it
on `GET /v1/token` returns `401`.

`POST /v1/tokens` accepts the login session and `{name, scopes}` (the legacy
singleton `scope` form is also accepted), stores a separate revocable device
row, and returns `secret` exactly once with its `token_id`, `device_id`, name,
canonical `scopes`, and `expires_at`. The device bearer can call
`GET /v1/token`, which returns `id`, `device_id`, `name`, `scopes`, and the
stable `account_id`; it never returns a secret. Missing, invalid, expired, or
revoked credentials return `401`. A valid device token without `sync` returns
`403` from the sync lane; a token without `library-read` returns `403` from
catalog routes.

The upstream contract and scope distinctions are documented in liseur-sync's
pinned [`openapi.yaml`](https://github.com/chmouel/liseur-sync/blob/f8ce32b79aca0cddde84e9004fedde121fb77365/docs/openapi.yaml).

**Implemented token policy:**

- Store a per-user session or device credential in `liseur_sync_tokens`; never
  store a bearer secret in a media row, URL, browser bundle, or log. Device
  rows carry their generated `device_id`, display name, canonical scopes,
  hashed secret, expiry, and revocation timestamp.
- Require a device token with `sync` for position, session, annotation, and
  generic work-resolution routes. The token's generated device id stamps
  pushed ops, sessions, and annotations.
- Require `library-read` for folders, books, covers, downloads, series, and
  catalog-book resolution. The catalog never grants access to a hidden library
  or media row.
- Accept and report `read-insights`, `library-manage`, `library-upload`, and
  `library-delete` for capability discovery. Upload/delete and series-claim
  mutations remain deferred; `admin` is restricted to server-owner accounts
  and implies the sync scope.
- A sync-only device token can resolve and synchronize an already-known or
  side-loaded identity, but cannot browse or download the catalog without
  `library-read`.

## Spec versus implementation mismatches to isolate

The adapter must code to the behavior it can verify and make each mismatch visible in tests and telemetry. These are not reasons to silently broaden the contract:

| Area | Documented description | Observed implementation | Design response |
| --- | --- | --- | --- |
| Duplicate writes | Integrating documentation describes a byte-identical retry as `duplicate`. | `SameAnnotationPayload` additionally requires the same `device_id` and compares the complete payload (including the stored timestamp at implementation precision); a different device with identical content is not necessarily a duplicate. | Persist device and canonical payload evidence; retry with the original device identity and treat cross-device retries as a conflict/replace decision. |
| TA identity | The contract specifies accent/punctuation-insensitive NFKD normalization. | `NormalizeName` only lower-cases and collapses whitespace, so accents and punctuation remain significant. | Keep TA matches low-confidence and retain the normalizer/version; never promote on a server/client normalization accident. |
| Note field | Stump calls its optional user text `annotation_text`. | liseur-sync's wire field is `body`; note kind requires body and forbids locator. | Map explicitly to `body`; do not invent `note`, and keep highlight text in locator/excerpt rather than confusing it with the user's body. |
| Locator semantics | The wire accepts any bounded reader-native JSON and replays it verbatim. | The server validates shape/size but does not interpret Readium ranges or convert reader formats. | Store raw JSON and only project to Stump when it is a valid, authorized local locator; otherwise hold it pending instead of guessing. |

Sources: ResearchLiseurSync, liseur-sync `docs/integrating.md:298-338`, `docs/openapi.yaml:2720-2794`, `internal/store/store.go:1100-1245`, `internal/api/annotations.go:84-183`, and `metadata/entities.go:9-27`.

## Implementation status and deferred work

1. **Identity and storage groundwork — implemented.** The migration adds
   user-scoped Work/Edition/Alias/media-link records, session/device token
   storage, per-user position/annotation counters, operation/session records,
   and annotation tombstones. The current pass does not project remote
   annotations into Stump's core rows.
2. **Sync and annotation endpoints — implemented.** The provider exposes work
   resolution, `POST /v1/ops`, `GET /v1/changes`, `GET /v1/heads`,
   `GET /v1/works/{id}/positions`, `POST /v1/sessions`,
   `POST /v1/annotations`, `GET /v1/annotations/changes`,
   `DELETE /v1/annotations/{id}?rev=`, and
   `GET /v1/works/{id}/annotations`. Writes preserve per-item conflicts,
   idempotency, CAS revisions, feed sequences, and delete tombstones.
3. **Conflict and retention hardening — partial.** Validation, tenant
   isolation, duplicate retries, CAS conflicts, and separate position and
   annotation high-water counters are implemented. Automatic retention
   sweeping, compaction recovery, and local projection reconciliation are
   deferred.
4. **Catalog capability — read-only implemented.** The provider exposes
   folder/book pages and search, book detail, cover and range-capable download,
   folder-derived series membership, and catalog-book work resolution. Upload,
   delete, and series-claim mutation routes remain deferred.
5. **Insights and remaining token administration — deferred.** The provider
   exposes login, device-token minting, self-introspection, and revocation, but
   not `/v1/register`, token listing, token scope updates, or `/v1/insights/*`.

## Explicit unknowns and gates

The implemented sync lane is usable, but these gates remain before calling the
provider fully interoperable with the entire upstream server:

- **Release stability:** the cited liseur-sync source is an unreleased commit.
  Pinning the OpenAPI and migration behavior to a released upstream contract
  remains a deployment decision.
- **Partial-MD5 equivalence:** `media.koreader_hash` is retained as evidence,
  but Stump has not proven that every value uses the exact upstream sampling
  algorithm and byte ranges required by `partial-md5`.
- **Alias lifecycle:** catalog/source IDs and `dc` identifiers are not
  discovered by this pass, so their stability across imports and replacement
  media remains unverified.
- **TA normalization:** TA-only matching is intentionally not performed until
  the documented NFKD normalizer and the deployed upstream normalizer agree.
- **Locator projection:** opaque locators are preserved in the adapter, but
  importing every reader-native shape into a Stump `ReadiumLocator` requires an
  explicit EPUB/KEPUB validation and mapping rule.
- **Local projection:** the bridge does not yet create or update core
  `media_annotations` or `bookmarks`; any future projection must preserve
  independently edited local rows and surface conflicts.
- **Retention and remaining administration:** the current pass has no
  tombstone/session retention worker, compaction horizon, token listing or
  scope-update API, or insight route.
- **Attachment retention:** the attachment lane below stores bytes under
  `<config_dir>/attachments`. A tombstoned annotation unlinks its files, and
  the table's foreign key cascades rows when a work or an account is removed,
  but nothing sweeps the bytes a hard row delete leaves behind. A
  `<config_dir>/attachments/<annotation_id>` directory with no rows is
  therefore harmless but unreclaimed until a retention worker exists.

Until those deferred capabilities are deliberately specified, the safe
behavior is to retain raw evidence, report unresolved/conflict states, and
never make an approximate identity or locator appear exact.

## Audiobooks

The catalogue routes never list audiobook rows (`models::entity::media::AUDIO_EXTENSIONS`): Liseur reads paginated documents, and a folder book has no single file to download. Audiobooks are served by the Audiobookshelf profile (`/docs/developer/abs-compat`).
