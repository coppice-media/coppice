This page records the current, feature-gated Stump implementation of the
liseur-sync native protocol. The `liseur-sync` server feature exposes login,
token minting and device-token introspection, account settings, catalog
folders/books, covers, downloads, catalog work resolution, sync operations,
position changes, sessions, and annotation revision endpoints. Personal series
display-name overrides are supported; uploads/deletes, insights, token
listing/scope updates, series ordering, and series-claim mutations remain
deferred. Protocol evidence is pinned to liseur-sync
`906889ffe11fc7260b071c1f142aeee1fa8a1419`, Liseur v0.19.0
`62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6`, and Liseur v0.13.0
`799a8c7afac022d49388cb637f091765557b0acf`. The compatibility changes await
device replay against a rebuilt Stump server.

The server remains authoritative and the adapter remains optional, consistent
with the [server architecture](/docs/developer/server-architecture). This
implementation stores a user-scoped sync identity and revision bridge. Liseur
CAS records remain authoritative; linked valid Readium highlights and
bookmarks also have stable, filtered native projections.

## Current implementation status

| Area | Status | Stump implementation |
| --- | --- | --- |
| Authentication | **implemented (session + device tokens)** | `POST /v1/login` verifies Stump credentials and returns a one-hour token-management session bearer with no scopes. `POST /v1/tokens` accepts that session and returns a one-time device secret; `GET /v1/token` describes a device token. |
| Token management | **implemented (mint, introspect, revoke)** | Device rows store a generated device ID, name, canonical scopes, hashed secret, expiry, and revocation state separately from the login session. `DELETE /v1/tokens/{id}` revokes a device token with the login session. |
| Scope boundary | **implemented (catalog + sync lanes)** | Login sessions can mint or revoke but cannot sync or catalog. Minted device tokens must carry `sync` for work/position/session/annotation routes and `library-read` for folders/books/covers/downloads/series/resolve. |
| Account settings | **implemented** | `GET/PUT /v1/me/settings` is behind the sync-token boundary. Settings are account-scoped, bounded by the migration-backed key/value map, and PUT returns the merged LWW snapshot. |
| Work identity | **implemented (partial identifier coverage)** | User-scoped Work/Edition/Alias/media-link tables are created by the liseur migration; media-backed SHA-256 resolution computes a full-file digest when readable and retains Stump's sampled/Koreader hashes as evidence. |
| Position sync | **implemented** | `POST /v1/ops`, `GET /v1/changes`, `GET /v1/heads`, and `GET /v1/works/{id}/positions` use per-user sequence counters and idempotent `op_id` writes. Structured atomic refusals identify the rejected item for stale-work recovery and oversized locators. |
| Sessions | **implemented** | `POST /v1/sessions` stores immutable, idempotent closed sessions. Optional `active_ms` is authoritative when present; the device token advertises `session_active_ms: true`. A linked work is projected into `reading_sessions` in the same transaction with its Liseur session id and device. |
| Annotations | **implemented (bidirectional CAS bridge)** | Liseur CAS and eligible linked native Readium highlights, body-bearing notes, and bookmarks share stable records, revisions, monotonic sequences, and tombstones. Liseur writes update the same native source/projection; Home writes use optional revision preconditions and preserve locators. Legacy Liseur colors remain capability-gated. |
| Attachments | **implemented (Stump extension)** | `PUT /v1/annotations/{id}/attachments/{kind}` and `GET .../attachments` store markup/notebook bytes as side objects keyed by annotation id, idempotent on SHA-256; downloads go through an authenticated `/api/v2` route. Not part of the pinned OpenAPI. |
| Catalog | **implemented (read + personal names)** | `GET /v1/folders`, folder books/search, book detail/cover/download/series, and `POST /v1/books/{id}/resolve` are mounted. `PUT/DELETE /v1/entities/series/{id}/name` stores a personal display overlay without changing the scanned series name. Uploads, deletes, ordering, and series claims remain deferred. |

The package is compiled only when the server's `liseur-sync` feature is
enabled; `headless` enables it alongside the other compatibility providers.

## At a glance

liseur-sync is the annotation lane because its native contract models annotations as mutable, user-owned records rather than as a side effect of progress or catalog transport. Each record has a client identity, a server revision, compare-and-set writes, a separate change sequence, and deletion tombstones. Komga, Kobo, and OPDS can carry books, files, progression, or position data, but their observed contracts do not carry a portable highlight/note/bookmark object with this lifecycle.

The current Stump adapter:

- keeps native `media_annotations` and `bookmarks` as the original rows, and
  exports linked, visible rows with valid Readium locators as CAS annotations
  under deterministic `stump-native:annotation:<native-id>` and
  `stump-native:bookmark:<native-id>` IDs;
- keeps Liseur-created CAS rows authoritative and projects supported linked
  notes, highlights, and bookmarks into Stump under
  `liseur-sync:<user>:<annotation>` IDs;
- reconciles both directions on annotation reads/writes: native edits, deletes,
  and lost work links advance the CAS revision/sequence or publish tombstones,
  while Liseur edits/deletes update or remove the native projection;
- preserves the native Readium locator on Home edits and writes only note text
  and highlight color through CAS; `AnnotationEntry.revision` is the current
  CAS revision, and `lastEditedSource`/`lastEditedAt` describe the last writer;
- stores immutable CAS creator attribution in `origin_device_id` while wire
  `device_id` continues to identify the most recent writer; and
- hides either projection direction from native GraphQL and annotation-sync
  exports so one annotation never appears twice or loops back as a new record.

Native annotation colors remain distinct from KOReader's `drawer` style. The
full palette is returned only when the request opts in with
`X-Liseur-Annotation-Capabilities: annotation-color-drawer-v1`; older Liseur
clients receive the same annotation with unsupported extended colors omitted.

The current liseur-sync source baseline is commit
`906889ffe11fc7260b071c1f142aeee1fa8a1419`; its OpenAPI document reports API
version 1.0. Source links below distinguish that document from the Go routes
and handlers. Liseur client source pins are v0.19.0
`62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6` and v0.13.0
`799a8c7afac022d49388cb637f091765557b0acf`; neither is device-test evidence.
The existing 2026-09-04 device-tested run remains separately pinned to Liseur
`31f8182d`.
The protocol's annotation ADR explicitly keeps annotations beside, rather than inside, the append-only
position-operation log and says that KOReader/KOSync adapters do not carry
annotations ([`docs/adr/0028-annotation-sync.md`](https://github.com/chmouel/liseur-sync/blob/f8ce32b79aca0cddde84e9004fedde121fb77365/docs/adr/0028-annotation-sync.md)).

The other observed lanes are insufficient as annotation contracts:

- **Komga:** the Liseur Komga client uses an API key and synchronizes catalog/file and `R2Progression` position data. Its position fallback can fetch saved positions, but the client has no annotation endpoint or annotation object ([ResearchLiseurSync, `docs/SERVER_CAPABILITIES.md:10-74`; Liseur `KomgaCatalogClient.kt:1-180`, `KomgaProgressionClient.kt:1-220`).
- **Kobo:** Stump's current Kobo surface is a library/metadata/download compatibility adapter. Its advertised reading-state and tag routes are handled by compatibility stubs, and its inbound contract does not provide annotation text, notes, bookmarks, or Readium ranges ([`sync-platforms.mdx`](/docs/developer/sync-platforms) and ResearchLiseurSync, `docs/SERVER_CAPABILITIES.md:10-74`).
- **OPDS:** OPDS 1.2/2.0 surfaces catalog and progression/download capabilities; they do not define a user-scoped, revisioned annotation resource or delta feed. OPDS progression therefore cannot be stretched into annotation replication without inventing a second protocol ([`server-architecture.mdx`](/docs/developer/server-architecture) and ResearchLiseurSync, `docs/adr/0028-annotation-sync.md:266-280`).

This is a protocol distinction, not a claim that those clients cannot display local annotations. Stump now bridges its existing native GraphQL/EPUB annotations through the Liseur CAS contract; Komga, Kobo, and OPDS remain unsuitable annotation transports without changing their public protocols ([`sync-platforms.mdx`](/docs/developer/sync-platforms)).

### Current event route; explicit refusal

The current liseur-sync server (`906889ffe11fc7260b071c1f142aeee1fa8a1419`)
does expose authenticated `GET /v1/events` as an SSE topic-invalidation feed
([`openapi.yaml:51-89`](https://github.com/chmouel/liseur-sync/blob/906889ffe11fc7260b071c1f142aeee1fa8a1419/docs/openapi.yaml#L51-L89),
[`routes.go:365-367`](https://github.com/chmouel/liseur-sync/blob/906889ffe11fc7260b071c1f142aeee1fa8a1419/internal/api/routes.go#L365-L367)).
That route was added after the older `f8ce32b7` baseline; the old “no push
lane” conclusion is no longer true of the server.

Liseur has subscribed to it since v0.15.0: `LiseurSyncLive.stream` opens
`GET /v1/events` with `Accept: text/event-stream` and the Bearer token once per
foreground liseur-sync session and reacts only to `invalidate` events carrying
`positions`, `annotations`, or `insights` topics
([`LiseurSyncLive.kt:31-46,142-149`](https://github.com/chmouel/liseur/blob/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6/app/src/main/kotlin/com/chmouel/liseur/data/liseursync/LiseurSyncLive.kt#L142-L149)).
`LiveRetry.delayMillis` stops for the session on 401/403/404/501 and retries
with capped backoff on every other outcome, including a redirect to an HTML
page
([`LiveRetry.kt:19-20`](https://github.com/chmouel/liseur/blob/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6/app/src/main/kotlin/com/chmouel/liseur/data/remote/LiveRetry.kt#L19-L20),
[`LiveSyncConnector.kt:131-152`](https://github.com/chmouel/liseur/blob/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6/app/src/main/kotlin/com/chmouel/liseur/sync/LiveSyncConnector.kt#L131-L152)).
Stump therefore mounts `GET /v1/events` inside the bearer-protected router as
an explicit `404 {"error":"live event stream is not implemented"}`
(`crates/liseur-sync/src/lib.rs`, `deferred_events`) so the client falls back
to request/response sync for the session instead of retrying against the SPA
fallback. The adapter does not invent a separate push protocol; periodic and
foreground syncs are unaffected.

### Annotation wire shape

`AnnotationInput` requires `id`, `base_rev`, `work_id`, `kind`, and `client_ts`.
`kind` is `highlight`, `note`, or `bookmark`; highlights/bookmarks require a
locator, a note requires a non-empty body and may retain a locator, and a
bookmark carries no body. Optional fields include `edition_sha`, `locator`,
`progression` in `[0,1]`, `excerpt`, `body`, `color`, and KOReader's distinct
`drawer`. Stump accepts the six Liseur colors (`yellow`, `green`, `blue`,
`pink`, `purple`, `orange`) plus KOReader's `red`, `olive`, `cyan`, and `gray`;
`drawer` is one of `lighten`, `underline`, `strikeout`, or `invert`. The pinned
Liseur v0.13/v0.18 `AnnotationWire.kt` decoder accepts only its six colors and
drops a complete record when another color is present, so the adapter keeps
the record but omits extended fields unless the request carries
`X-Liseur-Annotation-Capabilities: annotation-color-drawer-v1`. With that
header it returns the full palette and `drawer`; without it, extended colors
are omitted and the highlight remains visible. The paired KOReader client
sends this header on annotation POSTs, full-work annotation reads, and DELETE
requests that may return conflicts; it does not currently consume
`/v1/annotations/changes`. Other changes-feed clients must also send the header.
`drawer` is ignored by the pinned Liseur decoder. Locator
JSON remains opaque and is preserved verbatim; the default locator cap is
16 KiB.

A live wire record includes `id`, `rev`, `seq`, `work_id`, `edition_sha`,
`kind`, `locator`, `progression`, `excerpt`, `color`, `drawer`, `body`,
`device_id`, `client_ts`, `updated_at`, and deletion flags. Tombstones carry
identity/revision/sequence and deletion timestamps. An update that omits a
standard Liseur color clears it; an omitted extended color or drawer preserves
the existing KOReader value, while explicit empty strings clear either field.
For notes/bookmarks, empty color/drawer values are accepted and non-empty
values are rejected.

Liseur v0.19.0 still maps its six persisted/sync colors to exact Android
values: yellow `#FFD54F`, green `#9CCC65`, blue `#64B5F6`, pink `#F06292`,
purple `#B39DDB`, and orange `#FFB74D`
([`Annotations.kt:27-32`](https://github.com/chmouel/liseur/blob/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6/app/src/main/kotlin/com/chmouel/liseur/reader/annotations/Annotations.kt#L27-L32)).
These hex values are client evidence; the wire contract carries lowercase
tokens ([`AnnotationWire.kt:25`](https://github.com/chmouel/liseur/blob/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6/app/src/main/kotlin/com/chmouel/liseur/data/liseursync/AnnotationWire.kt#L25)).

The server never merges stale edits. A stale `base_rev` returns the current copy; the client must show or choose a copy and retry from the new revision. The batch can fail items independently, while malformed, empty, over-100-item, or impossible-sized requests are rejected as a whole ([ResearchLiseurSync, `docs/integrating.md:298-312`; `docs/openapi.yaml:625-670`).

## Attachments

A Stump extension, not part of the pinned liseur-sync OpenAPI: `AnnotationInput`
carries only bounded text (`locator` and `body` 16 KiB, `excerpt` 1 KiB), so a
Kobo handwritten markup — an SVG stroke layer plus a JPEG page snapshot of a
few hundred KiB — has nowhere to go. Attachments are **side objects keyed by
annotation id**: storing one never touches the record's revision or feed
sequence, so the compare-and-set contract above is unchanged and a client that
ignores these routes sees exactly the protocol it pinned.

| Route | Scope | Behavior |
| --- | --- | --- |
| `PUT /v1/annotations/{id}/attachments/{kind}` | `sync` | Raw body. `Content-Type` is the media type, `X-Attachment-Sha256` the lowercase-hex digest of the bytes, `Content-Length` the size. `200` returns `{id, sha256, byte_size}`. |
| `GET /v1/annotations/{id}/attachments` | `sync` | `{ attachments: [{id, annotation_id, kind, media_type, byte_size, sha256, created_at}] }`, oldest first. |
| `GET /api/v2/annotations/{id}/attachments/{attachment_id}` | owner | The bytes, with the stored media type and `Cache-Control: private, max-age=31536000, immutable` (the path is content-addressed). Accepts the owner's Stump session/API key **or** the liseur device secret already used on `/v1/*`. |
| `annotationAttachments(annotationId: ID!)` | any user, own records | GraphQL metadata list, including the filename `extension` the bytes are stored under. |

`kind` is closed: `markup-svg` (handwritten strokes), `markup-page` (the page
snapshot they were drawn on), or `notebook` (a device notebook export). The
accepted media types are per kind — `markup-svg` requires `image/svg+xml`,
`markup-page` accepts `image/jpeg` or `image/png`, and `notebook` accepts PDF,
ZIP, EPUB, DOCX, HTML, plain text, or one of those images. Anything else is a
`400`.

**Limits.** One attachment is at most `STUMP_ATTACHMENT_MAX_BYTES`
(`protocols.attachment_max_bytes`, 8 MiB by default). A `Content-Length` over
the limit is refused with `413` before the body is streamed; a chunked body is
cut off by the same bound while reading. An empty body is a `400`. The
annotation id names the directory the bytes live in, so an id carrying
attachments must match `[A-Za-z0-9._-]` and must not start with a dot; a
`400` says so rather than letting a client-chosen id escape the attachment
root. The annotation lane itself keeps accepting any bounded id.

**Idempotency.** The digest is the key. The server hashes the received bytes
and compares them to `X-Attachment-Sha256`; a mismatch is `409` and nothing is
stored. A repeat of the same digest returns the **same attachment id** and
writes nothing, so a device replaying a batch on its backup URL costs one
request and never a second copy. A *different* digest for the same
`(annotation, kind)` replaces the slot: the row keeps its id, the new bytes
land, and the superseded file is unlinked. An unknown or tombstoned annotation
is `404`; a missing or invalid bearer is `401`, and a login session (or a
device token without `sync`) is `403`.

**Storage.** Bytes live at
`<config_dir>/attachments/<annotation_id>/<sha256>.<ext>` and the row stores
that path relative to the attachment root, so moving the configuration
directory does not invalidate rows. Writes go through a sibling `.partial`
file and a rename, so a reader never sees a half-written content-addressed
file. `annotation_attachments` (migration `m20260926`) carries
`id`, `user_id`, `annotation_id`, `kind`, `media_type`, `byte_size`, `sha256`,
`storage_path` and `created_at`, with a unique index on
`(user_id, annotation_id, kind)` and a foreign key to the annotation's
`(user_id, annotation_id)` unique index that cascades on delete — a liseur
annotation id is client-chosen and therefore unique per user, never globally.
A CAS delete cascades explicitly: the tombstone keeps identity and revision,
not content, so the rows are dropped and the files unlinked in the same
transaction that writes the tombstone.

The first producer is NickelCoppice, which uploads both halves of a
`.kobo/markups/<BookmarkID>.{svg,jpg}` pair and keeps a per-book digest ledger
so a steady-state sync uploads nothing
(`nickelcoppice/docs/PROTOCOL.md`, "Handwritten markups"). Kobo notebook exports
still do not travel: the `notebook` kind exists, but an attachment needs an
annotation to hang off and a notebook has no `Bookmark` row.

Catalog list/detail responses deliberately omit `sha256`: Stump's stored
`media.hash` is a sampled fingerprint, not a full-file digest. Explicit
`POST /v1/books/{book_id}/resolve` opens and hashes the visible file and always
includes the stable `source` identifier, so digest evidence is bound to the
file the server actually serves.

Folder `after` and book `cursor` values are opaque URL-safe base64 tokens
encoding the last `(name, folder_id)` or `(title, book_id)` sort key. The
client URL-encodes them before sending (`LiseurSyncApi.kt:136–148`), and the
client requests pages of 200 (`LiseurSyncCatalogClient.kt:104–115`). A malformed
cursor or a `limit` outside 1–200 is a `400`; a hidden or unknown folder/book
is a `404`. `cover_url` is an absolute URL formed from the request origin so
the client can fetch it without path rewriting.

Upload (`POST /v1/folders/{folder_id}/books`), delete
(`DELETE /v1/books/{book_id}`), and series ordering/claim mutation routes
remain deferred. The folder response advertises `accepts_uploads: false`;
the deferred entity-order route returns a JSON `404` with an `error` field
instead of an empty Axum not-found body. Upload status handling remains
documented by the oracle at `LiseurSyncUploadClient.kt:90–146`.


## Stump annotation exchange (native ↔ CAS)

### Preserve the core entities

Liseur-origin CAS rows remain canonical and project into a native
`media_annotations` or `bookmarks` row under `liseur-sync:<user_id>:<annotation_id>`.
Linked native rows export as deterministic CAS IDs
`stump-native:annotation:<native_id>` or `stump-native:bookmark:<native_id>`.
For those rows the original native row remains the native-side identity; the
CAS record supplies the shared revision, sequence, change-feed, and tombstone
contract. Neither direction re-exports its mirror.

Liseur-authored rows are stored and replayed as the raw locator JSON, so an
exact-screen bookmark (v0.17.0+, `locations.liseurAnchor: 1`,
`locations.cssSelector`, `text.{before,highlight,after}`; see
[`ExactLocatorAnchor.kt:51-65`](https://github.com/chmouel/liseur/blob/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6/app/src/main/kotlin/com/chmouel/liseur/reader/progress/ExactLocatorAnchor.kt#L51-L65))
keeps its anchor across devices. Native `stump-native:bookmark:<native_id>`
exports are typed `ReadiumLocator` values (`href`, `type`, `locations`,
`text`) without a viewport anchor: Liseur v0.19.0 lists and jumps to them and
prints `locations.position` as their page number, but matches the bookmark
ribbon only by `href` plus integer `position`/`progression`
([`ReadingPlace.kt:28-47`](https://github.com/chmouel/liseur/blob/62ecb5a5c9dd8eb4e7fa6d97ce50d1bddae0bcd6/app/src/main/kotlin/com/chmouel/liseur/reader/progress/ReadingPlace.kt#L28-L47)).
Only the reader's own viewport can produce the anchor, so no server-side
shape change is required or possible.

| Bridge field | Purpose |
| --- | --- |
| `user_id` | Tenant boundary for every lookup and feed cursor. |
| `annotation_id` (`id`) | Liseur-chosen ID, or stable prefixed ID for a native Stump source row. |
| `rev` / `seq` | Compare-and-set revision and monotonic per-user annotation-feed sequence. |
| `work_id` / `edition_sha` | User-scoped Liseur identity and exact-edition preference for media linking. |
| `kind`, `locator`, `progression` | Wire kind and Readium anchor; native exports retain the full locator, including `text.before`, `text.highlight`, and `text.after`. |
| `excerpt`, `color`, `drawer`, `body` | Selected passage, supported highlight color, KOReader drawer, and note text; drawer is distinct from color. |
| `device_id` / `client_ts` | Last writer and original client timestamp. `origin_device_id` is server-side immutable creator attribution, not a wire field. |
| `updated_at`, `deleted`, `deleted_at` | Current record/tombstone lifecycle state. |
| `payload` | Last request payload used for retry/conflict comparison and audit. |

Projection and export rules:

- A linked, visible native highlight or body-bearing note with a non-empty
  Readium `href` and `locations` enters the CAS feed. A linked native bookmark
  must also carry a valid Readium locator. The `work_id` and `edition_sha` come
  from the user's existing media-link resolution; unlinked or invisible media
  never crosses the user boundary.
- A Liseur `highlight` maps to `media_annotations` with its selected text,
  optional native note, and exact color. A Liseur `note` maps to a native note
  with `text.highlight` cleared. A valid Liseur `bookmark` maps to `bookmarks`.
- Native deletes, losing the link, or becoming ineligible publish a CAS
  tombstone with an increased revision and sequence. Liseur deletes and kind
  transitions remove the corresponding `liseur-sync:` mirror.
- Liseur clients edit native-export records through normal `POST
  /v1/annotations` `base_rev` CAS writes; the server writes note text, color,
  and the submitted Readium anchor back to the same native row. Home GraphQL
  uses `updateAnnotation(input: { id, annotationText?, color?,
  expectedRevision? })` and `deleteAnnotation(id, expectedRevision?)`.
  `expectedRevision` is optional; when supplied it must match the current
  `AnnotationEntry.revision`. Updates change only note text/color, preserve the
  locator and creator, and advance CAS revision/sequence. Deletes publish a
  tombstone and remove the native or Liseur mirror row.
- A stale GraphQL revision makes the non-null root mutation result `data: null`
  and returns
  `errors[0].message: "annotation revision conflict: expected <requested>,
  current <revision>"`; no `extensions.code` is returned. The CAS update is
  rolled back. GraphQL entries expose current `revision`, `editable`, immutable
  creator `source`/`sourceDeviceId`, and separate
  `lastEditedSource`/`lastEditedAt`.
- The creator column is backfilled from the pre-existing `device_id`;
  subsequent Liseur or Home edits change only `device_id`.
- GraphQL annotation pages and annotation-sync exports suppress both
  `liseur-sync:` native mirrors and `stump-native:` CAS rows. A Home annotation
  is therefore listed once, with its original native ID.

Example native export (a KOReader-capable response may include the extended
`red` color):

```json
{
  "id": "stump-native:annotation:7d9a2d9c-4d67-4a84-9d0a-60c5f02f11e1",
  "rev": 1,
  "seq": 84,
  "work_id": "work-123",
  "edition_sha": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "kind": "highlight",
  "locator": {
    "href": "OPS/chapter.xhtml",
    "locations": { "position": 12, "progression": 0.37, "totalProgression": 0.57 },
    "text": { "before": "words before", "highlight": "selected passage", "after": "words after" }
  },
  "progression": 0.57,
  "excerpt": "selected passage",
  "color": "red",
  "body": "Home note",
  "device_id": "stump-native",
  "client_ts": "2026-09-11T12:00:00Z",
  "updated_at": "2026-09-11T12:00:00Z"
}
```

`origin_device_id` is intentionally absent from the response. Without
`X-Liseur-Annotation-Capabilities: annotation-color-drawer-v1`, the server
omits unsupported extended colors such as `red` but keeps the annotation
record; with the header, the full palette and KOReader drawer are available.
This preserves pinned Liseur v0.13/v0.18 decoders, which otherwise discard an
entire record for an unsupported color.
`GET /v1/annotations/changes` and
`GET /v1/works/{work_id}/annotations?include_deleted=true` require a valid
bearer token with `sync`. Both reconcile native rows before returning the
change stream/snapshot. `POST /v1/annotations` updates use `base_rev`; stale
revisions conflict instead of overwriting. `DELETE /v1/annotations/{id}?rev=`
publishes a tombstone with a new revision and sequence.

No client change is needed to receive these records: they use the existing
work-annotation response and record schema. The pinned Liseur Android sync
calls `GET /v1/works/{id}/annotations` (`LiseurSyncApi.kt:74–84`,
`WorkResolver.kt:226–238`). The Coppice KOReader sync also pulls the full work
snapshot through `api:liseurWorkAnnotations(..., true)` and reconciles
`response.annotations` (`coppice_annotation_sync.lua:238–244, 740–752`); that
plugin does not consume `/v1/annotations/changes`, so a native edit appears on
its next normal per-book sync. The capability header remains necessary for
extended colors/drawers.

No standalone annotation SSE route or `CoreEvent` is added: clients receive
records through the existing work snapshot (and the authenticated
change-feed endpoint where used), with KOReader seeing updates on its next
normal per-book sync.


## Work, Edition, and Alias identity (implemented with limits)

liseur-sync separates an abstract Work, a concrete Edition, and identifiers (Aliases), because positions and annotations are private to a user while catalog files may be shared. The verified model uses user-scoped records, resolves aliases in priority order `sha256 > partial-md5 > source > dc > ta`, and rejects conflicting strong aliases without mutation. Title/author (`ta`) is low-confidence and is not promoted until confirmation ([ResearchLiseurSync, liseur-sync `docs/adr/0003-catalog-work-identity.md:14-83`; `docs/DESIGN.md:138-194`; `internal/store/store.go:888-955`; `internal/workident/identifiers.go:20-117`).

**Implemented:** the adapter owns a user-scoped identity layer rather than
treating a Stump `media_id` as a globally valid `work_id`:

- **Work:** `(user_id, work_id, title, author, pending)` for the user's abstract reading identity.
- **Edition:** `(user_id, edition_sha, work_id, page_count, char_count, metadata)` for the exact publication bytes and their optional derived metadata.
- **Alias:** `(user_id, kind, value, work_id)` for `sha256`, `partial-md5`, stable `source`, EPUB `dc`, or low-confidence `ta` evidence.
- **Media link:** `(user_id, media_id, work_id, edition_sha, resolution_status)` connecting the Stump file to the user's identity without making catalog identity global.

A full-file SHA-256 is computed for explicit media-backed resolution whenever
the file is readable; ordinary catalog listing does not hash the object.
Stump's sampled `media.hash` and optional `media.koreader_hash` are retained as
evidence, never substituted for a verified full digest. A bare caller-provided
`sha256` can create unverified edition evidence but cannot select a media row;
a stable `source` identifier is required to open and verify the corresponding
file. If that source-backed verification later produces the same digest, the
existing edition is upgraded to verified provenance. `partial-md5` and
`source` remain the only direct media lookups; `dc` and `ta` aliases are stored
as opaque identity evidence and do not receive approximate matching.

The TA normalizer remains a known compatibility hazard. The liseur contract
and Android `WorkIdentifiers.kt:73-108` specify Unicode NFKD, removal of
combining marks, lower-casing, punctuation/non-alphanumeric runs converted to
spaces, and normalization. The server implementation at
`metadata/entities.go:9-27` currently only lower-cases and collapses
whitespace, preserving accents and punctuation (ResearchLiseurSync,
`docs/integrating.md:154-163`). Stump therefore keeps TA-only evidence
unresolved and never silently merges because two incompatible normalizers
happen to match.
## Scope and authentication model (implemented session/device split)

The external API uses `Authorization: Bearer <token>`. Stump's
feature-gated `POST /v1/login` verifies a Stump username and password, stores a
per-user token-management session, and returns its one-hour `auth_token` with
an empty scope set. The session is accepted only by `POST /v1/tokens` and
`DELETE /v1/tokens/{id}`; using it on a sync route returns `403`, and using it
on `GET /v1/token` returns `401`.

`POST /v1/tokens` accepts the login session and `{name, scopes}` (the legacy
singleton `scope` form is also accepted), stores a separate revocable device
row, and returns `secret` exactly once with its `token_id`, `device_id`, name,
canonical `scopes`, and `expires_at`. The device bearer can call
`GET /v1/token`, which returns `id`, `device_id`, `name`, `scopes`, the stable
`account_id`, and the current `session_active_ms: true` capability; it never
returns a secret. Missing, invalid, expired, or revoked credentials return
`401`. A valid device token without `sync` returns `403` from the sync lane; a
token without `library-read` returns `403` from catalog routes.

The current upstream API contract is pinned to liseur-sync
[`906889ffe11fc7260b071c1f142aeee1fa8a1419`](https://github.com/chmouel/liseur-sync/blob/906889ffe11fc7260b071c1f142aeee1fa8a1419/docs/openapi.yaml).
Use the linked Go route/handler sources for `/v1/me/settings`, which that
OpenAPI document currently omits.

**Implemented token policy:**

- Store a per-user session or device credential in `liseur_sync_tokens`; never
  store a bearer secret in a media row, URL, browser bundle, or log. Device
  rows carry their generated `device_id`, display name, canonical scopes,
  hashed secret, expiry, and revocation timestamp.
- Require a device token with `sync` for position, session, annotation, and
  generic work-resolution routes. The token's generated device id stamps
  pushed ops, sessions, and annotations.
- Require `library-read` for folders, books, covers, downloads, series, and
  catalog-book resolution. The catalog never grants access to a hidden library
  or media row.
- Accept and report `read-insights`, `library-manage`, `library-upload`, and
  `library-delete` for capability discovery. Upload/delete and series-claim
  mutations remain deferred; `admin` is restricted to server-owner accounts
  and implies the sync scope.
- A sync-only device token can resolve and synchronize an already-known or
  side-loaded identity, but cannot browse or download the catalog without
  `library-read`.

## Spec versus implementation mismatches to isolate

The adapter must code to the behavior it can verify and make each mismatch visible in tests and telemetry. These are not reasons to silently broaden the contract:

| Area | Documented description | Observed implementation | Design response |
| --- | --- | --- | --- |
| Duplicate writes | Integrating documentation describes a byte-identical retry as `duplicate`. | `SameAnnotationPayload` additionally requires the same `device_id` and compares the complete payload (including the stored timestamp at implementation precision); a different device with identical content is not necessarily a duplicate. | Persist device and canonical payload evidence; retry with the original device identity and treat cross-device retries as a conflict/replace decision. |
| TA identity | The contract specifies accent/punctuation-insensitive NFKD normalization. | `NormalizeName` only lower-cases and collapses whitespace, so accents and punctuation remain significant. | Keep TA matches low-confidence and retain the normalizer/version; never promote on a server/client normalization accident. |
| Note field | Stump calls the user's text `annotation_text`; the wire field is `body`. | Upstream describes a note without a locator; Stump permits an optional retained locator so a CAS annotation can change kind without losing its anchor. | Map explicitly to `body`; never invent `note`, and keep highlight text separate from the user's body. |
| Locator semantics | The wire accepts any bounded reader-native JSON and replays it verbatim. | The server validates shape/size but does not interpret Readium ranges or convert reader formats. | Store raw JSON and only project to Stump when it is a valid, authorized local locator; otherwise hold it pending instead of guessing. |

Sources: ResearchLiseurSync, liseur-sync `docs/integrating.md:298-338`, `docs/openapi.yaml:2720-2794`, `internal/store/store.go:1100-1245`, `internal/api/annotations.go:84-183`, and `metadata/entities.go:9-27`.

## Implementation status and deferred work

1. **Identity and storage — implemented.** User-scoped Work/Edition/Alias/media
   links, device tokens, settings, position/annotation counters, CAS records,
   tombstones, and nullable KOReader drawer persistence are migration-backed.
2. **Sync and annotation endpoints — implemented.** Work resolution, settings,
   ops/changes/heads, positions, sessions, annotations, conflict responses,
   tombstones, and attachment side objects preserve their identity, status,
   and idempotency contracts.
3. **Native annotation exchange — implemented in both directions.**
   Linked, visible native Readium highlights/notes/bookmarks enter CAS with
   deterministic IDs; Liseur-owned records project into native rows. Both
   mirror IDs are suppressed from re-export, and deletes advance tombstones.
4. **Catalog — read-only implemented, with personal series names.** Folder and
   book pages/search, details, covers, downloads, and work resolution are
   mounted. Personal display-name changes overlay the scanned series name.
   Upload/delete, ordering, and series-claim routes remain deferred.
5. **Token administration and insights — deferred.** The provider supports
   login, device-token minting, self-introspection, and revocation, but not
   `/v1/register`, token listing/scope updates, or `/v1/insights/*`.

## Explicit unknowns and gates

The implemented sync lane is usable, but these gates remain before calling the
provider fully interoperable with the entire upstream server:

- **Release stability:** the cited liseur-sync source is an unreleased commit.
  Pinning the OpenAPI and migration behavior to a released upstream contract
  remains a deployment decision.
- **Partial-MD5 equivalence:** `media.koreader_hash` is retained as evidence,
  but Stump has not proven that every value uses the exact upstream sampling
  algorithm and byte ranges required by `partial-md5`.
- **Alias lifecycle:** catalog/source IDs and `dc` identifiers are not
  discovered by this pass, so their stability across imports and replacement
  media remains unverified.
- **TA normalization:** TA-only matching is intentionally not performed until
  the documented NFKD normalizer and the deployed upstream normalizer agree.
- **Readium projection scope:** only non-empty hrefs with parsed `locations`
  map to native rows. Custom or invalid locator shapes remain in the CAS bridge
  for the originating Liseur client.
- **Retention and remaining administration:** the current pass has no
  tombstone/session retention worker, compaction horizon, token listing or
  scope-update API, or insight route.
- **Attachment retention:** the attachment lane below stores bytes under
  `<config_dir>/attachments`. A tombstoned annotation unlinks its files, and
  the table's foreign key cascades rows when a work or an account is removed,
  but nothing sweeps the bytes a hard row delete leaves behind. A
  `<config_dir>/attachments/<annotation_id>` directory with no rows is
  therefore harmless but unreclaimed until a retention worker exists.

Until those deferred capabilities are deliberately specified, the safe
behavior is to retain raw evidence, report unresolved/conflict states, and
never make an approximate identity or locator appear exact.

## Audiobooks

The catalogue routes never list audiobook rows (`models::entity::media::AUDIO_EXTENSIONS`): Liseur reads paginated documents, and a folder book has no single file to download. Audiobooks are served by the Audiobookshelf profile (`/docs/developer/abs-compat`).
