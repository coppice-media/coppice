This page is the authoritative specification for Stump's Audiobookshelf compatibility profile. It describes the **implemented profile**, not the full Audiobookshelf API: the routes and DTOs that the pinned Audiobookshelf client calls, reproduced against Audiobookshelf **2.36.0** (`ghcr.io/advplyr/audiobookshelf:2.36.0`, captured from the `abs-ref` container). An endpoint or field not listed here is not implied to be supported.

## Scope and evidence

- **The clients that drove the profile:** Lissen **1.11.22-release** (`f30bf9be`), an Android audiobook player, and the **official Audiobookshelf app** `v0.14.0-beta` (`12025ab5`, Nuxt 2 + Capacitor). Lissen's entire server contract is one Retrofit interface, `channel/audiobookshelf/common/client/AudiobookshelfApiClient.kt` — 26 declarations, of which 4 belong to the podcast lane this profile does not serve. Every Lissen path in this page is relative to `app/src/main/kotlin/org/grakovne/lissen/`, and a bare `:NN` in the route matrix means that API-client file. The official app's 23 REST paths are in `server/ApiHandler.kt:427-854` and its socket contract in `plugins/server.js`; both are cited by file and line where they drove a decision.
- **The server that pinned the wire shapes:** a live `abs-ref` container (`abs/compose.yml`, port 13450) in the `komga-compat` sibling repository. `abs/capture/capture.sh` drives it end to end — init, login, library create + scan, item detail, play session, sync, close, progress patch, bookmarks, byte ranges, negatives, refresh — and writes every response verbatim to `abs/capture/<name>.json`, so DTOs are diffed against the reference rather than guessed.
- **Licensing boundary:** Audiobookshelf is GPL-3.0 and Stump is MIT. Nothing in `crates/abs` is derived from Audiobookshelf source; the profile is written from observed behaviour and captured JSON only. Lissen's own Retrofit declarations (paths, query parameters, field names) are cited as the client contract, which is what a client contract is for.
- **Contract types** live in [`crates/abs/src`](https://github.com/stumpapp/stump/tree/nightly/crates/abs/src) (`stump_abs`): DTOs in `dto.rs`, the audio projection in `model.rs`, tokens in [`auth.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/abs/src/auth.rs), allocated identities in [`ids.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/abs/src/ids.rs), the socket lane in [`socket/`](https://github.com/stumpapp/stump/tree/nightly/crates/abs/src/socket). The server adapter is `apps/server/src/routers/abs_backend.rs`; persistence comes from migrations `m20260935_000000_add_abs_compat` (`abs_ids`, `abs_sessions`) and `m20260943_000000_add_abs_session_play_method`.
- **Replay harness:** `specs/abs.hurl` with `make replay-abs`, plus `make replay-abs-diff` (a JSON key-set diff of Stump's responses against `abs-ref`), in the `komga-compat` sibling repository; bring-up and capture steps are in its `abs/README.md`.
- **Verification status:** no device run of either app is recorded against Stump yet, and Lissen is still the only recorded live ABS client. The socket lane was verified at the protocol level: frame-for-frame against `abs-ref` 2.36.0, and end to end with a `socket.io-client@4` script (`transports: ['websocket']`) against a fixture instance — `init` on connect, `user_item_progress_updated` after a REST progress patch. The captures establish the target wire shape, not that either app works.

### Non-goals

- This is not a claim of complete Audiobookshelf server compatibility.
- Podcast libraries, playlists, ereader devices, and OIDC are outside the profile ([Known deviations](#known-deviations)). Collections and playlists answer an empty page rather than a `404`, because the app opens both tabs.
- Audiobookshelf endpoints outside the route matrix answer `404`.

## Enabling

Two independent gates must both allow the profile, the same pattern as the Komga and Kavita adapters:

1. **Cargo feature:** the server must be compiled with the `abs` feature, which is on in `headless` and `full`. The route module and the optional `stump_abs` contract crate are compiled only under that feature.
2. **Runtime configuration:** the effective `enable_abs` setting must be `true`, normally set with `STUMP_ENABLE_ABS=true` ([`core/src/config/protocols.rs`](https://github.com/stumpapp/stump/blob/nightly/core/src/config/protocols.rs), `StumpConfig.protocols.enable_abs`, default `false`).

When the setting is off the routes are **not registered at all**, so every path in the matrix answers `404` rather than `401` or `403`. `STUMP_ENABLE_ABS=true` on a binary compiled without the `abs` feature mounts nothing; the native API is unaffected either way.

Every route is mounted at the server root, because Audiobookshelf clients build absolute paths from a bare host: `GET /ping`, `POST /login`, `POST /auth/refresh` and the `/api/...` tree. Lissen concatenates the host and the declared path with no prefix (`AudiobookshelfApiClient.kt:40-194`), and builds `/api/items/{id}/file/{ino}` itself (`channel/audiobookshelf/common/AudiobookshelfChannel.kt:48-64`), so there is no configurable base path to hide behind.

## Authentication

### The three tokens

`abs-ref` 2.36.0 issues three JWTs from one login. All three are `HS256`; Stump signs them with its own access-token secret and reproduces the claim sets and lifetimes ([`crates/abs/src/auth.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/abs/src/auth.rs)).

| Field | Claims | Lifetime | Purpose |
| --- | --- | --- | --- |
| `user.token` | `{userId, username, iat}` | none — never expires | The legacy Audiobookshelf token. Lissen falls back to it when no access token is stored (`channel/common/OkHttpClient.kt:55`) |
| `user.accessToken` | `{userId, username, jti, type:"access", iat, exp}` | 1 h | The bearer for every authenticated request |
| `user.refreshToken` | `{userId, username, jti, type:"refresh", iat, exp}` | 30 d | Only buys a new pair at `POST /auth/refresh`; rejected as a request credential |

Stump adds one claim Audiobookshelf does not have: `device`, the `devices.id` row the login registered. It is optional, ignored by clients, and carries the per-device library scope into every later request on that token.

Header semantics, observed on the reference and required by the client:

- `x-return-tokens: true` on `POST /login` and `POST /auth/refresh` makes `user.refreshToken` a real token; the key is always present and `null` otherwise. Lissen sends the header on both (`:165`, `:171`), and so does the capture rig (`capture.sh:29`, `capture.sh:141`).
- `x-refresh-token: <jwt>` carries the refresh token to `POST /auth/refresh` — it is a header, not a body field (`:173`).
- `login.json` also carries `isOldToken: true`; `refresh.json` does not carry the key at all.

Lissen's refresh loop is worth knowing, because it decides what a wrong `401` costs: any `401` triggers one refresh and one retry of the same call, guarded by a mutex and a token-identity check so concurrent requests refresh once (`channel/audiobookshelf/common/api/AudioBookShelfApiService.kt:41-106`). A `401` that a refresh cannot fix therefore surfaces to the user after two round trips, not one.

### Credentials accepted

| Credential | Where | Behaviour |
| --- | --- | --- |
| `Authorization: Bearer <jwt>` | any authenticated route | An access or legacy token minted by this profile. A refresh token is refused except at `POST /auth/refresh` |
| `Authorization: Bearer stump_...` | any authenticated route | A Stump API key |
| `?token=<jwt \| api key>` | any authenticated route | The reference accepts it too (`capture/negatives.txt`: `query token /api/me: 200`), which is how a media player that cannot set headers streams audio |
| `Authorization: Basic <base64>` | any authenticated route | Stump username and password |

An unauthenticated request is `401` (`negatives.txt`: `unauthenticated /api/me: 401`), and a wrong password on `POST /login` is `401` (`bad password /login: 401`). A `POST /login` registers a `devices` row of kind `ABS`, so `devices.library_scope` restricts what that one token sees — enforced in the shared query funnel, not in this adapter, exactly as for Kobo, Komga, Kavita, OPDS, KOReader and GraphQL ([devices — library scope](/docs/developer/devices#library-scope)).

Audio bytes are fetched by ExoPlayer through the same authenticated OkHttp client as the API calls (`playback/service/LissenDataSourceFactory.kt:37-45` wraps `createOkHttpClient`, whose interceptor sets the bearer at `channel/common/OkHttpClient.kt:55-57`), so `GET /api/items/{id}/file/{ino}` is an authenticated route with `Range` support, not a public asset.

#### Offline sessions

The official app plays downloaded books offline and uploads whole sessions afterwards — one per call while it plays (`media/MediaProgressSyncer.kt:274`), the backlog in one request on reconnect. The body is its `createPartialPlaybackSession` (`ApiHandler:650-668`): identity, book, `currentTime`, `timeListening` and `updatedAt`, plus `deviceInfo`.

`updatedAt` is the **device clock time of the position**, not of the upload, and that is what the merge turns on: the profile passes it as the source time of the reading-state update, so the unified head's ordinary conflict rule decides. An upload dated more than the 60 s tolerance behind the head that also reports **less** progress is recorded as provenance and does not move the position; anything else moves it. `local-all` reports that decision per session as `progressSynced`, which is what the app logs and what tells it the server was already ahead. A session that names a book the caller cannot see comes back as `success: false` with an error, never as a status code: the app matches results to stored sessions by id and only deletes the ones that succeeded (`ApiHandler:780-795`).

Either way the upload becomes a listening-history row with `playMethod: 3` (Local) — the listening happened even when the position did not move. That is what `abs_sessions.play_method` (migration `m20260943_000000_add_abs_session_play_method`) exists for: a history that could not tell offline listening from streamed listening would report every uploaded session as if the server had served the bytes.

#### Personalized shelves

The app's Android Auto browser keys on four shelf ids and refuses to decode a `type` outside `book|series|authors|episode|podcast` (`media/MediaManager.kt:215-290`, Jackson `@JsonSubTypes`). The profile serves `continue-listening` (book), `recently-added` (book), `recent-series` (series), `discover` (book) and `newest-authors` (authors), with abs-ref's ids, labels and `labelStringKey`s. `newest-episodes` is podcast-only and is not served.

Reference status codes reproduced from `capture/negatives.txt`: unknown item `404`, unknown library `404`, unknown library items `404`, unknown progress `404`, unknown session sync `404`.

### Listing parameters

`sort` takes exactly the four values Lissen can send (`library/converter/LibraryOrderingRequestConverter.kt:16-19`):

| Lissen option | `sort` value |
| --- | --- |
| Title | `media.metadata.title` |
| Author | `media.metadata.authorName` |
| Created at | `addedAt` |
| Updated at | `mtimeMs` |

`desc` is the string `"0"` (ascending) or `"1"` (descending) — never a boolean (`LibraryOrderingRequestConverter.kt:24-25`). `minified` defaults to `"1"` and `collapseseries` to `"0"` (`:87`, `:89`).

`filter` is `"<key>.<base64 of the value>"` (`common/api/EncodeLibraryFilter.kt:5-8`, `Base64.NO_WRAP`). Lissen sends two forms: the hard-coded `progress.bm90LWZpbmlzaGVk` — base64 `not-finished`, its "hide completed" toggle (`library/converter/LibraryFilteringRequestConverter.kt:15`) — and `series.<base64 series id>` when it drills into a collapsed series (`common/api/AudioBookshelfRepository.kt:158`, `library/LibraryAudiobookshelfChannel.kt:91-94`). The envelope echoes the value back as `filterBy`, which is absent from the response entirely when no filter was sent.

The response envelope is `{results, page, total, limit, offset, sortBy, sortDesc, mediaType, minified, collapseseries, include}` plus `filterBy` when filtered; Lissen only requires `results`, `page` and `total` to be present and non-null (`library/model/LibraryItemsResponse.kt`), but the whole reference envelope is emitted.

### Where the capture and the client disagree

- **`POST /api/authorize`** carries `user.token` alone on the reference — no `accessToken`, no `refreshToken` (`authorize.json`), unlike `login.json` and `refresh.json`, which carry all three. Stump matches the capture: Lissen reads no token from this route, only `user.username` (required) and the optional `serverSettings.version`/`buildNumber` (`common/model/connection/ConnectionInfoResponse.kt`).
- **`GET /api/libraries/{id}/personalized`** on the reference returned four shelves — `recently-added` / `LabelRecentlyAdded`, `recent-series` / `LabelRecentSeries`, `discover` / `LabelDiscover`, `newest-authors` / `LabelNewestAuthors` — and **no** continue-listening shelf, because nothing was mid-listen when the capture ran. Lissen reads exactly one shelf, selected by `labelStringKey == "LabelContinueListening"` (`common/converter/RecentListeningResponseConverter.kt:17,34`), so a profile that emitted only what the capture contains would leave its home screen permanently empty. Stump therefore serves `continue-listening` with `labelStringKey: "LabelContinueListening"` alongside the four the capture shows ([Personalized shelves](#personalized-shelves)).
- **`serverSettings.buildNumber`** is the JSON number `1` on the reference, while Lissen types the field as `String?` (`common/model/connection/ConnectionInfoResponse.kt`). Moshi's `nextString()` coerces a JSON number, so the number decodes; the profile emits the number to match the reference (`stump_abs::ABS_BUILD_NUMBER`) rather than the client's declared type. This is the same class of mismatch that broke Komelia on Readium `rel` ([Komga adapter](/docs/developer/komga-compat)), so it is worth knowing which side each field follows.

## socket.io

Audiobookshelf pushes state changes over socket.io, and the official app **hides its bookmark button unless the socket is connected** — `v-if="… && socketConnected"` (`components/app/AudioPlayer.vue:68`, state in `store/index.js:15,176`). A REST-only server therefore costs that app a feature no REST route can give back, which is why this lane exists. Lissen has no socket.io dependency at all and is unaffected either way.

The lane is a **sink**: it holds no reading position, no session and no user list of its own. Everything it emits is translated from a change another lane already committed, so a dropped socket loses notifications, never data.

### Framing

Hand-rolled in [`crates/abs/src/socket/protocol.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/abs/src/socket/protocol.rs) from the MIT-licensed `socketio/engine.io-protocol` and `socketio/socket.io-protocol` specifications, and verified frame for frame against `abs-ref` 2.36.0. No socket.io crate is linked: the app forces `transports: ['websocket'], upgrade: false` (`plugins/server.js:36-42`), which reduces both protocols to the closed set of text frames below, and a server crate would bring its own connection model, namespaces and polling transport for a lane that needs none of them.

```text
GET /socket.io/?EIO=4&transport=websocket        (also /socket.io, no redirect between them)
server → 0{"sid":…,"upgrades":[],"pingInterval":25000,"pingTimeout":20000,"maxPayload":1000000}
client → 40                     Socket.IO CONNECT, default namespace
server → 40{"sid":…}            a second id, the socket's, exactly as abs-ref answers
client → 42["auth","<jwt>"]
server → 42["init",{userId,username,usersOnline:[…]}]   or  42["auth_failed",{"message":…}]
server → 2      client → 3      heartbeat, every 25 s, 20 s to answer
```

`upgrades` is empty because there is no second transport to upgrade to. The heartbeat is server-initiated per Engine.IO v4: a socket that misses a pong for `pingTimeout` is closed. A client `2` is answered with a `3`. A namespace other than `/` is refused with `connect_error` and the socket stays open. An unknown frame — a binary attachment, an ack, garbage — is ignored, never fatal.

### Authentication

The upgrade request carries **no credential**: a socket.io client cannot put a header on it. The endpoint is therefore mounted outside the profile's auth middleware, and the token arrives afterwards in the `auth` event — the same HS256 token `POST /login` mints, verified with the same secret ([`crates/abs/src/auth.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/abs/src/auth.rs)). A refresh token is refused: it buys a new pair at `POST /auth/refresh` and must not open a live channel.

A failed `auth` answers `auth_failed` and **keeps the socket open**, because the app retries on the same connection once it has refreshed. Nothing at all is pushed before a successful `auth`: an unauthenticated socket has no user to scope visibility by. When the token's `exp` passes, the socket is closed — the client reconnects and re-`auth`s with a fresh token, exactly as it does after a REST `401`. One user may hold several sockets; `usersOnline[].connections` reports how many, from the per-server presence registry the lane keeps.

### Events emitted

| Event | Source | Payload |
| --- | --- | --- |
| `init` | a successful `auth` | `{userId, username, usersOnline[]}` |
| `auth_failed` | a rejected `auth` | `{message}` |
| `user_item_progress_updated` | `ReadingHeadChanged` for this user, on an audio book they may see — **any** protocol's write, including Kobo, KOReader and the native API | `{id, sessionId, data}`, where `data` is the same `MediaProgress` object `GET /api/me/progress/{id}` answers. The app's store applies `payload.data` wholesale (`plugins/server.js:117-121`) |
| `user_updated` | the same head change, and every bookmark write | The whole `/api/me` user object, built by the one function `GET /api/me` uses |
| `items_added` | `CoreEvent::CreatedMedia` | The new books, minified, filtered to the ones this user may see |
| `item_updated` | `CoreEvent::ProviderSeriesMaterialized` | One event per audible book of the series, minified |

**`sessionId` is always `null`.** abs-ref names the playback session that moved the position; a Stump reading head is shared by every protocol, so the change that reached this lane may not have come from an ABS session at all, and naming an unrelated open one would be a lie. The app does not read the field.

**Bookmarks are published by the profile's own routes**, not by a core event: nothing outside `crates/abs` writes an ABS bookmark, so `POST`/`PATCH`/`DELETE /api/me/item/{id}/bookmark` announce themselves on the bus. This is what keeps the socket-gated bookmark UI live.

**Not translated:** a filesystem rescan announces a count and a series (`CoreEvent::CreatedOrUpdatedManyMedia`) with no media ids, so it cannot name an item. Every other core event is server business no Audiobookshelf client subscribes to.

### What the app gets, against abs-ref

| abs-ref emits | This lane | Why |
| --- | --- | --- |
| `init`, `auth_failed`, `user_updated`, `user_item_progress_updated` | yes | The four the app's socket plugin subscribes to (`plugins/server.js:52-61`) |
| `playlist_added` | no | Playlists are outside the profile; the app uses the event only to decide whether to show a playlists tab |
| `user_online` / `user_offline` | no | Presence broadcast to other users. The app ignores both |
| `user_stream_update`, `user_session_closed` | no | Live stream state per socket, which this lane does not track |
| `item_added`/`_removed`, `library_*`, `series_*`, `author_*`, `collection_*` | partly (`items_added`, `item_updated`) | Only the ones a Stump core event can name |
| `task_*`, `track_*`, `episode_download_*`, `metadata_embed_queue_update`, `backup_applied`, `notifications_updated`, `rss_feed_*`, `share_*`, `admin_message` | no | Server administration, podcast downloads and RSS feeds, none of which the profile serves |
| `cover_search_result`, log listeners, `cancel_scan` | no | Socket-only administration surfaces |

The endpoint is gated exactly like the REST surface: the `abs` cargo feature and `STUMP_ENABLE_ABS`. With the profile off, `/socket.io` is not registered and answers `404`.

## Identity mapping

Audiobookshelf identifies everything by uuid and so does Stump, so libraries, library items and series are exposed **under their Stump uuid verbatim** — no mapping, no lookup, no second identity system. Three Audiobookshelf ids have no Stump uuid to borrow and are allocated in the `abs_ids` table (migration `m20260935_000000_add_abs_compat`, accessors in [`crates/abs/src/ids.rs`](https://github.com/stumpapp/stump/blob/nightly/crates/abs/src/ids.rs)):

| `abs_ids` kind | Keyed by | Why it exists |
| --- | --- | --- |
| `author` | the author's name | Stump has no author row at all; authors are comma-separated `media_metadata.writers` strings |
| `book` | the media id | `media.id` is a second uuid beside `libraryItem.id` in the Audiobookshelf item shape (`item.json`) |
| `folder` | the library id | `libraryFolder.id` is a third uuid beside the library's own (`library_include_filterdata.json`) |

Ids are allocated on first use, never reused, and survive restarts; the table is keyed by the Audiobookshelf uuid so `GET /api/authors/{id}` resolves a uuid back to an author name in one indexed lookup.

| Audiobookshelf | Stump |
| --- | --- |
| Library | Library, if it contains at least one audio file. `mediaType` is always `book`; `folders[0]` is the library path under an allocated `folder` id |
| Library item | One media row whose extension is an audio container. `ino` echoes the item's own id; `libraryFiles[]` is that one file |
| `media` (book) | The same media row's audio metadata, under an allocated `book` id |
| `media.audioFiles[]`, `media.tracks[]` | `media_audio_tracks` rows, ordered by `index`. On the wire `index` is 1-based (`item.json`), while `ino` is the 0-based Stump track index |
| `media.chapters[]` | `media_audio_chapters` rows: `{start, end, title, id}` with `id` the 0-based chapter index |
| `media.audioFiles[].chapters[]` | The book's chapters that fall inside that file, clipped to it and rebased to the file's own timeline — abs-ref reads them from each file's embedded marks, so they are file-relative while `media.chapters[]` is publication-relative (`mapper::file_chapters`) |
| `audioFiles[].metaTags` | Only tags Stump read are emitted, as abs-ref does. `tagAlbum` is the book title (`media_metadata.title`, falling back to `series`): the probe reads a folder book's title from the shared `album` tag in the first place. `tagEncoder` is never emitted — the probe does not keep it |
| `deviceInfo` | `{deviceId, clientName, clientVersion}` are stored with the session; `deviceName`, `manufacturer`, `model`, `sdkVersion` are echoed from the `play` request and `null` when read back through `GET /api/session/{id}` |
| Series | Stump series, exposed as the `series`/`collapsedSeries` shape |
| Author | A `media_metadata.writers` name under an allocated `author` id; `numBooks` counts the media carrying that name |
| `MediaProgress` | The unified reading state (below) |
| Bookmark | A Stump bookmark on the media, addressed by whole-second `time` |

## Units

Audiobookshelf mixes two units in one document, and the profile converts at the boundary:

| Kind of value | Wire unit | Examples |
| --- | --- | --- |
| Positions and durations | **seconds**, fractional | `mediaProgress.currentTime: 4.5`, `duration: 12`, `chapters[].start`/`end`, `audioTracks[].startOffset`, `timeListened`, bookmark `time` |
| Timestamps | **milliseconds** since the epoch, integer | `lastUpdate`, `startedAt`, `finishedAt`, `addedAt`, `updatedAt`, `mtimeMs`, `ctimeMs`, `birthtimeMs` |

Stump stores every audio time in **milliseconds** — `media_audio.duration_ms`, `media_audio_tracks.duration_ms`/`start_offset_ms`, `media_audio_chapters.start_ms`/`end_ms` — so seconds-valued fields are divided on the way out and multiplied on the way in, and millisecond timestamps pass through unchanged. `progress` is the fraction `0.0..=1.0`, not a percentage.

Both units in one object, verbatim from `capture/progress.json` — `currentTime` is 4.5 seconds into a 12-second book, `lastUpdate`/`startedAt`/`finishedAt` are millisecond epochs. `isFinished`/`progress` are `true`/`1` here because `capture.sh` is idempotent and a previous pass had already sent `PATCH {"isFinished":true}` for this item; they are not computed from the `currentTime` in the same document (`progress_after_close.json` shows `currentTime: 6` with `progress: 0.5`).

```json
{
  "id": "20954ded-d980-4d96-863e-4d634c2fd188",
  "userId": "eea931a8-d6a9-4048-98b3-275dfaa18a5b",
  "libraryItemId": "12e6822c-56c4-48bd-8a11-ef62420bc8f3",
  "episodeId": null,
  "mediaItemId": "3e1e006c-5490-4630-8475-8f72a5e78e25",
  "mediaItemType": "book",
  "duration": 12,
  "progress": 1,
  "currentTime": 4.5,
  "isFinished": true,
  "hideFromContinueListening": false,
  "ebookLocation": null,
  "ebookProgress": 0,
  "lastUpdate": 1788699586130,
  "startedAt": 1788699327363,
  "finishedAt": 1788699586130
}
```

`mediaItemId` is the `abs_ids` `book` id and `episodeId` is always `null` here, since the podcast lane is not served.

## Reading progress

An Audiobookshelf position is a Stump `Position::Time { position_ms, track_index }` reading state — the same unified reading state Komga, Kavita, Kobo and KOReader write ([unified reading state](/docs/developer/unified-reading-state)). Listening progress from an Audiobookshelf client is therefore visible everywhere else in Stump, and progress made elsewhere on the same audiobook is visible to it.

- `POST /api/session/{id}/sync` writes `currentTime` (seconds) as `position_ms` with the track the offset falls in, and adds `timeListened` seconds to the session's listening total. Lissen sends `{currentTime, timeListened}` only (`common/model/playback/ProgressSyncRequest.kt`); `duration` is accepted and ignored.
- `POST /api/session/{id}/close` does the same, then closes the session.
- `PATCH /api/me/progress/{itemId}` is a partial update: `{currentTime}` moves the head, `{isFinished}` sets or clears completion.
- `GET /api/me/progress/{itemId}` and the `mediaProgress[]` array in `/api/me` project the reading state back: `currentTime` in seconds, `progress` as a fraction, `isFinished`, and `lastUpdate`/`startedAt`/`finishedAt` in milliseconds. Lissen requires `libraryItemId`, `currentTime`, `isFinished`, `lastUpdate` and `progress` to be present (`common/model/MediaProgressResponse.kt`).

A session lives in `abs_sessions`. The important asymmetry is that `POST /api/items/{id}/play` returns a session whose id is what Lissen then syncs against — the sync path parameter is the **session** id, not the item id, despite Lissen naming the parameter `itemId` (`:145-149`, `common/api/library/AudioBookshelfLibrarySyncService.kt:17-28`). Lissen never calls `close`, so a session is closed by the server, not the client.

Lissen only reads `{id, libraryItemId}` from the play response (`common/model/playback/PlaybackSessionResponse.kt`) and builds its own audio URLs from the item's `audioFiles[].ino` (`common/AudiobookshelfChannel.kt:48-64`, `library/converter/BookResponseConverter.kt:54`). `contentUrl` in `audioTracks[]` is therefore reproduced for correctness, not because this client follows it — but `ino` must round-trip exactly, because it is the only thing standing between the item and its bytes.

One track, trimmed from `capture/play_session.json` (`metadata` and the ffprobe-derived fields elided) — `index` is 1-based, `ino` is the path segment, `startOffset` and `duration` are seconds:

```json
{
  "index": 1,
  "ino": "105885034",
  "duration": 12,
  "codec": "aac",
  "mimeType": "audio/mp4",
  "title": "Analytical Engine.m4b",
  "startOffset": 0,
  "contentUrl": "/api/items/12e6822c-56c4-48bd-8a11-ef62420bc8f3/file/105885034"
}
```

## Known deviations

| Deviation | Reason |
| --- | --- |
| **Podcast libraries are not served.** `mediaType` is always `book`, so a client never enters its podcast lane | Stump has no podcast model — no feed, no episode, no download queue. Lissen has a complete podcast channel (`channel/audiobookshelf/podcast/**`, declarations at `:92-100`, `:118-123`, `:130-133`, `:151-156`) which stays dormant because it is selected by library type (`channel/audiobookshelf/AudiobookshelfChannelProvider.kt:26-30`) |
| Only media whose extension is an audio container (`.m4b`, `.m4a`, `.mp3`, `.opus`, `.ogg`, `.flac`) appear, and a library with no audio at all is hidden from `GET /api/libraries` | Audiobookshelf has no per-page reading position, so a Stump ebook has nothing to say here. A visible library full of unplayable items is worse than an absent one |
| `libraryItem.ino` echoes the item's own id and `audioFiles[].ino` is the 0-based track index — neither is a filesystem inode | The reference reports real inode strings (`"105885034"` in `item.json`), but Stump has no inode that survives a rescan. The values only need to be stable and to round-trip through `GET /api/items/{id}/file/{ino}`, which they do |
| `media.id`, `libraryFolder.id` and author ids come from `abs_ids` | They are second, third and fourth uuids for things Stump identifies once, or not at all ([Identity mapping](#identity-mapping)) |
| `playMethod` is always `0` (DirectPlay) | Stump never transcodes. `forceTranscode` in the play request is accepted and ignored |
| `ereaderDevices` is always `[]` | Stump's Kindle/ereader registry is not exposed through this profile; nothing in the client reads it |
| `serverSettings` fields Stump has no analogue for carry the `abs-ref` 2.36.0 defaults verbatim | The block is large, mostly about scanner and metadata behaviour Stump implements differently, and clients read a handful of flags from it. Reproducing the reference defaults is honest about what is not configurable here |
| No `/api/search/books`, no playlists, no collections, no session list | Lissen never calls them, and each would need a mapping decision that no client is asking for. `numUserPlaylists` is `0` |
| `GET /api/authors/{id}/image` is always `404` | Stump stores no author images; the client's author-image fetch simply fails (`common/AudiobookshelfChannel.kt:77-80`) |
| `POST /api/authorize` omits `accessToken`/`refreshToken` | Matching the reference (`authorize.json`), not the login envelope |
| `recent-series` and `newest-authors` shelves are not served, and `continue-listening` is served although it is absent from the capture | The client reads exactly one shelf, by `labelStringKey == "LabelContinueListening"` ([the note above](#where-the-capture-and-the-client-disagree)) |
| A refresh token is refused everywhere except `POST /auth/refresh` | The reference gives it a `type:"refresh"` claim and a 30-day life; accepting it as a request credential would turn a long-lived token into a session token |
