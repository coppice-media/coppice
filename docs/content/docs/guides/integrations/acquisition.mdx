Coppice owns a metadata-backed request ledger and an explicit, manager-triggered
MAM Bridge integration for approved requests. Metadata search identifies works;
a result is never evidence that a file was found or acquired.

## What Coppice owns

The shipped request system keeps:

- request metadata and optional destination intent;
- requester identity, permissions, and per-user visibility;
- mine/all views for authorized managers;
- operator approval and rejection decisions;
- request notifications; and
- the social recommendation-to-request handoff.

An approved request does not search or grab automatically. A manager with
`AcquireReleases` must explicitly search releases for that approved request and
confirm the selected grab. A completed handoff is copied into staged ingest;
Editor approval then fulfils the request and notifies its owner.

```text
metadata search or recommendation
  -> request
  -> permission and visibility checks
  -> operator approval
  -> manager explicitly searches and confirms a release grab
  -> completed handoff copied into Editor staged review
  -> ingest approval fulfils request and notifies requester
```

## MAM Bridge

The Coppice server talks to the separately authenticated MAM Bridge sidecar;
the browser never calls the bridge and never receives its token. The feature
requires a headless/full build with `mam-acquisition` and the default-off
`STUMP_ENABLE_MAM_ACQUISITION=true` runtime switch. Configure:

- `MAM_BRIDGE_URL` — the bridge base URL (HTTPS, except loopback HTTP for
  development);
- `MAM_BRIDGE_TOKEN_FILE` — path to a file containing the bearer token. The
  token is not returned in GraphQL or logged;
- `MAM_BRIDGE_HANDOFF_ROOT` — optional local path corresponding to the bridge's
  `/downloads` mount (for example, `/nfs/downloads` in development); and
- `MAM_BRIDGE_SOURCE_ROOT` — optional source-worker root label covering
  `/downloads`. When configured, Coppice uses the source worker's verified
  read/materialization path instead of the local mapped path.

Search is on demand for an approved request and cached on that request;
`cachedReleaseSearch` does not contact MAM. The first successful query is
limited to the bridge's five-result probe. A paused search returns
“Search is paused, check the bridge”; Coppice does not re-enable or reset the
bridge. Rate limits report how many seconds to wait. A manager must explicitly
confirm each grab; the server sends the bridge's required confirmation text.
Active grabs are refreshed by the background job system.

When a completed manifest points below `/downloads`, Coppice copies the file or
folder into staged ingest. It never moves, renames, or deletes the source, so
MAM can continue seeding. With a source worker, bytes are verified against the
reported size and digest during materialization; otherwise the configured local
mount must contain the handoff path. The Editor remains the publication review:
approving the staged item marks the linked approved request fulfilled and
notifies the requester.

## Ingest review

Acquisition ends at the existing staged-ingest workflow. It does not bypass
metadata review, quality checks, or Editor approval. See
[modular ingest](/docs/developer/modular-ingest) for that lifecycle and
evidence.

## Read-aloud alignment is separate

Read-aloud alignment begins only after an ebook and audiobook pair already
exists and has been confirmed. It is not metadata search, request approval, or
acquisition. See [read-aloud](/docs/developer/read-aloud) for that independent
workflow.
