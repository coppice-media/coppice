# KOReader Sync

Coppice implements the KOReader-compatible sync API under
`/koreader/{api_key}`. The server surface is **Shipped** and
**Contract-tested**. Liseur's KOReader-sync flow is **Device-tested**, but the
native KOReader app itself has not been loaded against Coppice. The first-party
`stump.koplugin` remains **Source-only**; direct native-app verification is
**Blocked**. See the [compatibility matrix](/docs/guides/integrations/compatibility)
and [KOReader developer record](/docs/developer/koreader-plugin).

<Callout title="Permission required">
	This functionality is gated behind the `ACCESS_KOREADER_SYNC` and `ACCESS_API_KEYS` user permissions. To learn more about permissions, see the [permissions](/docs/guides/access-control/permissions) guide.
</Callout>

## What is synchronized

KOReader sends a book hash, an x-pointer progress string, a percentage, and a
device identifier. Coppice stores those values for KOReader lookups. The
current adapter supports **hash-based matching only**; it does not fall back to
matching by filename.

## Setup

<Steps>

<Step>

### Install KOReader

Install [KOReader](https://koreader.rocks/) on the device you intend to use.
The installation itself is outside Coppice.

</Step>

<Step>

### Compile and enable the sync route

The server must be compiled with the Cargo `koreader` feature. The default
`full` and `headless` profiles include it. To prove a smaller composition, use
the exact KOReader-only command from the [modular deployment
guide](/docs/guides/configuration/modular-deployment):

```sh
ENABLE_KOREADER_SYNC=true cargo run -p stump_server --bin stump_server \
  --no-default-features --features koreader
```

For an existing full server, set `ENABLE_KOREADER_SYNC=true`, or set
`enable_koreader_sync=true` in the `Stump.toml` configuration file. The runtime
switch cannot add the route to a binary compiled without `koreader`.

</Step>

<Step>

### Generate KOReader-compatible hashes

Enable **KoReader-compatible hashes** for each library that will sync. The
scanner must calculate the KOReader binary hash for the file; a missing hash
causes the server lookup to return `404`.

For an existing library, run a scan configured to recompute hashes. The
[scanner guide](/docs/guides/fundamentals/scanner) explains the library setting
and scan controls.

</Step>

<Step>

### Add the device in the Home app

Open the Home app at `/app`, choose **Devices** → **Add client**, and select
**KOReader**. The [Devices guide](/docs/guides/features/devices) explains the
one-time secret, endpoint URL, and username. Copy those values into KOReader's
**Progress sync** → **Custom sync server** configuration before closing the
dialog; the full secret is shown only once.

</Step>

<Step>

### Fallback: Create an API key

<Callout type="warn" title="API-key fallback">
	This still works, but a raw API key does not provide a device kind, per-device
	library scope, last-seen tracking, or device credential rotation. For reader
	devices, the Home app flow above is the preferred path.
</Callout>

<Callout type="warn">This step requires the `ACCESS_API_KEYS` user permission.</Callout>

In the Coppice web UI:

1. Open app settings (`/settings/app`).
2. Open **API keys** (`/settings/app/api-keys`).
3. Select **Create API key**.
4. Grant at least `ACCESS_KOREADER_SYNC`.
5. Save the complete value when it is shown.

</Step>

<Step>

### Configure the sync server

In KOReader, open **Progress sync** → **Custom sync server** and enter:

```text
http(s)://your-server(:port)(/baseUrl)/koreader/{api_key}
```

The `api_key` is the complete Coppice API key for the API-key fallback. With the
Home app flow, use the complete endpoint URL and username shown by the app
instead.

</Step>

<Step>

### Register and choose binary matching

KOReader asks for a username and password during registration even when the
server URL carries an API key. Enter any values; Coppice currently accepts the
API-key route only and does not validate those placeholder credentials.

Then open **Progress sync** → **Document matching method** and select
**Binary**. Filename matching is not supported by the current adapter.

</Step>

</Steps>

## Troubleshooting 404 responses

A `404` on a progress `PUT` usually means the library item has no stored
KOReader-compatible hash, or KOReader is using filename matching instead of
binary matching. Enable the library hash setting, recompute hashes with a scan,
and retry with **Binary** selected.

## Evidence and limits

- **Shipped:** the API-key route, hash lookup, progress PUT/GET, and stored
  KOReader progress fields.
- **Contract-tested:** server probes cover `users/auth` and progress requests.
- **Device-tested:** Liseur's KOReader-sync client path has run against the
  server.
- **Source-only:** the `stump.koplugin` source has been reviewed and its route
  contract is documented, but it has not been loaded by KOReader.
- **Blocked:** a direct KOReader app/device run and any device-specific UI or
  firmware behavior remain unverified.
- **Planned:** device management UI and richer translation of x-pointer data
  into the native reader's position model are future work.
