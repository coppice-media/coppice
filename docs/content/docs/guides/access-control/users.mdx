Coppice has two account types:

- **Server Owner**: The first account created on an empty server. The owner has
  full control, including locking and deleting other accounts.
- **Server Member**: An account whose access is determined by its assigned
  permissions, library visibility, and age restrictions.

The server does not automatically open a registration screen. To bootstrap a
local owner on an empty server, send a JSON request with `username` and
`password` to `POST /api/v2/auth/register`, then sign in at `/app/login`. Once
an active account exists, unauthenticated registration is rejected. If OIDC is
configured with registration enabled, the first OIDC account on an empty server
becomes the owner instead. The Home **Users** screen manages subsequent local
accounts; it does not offer the initial-registration flow
(`apps/server/src/routers/api/v2/auth.rs`, `oidc.rs`).

## Management

<Callout title="Permission required">
	The **Users** screen is listed under *Manage* in the Home app for the server owner and for users
	with `READ_USERS`, who see the list without edit controls. Creating and editing accounts needs
	`MANAGE_USERS`; locking, signing out, and deleting accounts are reserved for the server owner. To
	learn more about permissions, see the [permissions](/docs/guides/access-control/permissions)
	guide.
</Callout>

### Create a user

<Steps>

<Step>
### Open the Users screen

Open the Home app (`/app`) and choose **Users** in the *Manage* group of the sidebar (`/app/users`). It lists every account with its status, last sign-in, active sessions, and permission count.
</Step>

<Step>
### Click the `New user` button

This opens the form for a new local account.
</Step>

<Step>
### Fill out the form

- **Username** and **Password**: what the user signs in with. Share the password with them directly; whether they may change it later is the _Change own password_ permission
- **Permissions**: grouped by area. A new account starts with none. Ticking a permission also grants the permissions it includes, which show as _Included_
- **Age restriction**: the _optional_ **highest** age rating the user can access. For example, if you enter `13` then the user will be able to access books with an age rating of `13` or lower. See the [age restrictions](/docs/guides/access-control/age-restrictions) section of the Access Control guide for more information
  - **Note**: If you check _Also hide books without a rating_, then the user will only be able to access books that:
    1. _Explicitly_ have an age rating set (on the book or its series)
    2. The age rating is less than or equal to the user's age restriction

    Otherwise, the user will be able to access books that _do not_ have an age rating set
- **Session limit**: the _optional_ number of sessions that may be signed in at once. At the limit, signing in again ends the oldest session
</Step>

<Step>
### Click the `Create user` button

If the server refuses the account, its reason is shown above the button.
</Step>

</Steps>

### Editing a user

On the Users screen, click **Edit** on the user's row. The form starts from the user's current permissions, age restriction, and session limit; saving replaces all three and signs the user out everywhere, so the changes apply at their next sign-in. Nobody can edit their own account (the server ignores permission changes to yourself), and the server owner's account cannot be edited because the owner already holds every permission. Usernames and passwords are not changed here; see [Password reset](#password-reset).

Accounts that sign in through OIDC are marked **OIDC**. While OIDC sign-in is enabled and [OIDC permission synchronization](/docs/guides/access-control/oidc#group-to-permission-synchronization) is on, their permissions are replaced at every sign-in, so edits to them last only until then.

### Signing a user out

Open the user's actions menu (three dots) and choose **Sign out everywhere…**. Every session of the account ends; the user can sign in again right away unless the account is locked.

### Deleting a user

Open the user's actions menu (three dots):

- **Delete…** marks the account deleted and keeps its username reserved.
  Sign-in is blocked. Sessions, refresh tokens, API keys, Liseur/device
  credentials, and guest-reader capabilities linked to or issued by this
  account are revoked. Pending club invitations it issued and active/pending
  social shares involving it are revoked; reader sessions it created are
  closed. Reading history, requests, and most other account data remain
  stored. This is not an account-data purge.
- **Delete permanently…** removes the account and its private database
  records, including reading progress, bookmarks, annotations, requests,
  preferences, notification settings, personal integrations, collections,
  private reading and smart lists, and device credentials. It also removes
  the user's club membership and invitations. The server's books, series,
  files, and libraries are not deleted. Explicitly shared/public reading
  and smart lists and server-wide emoji are retained under the server owner's
  custody rather than silently discarded. Club-reader sessions created by
  the account are closed and kept under that custody, with their participant
  history retained and guest credentials revoked. Other shared audit/history
  records can remain with the account link removed (for example, another user's
  request keeps its approval status but not the deleted approver's identity).

**Neither action removes copies outside the database**: Markdown/Git annotation
exports, remote repositories, already-sent emails and notifications, device
downloads, and backups need separate retention review. In-flight external
delivery cannot be recalled. Soft deletion retains the account data; permanent
deletion does not erase text/display names already included in another
member's shared club history. Type the username to confirm permanent
deletion. Neither action can be undone or used on your own account or the
server owner's.

## Security

Coppice currently does not enforce any password complexity requirements. This can change if there is enough demand for it. In general, Coppice follows a fairly standard security model:

- Stored passwords are hashed and salted
- All ASCII/Unicode characters are allowed
- There are no knowledge-based authentication (KBA) recovery options, such as “What was the name of your first pet?”
- Users are allowed 10 failed password attempts before being locked out completely (until an administrator unlocks the account)

### Account locking and unlocking

If a user has been locked out of their account, it is up to the server owner to unlock the account to restore access. This can be done using either of the following methods:

1. On the Home app's **Users** screen (`/app/users`), open the actions menu (three dots) for the user you wish to unlock and choose **Unlock…**, then confirm. **Lock…** in the same menu locks an account: it is signed out everywhere and every sign-in is refused until it is unlocked. The server owner cannot lock their own account here.
2. Use the embedded CLI in the Coppice server to unlock the user account. See the [CLI](/docs/developer/cli) guide for more information. In general, the command will look like this:

   ```bash copy
   ./stump account unlock --username <username>
   ```

   Similarly, you can lock a user account using the following command:

   ```bash copy
    ./stump account lock --username <username>
   ```

In the event the server owner account becomes locked, you will only be able to unlock it using the CLI.

### Password reset

If a user has forgotten their password, you will have to use the embedded CLI in the Coppice server to reset the user's password. See the [CLI](/docs/developer/cli) guide for more information. In general, the command will look like this:

```bash copy
./stump account reset-password --username <username>
```

It will prompt you for a new password with confirmation. Once the password has been reset, the user will be able to log in with the new password.
