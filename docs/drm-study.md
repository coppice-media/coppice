# Ebook DRM schemes and how DeDRM_tools removes them

READ-ONLY memo. No code written, no repo files touched. Detection-signature section was sent to `CalibreAdapter` via hub before this was finalized (they own `crates/media/src/drm.rs`), plus a follow-up confirming the exact `keyType` attribute spelling and a MOBI header-length guard.

## 0. Provenance of everything below

- Upstream: <https://github.com/noDRM/DeDRM_tools> (fork of apprenticeharper's, which is unmaintained). Latest stable release **v10.0.3** (2022-07-13); latest beta **v10.0.9** (2023-08-02, RC for 10.1.0) and `DeDRM_plugin/__version.py` on master still reads `10.0.9`. Releases: <https://github.com/noDRM/DeDRM_tools/releases>, version file: <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/__version.py>.
- calibre range: README states the plugin works on calibre 5.x/6.x (Py3) **and** calibre 4.x and older (Py2); Apprentice Harper's older guidance was "calibre 5+ → 7.2.0 or later, calibre 4 or earlier → 6.8.x" (<https://github.com/noDRM/DeDRM_tools/blob/master/README.md>). CHANGELOG confirms Qt6/calibre 6 support landed in 10.0.3 and calibre-4 regressions were fixed in 10.0.9 (<https://github.com/noDRM/DeDRM_tools/blob/master/CHANGELOG.md>).
- Field reports in this memo are from real issue logs on that tracker; they are dated and linked.
- Third-party versions above 10.0.9 seen in the wild (e.g. "DeDRM 10.0.23" in issue #1028) are fork/autorelease builds, not noDRM releases; CHANGELOG explicitly notes 10.0.4/5/6 "were released by other people in various forks".

## 1. Adobe ADEPT — EPUB

**(1) Detection.** ZIP must contain **both** `META-INF/rights.xml` and `META-INF/encryption.xml`. Parse `rights.xml`, read text of `{http://ns.adobe.com/adept}encryptedKey`: base64 length **>= 172** → ADEPT (RSA-wrapped); `adeptBook()` also accepts lengths in `[192, 172, 64]`; **64** → Adobe PassHash (Barnes & Noble). Attribute `keyType` (un-namespaced, that exact camelCase, default `"0"`) on the same element with `int(keyType,10) > 2` → "hardened" DRM (RMSDK >= 10). Encrypted resources are `EncryptedData/CipherData/CipherReference@URI` whose sibling `EncryptionMethod@Algorithm` is exactly `http://www.w3.org/2001/04/xmlenc#aes128-cbc` (deflate-then-encrypt) or `http://ns.adobe.com/adept/xmlenc#aes128-cbc-uncompressed`; any other algorithm in that file is *not* DRM (obfuscated fonts etc.) and DeDRM deliberately leaves those entries in place. `{adept}user` holds `urn:uuid:<uuid>` of the licensed account. Source: <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/ineptepub.py>; the canonical cross-vendor EPUB probe is <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/epubtest.py>.

**(2) Cipher chain.** Book key: RSA **PKCS#1 v1.5** decrypt of the base64 `encryptedKey` under the account's 1024-bit RSA private key (172 b64 chars = 128-byte block). Hardened variant adds a KEK layer *before* the RSA step: IV = raw bytes of `UUID(resource ^ device ^ fulfillment)` (three UUIDs XORed as integers), KEK = rearranged SHA-256 of the decimal `keyType` string (`r = keyType mod 16`; `kek = H[2r:16+r] + H[r:2r]`), AES-128-CBC, PKCS#7. Content: **AES-128-CBC, 128-bit key**, IV prefixed to each ciphertext (DeDRM uses a zero IV and discards the first decrypted block, `decrypt(data)[16:]`), PKCS#7 padding, then **raw DEFLATE inflate** (`zlib.decompressobj(-15)`) unless the `-uncompressed` algorithm URI was used. PassHash path instead: book key = `unpad(AES-128-CBC(userkey[:16], IV=0).decrypt(b64(encryptedKey)))`, take last 16 bytes if longer.

**(3) Key source.** Pure vendor-app scraping, no crypto break (<https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/adobekey.py>):
- Windows: `HKCU\Software\Adobe\Adept\Device` value `key` → Windows **DPAPI** `CryptUnprotectData` with entropy = `struct.pack('>I12s3s13s', volume_serial, cpuid0_vendor, cpuid1_signature[1:], username)` (username preferentially read from the `username` registry value, else `GetUserNameW`) → "keykey"; then iterate `HKCU\Software\Adobe\Adept\Activation\%04d` credential blocks, take `privateLicenseKey`, base64-decode, `AES-128-CBC(keykey, IV=0)`, strip PKCS#7, **drop the first 26 bytes** → RSA private key in DER.
- macOS: `~/Library/Application Support/Adobe/Digital Editions/activation.dat`, XML element `{adept}privateLicenseKey`, base64-decode, drop 26 bytes. No DPAPI equivalent needed.
- Linux: unsupported natively (`"This script only supports Windows and Mac OS X"`); users run ADE under Wine, or supply a key from the DeACSM/ACSM Input plugin (auto-import added in 10.0.0).

**What broke / when.** ADE 3.0+ "hardened" ADEPT was unsupported until **v10.0.3** (merged PR #48 by a980e066a01); v10.0.0 had only added a clearer error for "the new, not-yet-cracked version of the Adobe ADEPT DRM" (CHANGELOG). Support for ADE 4.x-era books is the same code path — the discriminator is `keyType`, not the ADE version string. `ADEPTNewVersionError` still exists in `ineptepub.py` for future variants.

**(4) Crypto vs scraping.** Unwrap + decrypt = pure crypto, self-contained. Key acquisition = 100% vendor-app scraping (registry, DPAPI, CPUID/volume-serial entropy, or an ADE plist).

**(5) Ports.** **libgourou** — C++/LGPL-3 implementation of the ADEPT protocol including `adept_activate`, `acsmdownloader` and `adept_remove`: <https://github.com/SamuelMarks/libgourou> (mirror of Grégory Soutadé's upstream), containerized at <https://github.com/bcliang/docker-libgourou>. **knock** — Rust CLI (GPL-3) that turns an `.acsm` into a DRM-free EPUB, built on `libgourou-utils` + `inept-epub`: <https://github.com/esn/knock> (the original `BentonEdmondson/knock` URL now 404s; the README still references it).

## 2. Adobe ADEPT — PDF

**(1) Detection.** Parse the trailer `/Encrypt` dictionary; DRM iff `/Filter` is the name **`EBX_HANDLER`**. `initialize_and_return_filter` dispatches `Standard` (ordinary password PDF), `Adobe.APS`, `EBX_HANDLER` (ADEPT) — classify `/Standard` separately, it is not store DRM. The license blob is the `/ADEPT_LICENSE` string: base64 → **raw inflate** (`zlib.decompress(data, -15)`) → the same `{adept}encryptedKey` / `{adept}user` XML, with `keyType > 2` again meaning hardened. Adobe-specific hints in the same dict: `/V`, `/Length`, `/EBX_ENCRYPTIONTYPE` (DeDRM defaults it to 6). Source: <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/ineptpdf.py>.

**(2) Cipher chain.** Same book-key unwrap as EPUB (RSA PKCS#1 v1.5, plus the identical `removeHardening` AES-CBC KEK step). Content is **RC4**, not AES, with a per-object key: V=2 → `MD5(bookkey || objid_le[:3] || genno_le[:2])[:min(len(bookkey)+5,16)]`; V=3 → objid XOR `0x3569ac`, genno XOR `0xca96`, interleaved bytes plus the literal `sAlT`, then MD5 truncated the same way. `V` comes from `ebx_V`, or from the leading byte of the unwrapped key when its length is `Length/8 + 1`. B&N/PassHash PDFs take the AES-128-CBC user-key path for the book key and then the same RC4 object keys. (AES-V2/AES-V3/AES-256 code in this file serves `/Standard` PDFs, added in 10.0.3.)

**(3) Key source.** Identical to EPUB (`adobekey.py`). `adeptGetUserUUID(pdf)` reads `{adept}user` from `/ADEPT_LICENSE` so the right key is tried first.

**(4)/(5).** Same split and same ports as §1; `libgourou`'s `adept_remove` covers PDF as well as EPUB.

## 3. Kobo (obok)

**(1) Detection.** *There is normally no in-file marker.* Store kepubs are ZIPs whose per-resource keys live outside the book: table `content_keys(elementid, elementkey)` joined to `content` by `volumeid`, in `Kobo.sqlite` (desktop) or `KoboReader.sqlite` (device); the file itself is `<kobodir>/kepub/<volumeid>` with no extension. So "no `encryption.xml`" must not be read as "DRM-free" for Kobo-sourced files. `epubtest.py` does recognize one in-file variant: `META-INF/rights.xml` containing the literal `<kdrm>` (DeDRM marks that check as second-hand/untested). Sources: <https://github.com/noDRM/DeDRM_tools/blob/master/Obok_plugin/obok/obok.py>, <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/epubtest.py>.

**(2) Cipher chain.** Two-level **AES-ECB** (no IV anywhere): page key = `AES-ECB(userkey).decrypt(base64(elementkey))`; content = `AES-ECB(pagekey).decrypt(bytes)` with **PKCS#7** padding. Correctness is validated heuristically by MIME type (XHTML must start with printable ASCII after any BOM; JPEG must start `FF D8 FF`).

**(3) Key source.** Fully derived from local machine + account identifiers: `deviceid = SHA-256(hashkey || MAC)` hex, with `hashkey` from the hard-coded list `['88b3a2e13','XzUhGYdFp','NoCanLook','QJhwzAtXL']` and MAC uppercased with colons; `userkey = unhexlify(SHA-256(deviceid || userid).hexdigest()[32:])` (i.e. the second half → 16-byte AES key), `userid` from the `user` table. MACs are enumerated per-OS (`ipconfig /all` or WMI on Windows, `ifconfig -a` on macOS, `/sys/class/net/*/address` on Linux, `ip -br link` fallback); hardware-Kobo serials come from `<device>/.adobe-digital-editions/device.xml` `deviceSerial`. DB locations: `%LOCALAPPDATA%\Kobo\Kobo Desktop Edition\Kobo.sqlite`, `~/Library/Application Support/Kobo/Kobo Desktop Edition/…` , Linux via a cached filesystem-wide search for `Kobo.sqlite`, device at `<mount>/.kobo/KoboReader.sqlite`. obok also rewrites the SQLite header bytes 18–19 to `01 01` on a temp copy to defeat WAL.

**What broke / when.** Still fundamentally working, but brittle against Kobo Desktop schema and layout drift: issue #763 (2025-02) is `sqlite3.OperationalError: no such column: Series` from obok's `SELECT … Series FROM content_keys, content`, plus "Kobo changed the download location again"; issue #552 (open, 2024) is 12 candidate keys all failing on Windows Kobo Desktop while the standalone script works. master also carries a fix so removal doesn't fail when some books are undownloaded (#384). <https://github.com/noDRM/DeDRM_tools/issues/763>, <https://github.com/noDRM/DeDRM_tools/issues/552>.

**(4) Crypto vs scraping.** Essentially all scraping. The cipher is textbook AES-ECB; the DB hands over the keys.

**(5) Ports.** No Rust/Go/C implementation of Kobo DRM found. GitHub searches for `language:rust|go` + `drm/kobo/kindle/adept/mobi` surface only readers and converters — e.g. **kepubify** (Go, EPUB→kepub conversion, no DRM: <https://github.com/pgaskin/kepubify>) and **boko** (Rust, EPUB→KFX/AZW3 converter, no DRM: <https://github.com/zacharydenton/boko>).

## 4. Kindle MOBI / AZW / KF8 (and Topaz)

**(1) Detection.** File offset `0x3C..0x43` must be `BOOKMOBI` or `TEXtREAd`; record count = BE u16 at `0x4C`; record table of 8-byte entries from `0x4E`. **Encryption type = BE u16 at record-0 offset `0x0C`** (the PalmDOC "current position" field, reused): `0` none, `1` old Mobipocket, `2` current Mobipocket/Amazon. Only when `"MOBI"` sits at record-0 `0x10` and the header length (BE u32 at `0x14`) is large enough may you read `0xA8` DRM offset, `0xAC` DRM count, `0xB0` DRM size, `0xB4` DRM flags (`0xFFFFFFFF` = none); `drm_count == 0` with type 2 means "never initialised". EXTH exists iff bit `0x40` is set in the BE u32 at `0x80`, starts at `16 + mobi_header_length` with literal `EXTH`; DRM-relevant record types: **209** "tamper proof keys" (book-specific PID material — a strong DRM signal), 208 watermark, 406 rental expiry (nonzero u64 = borrowed), 405 rent flag, 401 clipping limit, 404 TTS flag, 1/2/3 `drm_server_id`/`drm_commerce_id`/`drm_ebookbase_book_id`. Topaz = first three bytes `TPZ`. Offsets and EXTH table are corroborated by the MobileRead wiki (<https://wiki.mobileread.com/wiki/MOBI>) and implemented in <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/mobidedrm.py> / <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/k4mobidedrm.py>.

**(2) Cipher chain.** **Pukall Cipher 1 (PC1)**, a stream cipher, throughout — no AES, no IV, no padding. Type 1: book key = `PC1('QDCVEPMU675RUBSZ', keydata)` where keydata is 16 bytes at record-0 `0x0E` (TEXtREAd), `0x90` (no MOBI header), or `mobi_length+16`. Type 2: for each candidate PID (padded to 16 bytes) `temp_key = PC1(keyvec1, bigpid, encrypt)` with `keyvec1 = 72 38 33 B0 B4 F2 E3 CA DF 09 01 D6 E2 E0 3F 96`; scan the DRM table in 0x30-byte records `(verification u32, size u32, type u32, cksum u8, pad3, cookie 32B)`, match `cksum == sum(temp_key) & 0xff`, `PC1(temp_key, cookie)` → `(ver, flags, finalkey[16], expiry, expiry2)`, accept when `verification == ver` and `flags & 0x1F == 1`. Text records are then `PC1(finalkey, record)` excluding trailing-data entries, whose size is decoded from the extra-data-flags word at record-0 `0xF2` (multibyte bit cleared unless HUFF/CDIC compression, i.e. `compression == 17480`).

**(3) Key source (PIDs).** <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/kgenpids.py>: e-ink Kindle → `SHA1(serial || EXTH209 || token)` → 8-char 6-bit-packed PID + 2-char CRC32 checksum, plus a legacy `pidFromSerial(serial,7)+'*'` for pre-2.5 firmware. Kindle for PC/Mac → `SHA1(DSN || kindle.account.tokens || EXTH209 || token)` and three variants; `DSN` is read from the key DB or derived as `encode(SHA1(MazamaRandomNumber || encodeHash(IDString) || encodeHash(UserName)), charMap1)`.
- Key DB extraction (<https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/kindlekey.py>): Windows `%LOCALAPPDATA%\Amazon\Kindle\storage\.kinf2018` (K4PC 1.25+), `.kinf2011` (1.9+), `…\Amazon\Kindle\storage\rainier.2.1.1.kinf` (1.6–1.8), `…\Amazon\Kindle For PC\storage\rainier.2.1.1.kinf` (1.5), `…\Amazon\Kindle For PC\{AMAwzsaPaaZAzmZzZQzgZCAkZ3AjA_AY}\kindle.info` (pre-1.5). macOS: `~/Library/Application Support/Kindle/storage/.kinf2018|.kinf2011|.rainier-2.1.1-kinf|.kindle-info` and the App-Store sandbox path `~/Library/Containers/com.amazon.Kindle/Data/Library/Application Support/Kindle/storage/…`.
- `.kinf2011` (version 5): values decrypted with **DPAPI** `CryptUnprotectData`, entropy = `SHA1(keyhash) + str(0x2df * build) + guid`. `.kinf2018` (version 6): `PBKDF2-HMAC-SHA1(passwd = charMap5_encode(SHA256(username + '+@#$%+' + IDString)), salt = str(0x6d8 * build) + guid, count = 10000, dkLen = 0x400)[:32]` → AES key, IV + ciphertext recovered via the `testMap8` character map. On macOS DPAPI is emulated with `PBKDF2(count = 0x800, dkLen = 0x400)` split into key/IV, and `IDString` is brute-forced over munged MAC addresses. Header values use `PBKDF2(b'header_key_data', b'HEADER.2011', dkLen = 256, count = 128)` + AES-CBC.

**What broke / when.** Kindle for PC/Mac **1.19+** switched downloads to KFX, so MOBI/KF8 extraction requires pinning 1.17 (`KindleForPC-installer-1.17.44170.exe`, SHA-256 `14E0F00…163200`) or disabling `renderer-test`; the Mac `chmod -x` trick works only on 1.19–1.31, not 1.32+; 1.25+ "may convert KF8 files to a new format that is not supported by these tools" (<https://github.com/noDRM/DeDRM_tools/blob/master/FAQs.md>). Kindle for Android (backup disabled), Kindle for iOS (key derivation changed) and Kindle Fire are all listed as unsupported in the same FAQ. Amazon removed "Download & transfer via USB" from the web store on **2025-02-26**, killing the main non-KFX source (<https://blog.the-ebook-reader.com/2025/02/12/download-transfer-for-kindle-ebooks-going-away-on-february-26/>).

**(4) Crypto vs scraping.** PC1 + PID matching is pure crypto and fully offline. Getting a PID is scraping (`.kinf*`/`kindle.info` + DPAPI + username/volume-serial), except for e-ink Kindles where the user just types a 16-char serial.

**(5) Ports.** The only non-Python implementations shipped were the **AlfCrypto** native libraries (C, PC1 + AES, `alfcrypto_src.zip`, `*.dll/.dylib/.so`) which DeDRM removed in 10.0.9 ("Removing ancient AlfCrypto machine code libraries, moving all encryption / decryption to Python code" — CHANGELOG; FAQ still documents the shared libs). No maintained Rust or Go port of MobiDeDRM was found.

## 5. Kindle KFX

**(1) Detection.** Bare `.kfx`/`.azw` whose first 8 bytes are `EA 44 52 4D 49 4F 4E EE` (`b"\xeaDRMION\xee"`) is an encrypted DRMION blob; DeDRM refuses it standalone because the voucher is a separate file. `.kfx-zip` (starts `PK\x03\x04`): a member is encrypted content iff it starts with that same 8-byte magic; the voucher member starts with the 4-byte Amazon **Ion binary version marker** `E0 01 00 EA` and contains the literal ASCII `ProtectedData`. Inside, Ion annotations are `com.amazon.drm.Envelope@1.0|@2.0`, `com.amazon.drm.EncryptedPage@…` (fields `cipher_text`, `cipher_iv`) vs `com.amazon.drm.PlainText@…`, and vouchers are `com.amazon.drm.VoucherEnvelope@<n>.0`. Sources: <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/kfxdedrm.py>, <https://github.com/noDRM/DeDRM_tools/blob/master/DeDRM_plugin/ion.py>.

**(2) Cipher chain.** Voucher: build `shared` by concatenating lock parameters (`"ACCOUNT_SECRET" + secret`, `"CLIENT_ID" + dsn`), run it through a per-VoucherEnvelope-version obfuscation (a `(magic, word)` table; the secret is zero-padded to a multiple of `magic`, shuffled, and XORed with `SHA-256(word)` halves — several distinct scramble variants plus hard-coded `process_V9708/V1031/V2069/V9041/V3646/V6052/V9479/V9888/V4648/V5683`), then `key = HMAC-SHA256(sharedsecret, b"PIDv3")` and `AES-256-CBC(key[:32], iv = cipher_iv[:16])` with PKCS#7 over the voucher ciphertext. Result is an Ion `com.amazon.drm.KeySet@1.0` containing `com.amazon.drm.SecretKey@1.0` with `algorithm == "AES"`, `format == "RAW"` and the raw `encoded` key. Pages: `AES-128-CBC(secretkey[:16], iv = cipher_iv[:16])`, PKCS#7, then optional **LZMA** (`FORMAT_ALONE`, first plaintext byte must be 0 = "UseFilter not supported"). License type is read and a non-`Purchase` license only warns.

**(3) Key source.** The same `kindlekey` DB as §4: candidate PIDs are split into `(dsn, secret)` by trying length pairs `(0,0),(16,0),(16,40),(32,0),(32,40),(40,0),(40,40)`. Container gathering requires jhowell's **KFX Input** calibre plugin (<https://www.mobileread.com/forums/showthread.php?t=291290>), per FAQ and README.

**What broke / when.** This is the least stable scheme by far, and Amazon has moved past DeDRM 10.0.9:
- Kindle for PC **2.9.1** (issue #1028, 2026-06): voucher is `com.amazon.drm.VoucherEnvelope@10022.0`, log shows `Got 0 shared key candidates {}`, `Lock parameters used: []`, all 13 obfuscation fallbacks fail with "Incorrect padding - Wrong key", then `Incorrect AES key length (0 bytes)`. <https://github.com/noDRM/DeDRM_tools/issues/1028>
- Kindle for PC **2.8.0** (issue #936, 2025-12): reporter documents a redesigned scheme — key store `%LOCALAPPDATA%\Amazon\Kindle\storage\.kinf2024` (base64 device credentials) which DeDRM never looks for, and a new `atv:kin:2:<b64 key>:<b64 hmac>` token inside the Ion voucher; renaming/importing yields `Unknown type encountered in envelope, expected VoucherEnvelope`. <https://github.com/noDRM/DeDRM_tools/issues/936>
- Even old 1.x paths fail in some setups (issue #561, K4PC 1.26 under Wine: "Failed to decrypt KFX DRM voucher with any key"). <https://github.com/noDRM/DeDRM_tools/issues/561>
- FAQ's own caveat: "It's quite possible that Amazon will update their KFX DeDRM to prevent DRM removal from KFX books again. So Remove DRM as soon as possible!"

**(4) Crypto vs scraping.** The page cipher is ordinary AES-CBC. Everything expensive is (a) app scraping for DSN/secret and (b) reverse-engineering each new `VoucherEnvelope@N` obfuscation — the latter is not crypto analysis but per-release RE of Amazon's client, which is why KFX rots on a release cadence.

**(5) Ports.** None found. `kfxlib` (the container/Ion parser) is Python inside the closed-distribution KFX Input plugin; `Satsuoni`'s KFX key-extractor experiments are referenced from issue #936 but not a library. No Rust/Go/C implementation exists.

## 6. Apple FairPlay (iBooks / Apple Books)

**(1) Detection.** `META-INF/sinf.xml` present **and** containing the literal `fairplay` (`epubtest.py`; DeDRM annotates this as "Untested, just found this info on Google"). Treat as detect-only.

**(2)–(4).** Not implemented by DeDRM at all. The repository README explicitly excludes it ("Except for the Requiem tools for Apple's iBooks…") and the FAQ states "they don't work on any ebooks from Apple's iBooks store" / "Apple regularly change the details of their DRM… Apple's Fairplay DRM scheme can be removed using Requiem if the appropriate version of iTunes can still be installed and used", crediting the separate tool by "Brahms" (<https://github.com/noDRM/DeDRM_tools/blob/master/FAQs.md>, <https://github.com/noDRM/DeDRM_tools/blob/master/README.md>). Key material is bound to the Apple ID and device keybag rather than to a scrapable file, so there is no offline analogue of `adobekey.py`.

**(5) Ports.** No maintained Rust/Go/C port; Requiem itself is abandoned and version-locked to old iTunes.

## 7. Barnes & Noble (legacy)

Two unrelated families.

**(a) Adobe PassHash ("ignoble") EPUB/PDF.** Detection: `rights.xml` + `encryption.xml` with `{adept}encryptedKey` base64 length exactly **64** (`isPassHashBook()`; `epubtest.py` labels it `"B&N"`). Cipher: user key derived from cardholder name + credit-card number — normalize both to lowercase without spaces, NUL-terminate, then `userkey = base64(SHA1( AES-128-CBC(key = SHA1(ccn)[:16], iv = SHA1(name)[:16]).encrypt( SHA1(name||ccn) + b'\x0c'*12 ) ))` (<https://github.com/apprenticeharper/DeDRM_tools/blob/master/DeDRM_plugin/ignoblekeygen.py>). Book key = `unpad(AES-128-CBC(b64decode(userkey)[:16], IV=0).decrypt(b64(encryptedKey)))`, last 16 bytes if longer; content decryption is then identical to §1 (AES-128-CBC + inflate). `ignobleepub` was merged into `ineptepub.py` and `ignoblepdf` into `ineptpdf.py` in 10.0.0/10.0.3. Key source: mostly *user-typed* (name + CC), i.e. no app scraping at all; 10.0.3 added scraping from the NOOK Microsoft Store app, from a NOOK Android data dump, and PassHash extraction from ADE (`adobekey_get_passhash.py`). Stability: static legacy scheme — nothing to break — but noDRM records the PDF side as "Fairly untested as I don't have any PDFs with B&N DRM" and Nook Study key retrieval as only partially fixed (#50).

**(b) eReader / Palm `.pdb` (Palm Reader, pre-EPUB B&N).** Handled by `erdr2pml.py`; key again from name + last 8 CC digits. Detection is by PDB creator/type, not by any XML marker. Master carries untested Python-2/3 fixes and a SHA-1 fix (#608).

**(5) Ports.** None known beyond the Python originals by i♥cabbages / The Dark Reverser.

## 9. Legal

**United States — 17 U.S.C. § 1201** (<https://www.law.cornell.edu/uscode/text/17/1201>):
- **(a)(1)(A)** bans the *act* of circumventing a measure that "effectively controls access"; **(a)(2)** bans manufacturing, importing, offering to the public, providing or otherwise trafficking in any technology that is (A) "primarily designed or produced for the purpose of circumventing" such a measure, (B) has "only limited commercially significant purpose or use" other than circumvention, or (C) is marketed for circumvention. **(b)(1)** mirrors (a)(2) for measures that protect a *right* of the copyright owner (copy control rather than access control).
- A DRM-*removal* tool implicates (a)(2) and (b)(1) on all three prongs; a DRM-*detector* that only reads format metadata circumvents nothing under the (a)(3)(A) definition ("descramble… decrypt… avoid, bypass, remove, deactivate, or impair") and does not fit "primarily designed… for the purpose of circumventing". That distinction is the whole legal reason to keep detection in-repo and removal out.
- Exemption asymmetry, which is decisive here: **(a)(1)(E)** says a triennial-rulemaking determination "may not be used as a defense in any action to enforce any provision of this title other than this paragraph", and **(d)(4)** says the library/archive exemption "may not be used as a defense to a claim under subsection (a)(2) or (b)". So even a user whose *conduct* is exempt confers no protection on whoever *distributes* the tool.
- The two potentially relevant statutory carve-outs are narrow: **(f)** reverse engineering applies to "a copy of a computer program" for interoperability of "an independently created computer program" — ebooks are literary works, so it does not reach book decryption; **(g)** encryption research exempts only good-faith research on lawfully obtained copies, weighted by dissemination manner, expertise and notice to the copyright owner, and (g)(4) permits sharing means only with collaborators/verifiers.

**Current Librarian of Congress exemptions — 37 C.F.R. § 201.40** (in force from the 2024 final rule, 89 FR 85446, Oct 28 2024; text: <https://www.ecfr.gov/current/title-37/chapter-II/subchapter-A/part-201/section-201.40>; rulemaking index and 2024 final rule PDF: <https://www.copyright.gov/1201/> and <https://www.govinfo.gov/content/pkg/FR-2024-10-28/pdf/2024-24563.pdf>):
- **§ 201.40(b)(6)** — literary works (and previously published musical works fixed as text/notation) distributed electronically whose TPMs "prevent the enabling of read-aloud functionality or interfere with screen readers or other applications or assistive technologies", for a lawfully obtaining **eligible person under 17 U.S.C. 121** (with remuneration for the inaccessible copy's market price) or an authorized entity under § 121. **This is the accessibility exemption, and it is the only one aimed at ordinary ebooks.**
- **§ 201.40(b)(5)** — literary works distributed electronically, for **text-and-data-mining** by a researcher affiliated with a nonprofit institution of higher education, on lawfully acquired/owned copies, with security measures, corpus access limited to affiliated researchers, and viewing limited to TDM research/teaching.
- **§ 201.40(b)(7)** — literary works consisting of medical-device data compilations (not book DRM).
- There is **no** exemption for personal archiving, format-shifting, backup, or platform migration of purchased ebooks. And § 201.40(a)/(b) state plainly that these classes lift only "the prohibition… set forth in 17 U.S.C. 1201(a)(1)(A)" — never (a)(2) or (b).
- The tenth triennial cycle is under way for the Oct 2027–Oct 2030 period (<https://www.copyright.gov/1201/2027/>), so any change to the ebook classes is a 2027 question, not a 2026 one.

**European Union — Directive 2001/29/EC (InfoSoc)** (<https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32001L0029>):
- **Art. 6(1)** requires protection against knowing circumvention of "effective technological measures". **Art. 6(2)** — the trafficking clause — requires protection against "the manufacture, import, distribution, sale, rental, advertisement for sale or rental, **or possession for commercial purposes**" of devices/components/services that (a) are promoted/advertised/marketed for circumvention, (b) have "only a limited commercially significant purpose or use other than to circumvent", or (c) are "primarily designed, produced, adapted or performed for the purpose of enabling or facilitating" circumvention. Note that 6(2) reaches commercial possession, which § 1201 does not; recital 49 also preserves national bans on private possession.
- **Art. 6(3)** defines "effective": protection via "an access control or protection process, such as encryption, scrambling or other transformation… or a copy control mechanism". Every scheme in this memo qualifies.
- **Art. 6(4)** obliges Member States, absent voluntary measures, to let beneficiaries of certain Art. 5 exceptions — including **Art. 5(3)(b), uses for the benefit of people with a disability** — actually benefit from them where they have legal access; private copying (5(2)(b)) is only optional. Crucially, the fourth subparagraph disapplies 6(4) entirely for "works or other subject-matter made available to the public on agreed contractual terms" on-demand — which is exactly how commercial ebook stores deliver, so the EU accessibility relief mostly evaporates for store-bought ebooks. Recitals 48 and 8(2) sanctions/seizure (Art. 8(2)) round this out; recital 48 does say protection "should not prohibit those devices or activities which have a commercially significant purpose or use other than to circumvent" and "should not hinder research into cryptography".

**Notable takedowns and prosecutions:**
- **EDRLab / Readium LCP DMCA notice, 2022-01-04**, against `noDRM/DeDRM_tools` and its then-forks (processed against a network of 11 repositories). The notice asserts EDRLab owns "LCP encryption profile 1.0", names `lcpdedrm.py`, `config.py`, `epubtest.py`, `prefs.py` and the LCP help file, and demands the repo be "shut down entirely". Result: LCP support was stripped and the module reduced to an error stub. <https://github.com/github/dmca/blob/master/2022/01/2022-01-04-readium.md>, <https://github.com/noDRM/DeDRM_tools/issues/18>.
- **United States v. ElcomSoft / Dmitry Sklyarov** — the first criminal § 1201 test, over the "Advanced eBook Processor" for Adobe eBook DRM: Sklyarov arrested 2001-07-16 after a DEF CON talk on Adobe's eBook security, charges deferred and dismissed in exchange for testimony; ElcomSoft was **acquitted on all counts** by a San Jose federal jury on 2002-12-17 on lack of willfulness. <https://www.eff.org/cases/us-v-elcomsoft-sklyarov>, <https://en.wikipedia.org/wiki/United_States_v._Elcom_Ltd.>, <https://www.justice.gov/archive/criminal/cybercrime/press-releases/2001/sklyarovAgree.htm>.
- **Apple FairPlay / Requiem** — never distributed with DeDRM and now unmaintained; the FAQ routes users elsewhere and notes Apple "regularly change the details of their DRM".
- Non-legal but load-bearing for feasibility: Amazon's 2025-02-26 removal of "Download & transfer via USB" (source above) and the fact that DeDRM's own FAQ frames the tools as using "the encryption key information already stored someplace on their computer or device" rather than breaking cryptography — the framing that matters if the (a)(2)(A)/(B) "primarily designed" analysis is ever argued.

**Practical read for this repo.** A read-only detector that reports "this file is ADEPT/KFX/Kobo-encrypted, here is the marker path/offset" performs no decryption, embeds no keys, and is not "primarily designed… for the purpose of circumventing"; it is closer to `epubcheck` than to `ineptepub`. A removal implementation is a § 1201(a)(2)/(b)(1) and Art. 6(2) artifact, would be hosted-platform-takedown bait on the LCP precedent, and — for KFX specifically — would be unmaintainable anyway. Keeping removal in a separate, clearly out-of-tree tool (and never vendoring key-scraping code into `stump`) is both the legally and the operationally correct split.
