Hi all — sharing findings from a parallel effort that may save you some time.

We've been building a Komga-compatible profile for Stump (Rust). Komelia 0.19.0 has been exercised against it end to end on a phone (browse, read, progress, edits, downloads), driven by a sanitized capture of Komelia's traffic and checked against the pinned komga-client 0.11.0 / Komelia source; Liseur's Komga and Grimmory profiles are implemented from its pinned source with contract specs and manual smoke probes, but not yet exercised from the app. Every regression we hit maps directly onto what Grimmory's `KomgaController` and Komga security chain do today, so I wrote the delta up as an attachment rather than a wall of text here.

The short version of what Komelia still needs from Grimmory at `main` (4e28fde):

1. **A session after Basic login, and no session-cookie clears on 401.** The Komga chain is `STATELESS` httpBasic. In the capture, Komelia sends `Authorization: Basic` only on `GET /api/v2/users/me?remember-me=true`; every other request relies on the `KOMGA-SESSION` cookie (plus `komga-remember-me` for its background download worker — PR #2333 covers issuing it, but the worker also needs it *accepted* on `/api/v1/books/{id}/file` with no `Authorization` header). Komelia's REST, SSE and image clients share one cookie jar (`RememberMePersistingCookieStore`, pinned source), so a `Set-Cookie: KOMGA-SESSION=; Max-Age=0` on any 401 — e.g. an SSE reconnect carrying a stale cookie — wipes the live session for all of them. Komga itself never clears the cookie on 401. This one explains "login works, then everything is Unauthorized."
2. **`POST /api/v1/books/list` and `/api/v1/series/list` with the search-condition DSL** (currently 501). These are Komelia's primary catalog calls. Komelia sends an *untagged* condition dialect (`{"allOf":[{"mediaProfile":{"operator":"is","value":"EPUB"}}]}`, no `type` field) while Liseur sends the tagged form; both have to decode. `size=0` is Komelia's count-only idiom and must return an empty page with `totalElements`, not an error.
3. **`book.url` must be a filesystem-style path ending in the real filename.** Komelia derives the local download filename from `Path(book.url).name` (`BookDownloadService.kt`); an API path yields an extensionless file and the import fails.
4. **SSE mutation events** (`SeriesChanged`, `BookChanged`, `ReadProgressChanged`, `ReadProgressSeriesChanged`, `CollectionChanged`), gated per subscriber (progress events only to the owning user). Without them every edit/mark-read needs a manual refresh.
5. **Readium `/manifest` + `/progression` for EPUBs**, `POST /api/logout`, the user-settings routes (`/api/v1/settings`, `/api/v1/announcements`, `PATCH /api/v2/users/me/password`, authentication-activity), and `readlists` / `books/ondeck` / `series/new|updated` (currently 501).

On Liseur vs Komelia, since it came up: they authenticate differently. Komelia is Basic-once-then-session. Liseur's Komga provider sends `X-API-Key` on every request with no `Authorization` header at all (and the untagged conditions). Liseur's Grimmory provider is a third shape: OPDS-user Basic on `/komga/api/v2/users/me` plus `GET /komga/api/v1/books?page=&size=200` paged listing with client-side `mediaType` filtering. Grimmory's `/komga` chain already satisfies that Liseur-Grimmory shape; the Komelia shape is the gap.

What we did **not** implement, so no claims there: Komga's full filesystem browser (ours is an owner-only, root-constrained directory listing for Komelia's picker), library create/delete/tasks, user CRUD beyond password and age restriction, sharing labels, and Komga's own KOReader/Kobo/OPDS routes (Stump has native ones). The attachment has the per-route matrix, the DTO/enum values the pinned Kotlin client actually accepts, the SSE gating rules, the remember-me contract with Komga's default lifetime, and pinned source citations (file:line at the listed commits) for each claim. Our contract tests are Hurl specs bound to our fixture IDs and session semantics, so they won't run against Grimmory as-is, but the request/response shapes are language-agnostic and we're happy to adapt/share them.

Happy to answer questions or compare traces.
