# Server

The `stump_server` binary composes the HTTP API and compatibility protocols with the built Home and Editor apps.

## Browser routes

- `STUMP_HOME_APP_DIR` optionally serves the Home app at `/app`.
- `INGEST_EDITOR_DIR` optionally serves the ingest Editor at `/editor`.
- With the `webui` Cargo feature and `STUMP_ENABLE_WEBUI=true`, `/` and unknown non-API browser paths redirect to `/app`.
- Native API and protocol routes resolve before browser redirects. Unknown API, OPDS, public, and KOReader paths remain not-found responses.

The `webui` Cargo feature remains the build gate for web UI routing and GraphQL playground behavior; the Home and Editor assets are independently configured runtime directories.

## Decisions

| Decision | Why | Evidence |
| --- | --- | --- |
| Compile Komf into `headless`/`full`, leave `minimal` without it, and keep mounting behind the default-off `STUMP_ENABLE_KOMF` runtime switch | Komf is a dormant compatibility route group unless explicitly enabled | `apps/server/Cargo.toml:8-10,30,36-37`; `core/src/config/protocols.rs:55-61`; `apps/server/src/routers/mod.rs:205-208` |
| Accept the `apiKey` query only on exact Komf route shapes, bind it to a device, and redact its value from request spans | Komelia stores a Komf base URL with its device key in the query; auth must not widen to Kavita or native `/api` routes | `apps/server/src/middleware/auth.rs:130-199`; `apps/server/src/http_server.rs:28-66` |
| Leave reads to authenticated device scope, require `EditMetadata` for metadata/job writes, and preserve `MetadataProviderManage` for config patches | Device keys default to download-only, while native provider configuration remains separately privileged | `apps/server/src/routers/komf_backend.rs:774-954`; `crates/graphql/src/mutation/metadata_provider.rs:28,44,66,87` |
| Komf jobs are retained in memory only while recent (24h, newest 1000 finished), replay at most 128 events each, and run at most 3 provider jobs concurrently; queued jobs report `RUNNING`/`Queued` until scheduled | Whole-library matches must not spawn unbounded provider work or grow the job store forever, while Komelia can still poll `/api/jobs` for recent results | `apps/server/src/routers/komf_backend.rs` `JobLimits`, `JobStore`; `crates/komf/README.md` |
| The Liseur adapter reconciles linked native Readium highlights, notes, and bookmarks into stable CAS records, and writes CAS edits/deletes back to their source rows | One user-scoped annotation stream reaches every reader without re-exporting either mirror or violating library visibility | `src/routers/liseur_sync/storage.rs` `reconcile_native_annotations`; `crates/graphql/src/mutation/epub.rs`; focused native annotation tests |
| `/v1/books/{id}/resolve` keeps the existing user/media binding, but self-heals it into the single alias-backed work when the linked work is alias-less and pairing-evidenced; multiple strong-alias works still produce 409 | Source, KoReader partial-MD5, SHA-256 edition and server-recorded file hashes converge without weakening genuine conflicts; runtime and append-only repair share the same data-preserving merge | `src/routers/liseur_sync/storage.rs::resolve_catalog_book`; `tests/liseur/mod.rs::linked_aliasless_pair_resolve_self_heals_and_preserves_identity_conflicts`; migration 20260963/20260966 |
| Include `mam-acquisition` in `headless`/`full` while keeping the runtime switch off by default; `minimal` omits it | Manager-only MAM bridge operations require the server API and staged ingest, but an unconfigured deployment must not contact the bridge | `apps/server/Cargo.toml`; `core/src/config/mam_acquisition.rs`; `apps/server/src/routers/mod.rs` |
| `get_media_thumbnail` never serves a raw page when it can encode one: with no stored and no on-disk thumbnail it calls `generate_thumbnail_on_demand` with the library's `thumbnail_config` (or the media crate's WebP 400×600 default) and the result is kept under `thumbnails/`; series/library fallbacks, Komga, Kavita, Kobo, OPDS 2.0, ABS, Liseur and the OPDS 1.2 `/books/{id}/thumbnail` route (previously a raw page 1 extraction of its own) all go through it | On the fixture no library has a `thumbnail_config`, so every cover on every profile's grid was a fresh 1–2 MB page extraction; a bounded file generated once and looked up by the existing `get_thumbnail` name is a plain read afterwards, while a configured library still gets exactly its configured format and size | `src/routers/api/v2/media.rs::get_media_thumbnail` + tests `unconfigured_library_gets_a_kept_bounded_thumbnail_not_the_page`, `configured_library_keeps_its_own_format`; `src/routers/opds_backend/v1_2.rs::get_book_thumbnail`; `crates/media/README.md` |
| Every Tokio runtime thread gets an 8 MiB stack (`RUNTIME_THREAD_STACK_BYTES`) instead of the 2 MiB default | async-graphql resolves nested objects recursively on the polling thread's stack; the KOReader plugin's book-detail query (media → series → media with its full field set) overflowed 2 MiB in a debug build and `abort`ed the whole server, so every client went offline. Stack is reserved address space; pages are committed only when touched | `src/config/runtime.rs`; reproduced 2026-09-26 with the plugin's `mediaById` detail query (server died), 10–12 ms and stable after the change |
| An import approval claims the proposal with one conditional `UPDATE … WHERE status = 'proposed'` before any side effect: `link` commits the claim, the identity re-check, and the location upsert in one write transaction; `materialize` claims first, stages, then records `staged_item_id`, and hands a failed claim back to `proposed` | Linking or staging first and deciding second let a rejection that landed in between win the status while the location or staged file stayed applied; a claim that lost reads back the decision that won and applies nothing | `src/routers/api/v2/source_workers.rs::claim_proposal`, `approve_link`, `approve_materialize`; tests `approval_applies_nothing_when_a_rejection_wins_the_claim`, `concurrent_approvals_link_exactly_once`, `a_proposal_is_decided_once` |
| An `approved` proposal with neither `applied_location_id` nor `staged_item_id` is a materialization in progress (409) while this process holds it in `MATERIALIZING`, and is resumed by the next `action=materialize` approval otherwise | Staging happens outside the database, so a crash between the claim and the recorded outcome must not strand the proposal; the staged upload is idempotent on `remote-source-import:<id>`, so a resume cannot duplicate bytes | `src/routers/api/v2/source_workers.rs::MaterializationGuard`, `settled_response` |
| `open_media_transfer` tries every online verified location newest-first and skips a copy whose source is offline or refuses the grant; only when no copy opens is the media reported unavailable | A disconnect marks the `remote_source` offline but never its locations, so a media with an older copy on a still-connected worker answered 503 as soon as the newest copy's worker dropped | `src/routers/api/v2/source_workers.rs::open_media_transfer`; test `remote_transfer_falls_back_to_an_online_copy` |
| Accepted remote byte streams carry a deadline on both transports: the pooled direct client sets `connect_timeout` and `read_timeout(SOURCE_TRANSFER_IDLE_TIMEOUT)`, and `RemoteBody::into_stream` surfaces the tunnel's idle timeout as `TimedOut`; verification, materialization, and reader responses all consume that one stream | `reqwest::Client::new()` had no timeout and `receiver.recv()` waited forever, so a worker that stalled mid-file held downloads and admin requests open without limit | `src/routers/api/v2/source_workers.rs::DIRECT_CLIENT`, `RemoteBody::into_stream`, `hash_body` |
| Manifest reconciliation keeps one `HashSet` of committed item ids per batch and stages only the current chunk's ids; `match_source` builds `CandidateIndex` once per request and runs indexing plus matching in `spawn_blocking` | Cloning the whole ledger per 256-item chunk was quadratic on the socket task, and scanning every local metadata/location row per remote item was `items × library` comparisons on a request thread | `src/routers/api/v2/source_workers.rs::reconcile_manifest`, `CandidateIndex`; test `candidate_index_matches_by_digest_identifier_and_title` |
| Numeric `modified_at` values in source manifests are decoded by the protocol's epoch rule (`expires_at_millis`): milliseconds as sent by the built-in worker, seconds when the magnitude is below 10^11 | The value was read as seconds, so every observation carried a date tens of thousands of years out; rows already stored are rewritten by the worker's next manifest, which resends every item | `src/routers/api/v2/source_workers.rs::modified_at`; test `modified_at_reads_worker_milliseconds_and_seconds` |
| A media link that is new, or whose edition digest changed, re-sequences the work's live CAS records (`models::services::liseur_annotation::resequence_work_annotations`: `seq` and the counter only; `rev`, timestamps, writer and payload untouched) in the same transaction, as does an identity merge; the projection cursor then always advances to the high water instead of holding behind unlinked records | The feed clock is the only cursor the projection writer, the annotation-sync exporter and devices share, and link changes never moved it, so a projected note stayed on the first-linked (often audio) book and sinks never re-read the work; a device replays an unchanged `rev` as a no-op, and an unlinked record is replayed when its link arrives, so re-projecting everything above a pinned seq on every poll was pure cost | `src/routers/liseur_sync/storage.rs::{resolve_work,merge_aliasless_pair_work,reconcile_annotation_projections}`; `crates/models/src/domain/edition_pair.rs::upsert_link`; tests `storage.rs::a_new_edition_link_replays_the_work_and_moves_its_projection`, `crates/library/src/editions/tests.rs::a_new_pair_link_resequences_the_work_but_an_existing_one_does_not` |
| Every consumer that attaches a Liseur record to a media row ranks the work's links with `models::shared::liseur_annotation_projection::projection_link_order_by`: the record's edition, then any non-audiobook (`media_audio`), then the oldest link | The projection writer picked the oldest link and could pin a Readium highlight to an audiobook linked before the ebook, while the hub already preferred the ebook; one shared `ORDER BY` keeps `media_annotations.media_id`, the hub's book and Home edits agreed, on SQLite and Postgres | `storage.rs::linked_annotation_media_id`; `crates/graphql/src/object/annotation.rs::load_liseur_rows`; `crates/graphql/src/mutation/epub.rs::visible_liseur_media_id`; test `storage.rs::a_new_edition_link_replays_the_work_and_moves_its_projection` |
| Native→CAS reconciliation is bounded per request: a write reconciles only the `stump-native:*` ids it names, a work read reconciles that work, and a feed poll sweeps the next `NATIVE_SWEEP_WORKS_PER_POLL` (64) works of a process-local rotating cursor; membership is a `HashSet`, and the native tables are joined on the window's works through a subquery rather than one bound id per linked media row | Every poll opened `BEGIN IMMEDIATE`, loaded all links and every native row of the account, tested membership quadratically and bound the whole media-id set into `IN` lists that can exceed SQLite's parameter limit; a targeted write still sees the freshest mirror `rev`, and a large account converges over a few polls without any poll paying for the library | `storage.rs::{reconcile_native_ids,reconcile_native_works,reconcile_native_annotations,native_sweep_window}`; test `storage.rs::annotations_preserve_extended_styles_and_reconcile_native_projections` |
