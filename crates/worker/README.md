# `stump_worker`

## Purpose

Remote workers: the `worker_jobs` queue and dispatcher, the socket protocol that
carries a job to a process on another machine, and the `stump-worker` client
binary that runs one.

Two halves behind two features, one shared protocol. It owns _routing_ (who runs
a job) and _state_ (what happened to it); it does not own the HTTP transport
(the axum `ws` glue is `apps/server/src/routers/api/v2/workers.rs`), the row's
schema (`crates/models`), or any job kind's server-side implementation — those
are registered by the host, because running a transcode needs `ffmpeg`, media
rows and the server's configuration.

It is not `stump_jobs`. A `jobs` row is _this server's_ background work and its
runtime owns the task; a `worker_jobs` row may be executed elsewhere, so it
carries what a stranger needs to run it and survives both a worker disconnect
and a server restart.

## Decisions

| Decision                                                                                                                                                                                                                          | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Evidence                                                                                                                                                                       |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| One crate, two features (`server`, `client`); the binary lives here rather than in `apps/worker`                                                                                                                                  | The frames and the capability matcher are shared by both ends, so a split crate would need a third for them — and `crates/*` is already a workspace-member glob, so `apps/worker` would also cost a root `Cargo.toml` line. `default = ["server","client"]` so `cargo test -p stump_worker` can run a real client against a real hub                                                                                                                                                                                                                 | `Cargo.toml`; `src/tests.rs`                                                                                                                                                   |
| The server half links no HTTP stack: the hub is fed frames and hands back an outbound channel                                                                                                                                     | `stump_core` links this crate unconditionally (like `stump_devices`), and pulling axum into `core` for a route that lives in `apps/server` would be paid for by every profile. It is also what lets the crate's own test drive the identical state machine through its own listener                                                                                                                                                                                                                                                                  | `src/hub.rs`; `core/Cargo.toml`; `apps/server/src/routers/api/v2/workers.rs`                                                                                                   |
| Every transition is one conditional `UPDATE` guarded by the status it leaves; a frame that loses the race is logged and dropped, never propagated                                                                                 | A `result` and a `cancel` genuinely cross on the wire. Failing the connection over it would strand every other job that worker holds                                                                                                                                                                                                                                                                                                                                                                                                                 | `src/service.rs::update_status`, `handle_frame`; test `cancel_stops_the_worker_and_marks_the_job_failed`                                                                       |
| A frame naming a job the sender does not hold is `NotAssigned`, and the upload route refuses the same way                                                                                                                         | Otherwise any paired worker could complete — or substitute the bytes of — another worker's job                                                                                                                                                                                                                                                                                                                                                                                                                                                       | `src/service.rs::assert_holder`, `upload_path`; test `a_worker_cannot_touch_a_job_it_does_not_hold`                                                                            |
| Reconnect re-offers by id: `claimed`/`running` stay assigned across a disconnect, an unclaimed offer is released at once                                                                                                          | A worker mid-encode is coming back and its hour of work must not be thrown away; an offer nobody started is free to re-route. Resume and cold start are then one code path, so there is no resume-only branch to rot                                                                                                                                                                                                                                                                                                                                 | `src/service.rs::{on_worker_connected,on_worker_disconnected}`; test `reconnect_resumes_a_claimed_job`                                                                         |
| Unclaimed offers expire after `CLAIM_DEADLINE` (30 seconds) and are requeued by a host-started sweep; the sweep uses `updated_at` as the offer timestamp and guards the release by both `queued` status and the exact `worker_id` | A connected but unresponsive worker must not hold a queue row forever, while a racing `claim` must win. Re-dispatch prefers another capable worker; when none exists, the normal capability selection may offer it to the same worker again                                                                                                                                                                                                                                                                                                          | `src/service.rs::{start_claim_sweep,sweep_claim_deadlines,update_status}`; tests `an_unclaimed_offer_is_requeued_after_claim_deadline`, `a_claim_before_deadline_is_not_swept` |
| A second `hello` from one device replaces the connection rather than adding one; detach is epoch-guarded                                                                                                                          | A worker that reconnects before the server notices the dead socket must not be offered every job twice, and the slow teardown of the old socket must not evict the new one                                                                                                                                                                                                                                                                                                                                                                           | `src/hub.rs::{attach,detach}`; test `a_second_hello_replaces_the_first_connection`                                                                                             |
| Source-worker inventory and byte serving use a separate credential, control protocol, hub, and data plane from compute jobs; the same binary may run either or both roles | A compute worker must not inherit filesystem visibility, and source media bytes must not compete with JSON control frames. Opaque one-use grants bind every read to one device, root, item version, exact byte interval, byte ceiling, expiry, and—after server verification—the server-computed whole-object SHA-256 that the worker rechecks before serving | `src/source_protocol.rs`; `src/source_hub.rs`; `src/source_client.rs`; `src/source_direct.rs`; `src/source_tunnel.rs`; `src/source_catalog.rs` |
| Source roots are explicit, read-only, catalog-mode directories backed by a private worker-local catalog; server frames contain opaque IDs and sanitized relative display paths, never absolute paths | Network-supplied paths would turn a source worker into an arbitrary file server. Stable local IDs permit rename continuity while the server still treats the lineage token as untrusted until it recomputes SHA-256 | `src/source_catalog.rs`; `src/source_scanner.rs`; `docs/content/docs/developer/remote-worker-libraries.mdx` |
| Successful whole-object SHA-256 checks are cached in a 128-entry LRU keyed by the opened file's local identity plus the expected digest | Repeated verified range reads avoid rehashing large files, while replacement, rewrite, inode, timestamp, or expected-digest changes cannot reuse stale verification | `src/source_catalog.rs::VerificationCache`; test `verified_digest_binds_a_grant_to_the_exact_object` |
| A `kind=calibre` source root reads `metadata.db` read-only, validates Calibre application/schema identity and joins the `data` table to filesystem-authoritative format paths | Calibre metadata enriches the opaque manifest without turning database paths into server authority; `data.name` is a basename and the actual file suffix is `data.format.to_ascii_lowercase()` | `src/source_calibre.rs`; [Calibre schema](https://github.com/kovidgoyal/calibre/blob/master/resources/metadata_sqlite.sql) |
| Calibre `user_version` 27 and 28 are both read (`SUPPORTED_SCHEMA_VERSION = 28`); newer versions are still rejected and the `cali` application-id check stays | Calibre master's `upgrade_version_27` only creates the viewer `book_storage` table, so schema 28 is purely additive over the v9.15.0 release schema; a hard `> 28` bound keeps unknown future column changes an actionable error rather than a guess | `src/source_calibre.rs` test `accepts_schema_28_book_storage_and_rejects_newer`; [`schema_upgrades.py::upgrade_version_27`](https://github.com/kovidgoyal/calibre/blob/master/src/calibre/db/schema_upgrades.py) |
| A grant's `expires_at` bounds acceptance only; an accepted tunnel is bounded by `SOURCE_TRANSFER_IDLE_TIMEOUT` (30 s between chunks) and its byte budget, and `wait_ready` gives up at the grant's own deadline | Every server grant carries a 60 s TTL, so a legitimate audiobook transfer was cut off mid-stream at the minute mark, while a worker that never answered `ReadReady` hung its route forever | `src/source_hub.rs` tests `accepted_tunnel_outlives_the_grant_expiry`, `wait_ready_ends_when_the_grant_expires`, `stalled_tunnel_times_out_for_the_consumer` |
| The hub tracks a grant only while something can act on it: the consumer releases it (`wait_ready` on a terminal state, `consume_direct`, a `TunnelReceiver` on drop or idle timeout, `finish_tunnel`), a worker-driven failure only marks it so the waiter still reads the worker's reason, and every registration sweeps expired, stalled, and terminal leftovers | Grants are one-use, so a permanent map entry per read grew server memory with every remote range request; a sweep on registration bounds the map without a timer task | `src/source_hub.rs` test `finished_grants_leave_the_hub`; `SourceHub::pending_grants` |
| `wait_ready` enables its `Notified` future before reading grant state | `notify_waiters` only wakes futures already registered, so a readiness frame landing on another thread between the state read and the first poll was lost and the route hung | `src/source_hub.rs::wait_ready`; stress test `wait_ready_never_misses_a_readiness_frame` |
| A tunnel grant id enters the client's in-flight set only once its transfer task is spawned | Every refusal before that (stale item, transport mismatch, full capacity) used to leave the id behind for the worker's lifetime | `src/source_client.rs` test `refused_tunnel_grants_do_not_stay_inflight` |
| Calibre discovery reads the catalog tables asynchronously and runs the per-format symlink/metadata/fingerprint loop in `spawn_blocking` | Sampling every format file blocks for seconds on a large or network-mounted library, which stalled the same runtime thread that services control frames and grants; the scanner's per-root permit already bounds the blocking task | `src/source_calibre.rs::observe_formats` |
| Capability matching is a structural JSON subset test, not a per-kind matcher                                                                                                                                                      | A new job kind then adds a vocabulary and no code. Arrays are containment so `{"hwaccel":["nvenc"]}` selects the GPU box out of a pool that all advertise `transcode`                                                                                                                                                                                                                                                                                                                                                                                | `src/kind.rs::satisfies` and its three tests                                                                                                                                   |
| `align` requirements carry the documented device scalar plus singleton model, algorithm, and precision arrays                                                                                                                     | Workers can advertise one execution device and multiple supported models/algorithms/precisions; the existing structural matcher selects a compatible worker without a second matching implementation                                                                                                                                                                                                                                                                                                                                                 | `src/kind.rs::align_requires`; `src/alignment.rs` tests                                                                                                                        |
| SyncMap v1 is a compact, provenance-bearing artifact with exact text/audio-manifest digests and duration-bounded integer-millisecond cues ordered by `(spine_index, ordinal)`                                                     | Validation belongs at the protocol seam: no runner or media probe is needed to reject stale job/input identity, malformed timing, overlap, ordering, confidence, or track-bound violations; `TrackDurationsMs` supplies track-local duration bounds; align results always use `application/vnd.stump.sync-map+json`                                                                                                                                                                                                                                  | `src/alignment.rs::{SyncMapV1,SyncMapValidationError,AlignResult}`                                                                                                             |
| ALIGN results are validated by the host before `done`, and the optional Storyteller adapter stays worker-local                                                                                                                    | Credentials and remote media must never enter the job row or server; the host rechecks requester/pair/source identity, output bytes, durations and target IDs before publishing                                                                                                                                                                                                                                                                                                                                                                      | `src/service.rs::ResultValidator`; `src/storyteller.rs`; `crates/library/src/sync_maps.rs::AlignmentResultValidator`                                                           |
| The native align runner invokes only an operator-configured local executable/model with CPU/fp32/CTC inputs and streams authorized audio to disk before uploading typed `SyncMapV1` | A complete non-Storyteller path must keep model ownership and media credentials on the worker and must not buffer a multi-gigabyte M4B in memory | `src/native_align.rs`; `src/bin/stump-worker.rs` |
| `kind` is TEXT and the kind registry is in code                                                                                                                                                                                   | Adding `align` must be a registry row, not a migration; the shape mirrors the ingest quality-check registry                                                                                                                                                                                                                                                                                                                                                                                                                                          | `crates/migrations/src/m20260944_000000_add_worker_jobs.rs`; `src/kind.rs::KindRegistry`                                                                                       |
| Cancellation is `failed` + a reason, not a seventh status                                                                                                                                                                         | The status set is the protocol's contract, and a cancelled job is exactly a job that will not produce its output                                                                                                                                                                                                                                                                                                                                                                                                                                     | `src/service.rs::cancel`; `docs/.../workers.mdx` §5                                                                                                                            |
| `needs_worker` resolves `enqueue_and_wait` immediately instead of waiting out the timeout                                                                                                                                         | Nothing is going to happen; making a player hold the connection for two minutes to learn that would be a worse answer than the stored bytes it is going to get anyway                                                                                                                                                                                                                                                                                                                                                                                | `src/service.rs::enqueue_and_wait`; test `a_job_with_no_capable_worker_and_no_fallback_needs_a_worker`                                                                         |
| Local and remote runs write to the same path (`output_dir/<job id>`) and report the same result shape                                                                                                                             | The awaiting caller publishes one file and never learns who produced it, which is the whole reason a VPS can move transcoding to a worker without changing a line of the delivery route                                                                                                                                                                                                                                                                                                                                                              | `src/kind.rs::LocalJob`; `src/service.rs::outcome_of`; test `a_kind_with_a_local_fallback_runs_on_the_server`                                                                  |
| The client runs one job at a time but **queues** what it is offered while busy, and claims every offer immediately                                                                                                                | A transcode saturates the host, so running two finishes both later than running them in sequence — but there is no decline frame, and the server has already assigned the row, so an offer the worker dropped would sit `queued` until the next reconnect. Claiming at once is what makes a reconnect resume a queued job by id. The completion signal is a channel, not a poll after the next frame: the reap used to run after the match, so the first offer arriving once a job finished was declined and stranded (found live by ChallengeSolve) | `src/client.rs::run_once`; tests `an_offer_arriving_after_a_completion_is_accepted`, `an_offer_arriving_while_busy_is_queued_not_dropped`                                      |
| A worker starts if it can do _something_: a missing `ffmpeg` drops `transcode` from what it advertises, a `--chrome` that does not run is fatal, and no capability at all refuses to connect                                      | Advertising a capability whose tool is missing keeps the server routing to this worker instead of using its own fallback — but a browser-only box with no `ffmpeg` on it is a legitimate deployment, so the old "no `ffmpeg`, no worker" rule had to become per capability. `--chrome` is explicit, so failing it silently would be the surprising outcome                                                                                                                                                                                           | `src/bin/stump-worker.rs`; `src/transcode.rs::probe`; `src/challenge.rs::ChallengeRunner::probe`                                                                               |
| CLI help says Coppice while the `stump-worker` binary name, `STUMP_WORKER_API_KEY`, API-key format, and wire vocabulary stay unchanged                                                                                            | Operators should see the product name without forcing a compatibility-breaking rollout of executable, environment, or protocol identifiers.                                                                                                                                                                                                                                                                                                                                                                                                          | `src/bin/stump-worker.rs`                                                                                                                                                      |
| `challenge_solve` is registered with **no** local implementation, and will never have one                                                                                                                                         | A server has no browser, and a managed challenge is precisely the test for that. `needs_worker` is the honest answer and the console shows it                                                                                                                                                                                                                                                                                                                                                                                                        | `src/kind.rs::CHALLENGE_SOLVE`; `apps/server/src/routers/api/v2/transcode_job.rs::registry` (no `with_local` line)                                                             |
| The browser runner drives Chrome **headed**, with a **persistent profile** under the worker's own data dir, and chromiumoxide's default flags dropped                                                                             | Headless plus `--enable-automation` plus a throwaway profile is the exact fingerprint a bot detector looks for; and a challenge that ends in a Turnstile checkbox needs a human who can see the window. The persistent profile is what makes the second solve instant. Never the operator's own profile: Chrome refuses a `--user-data-dir` another process holds, and a source has no business near those cookies                                                                                                                                   | `src/challenge.rs::{ChallengeRunner::solve,CHROME_ARGS}`; `docs/.../workers.mdx` §8                                                                                            |
| chromiumoxide sits behind a default-off `browser` feature                                                                                                                                                                         | It is the one capability with a heavyweight dependency (the generated CDP protocol crate, five minutes of compile). An operator who only wants Opus should not pay for a browser automation stack, and the default `cargo test -p stump_worker` should not either                                                                                                                                                                                                                                                                                    | `Cargo.toml`; root `Cargo.toml` `[workspace.dependencies]`                                                                                                                     |
| The runner reports observations — the jar, the agent, the cookie's own expiry — and no policy                                                                                                                                     | What to store, how to merge it with headers an operator configured, and how long to trust a clearance with no expiry are all questions about a _source_, which a protocol crate does not know about. `expires_at` is Unix seconds because that is literally what CDP hands over                                                                                                                                                                                                                                                                      | `src/kind.rs::ChallengeSolveOutput`; `crates/provider/src/challenge.rs`                                                                                                        |
| Tests run against the real migrated schema (`migrations::Migrator::up`), not a mirrored `CREATE TABLE`                                                                                                                            | The entity and the migration cannot drift apart unnoticed, which is the cost `stump_abs` pays for its hand-written DDL constants                                                                                                                                                                                                                                                                                                                                                                                                                     | `src/tests.rs::harness`                                                                                                                                                        |

## Layout

| File                      | Responsibility                                                                                                    |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `src/lib.rs`              | Feature map, re-exports; the `worker_jobs` entity is re-exported from `models`                                    |
| `src/protocol.rs`         | The seven frames; literal-JSON tests pin the wire names                                                           |
| `src/kind.rs`             | Job kind ids, `TranscodeInput`/`Output`/`Result`, `satisfies`, `align_requires`, `LocalRunner`, `KindRegistry`    |
| `src/alignment.rs`        | `AlignInput`/`Result`, typed SyncMap v1 provenance/cues, fixed artifact MIME, and duration-aware validation       |
| `src/service.rs`          | `WorkerJobs`: enqueue, `enqueue_and_wait`, dispatch, frame handling, cancel, the transport callbacks              |
| `src/hub.rs`              | `WorkerHub`: who is connected, what they advertise, how to push a frame                                           |
| `src/event.rs`            | `WorkerJobChanged`, forwarded by the host as `CoreEvent::WorkerJobChanged`                                        |
| `src/error.rs`            | `WorkerError`                                                                                                     |
| `src/client.rs`           | The protocol client: dial, `hello`, claim, run, report, reconnect                                                 |
| `src/source_protocol.rs`  | Bounded source hello/manifest/read-grant frames, separate from compute-worker frames                               |
| `src/source_hub.rs`       | Epoch-guarded source connections and one-use direct/tunnel transfer grants                                         |
| `src/source_catalog.rs`   | Private atomic root catalog, opaque item identity, path containment, exact slice resolution                        |
| `src/source_scanner.rs`   | Bounded read-only scans for explicitly configured catalog roots                                                     |
| `src/source_calibre.rs`   | Read-only Calibre `metadata.db` adapter with schema, path, and symlink validation                              |
| `src/source_client.rs`    | Source control socket, deterministic manifest replay, grant dispatch, and reconnect                                 |
| `src/source_direct.rs`    | Private-network HTTP endpoint accepting only one-use grant IDs                                                      |
| `src/source_tunnel.rs`    | Separate authenticated outbound binary WebSocket for tunnel reads                                                   |
| `src/transcode.rs`        | The client's `transcode` runner: probe, download, `ffmpeg`, upload                                                |
| `src/storyteller.rs`      | Optional worker-local Storyteller TUS/process/poll adapter; normalizes output to `SyncMapV1`                      |
| `src/native_align.rs`     | Operator-configured external aligner adapter; streamed inputs and typed result normalization                   |
| `src/challenge.rs`        | The client's `challenge_solve` runner (feature `browser`): launch Chrome, wait out the interstitial, read the jar |
| `src/bin/stump-worker.rs` | The binary: flags, logging, capability probe, run forever                                                         |
| `src/tests.rs`            | A real client against a real hub over a real `127.0.0.1` listener                                                 |

## How to verify

```sh
cargo test -p stump_worker
cargo test -p stump_worker --features browser        # the CDP runner's own logic
cargo test -p stump_server --no-default-features --features headless,liseur-sync \
  --test api_tests -- worker
cargo run -p stump_worker --bin stump-worker -- \
  --server http://127.0.0.1:25600 --api-key stump_… --name dev-box
cargo run -p stump_worker --features browser --bin stump-worker -- \
  --server http://127.0.0.1:25600 --api-key stump_… --chrome google-chrome-stable
cargo run -p stump_worker --bin stump-worker -- \
  --server https://coppice.example --source-api-key stump_… \
  --source-root 'books=/srv/books;label=Books;kind=ebooks;privacy=catalog' \
  --source-transport tunnel
```
