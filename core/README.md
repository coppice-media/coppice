# Core 🏭

The `core` crate contains Stump's core functionalities

## Structure 📦

The `src` directory contains the following modules:

- `config`: Configuration for the any apps consuming the core, including environment variables and tracing
- `db`: Database client, models, and utilities
- `filesystem`: Anything related to the filesystem and handling of files
  - `image`: Image processing and utilities
  - `media`: Media processing and utilities
  - `scanner`: The bulk of the indexing and scanning logic
- `job`: Background job processing and execution lifecycle helpers, Apalis-backed system
- `opds`: OPDS feed generation and XML utilities

## Decisions

| Decision | Why | Evidence |
| --- | --- | --- |
| Audiobook converter defaults are their own `AudioConfig` group (`STUMP_AUDIO_CANONICAL`, `STUMP_AUDIO_AAC_BITRATE`, `STUMP_AUDIO_FFMPEG`), all three validated by the config generator at load time, and `core` does **not** take a `stump_tools` dependency for the executable check | The `ffmpeg` path is operator-supplied, so a typo must stop the server rather than fail one conversion per audiobook for the rest of its uptime — the same rule as `ingest_preprocess_command`. `stump_tools::external::is_executable` answers the same question but drags `epub`, `zip`, `id3` and `mp4ameta` into every build including `minimal`, which one permission bit does not justify | `src/config/audio.rs`; `src/config/{mod,defaults,env_keys,stump_config}.rs`; tests `test_audio_defaults`, `test_audio_canonical_validation`, `test_audio_bitrate_validation`, `test_audio_ffmpeg_validation` |
| `collections`, `library`/`series` and `ingest` left `core` for `crates/{collections,library,ingest}`; the dependency direction differs per crate and the old paths are gone (no re-exports) | `stump_collections` and `stump_library` are application services *above* core — they need `Ctx`, the event channel and `job::stump_job` — so they depend on `stump_core` and nothing in core depends on them. `stump_ingest` is the reverse: `Ctx::ingest()` and `StumpConfig` are core's, so core depends on the pipeline and the pipeline must stay host-free. That is what makes `stump_core/ingest` (default on) able to drop it: with `--features minimal` the server links neither the crate nor `Ctx::ingest`. | `core/Cargo.toml` `ingest = ["dep:stump_ingest"]`; `src/ingest_host.rs` (settings, `RowFactory`, `ProviderClientFactory`, `IngestEventSink`, `From<IngestError>`); `src/context.rs` `Ctx::ingest`; `cargo tree -p stump_server --no-default-features --features minimal -i stump_ingest` matches no package; `crates/{ingest,collections,library}/README.md` |
| `utils::move_file` and `filesystem::media::visible_pages::DUPLICATE_PAGE_TOLERANCE` moved to `stump_media` | Both are shared by `stump_ingest`, which cannot depend on `stump_core`; duplicating a cross-filesystem move or — worse — the dHash tolerance would let the ingest quality check, the duplicate-page aggregation and the serve-time page skip drift apart | `crates/media/src/common.rs::move_file`, `crates/media/src/hash.rs::DUPLICATE_PAGE_TOLERANCE`; consumers `crates/library/src/series.rs`, `crates/ingest/src/{store.rs,quality/duplicate_pages_across_books.rs}`, `src/filesystem/media/visible_pages.rs` |
| SQLite migrations run on a dedicated `max_connections = 1` pool, which is closed before the serving pool opens; PostgreSQL keeps migrating on the serving connection | `sea-orm-migration` only transacts migrations for PostgreSQL (`sea-orm-migration-1.1.16/src/migrator.rs:261-272`), so on SQLite each DDL statement lands on whichever pooled connection is free. With `db_max_connections = 10` the create/copy/drop/rename in `m20260909_000000_add_ingest_media_targets` straddled connections and a fresh database failed to start with `(code: 1) there is already another table or index with this name: ingest_analysis_jobs`. | `src/database.rs` `SQLITE_MIGRATION_POOL_SIZE`, `migrate`, `sqlite_pool`; test `migrates_a_fresh_database_behind_a_multi_connection_pool` (fails with the constant raised above 1) |
| Each SQLite migration runs in its own transaction (`database::migrate` loops `Migrator::up(&txn, Some(1))` over the pending list); PostgreSQL is already transacted by `sea-orm-migration` | Without it a migration that fails or is interrupted after its first DDL statement leaves that DDL behind unrecorded, and every later boot dies with `table "ingest_analysis_jobs_media_targets" already exists` — the database is unbootable without hand surgery. SQLite DDL is transactional, so one transaction per migration costs nothing and is what `sea-orm-migration` does on PostgreSQL. | `core/src/database.rs::migrate`; `database::tests::a_failing_sqlite_migration_leaves_nothing_behind` (fails without the wrap, passes with it) |
| Every write transaction in `core` opens with `models::txn::begin_write` (SQLite `BEGIN IMMEDIATE`); read-only transactions keep `TransactionTrait::begin` | `delete_library`, the collection/shelf services, the scanner writers and the ingest store all read before they write, and SQLite will not run the busy handler when a deferred transaction has to promote its read snapshot to the write lock — `DELETE /api/v1/libraries/{id}` during a scan returned `500 database is locked`. | `crates/library/src/library.rs`, `crates/collections/src/service.rs`, `crates/ingest/src/store.rs`, `src/filesystem/scanner/utils.rs`; `crates/models/src/txn.rs`; test `delete_library_waits_out_a_concurrent_writer` |
| The ingest preprocess hook is resolved at startup (`StumpCore::init_config`), runs at most once per item behind `ingest_drop_items.preprocessed_at`, and re-hashes the staged file on exit `0` | A hook is operator-supplied, so the two failure modes are a command that never runs and a command that runs too often: an unresolvable `ingest_preprocess_command` validated lazily would silently skip every dropped file for the server's uptime, and a hook re-run on re-analysis would feed a conversion pipeline its own output. Re-hashing is what keeps `source_sha256`, the page index, the `quality_report`, and every candidate describing one file after the hook rewrites it. | `crates/ingest/src/preprocess.rs`, `crates/ingest/src/store.rs` `run_preprocess`, `crates/ingest/src/coordinator.rs` `run_phases`, `src/lib.rs` `init_config` (via `ingest_host::validate_ingest_config`); `crates/migrations/src/m20260927_000000_add_ingest_preprocess.rs`; tests `unresolvable_command_fails_validation`, `preprocess_hook_rewrite_is_rehashed_onto_the_item`, `preprocess_hook_failure_fails_the_item_with_the_stderr_tail`, `preprocess_hook_runs_once_per_item`, `preprocess_hook_runs_before_staged_analysis` |
| A series the scanner finds gone takes its books with it, and both scan jobs use one rule: `scanner::utils::handle_missing_series(conn, paths)` marks the series **and** every `media` row under it `MISSING` in the same chunked pass, `handle_recovered_series(conn, ids)` marks a series that is back on disk `READY` again (guarded by `FileStatus::is_recovered_if_present`, so it is a no-op for a `READY` series and never promotes an `ERROR` one), and the books of a recovered series are restored by the series walk that follows through `handle_restored_media`. `LibraryScanJob`'s init task and `SeriesScanJob`'s init both call all three | The library scan's init task flipped only the series row, so moving a series folder out and rescanning left `series.status = 'MISSING'` holding `media.status = 'READY'`: nothing in the listing funnels filters on the *series* status, so every profile kept serving books whose files were gone and reading one 404'd at the file read. `SeriesScanJob` carried a second, divergent copy of the rule whose media update filtered `media.series_id = <filesystem path>` and therefore never matched a row, and it had no recovery step at all — a rescan of a restored folder put the books back to `READY` under a series still marked `MISSING`, the exact mirror of the same bug. Restoring books needs the walk, which is the only step that knows which files came back; gating both directions on `is_recovered_if_present` keeps a folder move from laundering an `ERROR`/`UNSUPPORTED` book into `READY` | `src/filesystem/scanner/utils.rs` `handle_missing_series`/`handle_recovered_series`/`handle_restored_media`, `src/filesystem/scanner/library_scan_job.rs` init task, `src/filesystem/scanner/series_scan_job.rs` init; test `filesystem::scanner::utils::missing_series_lifecycle::missing_series_takes_its_books_with_it_and_gives_them_back`; live: library scan and `scanSeries` round trips on port 25806 flip `MISSING`/`READY` together and Komga `POST /api/v1/books/list` goes 20 → 18 → 20 |
