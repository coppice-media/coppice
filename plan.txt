Upstream already has the right seams

we can probably make it a lot lighter right? even with those faetures

Yes. I think Stump could be made substantially lighter while retaining almost all of the useful features.

The important distinction is:

Having a feature compiled into the binary is usually cheap.
Having that feature allocate caches, start workers, watch directories, initialize native libraries, or retain scan state is what costs RAM.

For example, OPDS, KOReader, Kobo routes, OIDC and a static web UI can all be present while doing essentially nothing at idle.

Where I’d aim

For a reasonably sized personal library, I think these are sensible engineering targets, not current Stump measurements:

Stump configuration	Idle target
Minimal API + SQLite	~25–50 MB
+ OIDC + OPDS + KOReader	~30–60 MB
+ Kobo routes	~35–70 MB
+ static web UI available	basically unchanged
+ metadata integrations available but idle	~40–80 MB
Full-featured but aggressively lazy Stump	~50–120 MB

I'd therefore aim to make a 128 MB container limit realistic for ordinary usage, with perhaps 256 MB for comfortable scan/import spikes.

That's considerably different from saying “strip Stump down until it has no features.”

Current Stump has several obvious optimization opportunities

Today its server always initializes both the scheduler and library watcher at startup. The source even has a TODO saying the watcher and scheduler need reorganizing and should be moved out of core.

Its central context also always constructs:

SQLite connection pool
event channel (capacity 1024)
in-memory Apalis job storage
Apalis worker state
LibraryWatcher

whether those facilities are needed immediately or not.

I'd change the lifecycle to more like:

startup
│
├── SQLite
├── HTTP
├── auth/OIDC config
├── OPDS
├── KOReader
└── Kobo
       ↓

~tiny idle state


first scan requested
       ↓
create scanner resources
       ↓
scan
       ↓
drop scanner state


watcher enabled?
       ↓
only then initialize notify


scheduled jobs configured?
       ↓
only then start scheduler

That alone makes the design much more predictable.

The scanner is probably a huge part of the historical numbers

This is especially important because the benchmark I quoted earlier used Stump v0.1.4.

That benchmark measured about 209 MB idle after scanning 10k books, rising substantially with library size.

But Stump's maintainer subsequently found some pretty serious scanner behavior.

Before v0.1.5 the scanner had a default concurrency limit of 200, mixed Tokio and Rayon workers, generated large numbers of futures, did repeated database operations, etc. The maintainer specifically identified that as likely responsible for the “massive memory pressure.”

v0.1.5 changed that to:

CPU-derived bounded concurrency
no Rayon in the scanner
fill/drain rather than huge pending-future sets
batched DB operations
cached tag state
fewer repeated scans
transactions/batching

with the maintainer saying the resource improvements should be most significant for libraries over 50k books.

So the 209/448/1160 MB numbers should not be treated as the floor for Stump's architecture.

They were partly measuring an implementation issue that's already being worked on.

There's another hidden problem: “idle after scan” isn't necessarily true live memory

This is something I'd explicitly profile.

A Rust process can do:

start          40 MB

scan
allocate       400 MB

scan finishes
live objects    60 MB

RSS            180 MB

because the allocator may keep freed heap pages around for future allocation instead of immediately returning them to Linux.

Docker reports RSS-ish resident memory, so the container can look “fat” even though the application isn't actually holding 180 MB of useful objects.

That distinction is important.

Before refactoring half of Stump, I would measure:

RSS
vs
live heap
vs
SQLite page cache
vs
mapped files/native libs

after:

clean startup
10 minutes idle
scan
immediately after scan
30 minutes after scan

If:

live heap = 40 MB
RSS = 180 MB

then we're partly fighting allocator retention, not Stump objects.

That can potentially be improved with allocator choices/decommit behavior rather than application redesign.

SQLite also deserves tuning

Current Stump uses a SqlitePool, but it does not currently specify a maximum pool size in its connection code.

For this application I wouldn't let the general-purpose DB library decide that.

I'd probably use:

max SQLite connections: 2–4

not 10/20/etc.

For SQLite:

HTTP reads ─┐
            ├─ small connection pool
MCP/API etc ┘
                ↓
             SQLite WAL

There's no benefit to having a large idle pool on a home book server.

I'd also explicitly tune:

PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA cache_size = ...;
PRAGMA temp_store = MEMORY;

with a deliberately modest page cache.

This could save tens of MB depending on what the current library stack does.

Web UI: keep it

Given all of this, I'm actually less interested in removing the web UI for RAM reasons.

Current Stump does:

browser
   ↓
static JS/CSS/HTML
   ↓
Axum

The browser consumes the UI memory.

Server-side, Stump just serves files. Its router currently mounts the SPA unconditionally, but it's just another Axum router.

rather than a big RAM optimization.

I would keep full Web UI support in the project.

OPDS / KOReader / Kobo should definitely stay

They're almost ideal server features because they're mostly dormant HTTP routes.

Current Stump already does exactly the right thing with KOReader and Kobo routing:

if enable_koreader_sync {
    mount(koreader)
}

if enable_kobo_sync {
    mount(kobo)
}

Their idle cost should be extremely small.

So I wouldn't sacrifice those to chase memory.

Even Kobo, despite having quite a lot of logic, can remain effectively dormant until a Kobo connects.

PDFium is a better optional boundary

This is one I'd pay attention to.

Stump's standard packaging includes libpdfium, and stump_core currently depends directly on pdfium-render.

There's no reason an EPUB user doing:

Kobo
OPDS
KOReader

should necessarily have a PDF renderer initialized.

So I'd split:

PDF support
├── identify/index/download PDF        cheap
└── render PDF pages/thumbnails        PDFium

and load the second only when actually required.

Same philosophy for image processing.

Metadata can stay too

External metadata support is mostly:

code
+ some config
+ HTTP client

while idle.

That's cheap.

The expensive part is:

1000 books
 ×
provider calls
 ×
images
 ×
parsing
 ×
database writes

So don't remove metadata.

Just run it as a bounded job:

metadata job starts
       ↓
N concurrent requests, e.g. 4
       ↓
batch writes
       ↓
release HTTP/body/image buffers
       ↓
idle again

Exactly the same for thumbnail generation.

My preferred architecture now

Not actually “Stump Lite.”

I'd aim for one Stump that is naturally light:

                     Stump
                       │
              ┌────────┴────────┐
              │   always-on     │
              │                 │
              │ Axum            │
              │ SQLite          │
              │ auth            │
              │ OIDC            │
              │ core API        │
              │ OPDS            │
              │ KOReader        │
              │ Kobo            │
              └────────┬────────┘
                       │
                   ~low RAM
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
      scanner        PDFium       metadata
      on demand      on demand    on demand
         │             │             │
         └─────────────┴─────────────┘
                       │
                  release memory

Then Cargo feature flags exist mostly to build specialized images, not because the full binary inherently needs lots of memory.

My target would be

I'd treat:

~50–80 MB clean startup idle

as a strong goal.

<100 MB after normal use

as the more important goal.

And:

<128 MB typical idle/full feature set

as a realistic success criterion.

During a large scan, PDF render, thousands-of-book metadata refresh, etc., I'd happily allow:

200–500 MB temporary

provided it falls back near baseline afterwards.

That's actually preferable to designing everything around never exceeding 100 MB. RAM exists to make active work fast; the waste is holding it forever while the server is doing nothing.

The fact that current Stump already has a maintainer actively fixing scanner memory pressure and has explicit TODOs around decoupling scheduler/watcher initialization makes me think this could also be a reasonable upstream optimization effort, rather than requiring a permanent fork.
